# 插件 peer 版本随 dsh 运行时绑定，升级即整批重发

状态：已采纳

背景：0.1.7-rc.1 起，DSH 在**装配前**预检插件声明的 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*`
peer 范围是否匹配当前运行时（`vendor/deepseek-harness/packages/boot/app-boot/src/plugin-compatibility.ts`；
profile 行与 bundle 两条边界都会被拒，豁免存在 profile 自己的 `compatibility.json`，按精确
`包名@版本` × 精确 dsh 版本授予，见同目录 `profile-compatibility.ts`）。我们的包一律按
[`dsh-plugin-upstream-sync`](../../.agents/skills/dsh-plugin-upstream-sync/SKILL.md) 的纪律用 workspace 协议声明上游
peer，pnpm 发布时把 peer 里的 `workspace:*` 写成 `^<本地版本>`——已发布物是实证：registry 上
`@morlay/session-rdb@0.0.20` 的 `@deepseek-ai/dsh-*` peer 全为 `^0.1.5-rc.2`。而 semver 的
pre-release 规则要求候选与范围内的比较器**同一 `major.minor.patch` 元组**，`^0.1.5-rc.2` 不认
`0.1.7-rc.1`：跨版本部署必然被判为不兼容。

**决定**

不引入豁免、不放宽 peer 写法：**插件与 dsh 运行时按同一版本配套发布与部署**，升上游就整批重发插件
包（版本 bump 走 CI），不靠 `dsh plugin allow-version` 兜。本地开发形态不受影响——源 manifest 里的
`workspace:*` 被上游视为「当前运行时」（同一份源码），检查恒过。

**考虑过的选项**

- **不声明 dsh peer**：上游明确「Missing DSH peers impose no constraint」，能绕开检查，但等于放弃
  「我依赖哪些上游契约」的表达，也让 pnpm 失去 peer 解析线索。
- **peer 写成更宽的范围**：写不出「任何 0.1.x（含 pre-release）都兼容」的 SemVer 范围——pre-release
  候选只被同元组的 pre-release 比较器接受，`-0` 后缀也救不了跨元组；范围越宽只会更松地表达一个
  我们并不保证的事实。
- **依赖 profile 级豁免**：豁免要求用户逐条确认「可能崩溃或丢数据」，且插件或 dsh 任一升级都不继承
  授权；把它当默认路径等于把版本配套责任推给用户。

**后果**

- pre-release 期间 runtime 与插件版本必须严格配套；dsh 升级后未重发的插件在装配处被拒（bundle 被跳过、
  行被 `disabled`），这是**升级纪律**而非可绕过的配置。
- dsh 出正式版后 `^0.1.x` 能覆盖同 minor 的后续版本（pre-release 排除规则不再生效），跨版本成本随之下降。
- peer 里的版本号来自**发布时**的 vendor 版本，是硬约束：`DEEPSEEK_HARNESS_VERSION` 一换，所有包都要
  重新发布才有配套的声明。
