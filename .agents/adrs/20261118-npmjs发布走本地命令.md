# npmjs 发布走本地命令，CI 只发 GitHub Packages

状态：已采纳——`just publish-npm` 是 npmjs 的唯一入口，CI 只发 GitHub Packages
背景：同一条版本线要进两个 registry：GitHub Packages（CI 已有的自动通道）与 npmjs（公开消费方实际安装的来源）。GitHub Packages 的认证是 `GITHUB_TOKEN`，适合无人值守；npmjs 的发布需要人工卡点（预发布是否该落 `latest`、版本号有没有被历史占用、发布哪几个包），且发布者本机的 `npm login` 凭据不该进 CI。原来的红线是「严禁本地私自 `pnpm publish`」，没有给 npmjs 留通道。

**决定**

GitHub Packages 只走 CI（自动发未发布的新版本）；npmjs 只经本地 `just publish-npm` 手动发同一组、同版本；其他形式的本地发布都不允许。

**考虑过的选项**

| 选项                           | 否掉的理由                                                             |
| ------------------------------ | ---------------------------------------------------------------------- |
| CI 自动发 npmjs                | npmjs 的 token 进 CI；预发布与版本号抢占无法在发布者眼前卡点           |
| 本地直接 `pnpm publish`        | 没有发布前校验（清单覆盖、目标存在、private 分档），漏包与漏键都挡不住 |
| 只在 CI 加手动触发的 npmjs job | token 仍进 CI；「手动」被藏进 workflow，发布者看不到待发清单           |

**后果**

- 红线措辞改成「GitHub Packages 发布只走 CI；npmjs 发布只经 `just publish-npm`」；其他 `pnpm publish` 仍禁止。
- `just publish-npm` 必须内置发布前校验（`publishConfig` 覆盖 `exports`、目标存在、`private` 分档、`engines.dsh` 与 `mise.toml` 同源），任一条红即停。
- 发布者本机需要自己 `npm login`；CI 不需要 npmjs 的 token。
- 两个 registry 的版本一致由发布者保证：同一份代码、同一个版本号，先后由人决定。
- 发布前必须先 `just build`（产物与清单是发布的前提，不是发布命令的副作用）。
