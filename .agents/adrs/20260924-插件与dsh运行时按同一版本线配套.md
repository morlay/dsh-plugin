# 插件与 dsh 运行时按同一版本线配套，兼容性由 `engines.dsh` 一条表达

状态：已采纳——每个插件包在 manifest 里声明 `engines.dsh`，值跟 `DEEPSEEK_HARNESS_VERSION` 同批改（当前 `">= 0.2.1-rc.1 < 0.2.2"`）
背景：上游在导入插件前逐个比对版本（[`plugin-compatibility.ts`](../../vendor/deepseek-harness/packages/boot/app-boot/src/plugin-compatibility.ts) 的 `evaluatePluginCompatibility`）：清单有 `engines.dsh` 就**只**看它、`peerDependencies` 被忽略；没有才逐个判 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` peer。预发布参与范围匹配。而 SemVer 的预发布规则要求候选与范围内的比较器同一 `major.minor.patch` 元组——peer 写不出"本 minor 线里任何预发布都算兼容"这种范围。

**决定**

兼容性只用 `engines.dsh` 一条表达，**每个插件包**都写（预检逐行做，非 bundle 的插件行缺了它就只能按 peer 判），范围覆盖当前 minor 线：上游 `0.2.2-rc.1` 对应 `">= 0.2.1-rc.1 < 0.2.2"`。不引入 profile 级豁免、不放宽成"任意版本"。

**考虑过的选项**

| 选项                                      | 否掉的理由                                                                                                                                                |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 不声明                                    | 上游对"两者都未声明"不施加约束，等于放弃"我依赖哪些上游契约"的表达，装配期也就失去硬判据                                                                  |
| peer 写成更宽的范围                       | 写不出跨 patch 线的预发布范围；范围越宽只是更松地表达一个我们并不保证的事实                                                                               |
| 依赖 profile 的 `compatibility.json` 豁免 | 豁免按"精确 `包名@版本` × 精确 dsh 版本"授予，要求用户逐条确认"可能崩溃或丢数据"，且插件或 dsh 任一升级都不继承——把它当默认路径等于把版本配套责任推给用户 |

**后果**

- `DEEPSEEK_HARNESS_VERSION` 一换，**所有**插件包的 `engines.dsh` 同批改：两个端点都写死在清单里（下界是上一条 patch 线的 rc.1，上界是当前 patch 线的正式版）。漏改的那一行在装配预检被拒（bundle 被跳过、行被 `disabled`），信号在装配处，不在运行期。
- 上游出正式版后范围写法可以改成 `^0.2.x` 那种（那时预发布排除规则不适用），跨版本成本随之下降。
- 上游依赖写 `dependencies: workspace:^`（装配面解析到 vendor 源码，见 [ADR-上游以side-workspace版本锁定完整代码而非发布版本](./20260917-上游以side-workspace版本锁定完整代码而非发布版本.md)）；`peerDependencies` 只留给"宿主必须提供、我们自己不 `import`"的契约（当前只有 `@morlay/zephyr` 的 `@deepseek-ai/cordis`），不再用 peer 表达 dsh 版本。
