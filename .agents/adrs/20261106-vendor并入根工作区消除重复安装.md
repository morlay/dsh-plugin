# vendor 并入根工作区，消除重复安装

状态：已采纳

背景：上游把 vendor 树声明成**独立的 pnpm workspace**（它自带 `pnpm-workspace.yaml` 与
`pnpm-lock.yaml`），pnpm 于是给它单开一个 store。同一个第三方包在 vendor 与根**各装一份物理副本**：

- 类型：`@types/react`（根 18.3.1 / vendor 18.3.31，以及 `@types/react-dom` 18.3.1 / 18.3.7）；
- 运行时与类型：`@deepseek-ai/cosmokit`（根 overrides 的 `link:` 与上游包各自的 `node_modules`）。

TypeScript 按**文件路径**判模块身份，两份副本就是两个模块。声明生成（`target/dts`，见
`@local/dts-prepare`）在 declaration emit 阶段要把推断出来的类型写进声明，遇到来自「另一份」的类型
就报 TS2883（`The inferred type of X cannot be named without a reference to …`）并**跳过该文件的
声明**。这些文件里有包入口的依赖（`reference-markdown`、`Button`、`Row`、`Stack`、`MessageItem`、
`SessionModeSeat`、`ConversationManagerIcon`、`MultilineField`），`just build` 随即在 `emitDts`
合并时报「声明缺失」。

同一类问题在依赖解析上还有另一处：根与各 devpackage 写的 `rolldown` 范围（`1.x` / `^1.2.8`）解析到
1.3.0，而 tsdown 0.23.5 与 vite 8 钉 `~1.2.16`，两套 `Plugin` 类型互不兼容，`just lint` 在
`tsdown-plugin-cordis` 报 TS2322 / TS2321。

**决定**

让全仓只装一次依赖链，类型只有一份：

1. `vendor/steps.ts` 的 patch 阶段删掉 vendor 自带的 `pnpm-workspace.yaml` 与 `pnpm-lock.yaml`，
   让 vendor 的包并入根 workspace、共用根 store；它原先那两条 `link:vendor/*` overrides 根里已有
   （见 [ADR-上游第三方补丁纳入根工作区](./20260923-上游第三方补丁纳入根工作区.md)）。
2. 根 `pnpm-workspace.yaml` 的 overrides 把 `@types/react` / `@types/react-dom` 与 `rolldown` 钉到
   单一版本（同版本 + 同 store = 同一物理目录）。
3. `generateWorkspaceDts` 把 tsc 的诊断降级：这一步是**产物生成**，不是类型门禁（门禁是两叶 + oxlint）。
   上游源码里仍有少量 TS2883（cosmokit 副本），它们的声明无人消费；真有入口声明缺失时，取声明的
   一侧（`emitDts`）会按路径报错，不会静默产出残缺声明。

**考虑过的选项**

- **给组件补显式类型（`NamedExoticComponent<…>` / `ForwardRefExoticComponent<…>`）**：能消诊断，但
  等于为了产物生成污染源码、放弃自动推导；vendor 与 `src/vendor/` 里那份上游代码还改不了
  （同步会覆盖）。
- **tsconfig `paths` 把 `react` 锚到一份**：TS7（tsgo）不支持 `paths`；而且它只影响模块解析，不改变
  已经被另一份副本引入的类型身份。
- **只在 dts 生成时忽略诊断**：诊断可以忽略，但 tsc 对报 TS2883 的文件**不落声明**，入口合并仍会
  报「声明缺失」——必须从根上消掉重复副本。
- **换 Oxc 的 isolated declaration 生成器**：语法级生成不做类型推断，`memo` / `forwardRef` 的声明会
  退化成 `unknown`，产物不可用。
- **保持 vendor 独立 workspace**：两份实现会在运行期与类型面持续漂移（同一依赖两份行为），不只
  影响构建。

**后果**

- 安装只剩一个 store（`node_modules/.pnpm`），`vendor/deepseek-harness/node_modules` 里的依赖由根
  提供；vendor 不能再在本仓库里独立 `pnpm install`——我们不依赖这条路径。
- `just prepare` 的顺序（sync → patch → dep → prebuild）成为硬约束：`sync` 会还原 vendor 的
  workspace 清单，必须先 `patch` 删掉再 `dep`。
- 上游的第三方补丁清单仍从上游那份清单文件抄进根（文件本体在同步时被删除，见上面的 ADR）。
- `just build` 的 dts 阶段会有上游源码的 TS2883 诊断输出，但不阻断；自有源码零诊断。
- 回归守护：`just lint`（rolldown 类型赋值）、`just build`（`target/dts` 全量 + `emitDts` 合并）、
  全量 `just test`。
