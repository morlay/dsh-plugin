# 上游第三方补丁纳入根工作区

状态：已采纳

背景：上游对**第三方依赖**也打补丁（`vendor/deepseek-harness/pnpm-workspace.yaml` 的
`patchedDependencies`，补丁文件在 `vendor/deepseek-harness/patches/`），因为 `@deepseek-ai/*`
是 vendor 的源码、第三方依赖却来自 registry。根工作区若不跟随这份清单，同一个依赖就有两份实现：
上游装的带修复、我们装的不带。0.1.7-alpha.2 的 `exceljs@4.4.0` 补丁是一例（OOXML 命名空间解析，
客户端 Excel 预览读不同前缀 producer 的文件）。

**决定**

根 [`pnpm-workspace.yaml`](../../pnpm-workspace.yaml) 的 `patchedDependencies` **照抄上游清单**，
路径指向 `vendor/deepseek-harness/patches/`，随 `DEEPSEEK_HARNESS_VERSION` 一起换版；上游清单里
**不在我们依赖图中**的条目不列（pnpm 会以 `ERR_PNPM_UNUSED_PATCH` 直接失败，例如只进上游单 exe
打包链的 `@yao-pkg/pkg`）。

**考虑过的选项**

- **不跟随，各自绕行**：同一个依赖两份实现，上游修好的缺陷在我们这照样存在，且下次还要重新判断
  一遍哪些补丁"其实与我们有关"。
- **只带本次新增的 `exceljs`**：其余差异同源（`pi-ai` 流、`node-pty`、`fortune-sheet`、`osx-sign`
  都在我们的依赖图与运行路径上），只是还没踩到。
- **把补丁文件复制进 `patches/`**：双份维护，上游更新补丁时必然漂移。

**后果**

- 补丁的**包名 + 版本号写在根清单里**是硬约束：上游换依赖版本或改补丁文件名，`pnpm install`
  直接失败（信号明确，改一行即可）。
- `pnpm deploy` 会把工作区的 `patchedDependencies` 带进桌面部署项目（[设计 桌面化工具](../../packages/desktop/dsh-desktopify/.agents/designs/20260917-桌面化工具.md)），
  桌面产物与工作区口径一致。
- 上游补丁被当作"上游认可的第三方修复"接受，不逐条评估其内容；上游删掉某条补丁，我们随
  版本一起失去它（`just vendor prepare` 后 install 报 `ERR_PNPM_UNUSED_PATCH` 即信号）。
- 同一口径也用在 vendor 内的 patch 步骤上：`patches/steps.json` 每步同步时逐条评估必要性
  （上游改用 `workspace:~` 声明 devDep 后，`native/system/package.json` 的 devDep 删除步骤已不需要）。
