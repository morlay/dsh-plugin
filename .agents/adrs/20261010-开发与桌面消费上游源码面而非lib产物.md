# 开发与桌面形态消费上游源码面，发布形态仍用官方产物

状态：已采纳——三种运行形态（`zephyr dev` / 打包闭包 / 壳）都吃 vendor 源码，只有 4 个可发布包的 `publishConfig.exports` 指 `dist/`
背景：上游以 side workspace vendor 进来（[ADR-上游以side-workspace版本锁定完整代码而非发布版本](./20260917-上游以side-workspace版本锁定完整代码而非发布版本.md)），但 `@deepseek-ai/*` 的 `exports` 原本一律指 `lib/`，于是每次跟随版本都要跑完整上游构建。约束是两条：上游只读（改它只能经 [`vendor/steps.ts`](../../vendor/steps.ts) 的 `patch` / `prebuild` 两阶段）；发布产物必须把 `@deepseek-ai/*` 留在包外，由消费方从 registry 装。

**决定**

开发与桌面形态把 `@deepseek-ai/*` 解析到 vendor 源码，发布形态照旧用官方产物：

- **出口改写是生成式步骤**（[`exports.ts`](../skills/zephyr-upstream-sync/scripts/upstream-sync/src/exports.ts)，由 `vendor/steps.ts` 的 `exports` 步骤驱动）：`lib/*` 目标按同构规则改指 `src`，`files` 的 `lib/` 项换成 `src`（另补 `lib/typert.*`），删掉 `"type": "module"` 包的顶层 `main` / `types`，同值条件对象压成字符串，运行期真用到的 `devDependencies` 挪进 `dependencies` 并整段删除——**不补** `./src/*` 出口（内部文件面不该变成包边界）。
- **转译分两处**：工作区进程由 [`pnpm-workspace.yaml`](../../pnpm-workspace.yaml) 的 `nodeOptions: --import @oxc-node/core/register` 一处挂上；闭包与壳里跑 [`@morlay/dsh-oxc-node`](../../packages/boot/dsh-oxc-node/register.mjs)——它自己 `registerHooks` + `oxc-transform`，因为 Node 的类型剥离拒绝 `node_modules` 下的 `.ts`，而 `@oxc-node/core` 刻意放行那类文件。
- **装饰器双协议**：[`decorator-dual-protocol.patch`](../../vendor/patches/decorator-dual-protocol.patch) 把上游写端（typert 的 `Remote` / `RemoteScope`、cordis 的 `Inject`）改成同时接受 TC39 与 legacy 两种调用约定，类型面也一样；本仓库根 `tsconfig.json` 开 `experimentalDecorators`，转译侧按 legacy 降级（[`vitest.config.ts`](../../vitest.config.ts) 的 `oxc.decorator.legacy`、`register.mjs` 的 `target: "es2022"`）。
- **tsconfig 只剩根一份**：上游的 `tsconfig*.json` 在 `patch` 阶段末尾整批删掉；typert 的生成走本仓库自己的 AST 生成器（[`@local/typert-generator`](../../devpackages/typert-generator/package.json)），不读上游 tsconfig。
- **发布形态**：可发布包（`@morlay/zephyr` / `zephyr-rdb` / `zephyr-desktop-shell` / `dsh-oxc-node`）写 `publishConfig.exports` 指 `dist/`，由 tsdown 出产物；`@deepseek-ai/*` 不进产物，`@deepseek-ai/cordis` 是 peer。

**考虑过的选项**

| 选项                                          | 否掉的理由                                                                                                                                                                                                                   |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| tsconfig `paths` 重定向到源码                 | 只在支持 `paths` 的链生效（tsc / 部分打包器），与 Node 原生解析两套口径；`exports` 改写走 Node 原生解析，一次覆盖所有链                                                                                                      |
| 每次跟随上游都构建 `lib/`                     | 升级耗时的主要来源，且"源码一份、产物一份"两套口径都要维护                                                                                                                                                                   |
| 让上游把 `src/*` 摊成出口、消费方按源码路径引 | 同一个包既按出口引、又按源码路径引，打包边界跟着乱；要用的上游内部文件改为按需复制进本包 `src/vendor/<短名>/`（`vendor` 步骤，清单在 [`vendored.ts`](../skills/zephyr-upstream-sync/scripts/upstream-sync/src/vendored.ts)） |

**后果**

- 升级链变成 sync → patch → dep → prebuild，上游不再构建；必须编译的只剩 `native/system` 的 addon。门禁仍是 `just test` / `just lint` / `just build`。
- 闭包（`pnpm deploy --prod`）按 workspace 现状装，所以包里仍是源码面的 `.ts`，`preview` 与桌面壳靠 `@morlay/dsh-oxc-node` 现场转译（见[债务 20261110-闭包里的包仍是源码面](../../packages/zephyr/zephyr-cli/.agents/debts/20261110-闭包里的包仍是源码面.md)）。
- 出口改写是生成式的：上游新增出口自动适配，**找不到源码的出口打印清单后保持原样**——那是上游新增产物形态的信号，不是同步失败；新增一类产物命名要加在 `srcCandidates` 里，而不是逐包写 `explicit`。typert 那三个生成物出口与少数"出口名 ≠ 源文件名"的包由 `vendor/steps.ts` 的 `generated` / `explicit` 两张表给。
- 装饰器写端 patch 复刻了上游 marker 的格式（version 1 与冻结语义）：上游改格式时补丁应用失败即信号。
- 前端静态面：dev 与 `zephyr build` 都由 vite 打（[`builder.ts`](../../packages/zephyr/zephyr-cli/src/build/builder.ts)），闭包里的 client 半由 client-modules 的联邦式预编译按包产出（[设计 客户端资源的联邦式预编译](../../packages/zephyr/zephyr-app/.agents/designs/20261013-客户端资源的联邦式预编译.md)）。
