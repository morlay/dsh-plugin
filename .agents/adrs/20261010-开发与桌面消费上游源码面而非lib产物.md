# 开发与桌面形态消费上游源码面，发布形态仍用官方产物

状态：已采纳

背景：上游 deepseek-harness 以 side workspace 形式 vendor 进本仓库（见 [ADR-上游以side-workspace版本锁定完整代码而非发布版本](./20260917-上游以side-workspace版本锁定完整代码而非发布版本.md)），当前 `@deepseek-ai/*` 一律经各包 `exports` 解析到 `lib/` 构建产物，因此每次跟随上游版本都要跑 `just vendor prepare` 的完整构建（`build:native-system` + 全仓 `tsc -b` 类型树 + 全仓 tsdown 打包 + `build:web`）。这条构建链是升级耗时的主要来源。

约束：上游只读（扩展走 cordis 插件层，本地 patch 是例外）；发布形态（`@morlay/*` 的 dist 与桌面 bundle）必须继续依赖 registry 上的官方包并保持 TC39 装饰器语义，因为发布产物把 `@deepseek-ai/*` 留在包外（`dsh-desktopify` 安装的也是官方包）。开发与桌面 dev 形态则已经用 `--import=tsx` 直载自有包源码（`dsh-desktopify/src/cli/dev.ts`），具备继续向源码面推进的接缝。

**决定**

开发与桌面两种形态（`dev` 与打包产物）都把 `@deepseek-ai/*` 解析到 vendor 源码：用生成式 patch 改写上游各包 `exports` 与 `files`（`lib/*` 出口与文件集改指 `src`，`typert` 产物改为生成 `.ts`，client 出口随 client-modules 的字节 provider 一起源码化），用 oxc loader 取代 tsx 做转译与 legacy 装饰器降级（dev 用工作区那份、打包产物随包一份），装饰器写端在上游 patch 成同时接受 TC39 与 legacy 协议的双协议实现；npm 发布的 `@morlay/*` dist 形态不改，仍 external 官方包 + TC39 标准降级。

**考虑过的选项**

- **tsconfig `paths` 重定向**：只在支持 paths 的链生效（tsx/tsc），vite/rolldown/Electron 侧要逐条补，且与 Node 原生解析两套口径；`exports` 改写是 Node 原生解析，一次覆盖所有链。
- **开发与发布都走 legacy 装饰器**：发布产物调用的是官方标准协议实现，legacy 降级会让两端语义分叉；patch 写端为双协议后，两端各自匹配。
- **在桌面壳里起 vite dev server 提供前端**：上游 `apps/web/vite.config.ts` 显式拒绝 `serve`（`__DSH_BOOT__` 必须由 host 注入），壳的页面被锁在自有 scheme 且拦外部导航，HMR 走 WS 穿不过协议管道。
- **fork `@deepseek-ai/dsh-client-modules`**：它是 1159 行的 client 模块系统核心，上游演进活跃；只把三处字节读取抽成可注入 provider 的 patch 面更小、语义保持与上游一致。
- **把 typert generator 的输出默认改成 `.ts`**：会改变上游自身构建与 gate 的产物口径；改用输出模式开关，本仓库开启、上游默认不变。

**后果**

- 升级流程从「sync + patch + 全量 build」变为「sync + patch + native（+ typert 生成）」，`just vendor prepare` 与 `dsh-plugin-upstream-sync` 技能的 build 档需要按此拆档；`build:web` 跳过后必须显式删除 `apps/web/dist`（上游 clean 与 gitignore 都不管它，残留会被静默服务）。
- 必须构建的面只剩 `native/system` 的 addon；其余以源码（或生成的 `.ts`）进入开发与 dev 桌面链。
- 装饰器：开发面 oxc legacy 降级 + 上游双协议写端 patch；发布面 TC39 标准降级 + 官方实现。写端 patch 复刻了 marker 格式（version 1 与冻结语义），上游改格式时补丁失效即信号。
- `exports` 改写是生成式补丁：1081 条按「lib→src」同构规则改写，白名单保留 28 包的 `typert`/`client/typert`/`remote`（生成器强制契约）与 bin、双模式 CJS、资产出口；322 包已有的 `"./src/*"` 出口原样保留。
- 前端在浏览器与桌面形态同样落在 host 的 `frontend-static`，改由 host 内的 prebundle 缓存 provider（named route）提供，壳的启动断言随之放宽。
- 落点：开发面的转译与装饰器降级在 `@local/devkit` 的 `ts-loader.mjs`（oxc，经 `NODE_OPTIONS=--import=…` 注入 dev 子进程与 `just build`）；写端双协议住在 `patches/decorator-dual-protocol.patch`（typert 的 `Remote`/`RemoteScope` 与 cordis 的 `Inject`）。测试与发布构建仍走 `standardDecoratorsPlugin`（esbuild 标准降级），分工与债见 [债务 标准装饰器降级分居两套机制](../debts/20260923-标准装饰器降级分居两套机制.md)。两条线的分工与不变量另见 [`devpackages/devkit/README.md`](../../devpackages/devkit/README.md)。
- 上线后修掉的两处串线：其一，`clientBundleSpec.define`（`process.env` / `import.meta` 替成空壳）曾被塞进 tsdown 的**全局** `define`，把 host 半的 `process.env.DSH_*`、`import.meta.url` 一起抹掉——Electron 壳读不到 `DSH_DESKTOP_APPCONFIG_DIR`、host 进程 `new URL(rel, ({ }).url)` 直接 `ERR_INVALID_URL`，另有 8 个包的 `dist` 同病；现在浏览器 define 只住在现场打包那条链。其二，上游各包自带的 `tsconfig*.json` 随 patch 删除（`patches/steps.json` 的 `rm` 步）：实测留着也能全量 `just build` 通过，删掉是让「谁的 tsconfig 说话」只有一份答案（本仓库根 `tsconfig.json`），避免 tsgo / oxc 按就近原则读到上游口径。这一份答案后来按 compiler face 分成两份：宿主面仍是根 `tsconfig.json`，client 面是根 `tsconfig.client.json` 加各 client 半目录里那份就近 `tsconfig.json`（症状、规则与构建那一份见 [如何写](../standards/how-to-write.md)）。
- 打包形态的落点（源码面进 bundle）：patch 顺带把上游 `files` 从 `lib/*` 改指 `src`（改了才是「清单在、代码也在」——deploy 闭包按 `files` 拷工作区副本，不改就是空壳：app 能起、host 起不来）；随包运行时载荷多一份 `loader/`（oxc loader + 它自己那份 rolldown），壳给 host 传 `--import=<loader>` 与 `DSH_SOURCE_LOADER`（后者的上游读者是 subprocess runner 的转译器选择，见 `patches/source-loader.patch`）；仍指着源码的 client 半在**打包时**打成模块表的工厂脚本（上游 client 包的浏览器实现依赖只在 devDependencies 里，运行期解析不到），`dev-client-bundles` 那条行因此只服务 dev，且内置在宿主变体自己的 overlay 里而不是 profile 的用户层；profile 的直接依赖带上本地依赖闭包（pnpm 对 `file:` 包的 `workspace:` 依赖静默跳过）。
