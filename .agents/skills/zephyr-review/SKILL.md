# 审查（review）

两个轴**分开跑、分开报**，互不掩盖：**标准**（是否符合项目记录的规范）、**规格**（是否忠实实现了发起它的设计或需求）。一次改动可能过一个轴而败在另一个轴，合起来排序就会互相掩盖。

本技能只定义 SOP；规范、记录与命令入口按**项目自己的约定**定位。

## 一、定固定点

固定点由用户给（提交 SHA、分支、标签、`main`、`HEAD~5`…），没给就问。先确认可解析、差异非空，再往下走——错误的引用或空差异应在这里失败，而不是在子代理内部：

```
git diff <fixed>...HEAD      # 三点式，基于 merge-base
git log <fixed>..HEAD --oneline
```

## 二、找规格来源

按序找发起这次改动的设计或规格：

1. 提交信息里的引用（`#123`、`Closes #45`…）；
2. 用户作为参数给的路径；
3. 与分支名或功能匹配的项目记录（设计 / 决策记录），或项目约定的临时规格目录（如 `.scratch/specs/`）；
4. 都没找到就问用户规格在哪；用户说没有，**规格轴跳过**并在报告里注明「无规格可用」。

规格轴回答三件事：规格要求但没做（或只做一半）、做了但没要求（范围蔓延）、做了但做法与规格不符。

## 三、定标准来源

- **工作区指令**与项目规范（如何写 / 如何验证）：**逐条对照**，本技能不复制其中条目；
- 既有决策记录：与它们冲突按设计讨论处理，不是自动否决；
- 各层的门面与术语表：该模块的用法与词汇；
- 外部依赖副本的只读边界与补丁登记要求（项目有上游副本时）；
- 坏味道基线 `references/smell-baseline.md`：项目规范优先于基线，基线永远只是判断。

## 四、两条轴并行跑

两个子代理**一起发出、前台运行**，再汇总它们的报告；每个都以全新的上下文窗口启动。

**标准子代理**的提示词包含：差异命令与提交列表；上面找到的标准来源文件列表；**坏味道基线全文**（子代理没有别的途径拿到它）；任务：

> 报告——在相关处按文件 / hunk——(a) 差异中每一处违反已记录标准的地方：引用标准（文件 + 规则）；(b) 你发现的任何基线坏味道：命名并引用该 hunk。区分硬性违规与判断：已记录标准的违反可以是硬性的，基线坏味道始终是判断，且已记录的规范优先于基线。跳过工具强制检查的内容（格式、lint / 类型检查）。400 词以内。

**规格子代理**的提示词包含：差异命令与提交列表；规格的路径或内容；任务：

> 报告：(a) 规格要求但缺失或只实现了一部分的；(b) 差异中未被要求的行为（范围蔓延）；(c) 看似实现了但实现方式有误的需求。每条发现引用规格原文。400 词以内。

## 五、审查时特别看什么

通用关注点，具体判据以第三节的来源为准：

1. **意图与接口**：改动两侧的接口是否都追过——行为、错误、取消、所有权、回收。
2. **生命周期与并发**：注册与 disposer、异步建立、回调、子进程；发布前的竞态、await 期间的取消、回收是否静默。
3. **边界与所有权**：只读区是否被改；依赖是否按用途声明（运行期面与测试面分开）；抽象是否只服务当前调用方；同一能力是否被两个模块各实现一半。
4. **范围与必要性**：每个抽象、状态机、选项、兼容路径是否对应现行契约与真实调用方；规格没要求的东西是否被顺手加进来。
5. **测试强度**：断言是否会在预期回归时失败；是否验证外部可观察行为而非复述实现；是否踩了 `testing-antipatterns`。
6. **记录同步**：动了边界、契约或流程，对应 home 是否更新，且没有在别处重复定义；外部依赖副本的补丁 / 步骤是否写清了为什么。
7. **验证证据**：作者跑了哪条命令；跨模块或配置类改动是否按证据矩阵跑了该跑的全量。

## 六、报告

在 `## Standards` 与 `## Spec` 下**分别**呈现两份报告，逐字或轻度清理；**不要合并、不要重新排序**——两个轴刻意分开，合并会互相掩盖。

每条给：缺陷、位置（文件 / hunk）、影响、证据；区分阻塞与建议；工具已强制的（格式、lint / 类型检查）不重复报；跳过项目规范明确认可的写法。

收尾一行：每个轴的发现总数，以及**各轴内**最严重的一条（如有）。不要跨轴选出唯一赢家——那正是分开审要防的。
