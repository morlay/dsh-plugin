# 实现（implement）

设计已对齐（见 `zephyr-design`）后走这条线：**接缝先约定，测试先红。**

本技能只定义 SOP；验证命令、规范与红线按**项目自己的约定**（工作区指令与各层规范），技能不复述。

## 一、按规模决定要不要规格与票据

| 改动                              | 产物                                     |
| --------------------------------- | ---------------------------------------- |
| 单模块小改、无契约变更            | 设计对话的结论（含验收判据）→ 直接进循环 |
| 跨模块 / 新契约 / 多票据 / 大重构 | 先写规格，再拆票据，再实施               |

- **规格**写到项目约定的临时产物目录（缺省 `.scratch/specs/<feature>.md`），骨架见 `templates/spec.md`：问题陈述、方案、用户故事、实现决策、测试决策、范围之外。**不要访谈用户**，只综合已知的东西；用术语表的词，遵守既有决策。
- **票据**写到 `.scratch/<feature>/issues/NN-<slug>.md`，骨架见 `templates/ticket.md`，一张一文件，按依赖顺序编号，写清**阻塞边**。**前沿**是任何阻塞者全部完成的票。
- 拆票规矩：每张票是一条**垂直切片**——穿过每一层的窄而完整的路径，本身能演示或验证，尺寸装得进一个全新的上下文窗口；**预重构先做**（先把改动变容易，再做那个容易的改动）。
- **大范围重构**（一个机械改动同时打断成千上万调用点）不硬塞进垂直切片，按**展开-收缩**编排：先加新形式、分批迁移调用点（每批一票、由展开那步阻塞）、最后删旧形式（由所有迁移批量阻塞）。连分批都各自绿不了时，让它们共享集成分支，并全部阻塞一张最终的集成与验证票——绿色只在那里承诺。
- 规格里的用户故事要**冗长**，每条写成「作为 <角色>，我想要 <功能>，以便 <收益>」，覆盖该功能的各个方面。

规格与票据是**易变产物**：不进仓库，也不要在设计文档里复制一份。

## 二、接缝先约定

写任何测试之前，把这次要穿的接缝写下来并与用户确认；每个候选接缝给一行注记：能捕获什么、会漏掉什么。优先沿用已有接缝，能在最高处就在最高处，一个够用就不要两个；真要新开，在力所能及的最高点开。

接缝的类别：

- **契约面**——模块对外承诺的类型、错误与不变量；
- **依赖面**——服务定位 / 注入的公开面，以及依赖的声明方式（运行期面与测试面分开）；
- **装配面**——装配清单、配置 schema 与默认值、包出口；
- **出口与命令**——HTTP / wire 端点、命令行与脚本的对外行为。

具体接缝与对应的守护测试按项目的各层规范，本技能不复制。

没确认接缝就不写测试。测试只写在接缝上：不 mock 内部协作者、不测私有成员、不绕过接口查内部状态（直读库表、读私有字段）。

**指代先对齐再动手**：反馈里的「这里 / 这个位置 / 这个 header」先用一句话确认是哪个容器、哪一行再改。

## 三、循环：一轮一个垂直切片

1. 写一个**会失败**的测试，只覆盖这一轮要的行为（一发曳光弹）；
2. 写**刚好**让它通过的实现；
3. 跑它，绿了进下一轮。

好测试通过公共接口验证外部行为，读起来像一份规格，重构后仍然活着。判据：**把实现的写法换一种，测试还应不应该红**——会红说明它测的是实现；期望值必须来自**独立真值**（手写 fixture、规格原文、外部实现里固定下来的字面量），不能由被测代码用同一种方式算出来。

不做：不先写完所有测试再写实现（水平切片）；不预写下一轮的测试；不加规格没要求的抽象、参数与钩子；**重构不属于循环**——它归 `zephyr-review`。

三条反模式与改法见 `references/testing-antipatterns.md`。

## 四、局部闭环先于联调

联调（起服务、真浏览器、真宿主）之前，模块必须先在**局部**跑绿：能跑单元测试的先用单元测试；需要真实包形状时用假包 / fixture。**两侧各用对方的假实现**——客户端半用 mock server，服务端半用 mock client——两侧都能在秒级测试里跑通；联调只做最后一道「装配 + 联通」验收，不当第一层调试手段。

## 五、票据多且互不阻塞时：子代理编排

单张票或串行链自己按第三节做。票据 ≥2 且互不阻塞时：

1. 建**集成分支**；项目走 PR 收尾时，在第一次合并之后开草稿 PR，否则集成分支本身就是交付物。
2. 每张票一个**实现者子代理**，各自工作树、各自分支；开工前确认工作树基于集成分支，完成前把集成分支最新顶端合进来。它按第三节做。
3. 每完成一张，由**合并子代理**合进集成分支；合并改变了前沿就再起一批，拿到最大并发。
4. 票全完成后对集成分支走 `zephyr-review`，再用**一个**实现者子代理修完问题。
5. 清理所有工作树。

子代理之间只传**上下文指针**（规格、票据、笔记、提交），不重复指针已经能拿到的信息。需要探索时先派探索子代理，让它把笔记写到 `.scratch/implement-spec/<feature>/notes/`。

## 六、验证与完成判据

按项目约定的**证据矩阵**选最小充分证据，贴出真实输出。缺一条就不算完成：

1. 行为有测试，且该测试会在回归时失败；
2. 所选证据跑过，并贴出**真实结果**（不是「应该能过」）；
3. lint（含类型检查）与格式没有引入**新**错误；
4. 记录同步：动了边界、契约或流程，对应 home 跟着改（home 表按项目约定）。

**数据为空 / 候选为空这类问题，先读运行时事实再改代码**：先用一次性打点确认是哪一环（服务在不在、调用返回了什么、走了哪条分支），再决定改哪里——打点写完就删。看起来像环境问题的，先证明是环境还是回归（记下确切命令与读数），不要按猜测改代码，也不要反过来把回归归给环境。

不做：不为过测试改断言——行为变了就连测试一起改并说明；不动项目的只读区。

## 七、边界与交接

- 只读区、依赖方向与发布纪律按项目约定（工作区指令与各层规范）。
- 动到项目的外部依赖副本（vendor / patch / 版本跟随）→ `zephyr-upstream-sync`。
- 实现完待审 → `zephyr-review`。
