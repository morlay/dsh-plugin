# 两套运行时的切入点

先回答「在哪对接」，再回答「怎么装」。切入点必须是**可替换的接口**，且两侧各自闭环——否则任何「对接」都只是让一侧寄生在另一侧。

## 一、两套运行时的构成

| 关注点       | dsh 运行时                                          | zephyr 运行时                                              | 是否对等                              |
| ------------ | --------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------- |
| 容器         | cordis `Context`（Service + fiber）                 | 令牌表 + `bootstrapApplication`（内部包一层 cordis fiber） | 对等                                  |
| 插件形态     | `name` / `inject` / `apply` 的插件对象或 Service 类 | Provider 类（`@Injectable` + `onInit` + 令牌）             | 对等                                  |
| 装配清单     | `cordis.yml` + bundle patch                         | `provide([...])` 清单                                      | 对等                                  |
| 服务注册     | `ctx.provide(name)` / `super(ctx, name)`            | `store.provide`（派生名 + 可选上游别名）                   | **不对等**：我们多一层「令牌 → 名字」 |
| 生命周期     | fiber 的 `onInit` / `onDispose`                     | `mountInstance` 包装的 fiber + `App.dispose`               | 对等                                  |
| 浏览器运行时 | `client-modules`（模块表）+ `ui-renderer`           | client bootstrap + `Slots` + `UiRenderer`                  | 对等                                  |
| 传输         | `connection.rpc` + `/api` 共享通道                  | `Connection` 契约 + `remote.invoke`                        | 对等                                  |
| 渲染槽位     | `ctx.slots.register`（SlotMap + children spec）     | `Slots` 契约 + `@Slot` / `@SlotView`                       | 对等                                  |
| 远端方法     | typert 注册表 + `@Remote` 服务方法                  | `@RemoteGroup` / `@RemoteMethod` + `RemoteHandlers` 路由表 | **不对等**：我们是自己的协议          |
| 部署参数     | profile 的 cordis 配置                              | `AppEnv`                                                   | 对等                                  |

结论：**九成对等，两处不对等**（服务注册多一层令牌；远端方法是我们自己的协议）。切入点必须落在这两处，而不是把整个运行时对缝。

## 二、切入点（Seam）

| #   | 切入点   | 我们这侧的接口                                            | dsh 那侧                               | 方向               | 闭环要求                                                                     |
| --- | -------- | --------------------------------------------------------- | -------------------------------------- | ------------------ | ---------------------------------------------------------------------------- |
| S1  | 服务解析 | 令牌（`InjectionToken` / `@Injectable({ name })`）        | `ctx.get(name)` / `ctx.provide(name)`  | 双向               | 两侧都能按名字解析；名字必须**同名同义**，不同义的必须改名或加前缀           |
| S2  | 行装配   | Provider 清单                                             | cordis 插件行                          | 我们 → dsh         | 我们的清单能单独 `bootstrapApplication`（无宿主）                            |
| S3  | 生命周期 | `onInit` / `onDispose` / `App.dispose`                    | fiber                                  | 双向               | 我们的 `dispose` 不销毁宿主 ctx（已满足）                                    |
| S4  | 渲染槽位 | `Slots` 契约（`register` / `inject` / `registerFactory`） | `ctx.slots`（SlotMap + children spec） | 双向               | 两侧各自能渲染（无对方时用自己的 `SlotsDefault`）                            |
| S5  | 传输     | `Connection` 契约（`rpc.call` / `fetch`）                 | `connection.rpc` + `/api`              | 双向               | 我们自带载体（`web` + `connection.service`）也能跑                           |
| S6  | 远端方法 | `RemoteHandlers` 路由表 + `@RemoteGroup`                  | typert `@Remote` / `/api`              | 单向（我们 → dsh） | 我们的协议必须**不依赖** dsh 的 typert 才能自跑（`local-remote` 已证明可行） |
| S7  | 模块表   | `ClientAssets` / client bootstrap                         | `client-modules`                       | 单向               | 我们自持时用静态资源（`static-client-assets.service`）                       |
| S8  | 部署参数 | `AppEnv`                                                  | profile 配置                           | 单向               | 我们自持时读自己的默认值                                                     |

**S1 与 S6 是唯一需要翻译的两处**：S1 翻译「令牌 → 名字」，S6 翻译「我们的方法协议 ↔ 上游 RPC 通道」。其余六处是**同构替换**（换实现，不换语义）。

## 三、闭环判据

| 侧          | 闭环含义                                                                                          | 当前状态                                                                          | 缺口                                    |
| ----------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------- |
| zephyr 单独 | 不装任何 dsh 包，`bootstrapApplication` 起 web server、渲染、远端调用（`local-remote`）、RDB 存储 | **部分**：web/remote/slots 都有自持实现，但契约里有 7 个只有契约没有实现          | 补 7 个自持实现或明确「必须由宿主提供」 |
| dsh 单独    | 原生 bundle 跑，不装我们的包                                                                      | 上游自身满足                                                                      | —                                       |
| 两侧共存    | compat 只做 S1 / S6 的替换，其余零翻译                                                            | **未达**：当前 compat 混了能力实现（`connection.seam.ts` 曾把整份实现搬进适配层） | compat 只许出 `<能力>FromHost` 一行     |

## 四、SOLID 对照

| 原则       | 要求                          | 现状                                                                                 | 要做                                                           |
| ---------- | ----------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| S 单一职责 | 一个契约一个能力              | `Remote` 混了 `invoke` + 事件 + `useAgentScopes`（替身因此写空方法）                 | 拆成 `RemoteInvoke` / `RemoteEvents` / `AgentScopes` 三个契约  |
| O 开闭     | 新增能力 = 新增集合，不改核心 | `provide([...])` 已满足                                                              | 保持；禁止在实现里加「宿主分支」                               |
| L 里氏替换 | 适配行与自持实现行为一致      | `XxxFromHost` 与 `XxxDefault` 签名一致，但错误面不一致（有的抛、有的返回 undefined） | 适配行缺宿主时**必须抛**，给出组合错误                         |
| I 接口隔离 | 契约只暴露消费方需要的成员    | `Remote` / `Connection` 把 host 与 client 面混在一个契约                             | 按面拆契约（`ConnectionRpc` / `ConnectionFetch` 等）           |
| D 依赖倒置 | 核心依赖契约，不依赖宿主      | 核心已不引 `@deepseek-ai/*`；但 `compat` 之前把实现搬进来了                          | compat 只允许「构造上游插件 + 采纳宿主实例」，不许承载能力逻辑 |

## 五、顺序（先闭环，后装配）

1. **定名**：类名一律不动。只补 `@Injectable({ name })` 的 alias——上游同名同义才写（表见 [契约定名表](./20261124-契约定名表.md)），其余靠装配器自动生成的派生名（`zephyr-` 前缀）。一契约两面（host/client 同名类）不改名：两份活在 node 与浏览器两个进程，作用域不重叠。
2. **拆契约**：按 SOLID 的 I 把 `Remote` / `Connection` 拆开，消费方只依赖它真正用的那部分。
3. **补闭环**：7 个只有契约没有实现的能力逐个定性——自持补实现，或标记「必须由宿主提供」并在缺时抛组合错误。
4. **收 endpoint**：`remote/**` + `api-remotes/**` 的协议部分合成一处 `endpoint`。
5. **compat 瘦身**：每行只做 S1/S6 的翻译（采纳宿主实例或 mount 上游插件），不承载能力实现。
6. **最后装配**：两套闭环都成立后，才谈 bundle 的 `provideHostSeams()` / `provideClientSeams()` 组合。

## 六、本轮不做的事

- 不迁移目录（分层与出口的设计另存，等闭环后再执行）；
- 不改 `bootstrap.ts` 的装配算法（`hostedValue` / 别名补发这些要等 S1 定名完成后才成立）；
- 不在实现类里加任何「宿主有则让位」的标记。
