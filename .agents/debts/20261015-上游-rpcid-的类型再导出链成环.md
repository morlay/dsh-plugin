# `RpcId` 的类型再导出链成环（上游源码面）

**状态**：接受中。**触发**：client 侧的连接包（`@deepseek-ai/dsh-client-connection`）在 dev / 打包形态被加载时。

## 现象

浏览器报 `Uncaught SyntaxError: Detected cycle while resolving name 'RpcId' in '…/connection/src/client/rpc.ts'`。

## 是什么

上游的 `api/remotes` client 面写着：

```ts
export type { …, RpcId, … } from '@deepseek-ai/dsh-client-connection/client'
```

这条**类型**再导出链是 `api/remotes/client → connection/client/index.ts → client/api.ts → ../rpc.ts`。而
`client/rpc.ts` 自己**按值**引入 `RpcId`（`RpcId(randomUuid())`），于是它在"类型被当值处理"（我们这边
`verbatimModuleSyntax: false`）时成了链上的中间站：谁想从这里再导出 `RpcId`，就在 `rpc.ts ↔ client/rpc.ts`
之间造出环。

**试过的错修**：给 `client/rpc.ts` 补一行 `export { RpcId } from '../rpc.ts'`——环正是这么来的（已撤）。

## 为什么先接受

- 只影响 client 侧连接包在**源码面**被加载的路径；
- 修它要动上游的再导出写法（本地 patch），而"哪种写法最稳"还没定：a) 让 `client/index.ts` / `client/api.ts`
  的再导出直接从 `../rpc.ts` 取；b) 让 `client/rpc.ts` 用 `export type { RpcId } from '../rpc.ts'`（类型再导出
  不生成运行期绑定，语义上也最准）。两种都要在 patch 里改上游文件，得先确认上游自己的构建面怎么处理这条链。

## 想收时怎么收

1. 按 b 改（类型再导出），跑 `just vendor sync && just vendor patch` 让补丁干净应用；
2. 用 `@local/dshdev` 起 dev 与打包形态各验一次（页面无 `cycle` 报错、`RpcId` 有值）；
3. 顺带看看上游有没有把这条类型链收成"只从 `rpc.ts` 出"的更干净写法——若有，跟上。
