# hmr 行在源码面下未激活

状态：未销账

**现象**

`just custom dev --web`（以及桌面 dev）启动时只有一行未激活：

```
dsh: warning: 1 entry did not activate
hmr (@deepseek-ai/dsh-hmr): failed to import
```

`failed to import` 是 [app-boot](../../vendor/deepseek-harness/packages/boot/app-boot/src/index.ts) 在
`entry.fiber === undefined` 时给的**字面量**——真实错误在 cordis loader 的装载阶段被折叠。表现是该行不参与
热更新；该行配置 `root: []`（本部署下不监听任何根），所以影响面是"少一行"而不是功能故障。

**已排除的项**（都实测过）

- 单独 import 成功：绝对路径、包目录内按包名、部署目录（`node_modules/.dsh-desktopify/development/project`）
  按包名，三种上下文用的是同一个 `@local/devkit/ts-loader`。
- `exports`、`main`、`types` 都已指 `src`（[patch.ts](../../.agents/skills/dsh-plugin-upstream-sync/scripts/patch.ts)
  的 `exports` 步骤会一起改）。
- 其它 60+ 行正常加载，包括同样用 `@Inject` 的 `plugin-manager`、以及同样 default 导入
  `@deepseek-ai/schemastery` 的包。
- 装饰器不是原因：typert `Remote`/`RemoteScope` 与 cordis `Inject` 都已 patch 成同时接受 TC39 与
  legacy 调用协议（[decorator-dual-protocol.patch](../../patches/decorator-dual-protocol.patch)）。

**待查**

cordis loader 的装载路径：`tree.ts` 在 `ctx.loader.internal` 存在时优先走
`ModuleLoader.fromInternal()`（Node 内部 ESM loader），失败信息在那里被 `composeError` 包装后丢失。
两个入手点：`vendor/loader/src/config/entry.ts` 的装载失败分支；或临时把该行换成普通 `import()` 对照，
拿到真实错误再决定是 loader 兼容问题还是上游既有行为。

**不修的理由**

影响面是"一行不参与热更新"；拿真实错误要动 vendor 内部 loader 或加临时调试。先把源码面的其它部分
（exports 改写、生成物、loader、装饰器双协议）稳住，这项单独跟进。

Done when：该行恢复激活，或确认它与源码面无关（上游在该版本下的既有行为，改记上游问题）。
