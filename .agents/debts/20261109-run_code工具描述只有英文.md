# `run_code` 的模型面说明只有英文，本仓的中文口径到不了那里

状态：未销账——模型面唯一入口工具的描述由上游执行器造死，本仓没有改它的接缝
位置：`packages/agent/dsh-ptc/src/tool-executor.service.ts`（执行器行）、`vendor/deepseek-harness/packages/core/tool-executor-ptc/src/ptc.ts`（`TYPESCRIPT_FLAVOR`）、`vendor/deepseek-harness/packages/core/tools/src/index.ts`（保留名与 `describe`）、`packages/agent-ex/session-mode/src/guidance/packs/code.ts`、`packages/agent-ex/session-mode/src/ptc-sdk.ts`（`renderSkeleton`）

**现象**

PTC 会话的模型面只声明 `run_code` 一条：执行器把 `tools:sdk` 换成稳定骨架，`describe()` 也只给保留名那一条。这条工具的 schema `description` 与 `code` 参数说明由上游 `TYPESCRIPT_FLAVOR` 构造，是英文。

本仓的中文只落在两处，都不在模型面的 schema 上：system 骨架（`renderSkeleton` 里那段「在 `run_code` 写的程序里调用工具」）与工具说明（`packages/agent-ex/session-mode/src/guidance/packs/code.ts` 的 `text` 与 `short`「用代码调用其它工具（PTC）」）。

改不到的原因在上游：`run_code` 是保留名——`tools.register` 抛「reserved for the PTC mode presentation transport」，`tools.restrict` 也不许点名它；模型面的 description 由 `executor.describe(definitions())` 产出，而它不在 `definitions()` 里。

**影响**

模型拿到的唯一直接入口是英文说明，与 system 骨架、工具说明里的中文口径不一致——同一个事实在模型面有两个说法。功能上不影响调用（参数名与骨架一致），影响的是中文语境下的理解成本与「一个事实只有一个说法」。

**触发条件**

两件事任一发生就先还：① 要统一模型面的中英文口径（对外演示或发布 PTC 形态时）；② 上游在执行器面暴露可配置的工具定义（`ToolRegistry.setExecutor` 那条线交出 definition 而不只是执行函数）。

**销账条件**

Done when：`run_code` 的模型面 `description` 来自本仓可配置的一段中文文本，并有 spec 钉住「模型面看到的是这段」。眼下没有这样的接缝，也没有这样的用例——`packages/agent-ex/session-mode/src/__tests__/tool-guidance-full.spec.ts` 里的 PTC 形态用的是替身执行器，那句英文说明是替身自带的。

**不修的理由**

要拿模型面的定义，必须经 `ToolRegistry.setExecutor` 与上游执行器的私有契约（transport、section、schema 三样都由它私有）耦合，上游一改就坏。这与「与上游行为分叉而非缺陷」是同一类代价，眼下又没有功能影响，先记成债。
