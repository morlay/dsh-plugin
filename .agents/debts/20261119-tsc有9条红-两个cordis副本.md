# 债：`tsc` 有 9 条红，根因是 `@deepseek-ai/cordis` 解析到两个副本

状态：未销账。**`vitest` 全绿但 `tsc` 红**——`vitest` 走 esbuild strip、不做类型检查，所以绿是假象。

## 现象

`pnpm exec tsc --noEmit -p tsconfig.json | grep '^packages/'` 有 9 条，全是同一类：

- `bootstrap.ts` ×2、`scoped-rows.spec.ts` ×1、`dsh-{job,ptc,sandbox,skill}` 的 spec ×4 —— `Context` ↔ cordis `Context` 的单层断言报 **TS2352「两个类型不够重叠」**；
- `scoped-rows.spec.ts` ×1 —— `emit("test/ping")` 不在 `keyof Events`（`declare module` 补的没生效，同根因）；
- `session-mode.service.ts` ×1 —— TS2375（`reasoningEffort?: string` 在 `exactOptionalPropertyTypes` 下的精确可选属性）。

## 根因

报错文本自己说了：

```
Type 'import("@deepseek-ai/cordis").Context' is missing ... from type
'import("…/vendor/deepseek-harness/vendor/cordis/src/context").Context':
set, accessor, mixin, fiber, … (9 个)
```

**`@deepseek-ai/cordis` 与 `vendor/deepseek-harness/vendor/cordis` 是两个模块实例**——前者缺 `events.ts`/`fiber.ts` 的模块增强（`set`/`accessor`/`mixin`/`fiber` 那 9 个成员由它们 `declare module` 挂上）。
而 `vendor/…/vendor/cordis/src/index.ts` 明明 `export * from './events.ts'` / `'./fiber.ts'`——所以是**解析路径分叉**：同一个包名在 program 里被判成两个模块（`audit` 的「上游唯一化」判据盯的就是这个，但它只看值导入）。

## 为什么本批才红

固定点 `9c018370` 上这 9 条**不存在**（`git worktree` 对比实测 0 条）。本批新增了 `ctx as CordisContext` / `as Context` 这类**跨副本断言**（`mountInstance` / `bindFace` / 各 spec 的 `freshContext`），才把两个副本的差异暴露出来。

## 销账条件

Done when：`pnpm exec tsc --noEmit -p tsconfig.json | grep -c '^packages/'` = 0，且 `@deepseek-ai/cordis` 在 program 里只有**一个**模块实例（判据：`tsc --explainFiles` 或 `--traceResolution` 里该裸包名只解析到一条路径）。

## 不修的理由

它牵动 workspace 的依赖解析（`pnpm` 的 `link:` 与 `vendor/**` 的嵌套 vendor 目录），不是一行改动；而且本批的**行为**是对的（`vitest` 1793 用例全绿、`just custom dev` 未见异常），缺的是**类型面的一致性**。
在修好之前，`tsc` 不能作为门禁——这也解释了为什么这一路的门禁只有 `just audit` + `vitest`。
