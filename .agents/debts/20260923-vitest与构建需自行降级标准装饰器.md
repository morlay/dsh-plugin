# vitest 与 fork 包构建需自行降级标准装饰器

状态：未销账（一份预转换：`@local/devkit` 的 `standardDecoratorsPlugin`，两个调用点——根 `vitest.config.ts`
与 `packages/subagent/dsh-subagent/tsdown.config.ts`）

**现象**

上游 typert 用**标准（TC39）装饰器**标记远程面（`@Remote('prompt')`、`@Remote('interruptByParent')`）。
上游的编译管线里这一步由 tsc 完成（先出 `lib/types/*.js`，rolldown 再打包），所以它们的 `lib` 里是
`__esDecorate`。本仓库的薄壳 fork 包**走源码入口**（dev 由 tsx、测试由 vitest、构建由 tsdown，三者都不经过
tsc），于是同一条源码在两处炸：

- **vitest**：`node:vm` 编译时报 `SyntaxError: Invalid or unexpected token`——Vite 8 默认转换器（oxc）
  不降级装饰器（实测 `transformWithOxc(target: es2018..es2024)` 均原样保留）；
- **tsdown**：rolldown/oxc 同样不降级，`dist/index.mjs` 保留 `@Remote(...)`，Node 加载直接语法错
  （实测 Node 26 不认这种语法）。

规避是一份 esbuild 预转换（检测到装饰器语法才转），住在 `@local/devkit`
（`devpackages/devkit/src/standard-decorators.ts` 的 `standardDecoratorsPlugin`），范围由调用点给——目前两处都在
`packages/subagent/`：`packages/subagent/dsh-subagent` 是第一个引入带装饰器上游源码的包。

**影响**

构建那一侧不是历史包袱，删了会在打包形态上炸得更远：dev 形态由 tsx 直载源码，源码入口本来就能跑，缺了它
本地看起来"一切正常"；打包形态的 profile 把 `@morlay/*` 的 exports 切成 `publishConfig` 那套
（`prepare-seed.ts` 的 `switchToPublishedExports`），**加载的正是 dist**——`@morlay/dsh-subagent` 那一行
import 失败 → `subagents` 服务没人注册 → 每个 preset 的 delegation 行都停在 `waiting for subagents` →
名册里所有 preset（含官方 `standard`）都是"加载失败"。判据：构建后
`node -e "import('./packages/subagent/dsh-subagent/dist/index.mjs')"` 能加载（装饰器残留时是 `SyntaxError`）。

范围是本仓库的配置，不改上游。

**触发条件**

本仓库的其它包引入同类（带装饰器的）上游源码时——那时把调用点的范围放宽（共享插件已经在 `@local/devkit`，
调用点只给 `scope`），并把这套规避覆盖到该包的测试与构建。两条一起踩过的判据：

- **`tsdown.config.ts` 的导出必须显式注解类型**：直接导出推断类型（例如包一层 async IIFE 合并 `plugins`）会让
  `default` 的类型引用 tsdown / hookable 的内部声明文件，于是**每个包**构建时都在同一个 TS program 里报
  `TS2883: The inferred type of 'default' cannot be named without a reference to 'Arrayable' from …`——不是只有
  那个包的 build 挂。写法：`type CordisPluginConfig = Awaited<ReturnType<typeof defineCordisPluginConfig>>`，
  导出显式标 `Promise<CordisPluginConfig>`；内部辅助函数不必标（只有**导出**的类型需要可命名）。
- **别用 `__esDecorate` 判断"装饰器降级生效了没有"**：esbuild 的标准装饰器转译在这个仓库的产物里长这样
  `[(_a = …, _prompt_dec = [Remote("prompt")], …)]`（方法名前挂 `_<name>_dec`）+ 文末的
  `__decorateElement` helper，`__esDecorate` 一次都不出现。看产物该 grep `Remote("prompt")` 的调用点与
  `__decorateElement`，或者直接 `node -e "import('./dist/index.mjs')"` 看能不能加载。

**销账条件**

Done when：满足任一条即可删插件——oxc/rolldown 支持装饰器降级（改用 `transformWithOxc` 或 target 设置）；
或本仓库接入可用的 TS 转译 API；或上游把 `@Remote` 从装饰器改成命令式调用。

上游有现成实现（`vendor/deepseek-harness/vitest.shared.ts` 的 `standardDecoratorPlugin`，用 `typescript` 的
`transpileModule`），本仓库用不了：`typescript` 在这里是 7.x（原生实现，JS API 里没有
`transpileModule`／`ScriptTarget`），且配置加载器把 CJS 包成 `{ default, "module.exports", … }`，
`import ts from "typescript"` 拿到的是包装对象。

**不修的理由**

两条路都要动仓库构建链（换 dts / 转换 generator，或自建转译管线），而 oxc 侧目前没有装饰器降级开关；
共享插件已经覆盖了所有走源码入口的包，新增同类包的接入成本只是一条 `scope` 配置。
