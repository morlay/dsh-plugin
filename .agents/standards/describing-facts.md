# 描述事实

**描述**是任何声称事实的文本：`README.md`、记录树、manifest 文案、schema 的字段说明、给模型看的文案。
这一层管两件事：**承载描述的地方必须与真源一致**；**引用代码必须写成人能核对、机器能校验的形式**。

判据是两条机械检查，别再手抄规则：

- [`doc-references.spec.ts`](../../devpackages/devkit/src/__tests__/doc-references.spec.ts)：行内代码里的工作区路径必须
  存在、`just <recipe>` 必须在根 [`justfile`](../../justfile) 里（例外表在这份 spec 里，那是它的 home）；
- [`markdown-links.spec.ts`](../../devpackages/devkit/src/__tests__/markdown-links.spec.ts)：相对链接必须可达。

## 一个描述只有一个真源

描述性载体不止 README 一种，**每一类各有自己的真源**——改描述 = 改真源，然后让载体跟上：

| 载体                                           | 真源                                     | 反例（都是真出过的形态）                                              |
| ---------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------- |
| `README.md`、`.agents/**` 的叙述               | 代码（行为、接缝、依赖方向）             | 文档说某个包「收窄工具目录」，而该包代码里只是记了一笔、没拦          |
| `package.json` 的 `description` / `keywords`   | 包的门面：该包 `README.md` 的一句话定位  | README 换了定位，`description` 还留着上一轮职责（消费方看到的是后者） |
| `locale/*.json` 的 `meta`                      | 同上（中英两份都得跟）                   | 换定位时只改了一个语言那份，另一份还是上一版；两份互相也不一致        |
| bundle 的 `cordis.patch.yml`（**生成物**）     | 它引用的模块（能力包的行与出口）         | 手改生成物里的行 `name`，下次构建被覆盖，装配面与真源分叉             |
| schema 的 `description()`（中英两份）          | 该字段**今天**的实际语义（含默认与边界） | 只写「配置为 `false` 时会丢掉」，不写「变化时也丢」                   |
| 给模型看的文案（工具说明、skill 目录、注入面） | 它对应的机制                             | 文案说「按 X 分组」，而分组实际由另一处常量决定                       |

规矩：

- **生成物只在真源处改**：bundle 的 `cordis.patch.yml` 由构建写出，要改就改能力包的入口 / `rows` 出口 /
  `tsdown.config.ts`，然后 `just build` 重建；`exports` 与 `publishConfig.exports` 同理（见
  [`how-to-write.md`](./how-to-write.md) 的「包出口」）。手改生成物 = 改完即失效，还会让真源看起来是对的。
- **描述不复制**：一处已定义的事实，别处只链接。home 表见 [`AGENTS.md`](../../AGENTS.md)。
- **给模型的文案与机制同源**：机制改了必须同一处改文案；文案里的行为、边界、默认值都要在代码里找得到。
- 判据：**只看载体，能回答「真源在哪」**——回答不了，说明这条描述没有真源，得先定真源再写。

## 引用代码：路径与行号

- **路径引用必须指向真实存在的文件**（判据：上面那条 spec）。判据与取舍：
  - 写**全路径**：`packages/<scope>/<name>/src/x.ts` 这种从仓库根起算的形式永远可核对；
    包内相对写法（`src/<模块>.ts`）只在该文档属于那个包时成立——本包文档写包内文件、跨包一律写全路径。
  - 行内代码里的路径才会被机械校验：**别把路径只写在链接文本里**（`[短形式](完整路径)` 这种），
    文本与目标要一致——机械检查只认链接目标那份。
  - `git show HEAD:<path>` 这类**历史修订路径**不受校验：那里的路径指的不是工作区当前状态，写清是哪个修订。
  - 以下形态直接不参与校验（不是文件引用）：占位（`<…>`、`…`、`*`、`{}`）、包名寻址
    （`@<scope>/<name>/src/x.ts`——那是包说明符，不是工作区路径）、URL、markdown 语法示例，
    以及构建产物、打包器内部布局（`dist/`、`lib/`、`node_modules/` 内）与运行期数据路径——
    后者不由仓库内容决定。
  - 上游文件的引用**要能落到 `vendor/**` 里的真文件**：写从上游仓根起算的相对路径（与上游仓内一致）比写
    一段短形式（`<上游包名>/src/x.ts`）强——短形式只在全仓唯一时才能被核对，上游布局一改就无人发现。
- **行号是债，能写文件名就别写行号**：引用优先写到**文件名或小节名**，让读者按名字找；一次重构会让几十处
  行号同时失效（本轮一次改名 + 拍平就是这样）。真要指到片段（`src/<模块>.ts:112-140`）就**在同一笔改动里同步**，
  不要留给下一次——检查会剥掉行号后缀只核对文件在不在，行号本身只能靠这条纪律守。
- 反例（占位示意，`<…>` 不参与校验）：

  ```
  （引用写法 · 反例）
  src/<模块>.ts:112-140   ← 行号与内容绑死：挪一次就漂，读者也不知道该信谁
  src/<模块>.ts           ← 只引文件，读者按文件名 / 小节名找
  ```

- **例外表不在这里**：确因上下文合理而机械解析不到的引用（通式、省略前缀、「同包」指另一个包、悬挂引用）
  逐条列在 `doc-references.spec.ts` 的 `EXCEPTIONS` 里，每条必须写清「为什么这条引用不该由这条检查判」。
  往例外表里加一条之前先想清楚：能不能改成写全路径或补链接。

## 注册顺序 = 瀑布嵌套顺序

cordis 的 `_hooks` 按插入序决定 waterfall 的嵌套：**先注册的在最外层**，站在内层 `next()` 之后看到的是
**内层**的结果。

- 要「别人的东西都跑完之后的最终结果」——收窄后的工具目录、或要丢掉别人 append 进来的注入——必须
  `{ prepend: true }` 抢最外层。**这不是优化，是正确性**：两个实例——
  `dsh-session-mode` 抑制官方 `agent-instructions` / `skill-catalog`（去掉 `prepend` 后「preset 先装」那档 3 条
  用例变红），`dsh-tool-guidance` 记录「该会话最终可见的工具目录」（不加 `prepend` 读到的是收窄前的全量）。
  机制与沿革见[抑制官方注入面](../../packages/profile/dsh-session-mode/.agents/designs/20260929-抑制官方注入面.md)
  与[工具说明与用法分组的送达](../../packages/profile/dsh-tool-guidance/.agents/designs/20260929-工具说明与用法分组的送达.md)。
- **判据**：写「拿到最终 X」这类 hook 时，问一句「我注册在谁的外面」；判据用例是那条**最内层结果**的断言
  （该包 `.agents/standards/` 写明落点，见 [`how-to-verify.md`](./how-to-verify.md)）。
- 反例：hook 里读 `next()` 之后的 `ctx.tools` 记作「最终目录」——实际拿到的是被后续行收窄前的全量，
  记录与真实可见面从此不一致（而且不报错）。

## 抑制类开关：两侧都要写满

抑制 / 接管官方注入面的配置项，语义有**两个方向**，只写一半就是 bug：

- 配置 **`false`**：**无条件丢**——首次注入丢，**内容变化后再次注入也要丢**；
- 配置 **`true`**：**零干预**——官方「首次注入 + 有变化才注入」的机制照常放行，不要自己重放或提前注入。

判据：同一份配置在「首次」与「内容变化后」两条路径上表现一致（各配置档 × 两档 = 用例矩阵，落点见该包
`.agents/standards/`）。反例：只实现「首次不注入」，变化时官方又注入一次；或把 `true` 实现成「主动补一次」，
于是双重注入。写文档的人同样容易只写一半：**写这类开关必须把 `false` / `true` 两侧的边界都写出来**。

## exports 与代码布局一一对应

代码放哪和出口叫什么是一件事，别让它们错位：

- **包根 `.` 就是 `<包>/src/index.ts` 本身**，它是实现本体，不做转发层。反例：那份入口里只写
  `export * from "./<实现>.ts"`——多一层没有语义的壳，读者要多跳一次。
- **单文件模块放 `src/<模块>.ts`**，不建 `src/<模块>/index.ts` 这种一层目录。
- **子出口 `./<面>` 对 `src/<面>.ts`**：加面 = 加一个入口文件 + `tsdown.config.ts` 的 `entries` 里加一项，
  `exports` 由构建按入口写回（规则在
  [`devpackages/devkit/src/package-exports.ts`](../../devpackages/devkit/src/package-exports.ts)）。反例：手改
  `exports` 指一个不存在或与入口不同名的文件——工作区里能跑，装出来的包少一个面。
- 判据：`src/<面>.ts`、`tsdown.config.ts` 的 `entries`、构建后的 `exports` 三处同名；改名的同一笔改动里
  一起改（并重建），否则装配链按包名 + 出口解析时会断。
