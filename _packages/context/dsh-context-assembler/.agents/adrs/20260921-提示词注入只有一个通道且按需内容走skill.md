# 提示词注入只有一个通道，按需内容走 skill

状态：已采纳（实施在包根（[通道本体](../../README.md)），与 [`@morlay/dsh-tool-guidance`（包根即运行时）](../../../../profile/dsh-tool-guidance/README.md) 的分发面一起工作）

背景：system prompt 的 section 由上游行与分发方各自注册，而 section 名不透明、遮蔽只能靠在 agent 作用域注册
同名空文本；两段部署文案的中文改写还依赖「本插件的 listener 排在 reminder 内层」这种顺序耦合。同时上游逐
工具说明（本部署实测约 7400 字符）整段丢弃：既不常驻，也不可及。

**决定**

系统提示词只留 `keep` 名单内的 section；本层要送的内容一律经 `ctx.contextAssembler` 一处送达——装配结果上改文本
（`replaceSection` / `suppressSection`）与降级 section 的按步送达（本步没留在提示词里的 section 改成紧随用户消息的
reminder，压缩后的重试再补投）。**按需内容走官方 `ctx.skills`**：目录常驻一行摘要、正文由官方 `skill` 工具按需
加载；工作区指令与技能目录这两面的注入归官方行（`agent-instructions` / `tool-skill`）自己的送达面，通道不参与。

**考虑过的选项**

- **维持各插件自注册 section**：注入逻辑分散在两处，遮蔽要靠 agent 作用域的同名空文本，于是清单不能含
  任何按 agent 作用域注册的说明（`team:policy` 就这么炸过一次），且改动顺序敏感。
- **用 cordis 事件让分发方广播内容**：耦合更松，但契约不显式、调试时看不到谁登记了什么。
- **全部常驻 reminder（不注册成 skill）**：省一轮请求，但每个组的用法都常驻，注意力与 token 都不划算，
  且"渐进"无从谈起。
- **全部按需 skill（base 组也按需）**：最省常驻，但每个会话第一步都要先加载一次基础组用法才敢动手文件。
- **上游说明继续丢弃**：省 token，但把上游已经写好的工具知识白白浪费，模型只能靠 schema 猜边界。

**后果**

- 本层注入只有一处 home：`keep` / `suppress` / `replace` / 降级送达都在
  [channel.ts](../../src/channel.ts) 一条流水线上；分发方改内容不动通道，通道改到达方式不动分发方。
- 同名空文本遮蔽不存在：过滤发生在装配结果上，于是「清单不能含 agent 作用域注册的说明」这条约束消失，
  覆盖性测试不必扫全树判断注册层。
- 改写与降级都发生在通道自己的瀑布里，不要求调用方排在内层。
- 上游逐工具说明可及：要点写进对应组的 skill 正文，按需加载；代价是正文由本仓库维护
  （`drops` 清单要跟上游 section 名，覆盖性测试兜住）。
- 常驻内容按条目幂等：档位变化只重发受影响的那一条 reminder，不是整段重发。
- 按需正文的送达面是官方的：谁注册进 `ctx.skills` 谁就有目录与按需加载；本层不持有目录发布与按会话修剪
  （见[设计 通道只做转换](../designs/20260929-通道只做转换.md)的"各面的归属"）。
