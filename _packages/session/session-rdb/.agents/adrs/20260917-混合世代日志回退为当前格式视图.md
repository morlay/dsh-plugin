# 混合世代 log 回退为当前格式视图

状态：已采纳

背景：旧写入器只在建会话时落一次 `f_version`，之后跟随上游演进继续向同一个 log 追加事件——log 因此可能是
混合世代（早年的行 + 新版本字段），不是任何单一已发布格式，严格的上游迁移链（v0 → v1 → v2 → v3 → v4）
对这种 log 必然拒绝；而拒绝意味着这些历史会话既打不开、也导不出（导出走同一条读取路径）。

**决定**

`readLog` 对 `f_version < SESSION_FORMAT_VERSION` 的会话先走上游迁移链，**迁移链拒绝时回退**为当前格式视图
（`adoptLegacyRows`：header 版本归一 + 字段级归一，不落库；实现步骤见
[设计 旧数据修复](../designs/20260917-旧数据修复.md)）。

**考虑过的选项**

- **只保留严格迁移链**：混合世代 log 永远加载失败（用户报错「过不了新版本验证」），只能导出再导入，
  而导出本身也走 readLog，同样失败。
- **放弃迁移链、统一按当前格式读取**：真正的旧格式数据（`assistant/chunk`、旧消息形状）会丢失迁移语义；
  迁移链仍是这些数据的正确路径。
- **原地改写数据行**：破坏「写路径零转换」不变量，且与读取视图修复重复。

**后果**

- 回退不放松 fail-loud：旧事件类型仍由 `validateStoredEvents` 拒绝，已提交区的 seq gap / 不可解析行仍由
  `scanRows` 拒绝；回退只是把「可迁移」判定的失败降级为「按当前格式解释」。
- 回退只作用于内存视图，不落库；下一次写入仍以原样存储追加。
- 读取视图修复（形状补全与坐标修复）见 [设计 读路径](../designs/20260917-读路径.md)。
- 迁移链会生成 / 合并事件，其读坐标与存储 head 不一致；`open(id, "write")` 检测到该差异时把迁移视图整体落库
  （`rewriteMigratedLog`），使读写同坐标（见 [设计 旧数据修复](../designs/20260917-旧数据修复.md)）。
