# 并发写入者检测（多个实例 / 进程共享同一数据库）

状态：已实现（并发写入 fail loud）
范围：多实例 / 多进程共享同一数据库时的写入者检测，以及同一介质内的写事务串行；决策与取舍见
ADR-同id单写入者与并发写入fail-loud。

## 结论摘要

| 议题         | 结论                                                                                   | 一句话理由                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 单写入者     | 同一 session id 同时只能有一个写入者，冲突当场 fail loud                               | 静默把批次续到对方尾部会拼坏 log（[ADR-同id单写入者与并发写入fail-loud](../adrs/20260917-同id单写入者与并发写入fail-loud.md)） |
| head 记录    | 每实例记录「本实例最后确认的稠密 head」（来自本实例的写入，或 `open` 观察）            | 磁盘 head 与本实例记录比对，就能发现「别人写过了」                                                                             |
| 校验位置     | `appendBatch` **事务内**比对磁盘 head；写 open 的迁移重写也走这道校验                  | 校验与写入同事务，中间不留窗口                                                                                                 |
| 未知会话     | 本实例从未读过该 session 却遇到已有行 → 拒绝并提示先 load                              | 那次续接没有授权，也不基于最新磁盘状态                                                                                         |
| 不同会话     | 不同 session id 的并发写互不影响                                                       | 各自独立 head；`busy_timeout` 只负责排队写锁                                                                                   |
| 同介质写事务 | storage 域的写经 `writeAtomically` 按介质串行（SQLite 按库路径、PG 按 `identityBase`） | PG 的事务句柄经实例级槽位传递，并发会让语句落进别人的事务                                                                      |

## 事实基线

本后端的事件**原样落库**（无过滤无重编号，事件 seq 即稠密 seq），而每个 `SessionPersistenceRdb` 实例只在
内存里维护自己的 handle cursor。因此两个后端实例（另一个 `dsh` 进程、或同一进程内重复加载的持久化插件）
共享同一 `sessions.sqlite` 时，**同一个 session id 只能有一个写入者**：

- 后端记录每个 session「本实例最后确认的稠密 head」（来自本实例的写入或 `open` 观察）；
  `appendBatch` 在事务内校验磁盘 head 与该记录一致（`src/write-guard.ts:15`、`src/index.ts:961`）。
- **write open 的迁移重写也走这条校验**：legacy 会话在读视图与存储长度不等时会被整段重写（删光桥接行再按
  视图重建）。这段重写前同样校验磁盘 head——本实例已有该会话的 head 记录时严格比较（能抓住「读完之后另一个
  实例又写了」），没有记录时以当前磁盘 head 为基准（重写只发生在刚读过这份日志之后，
  `src/index.ts:1144`）。没有这道校验，另一实例在 open 期间提交的事件会被重写静默丢掉。
- 磁盘 head 已被其他实例推进（另一写入者提交过）、或本实例从未读过该 session 却遇到已有行时，append
  **fail loud 拒绝**（`modified by another writer` / `has a persisted log this instance has not read`，
  `src/write-guard.ts:15-31`），不把本批次静默重编号到对方尾部。
- 不同 session id 的并发写不受影响（各自独立 head），两个实例各写各的 session 是受支持的多进程部署
  （`busy_timeout` 只负责让写锁竞争排队）。
- 一个实例 `open`（或 HMR adopt）过某 session 后可以继续 append——那是一次明确授权、基于最新磁盘状态的
  续接；同 id 双实例「都 open 过再各自写」仍不支持。

### 同一介质内的写事务串行

storage 域（工作区 / 归档集 / 投影缓存）的写走 `writeAtomically`：SQLite 侧由 `enqueueSqliteTx` 按数据库
路径串行（`src/sqlite.ts:249`），PG 侧由 `enqueuePgWrite` 按介质身份（宿主 + 库 + schema，即
`identityBase`）串行（`src/postgres.ts:42`、`src/postgres.ts:127`）。

这不是可选的整洁性，而是 PG 侧的**正确性前提**：事务句柄经实例级字段（`txOverride`）传给 `db()`，
两个并发的 `writeAtomically` 会互相覆盖槽位——后开始的事务抢走槽位后，先开始的语句落到别人的事务里
（一次失败会把另一个成功事务一起拖垮，PG 契约用例「并发写事务不交错（失败的那个不留痕迹）」覆盖），
或退化成 autocommit。

## 取舍

- **跨实例协调器 / 分布式锁**（否）：超出本后端职责，需要租约基础设施
  （[ADR-同id单写入者与并发写入fail-loud](../adrs/20260917-同id单写入者与并发写入fail-loud.md)）。
- **按介质串行的粒度选「进程内一把锁」**（否）：同一进程内不同库、不同 schema 的写互不相干，
  按介质身份分队列才能既串行又不过度阻塞。
- **让 storage 域继续整文档读改写、不串行**（否）：PG 的事务槽位是实例级单槽，并发写事务会串味。

## 开放问题

- 同 id 双实例「都 open 过再各自写」当前不支持：要支持得引入跨实例协调（租约 / 版本号 CAS），
  没有真实部署需求前不做。
