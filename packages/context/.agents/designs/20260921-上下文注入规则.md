# 上下文注入规则

状态：已定（落地进行中，见 §落地顺序）
范围：`packages/context/` 各包注入给模型的形态、覆盖语义与分层。各包的内部算法（发现、渲染、分组）在包内。

## 两类块

注入分**规则块**与**内容块**：规则块是持久的系统级指令（参与覆盖），内容块是这一刻要看的材料（一次性，
不参与覆盖）。两者框架不同，不混用。

```html
<!-- 规则块：系统级指令，id 必带，同 id 覆盖 -->
<system-reminder id="agent-instructions:5f3ac1d2:AGENTS.md">…</system-reminder>
<system-reminder id="agent-instructions:9b0e77aa:~/.dsh/AGENTS.md">…</system-reminder>
<system-reminder id="skill-catalog"><available_skills>…</available_skills></system-reminder>
<system-reminder id="section:plan:policy">…</system-reminder>

<!-- 内容块：技能说明与引用的材料，不带 id（常驻送达与按需加载同一形态） -->
<skill_content name="tool-group-base">
  <skill_instructions>…</skill_instructions>
</skill_content>
<file_content path="src/a.ts">…</file_content>
```

规则块：**id 必带**（解析规则：第一个冒号前是 owner，key 可含 `:` 与 `/`）；id 只放稳定标识，不放
seq / 时间 / digest 这类易变值；只有注入通道能写，注入方只声明 `registerRule({ id, text })` 或
`registerSkill({ name, title, description, content, requires?, injection? })`。

| 注入方                   | 规则块 id                                          | 覆盖粒度     |
| ------------------------ | -------------------------------------------------- | ------------ |
| 工作区指令               | `agent-instructions:<根标识>:<文件显示名>`         | 每个文件     |
| skill 目录               | `skill-catalog`                                    | 整份目录     |
| 常驻组正文（`base`）     | `tool-group-base`（即该组 skill 名）               | 每组         |
| 降级 section（含规则类） | `section:<section 名>`（如 `section:plan:policy`） | 每个 section |
| teammate 身份            | `agent-team:identity`                              | 一条         |

内容块两种：**skill 正文一律是 `<skill_content>`**——常驻送达的 `base` 组正文与按需加载的组正文同一形态，
区别只在"谁触发"；引用展开的文件是 `<file_content>`。

这些 skill 是**虚拟 skill**（运行时注册、没有资源目录），所以正文只有 `<skill_instructions>`，
不带上游 `<skill_resources>` 那段；渲染由通道一处产出，按需加载路径（`skill` 工具）在接管
`dsh-context-skill-catalog` 时统一到同一形态。注册表只能存一份正文（技能注册是装配期一次、全局可见），
所以按需加载时由 `contentFor(name, agent)` 按会话重算——组正文才和 `auto` 正文一样跟着工具走。

幂等键在 source 里（规则块用 id、skill 内容块用 skill 名），所以内容块虽不参与覆盖，也不会重复送达。

## 覆盖规则

**只适用于规则块**：同 id 的最新一条取代更早的同 id 条目，不重写会话历史。规则在系统提示词里声明一次
（[`rules.ts`](../../dsh-context-assembler/src/rules.ts)，随 `assembler:rules` section 常驻），因此任何一条
reminder 都只带 id 与正文，不重复解释；内容块不受覆盖影响（每次提供都是当次材料）。

- **幂等键 = id**：同 id 最近一条的文本未变就不注入，变了才追加一条；
- **顺序**：同一步的多条按 id 字典序注入，不随注册顺序抖动；
- **压缩后**：早期 reminder 进摘要 checkpoint 时，按 id 逐条补回。

### 幂等的判据是文本，不是"这件事变没变"

判据落在**已注入正文与本次要注入正文逐字相等**上（`latestReminderText` 读的是 surface 上同 id 的最近一条）。
所以重发只有两个来源，都不是"轮次"或"进程"：

| 情况              | 会不会重发 | 为什么                                                                                           |
| ----------------- | ---------- | ------------------------------------------------------------------------------------------------ |
| 服务重启后 resume | **不会**   | surface 由完整会话日志折叠而来（`session/end-seed` 之后重建），旧条目仍在 surface 上，逐字比得上 |
| 压缩              | 会         | 早期节点被摘要 checkpoint 覆盖，不再在 surface 上，属于"模型真的看不到了"                        |
| 内容变了          | 会         | 文件改了、section 文案变了、**目录里的技能集合/摘要变了**——旧正文对新事实已经过期                |

现场（`session-7e7768ac…`，一次会话内的完整时间线）：

```text
2616-2620  首次注入 5 条（AGENTS.md / 两个 section / skill-catalog / tool-group-base）
2743-2746  压缩：user/message replace{8..2735}
2753-2757  补发 5 条（压缩后，符合预期）
3336       session/end-seed（服务重启）
3343       只补发 skill-catalog
```

重启后没补的 4 条正文逐字未变；补的这条逐字变了——目录从 2 行变 3 行（多了
`dsh-plugin-implement`，`tool-group-team` 换成 `tool-group-delegation`）。全库扫一遍"同 id 同文本仍重复"
的条目，只有压缩那一组，没有无理由的重发。

推论：**改了组表 / 目录读取范围这类"会改变注入正文"的代码，重启后必然补发一次**——这是必要的，
否则模型手里的目录是旧的（会去 `skill` 一个已经不存在的 skill 名）。

## 分层：什么常驻、什么按需

| 内容                                                | 到达方式                                                                     |
| --------------------------------------------------- | ---------------------------------------------------------------------------- |
| `base` 组用法（read / edit / bash / web_search 等） | `auto`：正文随 reminder 常驻（每轮都可能用，不该等一轮加载）                 |
| `flow` / `delegation` / `team` 用法                 | 注册成 `tool-group-<key>` skill：目录常驻一行摘要，正文按需                  |
| 组的行为规则（如协作规则）                          | 与工具说明一起丢弃，要点写进该组正文                                         |
| 组是否出现                                          | 入口工具（`requires`）任一可见才注册：同名工具分属两个插件时，由组自己挑入口 |
| skill 目录                                          | 常驻（`skill-catalog`）                                                      |
| 工作区指令                                          | 会话开始一次（`agent-instructions:<根标识>:<文件>`），文件变化时重发         |
| 降级 section                                        | 规则块，按 section 一条（`section:<名>`）                                    |
| 引用展开（skill 正文 / 文件内容）                   | 内容块：`<skill_content>` / `<file_content>`，当次材料                       |

**工具不设门控**：所有工具始终可见、可调用；"组"只决定用法说明怎么分批送达。加载某组 skill 即取得该组
能力与用法，不需要元工具或命令。

## 包与职责

| 包                                       | 职责                                                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `@morlay/dsh-context-assembler`          | 唯一渲染者：信封、id、幂等、顺序、规则声明；声明面 `registerSkill` / `registerRule` / `replaceSection` / `suppressSection` |
| `@morlay/dsh-context-agent-instructions` | 工作区指令：`$DSH_HOME/AGENTS.md` + 项目根到 cwd 的逐级 `AGENTS.md` / `AGENTS.local.md`、字节预算                          |
| `@morlay/dsh-context-skill-catalog`      | skill 目录注入 + `skill` 工具与用户手势                                                                                    |
| `@morlay/dsh-context-reference`          | 用户消息里的 `@path` / `skill:name` 引用展开                                                                               |
| `@morlay/dsh-context-tool-guidance`      | 工具用法的分组、短描述投影、各组 skill 正文与丢弃清单                                                                      |
| `@morlay/dsh-context-scope`              | 工具白名单与 instruction 总开关：装配期投影工具目录 + 执行层 guard（不经 `tools.restrict`）                                |

落库的 source kind：接管上游那两面的沿用上游 kind（`agent-instructions` / `skill-catalog`，结构字段按上游形状给
——目录消息带 `entries`（就是目录行发布的那份清单），工作区指令的 `changes` 留空，因为我们不做上游那套按文件的
reconciliation），引用展开沿用 `file-reference` / `skill-invocation`；**我们自己的规则块用 `context-assembler`**
（与插件同名）。注入方声明规则时给 `source`，通道把幂等键 `id` 并进去——**幂等始终按 `id` 判定、不按 kind**，
所以换 kind 不会重发、旧条目也不会失去"已注入"身份。下游按 kind 认领的有两处：client 的「上下文注入」标签
（未知 kind 直接显示 kind 本身）与上游 `auto-review` 的 constraint 收集（只认 `agent-instructions`）。

## 装配约束（这几条都真实踩过）

| 约束                                        | 为什么                                                                                                        | 踩到时的样子                                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| preset 里的行**不能发布进程全局服务**       | 上游 `agent-presets` 的 `leakedServices` 校验会拒绝装载整块 preset                                            | `row(s) published process-global service(s) [contextAssembler]`，新建会话直接失败    |
| **按模式给提示词只能走 section**            | 同上：`system-prompt` 行发布 `ctx.systemPrompt`，搬不进产物                                                   | 用 `persona` 行（在 agent 作用域注册同名 `deployment:persona-*` section 遮蔽部署级） |
| 接管的 **host 行必须在 patch 里按 id 禁用** | preset 里的同名行只是覆盖 config，删不掉 host 行                                                              | host 的 `tool-skill` 跟我们的实现抢注册 `skill` 工具                                 |
| **patch 是运行期各形态都要的文件**          | 打包快照、直起 profile 都不经过 `pnpm build`                                                                  | 曾把它加进 `.gitignore` → 预设一个都注册不上                                         |
| **注入跟着工具走**                          | 不能用 `skill` 工具就没有技能目录，没有 `read` 就没有 `@path` 展开                                            | 各注入包在送出前看工具可用性，而不是让每个模式去列"不要哪些"                         |
| **读 skill 注册表要带 `cwd` 与作用域**      | 本地发现是 preset 层的行（host 层同名行被 web app 禁用），不带作用域只看得见全局层                            | `~/.agents/skills` 与 `{cwd}/.agents/skills` 全都不进目录，只剩仓库注册的组 skill    |
| 组的**成立判据是入口工具**                  | 同名工具可能有两个提供者（`send_message`：子代理控制行 / Agent Teams）                                        | 没装 Agent Teams 的会话也列出 `tool-group-team`                                      |
| `ctx.get(X)` 与 `ctx.X` 是两回事            | `ctx.get(X)` 不需要 `X` 在 `inject` 里声明，未提供时返回 `undefined`；只有属性访问 `ctx.X` 才要求声明，否则抛 | "可选搭档"用 `ctx.get` 取、判 `undefined` 即可——一个可选服务缺席不该让整个插件不激活 |

验证分三层：产物内容（`generated-presets.spec`）、装配静态校验（`preset-mount.spec`：服务泄漏 / host 行禁用 / id 唯一）、**真实会话冒烟**（目前靠人跑一次，尚未自动化——这几轮的失败都是它先发现的）。
