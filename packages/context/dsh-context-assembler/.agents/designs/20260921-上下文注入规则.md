# 上下文注入规则（`packages/context/` 各包注入给模型的形态与覆盖语义）

状态：已实现
范围：`packages/context/` 各包注入给模型的形态、覆盖语义与分层。各包的内部算法（引用发现、正文渲染、工具分组）在包内。
约束：上游 `@deepseek-ai/*` 只读；规则块只有注入通道一个写入口。

## 结论摘要

| 议题        | 结论                                                                                                         | 一句话理由                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| 两类块      | 规则块（持久的系统级指令，id 必带、参与覆盖）与内容块（这一刻要看的材料，不参与覆盖）                        | 信封与语义不同，混用会让覆盖失去边界       |
| 写入口      | 只有注入通道能写规则块；注入方只声明 `registerRule` / `registerSkill` / `replaceSection` / `suppressSection` | 信封、id、幂等与顺序都在一处判定           |
| 幂等        | 键（规则块用 id、内容块用 skill 名）相同且正文**逐字相等**才不重发                                           | 重发只来自压缩与内容变化，与轮次、进程无关 |
| 分层        | 每条内容自己声明常驻（`auto`）或按需（`on-demand`），形态相同、都跟着本会话的工具可见性                      | 用不到的工具不该送它的用法                 |
| 让位 / 抢面 | 工作区指令在 preset 自带上游行时**让位**；skill 面把 `skill` 工具注册进 agent 自己那一层**抢面**             | 「这一面归谁」是会话级事实，装配期裁不出来 |
| 包边界      | 通道与它的注入方一个包（能力名 = 子出口名）；引用展开独立成包                                                | 通道消费者跨包，隔离会把它们挡在组外       |
| 装配        | 通道一行装一次、不隔离；模式差异由 `scope` 出口按会话收口                                                    | 同一份通道服务供整个部署                   |

## 事实基线

### 两类块与 id

规则块是持久的系统级指令（参与覆盖），内容块是这一刻要看的材料（一次性，不参与覆盖）：

```html
<!-- 规则块：系统级指令，id 必带，同 id 覆盖 -->
<system-reminder id="agent-instructions:5f3ac1d2:AGENTS.md">…</system-reminder>
<system-reminder id="agent-instructions:9b0e77aa:~/.dsh/AGENTS.md">…</system-reminder>
<system-reminder id="skill-catalog"><available_skills>…</available_skills></system-reminder>
<system-reminder id="section:plan:policy">…</system-reminder>

<!-- 内容块：技能说明与引用的材料，不带 id（常驻送达与按需加载同一形态） -->
<skill_content name="tool-group-base">
  <skill_instructions>…</skill_instructions>
</skill_content>
<file_content path="src/a.ts">…</file_content>
```

规则块 id 的解析规则是「第一个冒号前是 owner，key 可含 `:` 与 `/`」（信封渲染见
[`reminder.ts:54-56`](../../src/assembler/reminder.ts)）；id 只放稳定标识，不放 seq / 时间 / digest 这类易变值：

| 注入方                                          | 规则块 id                                            | 覆盖粒度     |
| ----------------------------------------------- | ---------------------------------------------------- | ------------ |
| 工作区指令（`agent-instructions` 出口）         | `agent-instructions:<根标识>:<文件显示名>`           | 每个文件     |
| skill 目录（`skill-catalog` 出口）              | `skill-catalog`                                      | 整份目录     |
| 常驻组正文（`dsh-agent-toolkit` 的 `guidance`） | `tool-group-<组 key>`，`base` 组即 `tool-group-base` | 每组         |
| 降级 section（含规则类）                        | `section:<section 名>`（如 `section:plan:policy`）   | 每个 section |

内容块两种：**skill 正文一律是 `<skill_content>`**——常驻送达的 `base` 组正文与按需加载的组正文同一形态，
区别只在「谁触发」；引用展开的文件是 `<file_content>`
（[`dsh-reference/src/file-content.ts:141-143`](../../../dsh-reference/src/file-content.ts)）。

这些 skill 是**虚拟 skill**（运行时注册、没有资源目录），所以正文只有 `<skill_instructions>`，不带上游
`<skill_resources>` 那段（[`reminder.ts:58-70`](../../src/assembler/reminder.ts)）；渲染由通道一处产出，
按需加载路径（`skill` 工具）统一到同一形态。注册表只能存一份正文，所以按需加载时由
`contentFor(name, agent)` 按会话重算——组正文因此和 `auto` 正文一样跟着工具走。

幂等键在 source 里（规则块用 id、skill 内容块用 skill 名），所以内容块虽不参与覆盖，也不会重复送达。

### 覆盖与幂等

**覆盖只适用于规则块**：同 id 的最新一条取代更早的同 id 条目，不重写会话历史。规则在系统提示词里声明一次
（[`rules.ts:9-12`](../../src/assembler/rules.ts)，随 `assembler:rules` section 常驻），因此任何一条
reminder 都只带 id 与正文，不重复解释；内容块不受覆盖影响（每次提供都是当次材料）。

- **幂等键 = id**：同 id 最近一条的文本未变就不注入，变了才追加一条；
- **顺序**：同一步的多条按 id 字典序注入，不随注册顺序抖动；
- **压缩后**：早期 reminder 进摘要 checkpoint 时，按 id 逐条补回。

判据落在**已注入正文与本次要注入正文逐字相等**上（`latestReminderText` 读的是 surface 上同 id 的最近一条，
[`reminder.ts:78-80`](../../src/assembler/reminder.ts)）。所以重发只有两个来源，都不是「轮次」或「进程」：

| 情况              | 会不会重发 | 为什么                                                                                           |
| ----------------- | ---------- | ------------------------------------------------------------------------------------------------ |
| 服务重启后 resume | **不会**   | surface 由完整会话日志折叠而来（`session/end-seed` 之后重建），旧条目仍在 surface 上，逐字比得上 |
| 压缩              | 会         | 早期节点被摘要 checkpoint 覆盖，不再在 surface 上，属于「模型真的看不到了」                      |
| 内容变了          | 会         | 文件改了、section 文案变了、**目录里的技能集合/摘要变了**——旧正文对新事实已经过期                |

现场（`session-7e7768ac…`，一次会话内的完整时间线）：

```text
2616-2620  首次注入 5 条（AGENTS.md / 两个 section / skill-catalog / tool-group-base）
2743-2746  压缩：user/message replace{8..2735}
2753-2757  补发 5 条（压缩后，符合预期）
3336       session/end-seed（服务重启）
3343       只补发 skill-catalog
```

重启后没补的 4 条正文逐字未变；补的这条逐字变了——目录那一行集合变了。全库扫一遍「同 id 同文本仍重复」
的条目，只有压缩那一组，没有无理由的重发。

推论：**改了组表 / 目录读取范围这类「会改变注入正文」的代码，重启后必然补发一次**——这是必要的，否则模型
手里的目录是旧的（会去 `skill` 一个已经不存在的 skill 名）。

### 分层：什么常驻、什么按需

| 内容                                                | 到达方式                                                                     |
| --------------------------------------------------- | ---------------------------------------------------------------------------- |
| `base` 组用法（read / edit / bash / web_search 等） | `auto`：正文随 reminder 常驻（每轮都可能用，不该等一轮加载）                 |
| `flow` / `delegation` / `team` 用法                 | 注册成 `tool-group-<key>` skill：目录常驻一行摘要，正文按需                  |
| 组的行为规则（如协作规则）                          | 与工具说明一起丢弃，要点写进该组正文                                         |
| 组是否出现                                          | 入口工具（`requires`）任一可见才注册：同名工具分属两个插件时，由组自己挑入口 |
| skill 目录                                          | 常驻（`skill-catalog`）                                                      |
| 工作区指令                                          | 会话开始一次（`agent-instructions:<根标识>:<文件>`），文件变化时重发         |
| 降级 section                                        | 规则块，按 section 一条（`section:<名>`）                                    |
| 引用展开（skill 正文 / 文件内容）                   | 内容块：`<skill_content>` / `<file_content>`，当次材料                       |

常驻正文（`injection: "auto"` 的 skill）与规则块一样跟随**本会话的工具可见性**：它声明的 `requires` 工具一个
都不在会话白名单内时，这份正文不注入（与 skill 目录那侧的 `hiddenSkills` 同一判据，
[`channel.ts:162-180`](../../src/assembler/channel.ts)）。

**工具不设门控**：所有工具始终可见、可调用；「组」只决定用法说明怎么分批送达。加载某组 skill 即取得该组
能力与用法，不需要元工具或命令。

模式的 `instructions: false` 是**一切 instruction 类送达**的总开关：常驻组正文（内容块）、规则块、降级
section 都不注入；按需 skill 不受它管（模型自己调 `skill` 才拿到正文），引用材料也不经通道（`@` 引用走
[`@morlay/dsh-reference`](../../../dsh-reference/README.md) 的 `agent/pre-step`）。

### 包与职责

| 出口                                               | 职责                                                                                                                                                                                                                                    |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@morlay/dsh-context-assembler/assembler`          | 唯一渲染者：信封、id、幂等、顺序、规则声明；声明面 `registerSkill` / `registerRule` / `replaceSection` / `suppressSection`（[`channel.ts:98-127`](../../src/assembler/channel.ts)）                                                     |
| `@morlay/dsh-context-assembler/agent-instructions` | 工作区指令：`$DSH_HOME/AGENTS.md` + 项目根到 cwd 的逐级 `AGENTS.md` / `AGENTS.local.md`、字节预算（[`index.ts:27-32`](../../src/agent-instructions/index.ts)）                                                                          |
| `@morlay/dsh-context-assembler/skill-catalog`      | skill 目录注入 + `skill` 工具与用户手势                                                                                                                                                                                                 |
| `@morlay/dsh-context-assembler/scope`              | 工具白名单与 instruction 总开关：装配期投影工具目录 + 执行层 guard（不经 `tools.restrict`）；另带动态快照开关（`runtimeContext: false` → 按 scope 的 `suppressRuntimeContext`）（[`scope/index.ts:117-145`](../../src/scope/index.ts)） |

引用展开（`@path` / `skill:name`）是另一个包 [`@morlay/dsh-reference`](../../../dsh-reference/README.md)：它不依赖
通道服务（`inject` 只有 `skills`），装配在
[`@morlay/better-session`](../../../../bundles/better-session/cordis.patch.yml) 的 `reference` 行；信封形态仍按
本表（见[设计 文件引用内容注入](../../../dsh-reference/.agents/designs/20260920-文件引用内容注入.md)）。

落库的 source kind：工作区指令那一面沿用上游 kind（`agent-instructions`，`changes` 留空，因为不做上游那套
按文件的 reconciliation）；**skill 目录那一面用我们自己的 kind**（`context-assembler` + `form: 'catalog'` +
`entries`——上游 `tool-skill` 的账本扫法只认它自己的 kind，抢面之后它会用一条空目录把我们那条顶掉，见
[ADR 工作区指令让位 skill 面由通道抢面](../adrs/20260929-工作区指令让位skill面由通道抢面.md)）；引用展开沿用
`file-reference` / `skill-invocation`；**我们自己的规则块用 `context-assembler`**（与插件同名）。注入方声明规则
时给 `source`，通道把幂等键 `id` 并进去——**幂等始终按 `id` 判定、不按 kind**，所以换 kind 不会重发、旧条目
也不会失去「已注入」身份。下游按 kind 认领的有两处：client 的「上下文注入」标签（未知 kind 直接显示 kind
本身）与上游 `auto-review` 的 constraint 收集（只认 `agent-instructions`）。

**只沿用 kind 不够**：工作区指令还得带上游的认领凭据——`baseline: true` 与 `baselineIdentity`（身份逐字相等）。
上游那行按「kind 相同 **且** baseline 为真 **且** 身份相等」认领「基线已注入」
（[`vendor/.../context/agent-instructions/src/index.ts:46-63`](../../../../../vendor/deepseek-harness/packages/context/agent-instructions/src/index.ts)）；
少这两样它认为基线不存在，于是再注入一条自己的模板（"Use them as guidance…"）。症状只在**同会话切换
preset** 后显现：两条幂等键不同，模型无法理解后者作废前者。身份算法与上游 `workspaceBaselineIdentity` 对齐
（[`baseline.ts`](../../src/agent-instructions/baseline.ts)）。

### 装配约束

| 约束                                         | 为什么                                                                                                                                                                                      | 踩到时的样子                                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| preset 里的行**不能发布进程全局服务**        | 上游 `agent-presets` 的 `leakedServices` 校验会拒绝装载整块 preset（[`invariant.ts:36-39`](../../../../../vendor/deepseek-harness/packages/preset/agent-preset-registry/src/invariant.ts)） | `row(s) published process-global service(s) [contextAssembler]`，新建会话直接失败                                                                               |
| **按模式给提示词只能走 section**             | preset 里的行不能发布进程全局服务（上一条），而 `system-prompt` 正是发布 `ctx.systemPrompt` 的那一行                                                                                        | 用 `persona` 行（在 agent 作用域注册同名 `deployment:persona-*` section 遮蔽部署级，[`persona.ts:27-44`](../../../../profile/dsh-session-mode/src/persona.ts)） |
| preset 里的行**删不掉 host 行**              | preset 是独立 EntryTree（`Entry.id` 按树的 owner entry 前缀化），两棵树 id 空间不重叠                                                                                                       | 想按模式关掉 host 那层 `fs-observation-policy`，只能抢它的 waterfall（`relax-intent`）                                                                          |
| **bundle 的 patch 是运行期各形态都要的文件** | 打包快照、直起 profile 都不经过 `pnpm build`                                                                                                                                                | 把它加进 `.gitignore` → 预设一个都注册不上                                                                                                                      |
| **注入跟着工具走**                           | 不能用 `skill` 工具就没有技能目录，没有 `read` 就没有 `@path` 展开                                                                                                                          | 各注入包在送出前看工具可用性，而不是让每个模式去列「不要哪些」                                                                                                  |
| **读 skill 注册表要带 `cwd` 与作用域**       | 本地发现是 preset 层的行（host 层同名行在 web 组合里被禁用），不带作用域只看得见全局层                                                                                                      | `~/.agents/skills` 与 `{cwd}/.agents/skills` 全都不进目录，只剩仓库注册的组 skill                                                                               |
| 组的**成立判据是入口工具**                   | 同名工具可能有两个提供者（`send_message`：子代理控制行 / Agent Teams）                                                                                                                      | 没装 Agent Teams 的会话也列出 `tool-group-team`                                                                                                                 |
| `ctx.get(X)` 与 `ctx.X` 是两回事             | `ctx.get(X)` 不需要 `X` 在 `inject` 里声明，未提供时返回 `undefined`；只有属性访问 `ctx.X` 才要求声明，否则抛                                                                               | 「可选搭档」用 `ctx.get` 取、判 `undefined` 即可——一个可选服务缺席不该让整个插件不激活                                                                          |

装配形态（行清单的真源在代码里，不放装配层的 patch 副本）：

- 通道一行的组装出口是 [`src/index.ts:19-46`](../../src/index.ts)（`CAPABILITIES` / `Config.capabilities`，
  缺省四套能力）；
- 本包的 bundle patch 只装通道一行：`PATCH_ROWS` = `contextChannel({ capabilities: ["assembler",
"agent-instructions", "skill-catalog"] })`（[`rows.ts:59-64`](../../src/rows.ts)）；模式收口那一行是
  `scopeRow()`（[`rows.ts:46-51`](../../src/rows.ts)），由
  [`@morlay/dsh-session-mode`](../../../../profile/dsh-session-mode/README.md) 的配置面一起装；
- 本部署把这两行渲染进 [`@morlay/session-mode-profile`](../../../../bundles/session-mode-profile/cordis.patch.yml)
  的 patch（`context-assembler` / `context-assembler-scope` 两行）；
- 真装配的判据是 `pnpm exec tsx packages/desktop/dsh-desktop-host/tool/verify-session-mode.mts`：装配层可见
  一份通道、收口行装上、官方 preset 会话不受影响。

验证分三层：**包内静态校验**（各注入包的 `src/__tests__/`：信封、id、幂等、降级与改写）、**装配静态校验**
（`dsh-session-mode` 的 `patch.spec.ts`：行清单与产物一致、行 id 唯一、模式清单与源数据同形）、**真装配探针**
（上面那条 `verify-session-mode.mts` 判装配面的四条事实）。测试落点在 `src/__tests__/<capability>/`（根 vitest
的 include 是 `packages/**/src/__tests__/**`，所以不能按能力就近放 `src/<capability>/__tests__/`）；读上游
文件的覆盖性测试用 `process.cwd()`（vitest 从仓库根跑）。新增一个能力：加 `src/<capability>/`，再把它登记进
`src/index.ts` 的 `CAPABILITIES`（子出口与 tsdown 入口一起加），装配面不动。

## 取舍

| 选项                                                                | 为什么否掉                                                                                     |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 注册按 scope 分层（`registerRule(ctx, …)`）                         | 要动通道整个公开面（四个注册 API 加 ctx），当前装配不需要「部署级一份 + 会话级覆盖」以外的粒度 |
| 每个模式各装一份通道、关进 `isolate` 组                             | 模式之间零泄漏，但跨包消费者（工具说明）解析不到服务，行停在 waiting 且不报错                  |
| 各注入方自己注册 section、靠同名空文本遮蔽                          | 注入逻辑分散在两处，清单不能含任何按 agent 作用域注册的说明，且改动顺序敏感                    |
| 用 cordis 事件让分发方广播内容                                      | 耦合更松，但契约不显式、调试时看不到谁登记了什么                                               |
| 全部常驻（不注册成 skill）                                          | 省一轮请求，但每个组的用法都常驻，注意力与 token 都不划算                                      |
| 全部按需（`base` 组也按需）                                         | 最省常驻，但每个会话第一步都要先加载一次基础组用法才敢动手文件                                 |
| `instructions` 按面拆开关（规则块 / 降级 section / 常驻正文各一个） | 按面的诉求还没出现，一条总开关够用；真出现时再拆，判据落回 `channel.ts` 的三处过滤             |

决策与理由的 home 是各自 ADR：
[ADR-提示词注入只有一个通道且按需内容走skill](../adrs/20260921-提示词注入只有一个通道且按需内容走skill.md)、
[ADR-通道作为全局服务装配不隔离](../adrs/20260923-通道作为全局服务装配不隔离.md)、
[ADR-工作区指令让位skill面由通道抢面](../adrs/20260929-工作区指令让位skill面由通道抢面.md)。
