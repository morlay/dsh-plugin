# 通道作为全局服务装配，不隔离

状态：已采纳（2026-09-23，取代 [ADR-20260922-通道与注入行按模式isolate装配](../../../../profile/dsh-agent-preset/.agents/adrs/20260922-通道与注入行按模式isolate装配.md) 的隔离部分）

背景：那条隔离决策的前提是"通道住 host 层时，注册漏进官方 preset 的会话"——修法是通道与它的**全部消费者**
住同一个 `isolate` 组。这个条件在我们的装配里不成立：消费者**跨包**。工具说明那一行
（`@morlay/dsh-agent-toolkit/guidance`）由 toolkit 的 bundle patch 装、汉化与用法分组数据也归那个包；
它 `inject` 通道，却拿不到被关在组里的服务——实测 `dsh web` 的启动 audit 一直报
`tool-guidance: pending (waiting for service: contextAssembler)`，描述替换、schema 精简与用法分组全没生效
（行停在 waiting，不报错）。

同时，隔离的原始理由已经消失：官方四个 preset 都被我们禁用（`preset-standard` / `ptc` / `minimal` /
`cordis` 四行 `disabled: true`），选择器里只有我们的 `coding` / `chat`，不存在"注入漏进官方会话"这回事。

**决定**

1. 通道在本包的行清单里装**一次**、**不 isolate**（`cordis.patch.yml` 就是一行组装出口），
   profile 平面的任何行、任何包都能 `inject` 到它。
2. 模式之间的差异不在通道上表达，改由 `context-scope` 行收口：工具白名单（工具目录 + 与之同源的
   `tool:<工具名>` 说明 section）、`instructions`、`runtimeContext`。
3. 探针 `verify-preset-isolation.mts` 判据反转：装配层必须可见**一份**、任何 preset mount 里不得再有
   第二份；模式差异仍按成对判据守（chat 无动态快照、coding 有）。

**考虑过的选项**

- **让 tool-guidance 行插进隔离组**（`- id: <组 id> insert: [...]`）：保住隔离，但要求别的包往这个组的 id
  里插行——跨包的装配耦合进一个组名，且以后每加一个消费者都要记得插进去（漏了就是静默 waiting）。
- **通道注册按 scope 分层**（`registerRule(ctx, …)` 之类）：能把"谁注册的只对谁的会话生效"做对，但要动
  通道整个公开面，改动面大于收益，且当前装配不需要。
- **每个模式各装一份通道**（隔离的原始形态）：模式之间确实不串，但跨包消费者解析不到服务——就是本次修
  的症状本身。

**后果**

- 通道全局一份：跨包消费者直接 `inject`；`tool-guidance` 激活，汉化（描述替换 / schema 精简 / 用法分组）
  真正生效——`just custom dev --web` 的启动 audit 从 1 条 pending 归零，端口与 URL 照常。
- **恢复官方 preset 之前必须先重新评估**：全局通道会让官方 preset 的会话重新吃到我们的注入。要么那时
  回来隔离（并解决跨包消费者），要么把注入改成按 scope 收口。
- 模式差异的守卫落在 `context-scope`：它的白名单同时管工具目录与 `tool:` 说明 section，避免"工具没了、
  说明还在"。
