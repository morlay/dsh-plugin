# 运行期改配置走 volatile 引用

状态：已采纳

背景：`ctx.settings` 只把插件 Config 里标了 `.volatile()` 的字段投影成表单，改动由 config-editor 持久化回
profile patch 的 entry config（[`settings/src/index.ts`](../../../../../vendor/deepseek-harness/packages/settings/settings/src/index.ts)）。
插件侧要做的只有两件事：字段标 `.volatile()`，值从引用读（`config.providers.get()`）。

**决定**

`Config.providers` 标 `.volatile()`，适配器每次解析都从引用取当前值（`profiles()` 按引用值做 memoize），
并在 `loader/volatile-update` 里重算路由注册与可配置 provider 目录、在 `internal/config` 里校验候选配置
（无效更新被拒绝，运行引用保持原值）。`settingsNs` 用**行 id**（`ctx.fiber.entry?.options.id`）而不是包短名：
设置页按 entry 定位这份配置。

**考虑过的选项**

- **自己监听配置文件**：绕开 Loader 的引用语义，等于重做一套失效通知；上游已经给出 volatile 这一条路。
- **不做运行期可改**：配置只能改 patch 再重启——丢掉了「在 Models 页改 provider」这条既有能力。
- **用 namespace section 覆盖 config**（`ctx.settings` 的 installSection 那一路）：这层 API 不存在，编译期就会红。

**后果**

- `$DSH_HOME/settings.yaml` 的 `llm-openai-compatible` 段由上游在启动时导入同 id 的行 config，内容不丢；改配置
  就是改行 config 或走设置页表单。
- `assertServiceable` 的入参是「解析后的普通值」形状（`Options`）；引用读回的是 schema 的只读形状，调用处
  转换一次（与上游 `llm-pi-ai` 同做法），因为 `exactOptionalPropertyTypes` 下两者不直接兼容。
- 无效更新（例如 provider 无法解析）只被日志记下，运行中的路由保持原样——不会因为一次表单保存把已注册的
  路由清空。
