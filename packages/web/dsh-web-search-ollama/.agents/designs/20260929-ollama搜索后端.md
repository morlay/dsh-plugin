# Ollama 搜索后端（`ctx.web` 的 provider 与装配）

状态：已实现（`web_search` 走 Ollama 自己的 `/api/web_search`，链路由真端点 e2e 守）
范围：`packages/web/dsh-web-search-ollama/`——注册进 `ctx.web` 的这一个搜索后端：端点与请求形状、结果映射、错误面、配置字段、装配链路与验证门控。
约束：`vendor/**` 只读；只注册搜索后端，不碰抓取（`web_fetch` 仍走基础 bundle 的 `web-fetch-http`）；注册行在 host 平面只装一次。

## 结论摘要

| 议题       | 结论                                                                                                                             | 一句话理由                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 用哪个端点 | Ollama 自己的 REST：`POST https://ollama.com/api/web_search`                                                                     | 上游的 Anthropic Messages 路子在 Ollama 上走不通（见下）；这条路同一个 key、一次 HTTP、返回扁平 `{results:[{title,url,content}]}`                            |
| 为什么     | 上游 `@deepseek-ai/dsh-web-search-deepseek` 走 `web_search_20250305` server tool，只认服务端自执行的 `web_search_tool_result` 块 | Ollama 把这个 server tool 降级成普通客户端工具（`stop_reason: tool_use`，要求调用方回传 `tool_result`），上游 provider 找不到结果块就报 `WEB_PROVIDER_ERROR` |
| 结果映射   | 每条 `results[]` 一个 source；空的 `title` / `content` 视为缺失（`content` → `snippet`），**没有 `url` 的条目丢掉**              | seam 的 source 必须有 url；Ollama 不返回生成式答案，所以整条结果没有 `content`                                                                               |
| key        | 与 `llm-pi-ai` 的 ollama route 共用 `OLLAMA_API_KEY` 引用                                                                        | 一处凭证面（凭证服务，缺席时回退启动环境）；不把密钥写进配置文件                                                                                             |
| 装配       | 注册行在本包 `./rows` 出口，采用方的 bundle 渲染 patch 并在同一份 patch 里给 `web.searchProvider: ollama`                        | 装配归能力包、值归 bundle；选择权在 `web` 行的 `searchProvider`，那一行本来就是 host 行                                                                      |

## 事实基线

### 端点与请求

- `POST {baseURL}/api/web_search`（`src/provider.ts:85`），`redirect: "error"`，请求体
  `{query, max_results?}`，头 `authorization: Bearer <key>` / `content-type: application/json` /
  `accept: application/json` / `user-agent: morlay-dsh-plugin/…`。
- 链路是否成立的真凭据（一次真调用）：

  ```sh
  curl https://ollama.com/api/web_search -H "Authorization: Bearer $OLLAMA_API_KEY" \
    -H "content-type: application/json" -d '{"query":"cordis plugin framework"}'
  ```

- 上游 messages 路子在 Ollama 上不成立的原因：`POST https://ollama.com/v1/messages` 带
  `tools:[{type:"web_search_20250305", …}]` 时回的 `content` 只有 `thinking` + `tool_use`
  （`stop_reason: tool_use`）——Ollama 不自己执行搜索。Ollama 官方文档
  （[docs.ollama.com/api/anthropic-compatibility](https://docs.ollama.com/api/anthropic-compatibility)）说的
  "hosted web search are not fully supported" 就是这个意思。

### 结果映射与错误面

- `mapOllamaResult`（`src/provider.ts:37-49`）：没有非空 `url` 的条目直接丢弃；空串 `title` / `content` 视为缺失；
  `content` 映射成 `snippet`；响应信封形状不对（`results` 非数组）或不可解析 → 包成 `WEB_PROVIDER_ERROR`。
- `max_results` 上限 10（`OLLAMA_MAX_RESULTS_LIMIT`，`src/provider.ts:20,163-166`）：请求与配置给出的更大值在发出
  前压到 10；配置不给就是让 Ollama 用它的默认（5，`OLLAMA_DEFAULT_MAX_RESULTS`）。
- 错误码：HTTP 失败 → `WEB_PROVIDER_ERROR`（优先用响应体里的 `error` 文案，非 JSON 体退回
  `Ollama API error (HTTP <status>)`）；网络失败 → `WEB_PROVIDER_ERROR`；取消 → `WEB_ABORTED`（任何阶段，含读体）；
  取不到 key → `WEB_PROVIDER_CREDENTIAL_MISSING` 且**不发请求**。
- `available()`（`src/provider.ts:72-78`）不联网：只看 key 有没有来源、`baseURL` 能否解析、`maxResults` 是否正整数。

### 配置字段

四个字段都标 `.volatile()`，改完不用重挂这一行（`src/index.ts` 的 `apply` 用 getter 现场读引用）：

| 字段         | 默认                     | 含义                                                       |
| ------------ | ------------------------ | ---------------------------------------------------------- |
| `apiKey`     | —                        | 字面 key；优先用下面那个引用，别把密钥写进配置文件         |
| `apiKeyEnv`  | `OLLAMA_API_KEY`         | 每次搜索解析一次的凭证引用（凭证服务，缺席时回退启动环境） |
| `baseURL`    | `https://ollama.com`     | 端点根；`/api/web_search` 由 provider 拼                   |
| `maxResults` | —（Ollama 自己的默认 5） | 请求没带 `maxResults` 时的默认结果数                       |

### 装配

- **注册行在本包**：`./rows` 出口（`src/rows.ts` 的 `webSearchRows()`）给出
  `{insert: [{id: "web-search-ollama", name: "@morlay/dsh-web-search-ollama"}]}`，config 的值由部署那层按 id 覆盖。
- **采用它的部署 bundle 是 `@morlay/ollama-provider-profile`**：它渲染 patch，并在同一份 patch 里给 `web` 行
  `searchProvider: ollama` / `fetchProvider: http`、给 `llm-pi-ai` 的 ollama provider 与 `web-search-ollama` 的
  `apiKeyEnv`。部署侧把那个 bundle 列进 `dsh.profile.bundles` 即可。
- 注册行只能有一份：同一个 provider id 注册两次会撞 `WEB_DUPLICATE_PROVIDER`。
- **不做设置页 section**：配置面就是那一行 patch。

## 取舍

- **接 Ollama 自己的 REST，而不是把上游 messages 后端指过去**：那条路在 Ollama 上拿不到结果块（见事实基线）；
  代价只有一个约 200 行的 provider。
- **一次只选一个后端**：`ctx.web` 的 `searchProvider` 是单选，默认 `ollama`；`deepseek-official` 后端仍由基础
  bundle 注册着（`vendor/deepseek-harness/packages/bundle/base/cordis.patch.yml:478-479`），改写 `web` 行的
  `searchProvider` 即可切回（但它需要 `DEEPSEEK_API_KEY`）。
- **`available()` 不联网**：可用性检查只在注册期做形状判断，真链路是否成立由 e2e 守（不打外网就不该伪装成证据）。
