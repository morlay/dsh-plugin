# 按模式的 policy 拦截（模式自己声明哪条上游裁决生效）

状态：已实现
范围：`packages/profile/dsh-session-mode/` 的四个模式字段 `allowTools` / `denyTools` / `allowPolicies` /
`denyPolicies`——它们的形状、合成规则与装配期校验，policy 拦截挂在哪条接缝上、它对上游 waterfall 的裁决做什么，
以及它与会话模式其余扩展（persona、三个开关、默认模型）的关系。
约束：`vendor/**` 只读（红线）；只用上游公开的事件面（`ctx.on(..., { prepend: true })` 与 `ctx.waterfall` 的既有
契约）；归属只按**会话模式**判，不看 preset（[ADR-模式不绑定preset](../adrs/20260929-模式不绑定preset.md)）。
上游策略自身的行为不在本文范围（收口见
[ADR-allowTools留空即不设收窄](../adrs/20260929-allowTools留空即不设收窄.md)）。

## 事实基线

### 上游那两个 waterfall

- 事件 `fs/write-intent` / `fs/edit-intent` 都是 waterfall，签名 `(target, actor, next)`；`next()` 的语义写在注释里
  ——"裸 provider 的无条件写 / 编辑"：`vendor/deepseek-harness/packages/fs/fs/src/index.ts:52-54`、`:60-62`，
  签名在 `:59`、`:67`。
- 调用点是工具自己：`vendor/deepseek-harness/packages/fs/tool-fs/src/write.ts:115` 与
  `.../tool-fs/src/edit.ts:127`（最内层默认都是 `() => undefined`）。返回值直接当 `writeText` / `editText` 的
  `expected`，**省略就是无条件**（`fs/src/index.ts:254-272`、`:274-293`）。`tool-str-replace-editor` 也走同一对
  事件（`.../tool-str-replace-editor/src/index.ts:254`、`:289`、`:342`，其中 write 那条的最内层默认是
  `createIfAbsent`）。
- 谁在裁决：`fs-observation-policy` 在 write 上返回 `createIfAbsent` / `replaceIfVersion`
  （`.../fs-observation-policy/src/index.ts:65-71`；类型 `fs/src/types.ts:123-125`），在 edit 上未观察过就抛
  `FS_NOT_OBSERVED`、确认不存在抛 `FS_NOT_FOUND`、否则给 CAS 版本（同文件 `:78-88`）；两条注册**都不调
  `next()`**（同文件 `:116-122`）。没有这一行时，行为就是无条件的写 / 编辑。
- 拒绝怎么到模型：工具执行里抛出的错误只经 `remediateFsError` 改写 `FS_NOT_OBSERVED` / `FS_STALE_VERSION`
  两个 code，其余原样透传（`.../tool-fs/src/error.ts:21-34`）；沙箱那层只认 `FS_SANDBOX_DENIED`
  （`.../tool-fs/src/sandbox.ts:124-130`）。
- 于是改写它的裁决只有一条路：在**链首**把整条链先跑完（拿到结果、或接住拒绝）再决定丢弃。拦截之所以必须
  `prepend`，就是因为上游不调 `next()`——站在它后面就拿不到决策权。

### 事件分发不做 scope 过滤（接缝为什么只有这一种）

- `ctx.waterfall('fs/write-intent', …)` 把事件名放在第一个参数上；cordis 的 `dispatch` 只在**第一个参数是对象
  或函数**时才取 `thisArg` 并据它过滤（`vendor/deepseek-harness/vendor/cordis/src/events.ts:165-175`），waterfall
  的合成见同文件 `:234-243`。结论：注册在哪个 ctx 都收得到**每一次**调用。
- scope 过滤要求调用方把 `scopeTarget(...)` 当接收者传进去（`vendor/deepseek-harness/packages/core/scope/src/index.ts:170-185`），
  fs 的调用点没这么做。所以"注册在该 agent 的 ctx 上"买不到隔离——这决定了本设计的接缝位置（见「取舍」）。
- 归属只能从 `actor` 认：工具把自己的 `exec` 当 actor 传（`vendor/deepseek-harness/packages/core/tools/src/index.ts:339`
  的 `ToolExecution.agent?: Agent`），上游也是这么认的（`.../fs-observation-policy/src/types.ts:23-28` 取
  `agent.session`）。
- 同一手法在本仓库有过先例：`git show HEAD:packages/profile/dsh-agent-toolkit/src/relax-intent.ts`（preset 行里
  `prepend` + 沿 scope 父链判归属）。那份行数据已随自建 preset 一起删除
  （[ADR-不再持有行清单](../../../../bundles/session-mode-profile/.agents/adrs/20260929-不再持有行清单.md)）；
  本设计沿用手法，把归属判据换成会话模式。

### 本包现有的应用面

- 每个 agent 装一份的模式扩展在 `installFor`（`src/index.ts`）：模式没变就是空操作，变了先 `dispose` 旧的，再装
  persona、默认模型兜底与按会话收口（[`src/scope.ts`](../../src/scope.ts) 拿到 `allowTools` / `denyTools` 与三个开关）。
- 会话当前模式是投影 `sessionMode`（`?? 部署默认`），`modeOf` 是唯一读法；`select` / `applyTo` / 子代理继承都先把
  结论写成会话事件，再 `installFor`。
- 模式的形状与校验在 `src/modes.ts`（`modeSchema`）与同文件的 `configProblem`；行 config 由 `src/rows.ts` 渲染
  （空名单不进 config，与"可以省的键就不写"同口径）。
- `inject` 只有 `agents` / `sessions` / `sessionProjections` / `systemPrompt`——本设计不新增服务依赖，也就不新增
  激活条件（只多一条 type-only 的上游事件词汇依赖 `@deepseek-ai/dsh-fs`）。

## 形状与语义

```yaml
modes:
  coding:
    # 工具：`allowTools` 空 = 不设收窄（用会话挂着的 preset 的全部工具）；`denyTools` 从那份里减掉。
    denyTools: [bash]
    # 上游规则：`allowPolicies` 空 = 全部生效；`denyPolicies` 从那份里减掉（deny 优先）。
    denyPolicies: [fs/edit-intent]
```

- **四份名单都是数组**，schema `.default([])` 归一化：不写、写 `[]` 都是"这一份不参与"。渲染时 `rows.ts` 不写空
  数组（与 `allowTools` 留空同口径）。
- **合成规则**（判据一处，见 `installFor` 与 `policyInForce`）：可用工具 =（`allowTools` 空 ? 全部 : `allowTools`）
  − `denyTools`；生效规则 =（`allowPolicies` 空 ? 全部 : `allowPolicies`）− `denyPolicies`。两份同时命中时
  **deny 优先**，这是合法配置，不是错误。
- **命中原因要能分辨**：白名单外的调用由收口那句"`<工具>` 不在「`<模式名>`」的工具白名单里"表达；黑名单内的由收口
  按 `denyTools` 另给一句——两份名单的成因不同，别合成一句话。
- **装配期校验**（`configProblem`）：`allowPolicies` / `denyPolicies` 里有 `POLICY_NAMES` 之外的名字 → 拒绝装载，
  消息里列出已知名。值的合法性由 schema 承担。
- `src/shared.ts` 是名单的 home：`POLICY_NAMES`（`fs/write-intent` / `fs/edit-intent`）与 `PolicyName`——host 半的
  校验与 client 半的页面候选都读它（client 半不 import `modes.ts`，免得把 schemastery 拖进浏览器包）。
- **渲染进行 config 的形态**（`rows.ts`）：逐项拷进这一行的 `config.modes.<id>`，空数组与不写都不进 config。

## 接缝与生命期

- 注册一次：`SessionModes` 构造时在行自己的 ctx 上 `ctx.on(name, listener, { prepend: true })` 两条（与两条投影、
  `agent/created` 同一处注册），随行卸载一起撤。两条注册的事件名带 `satisfies PolicyName`——名单里删掉一个名字
  就编不过，而不是静默拦不住。
- 每次调用现算：`actor.agent` 认不出（没有 agent 的直接调用）→ `next()`；认得出 → `modeOf(agent.session)` →
  该模式的名单：写进来的规则在生效集合里 → `next()`；不在 → 先跑完上游（接住它抛出的拒绝）再 `return undefined`。
- 拦截路径**不因配置或投影问题抛错**：模式 id 在 config 里找不到（重挂前后的瞬间）时按"没配"读，绝不在这里抛。
- 幂等与切换（`select` / `applyTo` / 子代理继承）：`installFor` 完全不碰这两条监听器，所以"同一模式重复应用不
  重复注册"是结构上的事，不是靠判等维持的；也没有"换一份 / 撤一份"的动作——监听器读的是会话投影，模式是它每次
  调用现算出来的。子代理继承父模式时，它**自己的**会话也被写了模式事实，于是天然用同一份名单。
- 名单住在 volatile 的 `modes` 里：改了要等 Loader 重挂这一行，拦截读的是构造时的快照——与 persona、默认模型
  同一口径。

## 裁决语义

| policy            | 上游裁决                                                                            | 生效（在生效集合里）                           | 被禁（`denyPolicies` 命中 / 不在 `allowPolicies` 里）        |
| ----------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------ |
| `fs/write-intent` | 返回 `createIfAbsent`（没读过的目标）或 `replaceIfVersion`（按观察到的版本 CAS）    | 原样交回：陈旧版本保护与 `createIfAbsent` 都在 | 丢弃 → `undefined` = 无条件写（上面那层安全网一起不要）      |
| `fs/edit-intent`  | 未观察过 → 抛 `FS_NOT_OBSERVED`；确认不存在 → 抛 `FS_NOT_FOUND`；否则 `{ version }` | 原样交回（拒绝也原样抛出）                     | 丢弃（连那两个拒绝一起接住）→ `undefined` = 无版本前提的编辑 |

- **"被禁"是"丢弃这条 waterfall 的裁决"**，不是"跳过某个监听器"——因为上游独占决策槽，唯一宽松的形态就是无条件。
  对 `fs/write-intent` 来说它丢的是**安全网**（陈旧版本 / CAS 保护）；对 `fs/edit-intent` 来说它才是"免先读后改"
  的正主。本部署因此只禁后者（见 `mode-sources.ts`）。
- 异常路径：被禁时接住上游拒绝是为了让它"没拦成"（旧手法同此）。
- **未列出的规则、没配名单的模式、认不出 agent 的调用：一律照上游**（`return next()`）。这是默认，不需要在配置里
  声明。

## 与收口的关系

- 四份名单都放在 `modeSchema` 里（不放进 `preset`），是模式定义里与 persona / 三个开关 / 默认模型并列的会话级
  扩展。
- 收口（[`src/scope.ts`](../../src/scope.ts) 的 `SessionScope`）只多认两份**工具**名单：`installFor` 把模式定义里
  收口要的那几项整份推过去（`apply(agent, { name, allowTools, denyTools, instructions, skills, runtimeContext })`）
  ——模式定义是这些名单唯一的一份数据；两份 policy 名单不进这个形状（它们不落到收口那一层）。
- 收口的其余部分不动，理由三条：词汇——收口那一层的面是"工具目录 / `tool:<名字>` section / 执行层 guard / 通道
  开关"，`fs/write-intent` 是 fs 平面的事件名，塞进去等于让通用收口包认识上游 fs 词汇；时机——收口在装配期（与
  提示词同一轮），policy 拦截在**每次工具调用**的 waterfall 上；契约——`apply` 的入参是收口要的那几项（不是整份
  模式定义），policy 名单因此不必长进它的形状里。谁 `prepend` 谁就该是注册者，注册者住在本包（模式定义的家）。

## 设置页

- 四份名单都在 volatile 的 `modes` 里，通用 schema 表单按 schema 画出来
  （`packages/client/ui-primitives/src/client/schema-form/schema-node.ts` 的数组 / 字符串节点）。
- 两份 policy 名单的候选是一份封闭名单：client 半在**数组项**那一路径上登记候选值
  （`hints.select(SESSION_MODE_NS, ["modes", "*", "<字段>", "*"], …)`，见 `src/client/index.ts`），页面因此把每一项
  画成选择器，两条已知规则直接可选。`suggestKeys` 不适用于这里——它只喂 dict 字段的候选键
  （`controller.ts` 的 `addableAt`：数组层的"添加一项"是追加空项，没有键名可选）。

## 取舍

- **未知 policy 名不放过**（否掉"按已知名单注册、未知名静默无效"）：一份"看着像配过了"的策略不生效，正是本仓库
  明确不想留的失效方式（退役的顶层 `models` 就为此报错）。代价是名单写死在包里，上游新增一个可拦的 waterfall
  要改本包——但"能拦什么"取决于上游是否独占决策槽，本来就不是配置能自己长出来的东西。
- **不按 agent 各注册一份**（把监听器塞进 `installFor` 的 disposers，像 persona 那样）：fs 的 dispatch 没有
  scope 过滤（见事实基线），注册在 agent 的 ctx 上不产生隔离，只多出 N 份判断与一份要跟着模式换的闭包；而按
  agent 挂还会多出"旧闭包没撤干净"的悬挂面。
- **归属不按 preset / scope 父链判**（旧手法的判据）：模式不限制 preset（本部署的 `presetsOnly` 留空），同一份 preset
  上可能坐着不同模式的会话，
  preset 反查不出模式（[ADR-模式不绑定preset](../adrs/20260929-模式不绑定preset.md)）。
- **黑名单不省掉**（否掉"只留 `allowTools` / `allowPolicies`"）：`chat` 那种"只要三件"用白名单最直白，而"除了
  shell 都要"用白名单就得抄一份全量清单——清单已经不是我们的（行清单归 preset），抄一份只会漂移。
- **不给每条 policy 开一个字段**（`relaxWriteIntent: true` 那种）：上游每加一个可拦的 waterfall 就要加一个字段，
  而且字段名会与上游词汇漂移。
- **`deny` 不先跑上游**：那两个决策者今天没有副作用（`fs-observation-policy/src/index.ts:65-88` 只读自己的
  WeakMap / 抛错），先跑一遍再丢弃只是多一次计算。风险照实：上游哪天在这两个事件上开始记账，这里要重看。
- **被禁时抛的不是 `FsError`**：没有"拒绝"要产生——被禁就是让这次调用按"没有这条规则"继续，模型不该看见一条
  凭空多出来的失败。
- **代价照实**：
  - 禁掉 `fs/write-intent` 丢掉的不只是"先读后改"，还有陈旧版本 / CAS 这层安全网；本部署只禁 `fs/edit-intent`
    正是为了保住写的那层保护。
  - 禁掉的是**整条链**的裁决：`tool-str-replace-editor` 在 write 那条路上给的最内层默认是 `createIfAbsent`
    （`.../tool-str-replace-editor/src/index.ts:254-258`），也会一并被丢成无条件写（它自己在之前已经 stat 过、
    不覆盖已存在文件，所以丢的只是"再确认一次"）。
  - 拦截只覆盖走这两个 waterfall 的通路（`tool-fs` 的 write / edit、`tool-str-replace-editor`）；`bash` 之类自己写
    文件的通路不经过它们，禁掉也拦不住——想"这个模式不能改文件"，`allowTools` 拿掉 `write` / `edit` 更直白。
  - 上游对齐点：`fs-observation-policy` 的"独占决策槽 + 不调 `next()` + edit 用 throw 表达拒绝"是这份设计的全部
    前提。它升版若改成调 `next()` 或改用别的 dispatch 模式，"丢弃上游结果"就不再成立，要连同包内判据一起重看。
    这条前提由 `preset-plane.spec.ts` 里的真策略行钉住（成对判据）。
  - 链首位置靠 `prepend` 抢：另一个插件在**我们之后**也 `prepend`，就会插到我们前面；本部署没有第二个监听这两
    个事件的代码。
- **判据**（三层口径见 [`how-to-verify.md`](../standards/how-to-verify.md)）：
  - `src/__tests__/session-mode.spec.ts`：在真 `ctx.waterfall` 上，配一条与 `fs-observation-policy` 同形注册的
    替身上游（不调 `next()`；write 返回 intent、edit 抛 `FS_NOT_OBSERVED`）——被禁的规则下拿到 `undefined`（上游
    仍被问过一次）；没配名单的模式、以及**另一个 agent** 的同名调用，拿到上游原样的结果与拒绝；切模式后同一次
