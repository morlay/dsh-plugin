# 会话模式（模式作为数据，按会话应用）

状态：已实现（设置页那一面走通用 schema 表单）
范围：`packages/profile/dsh-session-mode/` 的模式来源、应用时机、会话 ↔ 模式的选择，以及页面上的选择面。
工具行本身在 [`@morlay/dsh-agent-toolkit`](../../../dsh-agent-toolkit/README.md)，收口的执行在
[`@morlay/dsh-context-assembler`](../../../../context/dsh-context-assembler/README.md)，装配入口在
[`@morlay/session-mode-profile`](../../../../bundles/session-mode-profile/README.md)，配置值在
[`@morlay/mydsh-profile`](../../../../bundles/mydsh-profile/README.md)。
约束：不放宽「上游代码不可修改」——只用上游公开的服务面（`systemPrompt.section`、`ctx.sessions`、
`sessionProjections`、`tools.guard`）与装配行。

## 结论摘要

| 议题           | 结论                                                                                                                                                     | 一句话理由                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 模式来源       | `session-mode` 行的 `config.modes`（`src/mode-sources.ts` 是真源，`src/rows.ts` 渲染成行 config）                                                        | "支持自定义"就是改一份 config，不是加行                                            |
| 行清单         | 归 preset 平面；本部署**自己注册一份**（`preset-mode-switch`，`config.plugins` 引用 toolkit 的 `TOOLKIT_PRESET_ROWS`），官方四个 shipped preset 照旧可选 | 一行只属于一个平面；官方 `minimal` 没有 `tool-web`，复用它会丢掉 `chat` 的联网     |
| 模式挂在哪     | 每个模式的 `preset` 声明它挂哪份 preset（**可以共享**；本部署两个模式同挂 `mode-switch`）                                                                | 行清单由那份 preset 提供，模式只回答"这些行怎么被用"                               |
| 提示词         | `agent.ctx` 上注册 `deployment:persona-prefix` / `-suffix`                                                                                               | 跨层遮蔽部署级那层；这条路上游给子 agent 也在用                                    |
| 工具与注入开关 | 推给 `ctx.sessionToolScope`（`context-assembler-scope` 行）                                                                                              | 谁注册了工具与"这个会话能用什么"无关；同时保持依赖单向                             |
| 应用时机       | `agent/created`（preset 换选时对已有 agent 再应用一次）                                                                                                  | 早于任何一次提示词装配，persona 必在首次装配前注册好                               |
| 会话 ↔ 模式    | session 事件 `session-mode/selected` + 投影 `sessionMode`（`null` = 没选过）；选模式即写入                                                               | 模式决定模型看到的工具与提示词，按仓库规矩必须进日志                               |
| 切换判据       | 只有空白会话：投影 `sessionModeEditable`（`turn/start` 一落库就 `false`）                                                                                | 跑过的历史属于旧装配，换了它日志与实际装配就对不上                                 |
| 页面通路       | 官方 roster 保留（`ui-agent-preset` 占 `conversation.hero.agentPreset`，单注册）+ 本包的 chip 在 list 槽位 `conversation.input.left`                     | 单注册槽位不能两个 seat；两套入口管的是两件事（挂哪套行 / 会话级扩展）             |
| 设置页         | 本行的 `plugins.row.config`（key `@morlay/session-mode-profile#session-mode`）编辑 `config.default` 与 `config.modes`（含各模式的 `defaultModel`）       | 模式定义（preset、提示词、工具、默认模型）就在这一行里，页面编辑的是同一份         |
| 模式角色       | `role`：`main`（用户选择器）/ `subagent`（可作子代理 mode 的候选），缺省 `["main"]`                                                                      | "谁能用这个模式"是一份声明，不是散在各处的判断                                     |
| 默认模型       | 模式自己的 `defaultModel`（可选）：只在会话**尚无模型事实**时接管请求路由，不写会话事件                                                                  | 它是配置事实（用户的选择与会话已有历史优先）；挂在模式里让定义自洽，页面照样能编辑 |
| 子代理的模式   | 继承父当前模式，并把继承写进子会话日志；`subagent` 角色只管"可被指定"的候选                                                                              | 模式决定工具与提示词，子代理那边同样得是一条可重建的会话事实                       |

## 事实基线

### 装配入口

- [`@morlay/session-mode-profile`](../../../../bundles/session-mode-profile/README.md) 一次装齐：`preset-mode-switch`
  （preset 声明）、`session-mode`（本行）、`context-assembler-scope`（本包模式定义的收口）、`subagent` 接管行、
  以及 host 平面的 `context-assembler` 与 `tool-guidance`。行清单只有一份真源：各能力包的 `rows` 出口由那个
  bundle 的 `tsdown.config.ts` 展开。
- 本包自己不发 `cordis.patch.yml`：只有插件实现与 [`rows` 出口](../../src/rows.ts)（`sessionModeRows()` 渲染
  `session-mode` 行的 config）。

### 数据形状

`src/modes.ts` 给形状与校验（`Config` schema + `configProblem`）：`default` 必须在 `modes` 里、必须是 `main`
角色，每个模式至少给一个 `allowTools`——空名单是写错了，不是"全都要"，装配期直接抛。同批判据还有：`modes`
不能是空的；`role` 不能是空数组（缺省等于 `["main"]`）；每个模式的 `defaultModel` 要么不写，要么 `provider` 与
`model` 都给全；退役的顶层 `models`（模式 id → 模型）**仍然声明**，但只做一件事——装配期看见它还配着值就报错，
提醒挪进对应模式，否则一份"看着像配过"的配置会静静地失效（它 `hidden()`，页面上不出现）。

`role` 是模式自己的面，默认模型也在模式自己身上：

- `role: ("main" | "subagent")[]`（缺省 `["main"]`）：`main` 进用户选择器（`list()` / `roster()` 只列它，
  `select` 拒绝非 `main` 的模式）；`subagent` 声明"它可以作为子代理的 mode"——目前只是候选集，因为按角色
  指派还没做（见「开放问题」）。
- `defaultModel?: { provider, model, reasoningEffort? }`（**每个模式自己**的字段）。形状与全局
  `agent-default-model` 一致；某个模式不写就跟着全局。判据见
  [ADR-默认模型住在模式定义里](../adrs/20260925-默认模型住在模式定义里.md)。

形状分两层：`Config` 是**源码形状**（`defaultModel` 可以整块省略，装配层与设置页写的都是它），
`ResolvedConfig` 是 schema 解析后的形状（`default` / `modes` 是 `Volatile` 引用，读它们要过 `.get()`）。schema 用
`z<Config, ResolvedConfig>` 声明——于是 `ctx.plugin(plugin, 装配层那份普通对象)` 与 `apply` 里的引用读法
同时成立（`packages/llm/llm-openai-compatible` 是同一套做法的先例）。

### 字段与落点

| 字段                   | 落到哪                                                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `preset`               | 挂哪份 agent preset（官方或本部署自建的 `id`）：**可以共享**；行清单由它提供，空串表示不挂（只能由 `applyTo` / 继承使用）       |
| `name` / `description` | 模式的事实文案（选择面归官方 roster，那里显示的是官方 roster 的清单）                                                           |
| `role`                 | 归谁用：`main`（用户选择器）/ `subagent`（可作子代理 mode 的候选）                                                              |
| `persona`              | 装配前注册到**该 agent 的 scope**（部署级那层被遮蔽）                                                                           |
| `allowTools`           | `context-assembler-scope` 收口：模型目录、`tool:<名字>` 说明 section、执行层 guard、常驻用法正文；**preset 没有的工具自动跳过** |
| `instructions`         | 同上：`false` 表示这个会话不要任何 instruction 类注入（工作区指令、技能目录、用法正文）                                         |
| `runtimeContext`       | 同上：`false` 表示不要动态快照（沙箱策略、审批策略）                                                                            |
| `defaultModel`         | 这个模式的默认模型（可选）：会话还没有模型事实时接管请求路由，不写会话事件                                                      |

### 生效方式

`default` 与 `modes` 都是 **volatile**：改了等 Loader 重挂这一行（设置面写完会重装被改的行），**已运行会话不
自动换定义**——重挂后新建的会话、或重新应用模式的会话才用新定义。模式名与说明是数据、不做语言翻译
（`src/mode-sources.ts` 里只有中文）。

### 应用

`agent/created` 事件里做，三件事：

1. `installPersona` 在 `agent.ctx.systemPrompt.section(...)` 注册两个 section（`prefix` / `suffix`，suffix
   缺省是空串——与上游 persona 行同语义：空串遮蔽部署级那层）。注册与注销都会发 `system-prompt/change`。
2. `ctx.sessionToolScope.apply(agent, mode)`：`context-assembler-scope` 行收到后做三件事——装配期投影
   （模型目录、`tool:<名字>` section 与可见工具同源过滤）、执行层 guard（挂在 `agent.ctx` 上，拒绝对话带模式名）、
   通道开关（`setInstructions` / `restrictTools`）与动态快照抑制。
3. `config.modes[<模式 id>].defaultModel` 的兜底：在 `agent.ctx` 上挂一个 `agent/request` waterfall，**只在会话尚无
   模型事实**（投影 `modelSelection` 的 `pending` 为空、且 `session.requestHeader()` 还没落）时把这一请求的
   provider / model / reasoningEffort 换成模式配的那份。它不写会话事件——模型选择是配置事实，会话里那条
   `model/selection`（由上游设置面写）才是用户的选择。

每个 agent 记着"当前装的是哪个模式"，模式没变就是空操作。切换模式时：先收回旧的一份（persona 的 effect、
scope 那边的 effect 树），再装新的。

### 会话与模式

`select(sessionId, mode)` 是唯一的写路径（HTTP 路由与本地服务同一份实现）：校验模式存在、会话存在、还没跑过
turn，然后在这个模式声明的 preset 与当前挂着的**不同**时把它换过去（`agentPresets.select`，行清单与它一起换，
见 [ADR-选模式就换preset](../adrs/20260928-选模式就换preset.md)；本部署两个模式共享一份，所以切 chip 走到这里
通常是空转），再 append `session-mode/selected`，最后对已有的 agent 重新应用。投影 `sessionMode` 是读路径：
`stateOf(session, "sessionMode") ?? config.default`。恢复（resume）与 fork 都从日志重建这条投影，不需要
header 字段。

**落点**（我们的部署是 [`@morlay/session-rdb`](../../../../session/session-rdb/README.md)）：事实是
`t_events` 里一条 `f_type = 'session-mode/selected'` 的事件行（`f_data` 是整条事件信封），按
`t_session_events` 的 `f_sequence` 挂在该会话上；`sessionMode` 的投影值另存 `t_session_projcache_row`
（`f_key = 'sessionMode'`，`f_val` 是 `"chat"` 或 `null`）——那是折出来的缓存，不是事实。表结构见
[设计 20260917-表结构](../../../../session/session-rdb/.agents/designs/20260917-表结构.md)。**header 里没有这个字段**
（上游 agent preset 那套的 `t_sessions.f_agent_preset` 我们不写）；默认模式来自装配 config，不落库。

**这个事件类型上游不认识**（上游的已知类型表由它自己仓库的声明生成），所以要靠 `ignorable` 信封过持久化校验
——信封由 [`@morlay/session-rdb`](../../../../session/session-rdb/README.md) 的 `OWN_EVENT_TYPES` 补（落库前补 +
读回时兜底）。本包**新增事件类型时必须同步登记**，否则写入就被拒，见
[设计 20260924-自造事件类型的信封](../../../../session/session-rdb/.agents/designs/20260924-自造事件类型的信封.md)。

### 子代理与继承

子代理是**新会话**（`session.header.parentSession` 指向父），模式按下面三条定：

- **默认继承父当前模式**：创建时（`agent/created`）若该 agent 有 durable 父会话且父还在场，就取父的当前
  模式，并把 `session-mode/selected` **写进子会话**——继承是一条会话事实，冷恢复与 fork 必须能重建它
  （读路径仍只认投影）。父不在场（孤儿会话、父已卸载）时不继承，回落部署默认。
- **继承不看 `role`**：`subagent` 角色声明的是"可被指定的候选"，不是"继承的白名单"。父在 chat 里派发的
  子代理仍然是 chat——否则同一个任务在父子两边跑着两套工具与提示词。
- **指定 mode 的入口还没做**：本包把接缝留在服务上——`applyTo(agent, mode, { record })`（不要求空白会话，
  子代理继承走的就是它）与 `modesFor("subagent")`（候选集）。将来无论是模型侧参数还是配置，都从这里进。

### 页面

client 半与 host 半同包（`./client` 入口，浏览器模块工厂加载）。两个槽位：

| 槽位                                                                    | 呈现                                                                        |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `conversation.input.left`（id `session-mode`）                          | composer 工具行左侧的模式 chip，点开是切换列表（新会话屏也是一个 composer） |
| `plugins.row.config`（key `@morlay/session-mode-profile#session-mode`） | 本行的配置入口：每个模式一行「默认模型」（provider / model / 档位）         |

chip 有两个形态：**空白期是选择器**；会话开过 turn 之后**只读**（只写当前模式，点不动、没有下拉面）。判据是 host
的投影 `sessionModeEditable`，与服务端拒绝切换读的是同一份事实；头部的只读标签不做——chip 本来就把当前模式写在
脸上。官方 roster 的选择面保留（它管"挂哪套行"），与 chip 并存：一个在 `conversation.hero.agentPreset`，一个在
`conversation.input.left`。chip 的清单在页面生命周期里是静态的（装配事实），模块级缓存一次；当前值由
`useSessions` 读投影，切换后跟着会话列表快照刷新。

行配置页渲染的是 `default` 与 `modes`（都是 volatile）：起始模式与模式清单（含各自的默认模型）。页面**不在本包**：
[`client/ui-primitives`](../../../../client/ui-primitives/README.md) 的通用 schema 表单按 schema 把它渲染成这一行的
配置页（`plugins.row.config`，key `@morlay/session-mode-profile#session-mode`）。页面形状来自 schema 本身：`modes` 是
dict，展开出每个模式的 `provider` / `model` / `reasoningEffort` 三行；编辑是 staged 的（改完按"保存"才发一次带
revision 栅栏的 `mutate`）——改一个模式是 `{ op: 'set', path: ['modes', <模式 id>, 'defaultModel'], value }`。本包
client 半只给这三行补中文标签与说明（提示面 `ctx.schemaFormHints.describe`，行式视图把它画成注释行），并注册
`llm-providers` / `llm-models` 两个具名候选源。

## 取舍

- **不在页面里改模式清单以外的东西**：模式定义是装配配置，页面改的就是 `default` 与 `modes` 本身——定义因此只有
  一个 home。
- **不声明 `settings.configure({ auto: false })`**：本行有 volatile 字段，`describe()` 会把它描述出来，
  `autoGenerate` 保持默认 true——这正是通用 schema 表单为这一行生成页面的依据。
- **切换只在空白会话**：不是懒，是语义——历史与装配必须对得上。想要"中途换模式"，正确做法是新开会话。
- **推模型而不是拉模型**：依赖方向保持单向（装配层 → 能力包）。代价是 `session-mode` 要认识
  `ctx.sessionToolScope` 的最小接口，而不是反过来。
- **HTTP 而不是 Typert Remote**：客户端能发现的服务清单由上游硬编码（`@deepseek-ai/dsh-api-remotes/client`），
  我们的服务不在里面。HTTP 路由是这个仓库既有的跨半通路（见 `/session-editor`）。
- **模式的默认模型不写会话事件**：它是配置事实，重启后仍由 config 决定；把它写成会话事实会让"部署改了
  默认模型"对已有会话失效，也会与用户自己在设置里选的那份（`model/selection`）混成一件事。
- **`default` / `modes`（含其中的 `defaultModel`）都取快照**：它们是装配期输入（persona 注册、工具白名单收口、
  默认模型都在装配或会话创建时用），改了等 Loader 重挂这一行——页面上写的是"重挂后新建的会话才用新定义"，
  不假装已运行会话会跟着变。
- **默认模型挂在模式里**：设置面只编辑 volatile 字段，而 `modes` 已经整段 volatile（模式清单本身就在页面上编辑），
  模式内的 `defaultModel` 跟着一起上页面——它自己不必、也不许再标一层 volatile。
- **配置页交给通用 schema 表单**：`default` / `modes` 两个 volatile 字段的编辑面（对象、dict → 每个模式一组
  字段）正是 schema 已经描述的形状，所以卡片不自己画；文案走提示面（`ctx.schemaFormHints.describe`，按模板路径
  `['modes','*','defaultModel',…]` 注册一次）、选择器的候选走**具名源**（`llm-providers` / `llm-models`）。
- **兜底条件苛刻（无 pending、无 header）**：宁可不动，也不覆盖用户的选择或会话已经跑过的历史模型。
- **模式名与说明不做语言翻译**：它们是数据（`src/mode-sources.ts` 里只有中文），选择面显示的就是这份文案；
  取舍如此，不是漂移。
- **两个模式共享一套 host 平面**：工具行、通道、压缩都装一次，模式只声明"能用哪些"。代价是"模式"不再能
  各自带不同版本的同名行；收益是加工具只改一处。

## 开放问题

- **按角色指派 mode 与"指定 mode"的入口**：接缝已在服务上（`applyTo(agent, mode, { record })` 与
  `modesFor("subagent")`），但模型侧参数与配置侧入口都还没做；继承暂时覆盖全部场景，判据见
  [ADR-模式角色与默认模型](../adrs/20260923-模式角色与默认模型.md)。
