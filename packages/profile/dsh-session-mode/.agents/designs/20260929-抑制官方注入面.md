# 抑制官方注入面（`chat` 怎么让工作区指令与技能目录不进模型）

状态：已实现
范围：按会话收口的两个**注入面**——官方 `agent-instructions`（工作区指令）与官方 `tool-skill`（技能目录）发布的
`skill-catalog`——怎么按模式丢掉、以及技能目录怎么按**技能名**收窄（`allowSkills` / `denySkills`）；工具面的收窄
（`allowTools` / `denyTools`）与三个开关的落点在同一份实现里
（[`src/scope.ts`](../../src/scope.ts)），本文只讲"丢注入"与"按名收窄目录"这两件事为什么只能这么做、代价是多少、
判据在哪。
约束：上游 `@deepseek-ai/*` 只读；不动注册表（`tools.restrict()` 不用）；模式定义仍是唯一的真源。

## 结论摘要

| 议题                  | 结论                                                                                                                                 | 一句话理由                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 接缝                  | 两条面都在 `agent/pre-step` 上丢：`source.kind` 是 `agent-instructions` 时看 `instructions`，是 `skill-catalog` 时看 `skills`        | 官方那两行**在装配投影之外**自己往这条瀑布里 append 消息；装配期没有它们的影子          |
| 顺序                  | 监听器 `{ prepend: true }`（抢最外层），`await next()` 之后再过滤                                                                    | 瀑布里先注册的是外层：站在官方行后面就看不到、也丢不掉它们 append 的条目（实测见下）    |
| 开关为 `false` 时     | **无条件丢**：这两类的条目一条都不进，不看内容有没有变、也不看是首次还是增量                                                         | 配置说"不要"就是不要，判断依据只有模式定义这一处                                        |
| 开关为 `true` 时      | **零干预**：原样返回 `decision`，官方那两行的注入节奏（首次注入、内容有变化才注入的增量）一概不动                                    | 抑制只发生在配置说"不要"时；开关为要的模式与"没有本行"时的模型输入完全一致              |
| 技能名单收在哪两处    | 目录消息（正文那几行**与** `source.entries` 一起删）与 `skill` 工具的**调用参数**                                                    | 目录是模型看到的名单、`skill` 是它拿到正文的路；只收一处都留着一条能绕过去的路          |
| 技能名单不收注册表    | 技能照旧注册着，收的是"模型看到什么、能加载什么"                                                                                     | 与工具面同一个取舍：注册表改写会惊动上游目录与别处的读数（见下"不用 `tools.restrict`"） |
| 正文认不出那几行时    | 那**一条目录消息整条不动**（正文与结构化名单不分叉），并打一条点名告警                                                               | 宁可多列一个名字，也不静默删错行；告警是这条名单面唯一的失灵信号                        |
| `skills` 的缺省       | 不写由模式自己的工具名单推导（含 `skill` 就要），本部署 `chat` 因此是 `false`                                                        | 开关只多一个字段时，推导值已经能表达"这个模式的工具面里没有技能"                        |
| 不用 `tools.restrict` | 它改的是**注册表**：触发 `tools/change`、让官方目录与别处的注册级判据一起失真、缺工具的 preset 上直接抛                              | 我们要收的是"模型看到什么"，不是"注册表里有什么"                                        |
| 代价                  | 官方那两行每步仍重读 `AGENTS.md`、重算要送的消息（结果被丢掉）；no-step turn 会在下一步才被认领丢掉                                  | 丢掉的是结果，不是它们的工作；不积压，但每步多一次 fs 读                                |
| 判据                  | 真装配两种装配顺序下成对断言（`chat` 两条都不进 / `coding` 两条都在）+ 连续三步稳定 + 技能面三条（黑名单 / 白名单 / 上游行形状漂移） | 去掉 `prepend` 这两条会红（实测），所以它钉得住                                         |

## 事实基线

### 两条面为什么在装配期收不到

| 面                               | 谁 append                                                                                                            | 时机                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 工作区指令（`AGENTS.md`）        | 官方 [`agent-instructions`](../../../../../vendor/deepseek-harness/packages/context/agent-instructions/src/index.ts) | 自己挂 `agent/pre-step`：每步重算 desired 再插入 |
| 技能目录（`<available_skills>`） | 官方 [`tool-skill`](../../../../../vendor/deepseek-harness/packages/skill/tool-skill/src/index.ts)                   | 自己挂 `agent/pre-step`：发布 `skill-catalog`    |

两条都不经过我们的通道（通道只做装配结果上的文本转换与降级 section 的送达），也都不是 section：**它们的产物是
`agent/pre-step` 的 `decision.messages` 里的一条 user 消息**。所以收口能落的地方只有两处——装配投影（看不到它们）
与这条瀑布（看得到）。装配期过滤（`system-prompt/assemble`）在这里无从下手。

我们的通道那一侧的降级注入是另一件事：它按 agent 记状态，`instructions: false` 时 `collect` 直接返回空
（[`channel.ts`](../../../../context/dsh-context-assembler/src/channel.ts)），不需要在瀑布上丢。

### 开关的两侧：`false` 才丢，`true` 是纯转发

过滤器落在 `await next()` 之后，但开关为 `true` 时它一条都不匹配：`decision.messages` 原样返回（`kept.length` 等于
原来那份，返回的还是同一个 `decision`）。于是官方那两行的行为与"没有本行"时完全一致——首次装配该注入就注入，
之后**内容有变化才注入**的增量也照常进；我们既不补齐也不拦截，判断依据只有模式定义里的 `false`。

`false` 那一侧相反：**无条件丢**，不看这条消息是首次还是增量、也不看内容有没有变——配置说"不要"就是不要。

没 apply 过的会话（行在它之后才激活、或这个部署没装模式那一层）根本不在收口的登记表里：这条监听器对它完全不动，
`next()` 的结果原样返回。

### 技能目录按名收窄：改的是消息，不是注册表

技能名单（`allowSkills` / `denySkills`）与工具名单同一套合成规则（白名单留空 = 不设收窄，deny 优先），收窄落在三处：

| 面                                        | 谁读它                                           | 我们怎么收                                                                  |
| ----------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------- |
| 目录消息的正文（`<available_skills>` 块） | 模型（它按这份名单挑技能）                       | 删掉 ``- `<名字>`:`` 行首的那几行                                           |
| 目录消息的 `source.entries`               | 会话日志与页面（官方把发布的条目结构化记在这里） | 同一个集合一起删——两处不分叉                                                |
| `skill` 工具的调用参数                    | 模型加载技能那条路（工具本身仍归 `allowTools`）  | 执行层 guard 读 `exec.arguments.name`，命中就拒，文案说白名单外还是黑名单内 |

技能注册表不动：`ctx.skills.list()` 照旧列出被拒的技能，收的是"模型看到什么、能加载什么"（与工具面同一个取舍）。
`ctx.skills` 也没有按名遮蔽或反注册的入口（`registerProvider` / `register` 只返回自己那份的 disposer），
所以"收注册表"这条路本来就不存在。

正文行认的是官方渲染形状（``- `<名字>`: <说明>``）；认不出被拒名字的行时，**那一条目录消息整条不动**——正文与
结构化名单宁可一起多列，也不出现"正文里有、名单里没有"的分叉——并打一条点名告警。这是本设计里唯一一条
"上游改渲染形状就静默失效"的面，告警因此是它的失灵信号；自动判据用两条自造目录消息构造（官方那一行只接管第一条）。

### 为什么 `prepend` 是必需的

cordis 的瀑布是"**最先注册的在最外层**"：外层在 `await next()` 之后还能改最终结果
（[`cordis/src/events.ts`](../../../../../vendor/deepseek-harness/vendor/cordis/src/events.ts)）。官方那两行比本行早注册
（会话挂着的 preset 先于 host 平面），于是它们是**外层**——我们若不抢最外层，`next()` 拿回的消息表里根本没有它们
append 的条目，也就丢不掉。

实测（把 `src/scope.ts` 里的 `{ prepend: true }` 临时去掉，跑真装配用例）：

- "preset 先装"那一档 **3 条用例变红**：`chat` 的 `agent-instructions` 照旧进（断言拿到 `["upstream"]`）；
- "host 先装"那一档全绿。

所以判据落在**两种装配顺序都成对断言**上（[`preset-plane.spec.ts`](../../src/__tests__/preset-plane.spec.ts)），
顺序敏感性不会漏掉。

### 为什么不用 `tools.restrict()`

实测（同一批真装配用例，带官方 `tool-skill` 与 per-agent 注册的 `subagent`）：

| 观察                                                | 结果                                                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `restrict({deny: ["skill"]})` 触发的 `tools/change` | 1 次（连打 3 次 = 3 次）                                                                            |
| `restrict` 之后的注册表读数                         | `ctx.tools.get("skill", agent)` → `false`（`read` 同样 `false`）：注册表级视图被改写                |
| 缺工具的 preset 上 `restrict({allow: [三件]})`      | 直接抛 `tools.restrict() names unknown global tools "ask_user_question", "web_fetch", "web_search"` |
| 工具目录                                            | 照样收成三件（那是我们要的结果，但代价是上面两条）                                                  |

三条都不划算：`tools/change` 是上游 composition reconcile 的输入（谁注册工具谁被惊动）；注册表级视图被改写会让
**按注册级判定的官方目录**与别处的读数一起失真（`chat` 的目录会"看起来没注册"，而不是"我们不送它"）；缺行清单的
preset 上还会直接把会话打挂。收窄落在装配投影与执行 guard 上（[`scope.ts`](../../src/scope.ts)）就够了：模型看到
什么由投影决定，越界调用由 guard 拒掉。

### 代价（实测数字）

真装配（真 `Loader` + 真 registry + 官方 `standard` 同形行 + 真 fs 与 skill 注册表），`chat` 会话，3 个 turn × 每 turn 1 步：

| 观察                                                     | 结果                                                             |
| -------------------------------------------------------- | ---------------------------------------------------------------- |
| 每步 fs 读 `AGENTS.md`                                   | **1 次**（官方每步重算 desired；我们只是把结果丢掉，不省这次读） |
| 每步 fs `stat`                                           | 首次 19 次，之后每步 6 次（官方自己的发现开销，与是否丢弃无关）  |
| `agent.inbox.nextStep`                                   | 每步 **0**（没有攒着下一步再来的条目）                           |
| 会话日志里的 `agent-instructions` / `skill-catalog` 条数 | **0**（丢在注入之前，不是"注入了再删"）                          |
| 技能注册表（`ctx.tools.get("skill", agent)`）            | 仍可见（我们没动注册表）                                         |

no-step turn（本步没有认领到任何用户消息）是个例外形状：官方此时把待送内容记进 `inbox.nextStep`（实测 1 条），
下一步认领时被我们丢掉、inbox 归零——**不积压，但会延后一步**。同一 turn 内连跑 3 步同样每步各付一次 fs 读。

## 取舍

| 选项                                                   | 为什么否掉 / 为什么留                                                                                                  |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 在技能注册表上按名摘除（或遮蔽）provider               | 没有这样的入口：`registerProvider` / `register` 只返回自己那份的 disposer；`list()` 的结果没有任何钩子可挂             |
| 只拦 `skill` 工具、目录照旧列                          | 模型会去调一件永远拒它的技能：多一次白跑的调用，还把"这技能在哪"的错判带进后续步骤                                     |
| **目录消息删行 + `skill` 参数被判（现行）**            | 收的正是"模型看到什么、能加载什么"；两处同一个集合，不改注册表、不动别人的行                                           |
| `tools.restrict({ deny / allow })`                     | 改注册表：触发 `tools/change`、让按注册级判定的官方目录失真、缺工具的 preset 上抛（见上表）                            |
| 在装配投影上丢（`system-prompt/assemble`）             | 那两条注入不是 section：它们只在 `agent/pre-step` 的消息表里出现，装配期根本没有它们的影子                             |
| 让官方行自己按模式关（改 preset 的行清单 / 传 config） | 那是**会话挂着的 preset** 的事（用户在官方 roster 里选的），模式不该改别人的行；行清单里也没有"按模式开关"这一栏       |
| 站到官方行内层、在 `next()` 之前或之后就近处理         | 内层拿不到外层 append 的条目（实测：去掉 `prepend` 后"preset 先装"那一档 3 条用例红）                                  |
| **`prepend` + `await next()` 之后过滤（现行）**        | 只看最终消息表，不关心谁先注册；丢掉的是"这一步要送什么"，不动任何注册表与别人的行                                     |
| 开关为 `true` 时也走一遍过滤（写成"照内容判要不要"）   | 判据会从"模式定义说什么"漂成"这条消息长什么样"：官方的增量与首次注入要靠读它的正文才分得清，而 `true` 本来就该原样放行 |
| `skills` 只做显式开关（不推导）                        | 本部署两个模式就得各写一遍：`coding` 要写 `true`，而它连 `allowTools` 都没写——"全部工具"里显然含 `skill`               |
| 把 `skills` 并进 `instructions`（一个开关管两条面）    | 工具收窄但目录照旧列是个合理形状（`skills: true` 压过推导），合成一个开关就表达不了                                    |
| 丢掉后再把官方那条从 inbox 里清掉                      | 官方的 inbox 归它自己管（`syncInbox`）；实测不积压（下一步认领时自然被丢），多一处清理只会多一份对上游私有状态的假设   |

## 验证判据

[`preset-plane.spec.ts`](../../src/__tests__/preset-plane.spec.ts)（真装配，两种装配顺序各跑一遍）：

- **成对**：`chat` 的 `agent-instructions` 与 `skill-catalog` 都不进（`coding` 那边两条都在——官方 `agent-instructions`
  一条、官方目录一条；成对判据让"把两条面全局关掉"这种实现也过不了），而 `coding` 那两个**注入面**开关
  `instructions` / `skills` 都缺省为要，所以那边断言的正是"开关为 `true` 时零干预"这一侧：注入与没有本行时一样；
- `chat` 的 `skill` 不在模型目录里，真调用被收口拒（文案带模式名）；
- **连续三步稳定**：每步都丢掉、`inbox.nextStep` 每步为空、日志里这两类一条都没有；
- **`skills` 推导与显式值**：`coding`（不写）→ 目录在；`chat`（三件）→ 目录不在；推导的减法那一半也成对钉住
  （名单留空 + `denyTools: [skill]` → 目录不注入，而同一条路上的工作区指令照旧进）；显式 `skills: true` 时名单里没有
  `skill` 也照显式值办（目录在），而工具面照旧按名单收窄。
- **技能名单三条**：黑名单（被拒那件从正文与 `source.entries` 一起消失，其余技能照旧；另一份没配名单的定义里两件都在）
  与白名单（名单外的技能同样收掉，`skill` 工具加载它按"白名单外"拒）；行形状漂移那一条（认不出行的目录消息整条不动、
  告警点名）——去掉 `if (missing.length > 0) return undefined` 这条会红（实测）。

单元层（[`scope.spec.ts`](../../src/__tests__/scope.spec.ts)）：收口本身的工具面行为（白名单 / 黑名单合成、换一份收回旧 guard、
开关拨给通道、动态快照只覆盖本会话）。工具说明那一侧读不到这些开关的代价在
[`tool-guidance` 的设计](../../../dsh-tool-guidance/.agents/designs/20260929-工具说明与用法分组的送达.md)里。
