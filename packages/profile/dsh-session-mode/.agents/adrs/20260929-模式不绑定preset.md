# 模式不绑定 preset

状态：已采纳（部分取代 [ADR-选模式就换preset](./20260928-选模式就换preset.md) 的**适用范围**：机制照旧，本部署不再走它）

背景：模式声明的 preset 白名单（`config.modes.<id>.presetsOnly`）表达的是「这个模式允许挂哪些行清单」；本部署三个
模式都留空，也就是**允许挂任意一份**。单个 `preset` 字符串那种形状（现在写它就是装配期拒绝的退役键）把模式与
preset 强绑：会话一旦挂着官方 preset（用户在 roster 里选的），切模式就会把 preset 拽回模式写死的那份，**覆盖用户对
行清单的选择**；模式本身其实不需要这份绑定——`allowTools` 收口、persona、三个开关都是会话级的，不认 preset。

实测（真装配：模式不留白名单 + 会话挂官方 `standard`）确认了边界：persona 注册在 agent scope，preset 是它的**父**层
（`standingMountFor`：agent key 的父是 preset key），所以我们的 persona 遮蔽上游那份；`allowTools` 收口在装配期
过滤工具与 `tool:<名字>` section、执行层加 guard，与 preset 无关；`runtimeContext: false` 用
`systemPrompt.suppressRuntimeContext()`，按 scope 链判「有没有抑制器」，也成立。

原本唯一不成立的是 `instructions: false`：那时它只关**我们通道**这一侧，而官方 `standard` / `ptc` / `cordis` 自带
上游 `agent-instructions` 行（在 `agent/pre-step` 里自行 append，不经通道）——这正是 ADR-选模式就换preset 当初换
preset 的理由。现在这一条也收住了：官方那两条注入面（`agent-instructions` 与 `skill-catalog`）由收口在
`agent/pre-step` 上按 `instructions` / `skills` 丢掉，代价是官方每步仍重算一次要送的内容（结果被丢掉），见
[设计 抑制官方注入面](../designs/20260929-抑制官方注入面.md)。

**决定**

`config.modes.<id>.presetsOnly` 是一个**可选白名单**（`string[]`，schema 默认空数组），本部署三个模式都不写它
（行 config 里没有这个键）：**留空 = 不限制**，选模式不换 preset，行清单归会话挂着的那份。写了的时候切模式把会话
那份**落进名单**：已经在名单里就原样不动，否则换成名单里的**第一个**（几个模式可以共享同一份名单）。

- 「允许哪些」是配置层要表达的东西，「落哪一个」是切换动作的结论，两者都在 `SessionModes.select` 一处收口
  （`src/index.ts` 的 `presetTarget`）。
- 候选在页面侧由部署 registry 给（`remote.agentPresets.list()` 登记成具名源 `agent-presets`，schema 上
  `role('select', { source })` 认领）：写名单不必手抄 id。
- 退役的单个 `preset` 还配着值就**拒绝装载**（`configProblem`）——它在新语义下不再生效，静默失效比报错更坏。

行清单的来源仍是会话挂着的 shipped preset——registry 的 `default` 由官方 web-app 给（`standard`），本部署不再自建、
也不再覆盖它（[ADR-不再持有行清单](../../../../bundles/session-mode-profile/.agents/adrs/20260929-不再持有行清单.md)，
那份自建的 `mode-switch` 与它的行数据已删除）。

**考虑过的选项**

- **把 upstream 注入面留在会话级收口之外**（换 preset 或让 preset 的行清单替我们关）：那会覆盖用户在官方 roster
  里选的行清单，而且"按模式开关"不是 preset 的行清单能表达的东西。**改走**：在 `agent/pre-step` 外层（`prepend`）
  丢弃上游注入的消息——见 [设计 抑制官方注入面](../designs/20260929-抑制官方注入面.md)。
- **只给 `chat` 写名单、`coding` 留空**：名单是"这个模式允许哪套行"的声明，两个模式的差异本来就不用行清单表达
  （共享一份是刻意的），只给一个写只会让 chip 的行为在两者之间不一致。
- **不在名单里就拒绝切换**（保住"用户选的 preset 绝不被动"）：那会让"会话挂着一份名单外的 preset"变成**换不了模式**
  的死局，用户得先去官方 roster 换 preset。**改走**：落进名单的第一个——切换动作总有一个确定落点，而用户在名单内的
  选择照旧不被覆盖。
- **保留单个 `preset` + 给它候选**：表达不了"这个模式允许几份"，而"允许几份"才是配置层真正要写的东西。
- **连自己那份 preset 一起删掉**（行清单全交官方 shipped preset）：汉化 guidance、plan-mode 中文契约、subagent
  换实现、各工具行的 `config` 调参、先读后改豁免全随行丢失；host 平面又补不了（官方已把这些行 `disabled`，且
  `validatePresetPlaneSeparation` 校验一行只属于一个平面）。

**后果**

- 选模式**不换 preset**（本部署三个模式都留空名单）：`SessionModes.select` 里那段换 preset 的代码只在名单非空时
  才走。官方 roster 选的那份 preset 不再被 chip 覆盖；反过来，名单非空的部署里，落在名单内的选择也不被覆盖。
- 代价照实：官方那两行每步仍会重读 `AGENTS.md`、重算要送的消息（我们只是把结果丢掉），`tool-guidance` 的常驻正文
  也读不到模式开关（它按"常驻就是常驻"定义自己）。模式描述与 README 按这个口径写。
- 行清单里没有的工具照旧"收口时自动跳过"：`chat` 的三件在官方 `standard` / `ptc` / `cordis` 上都齐（那三份都有
  `tool-web` 与 `tool-ask-user`），在官方 `minimal` 上一件都不剩。
- 子代理的中文回报指引**不限 preset**：装配里不传 `localizedReturnGuidancePresets`（不配名单 = 官方四个 shipped
  preset 与还没绑 preset 的会话都用我们的中文文案），判据是 `patch.spec.ts` 里那一行没有 `config`；要按 preset 或按
  模式收窄得改 `@morlay/dsh-subagent` 那一侧，这次不动。
- 判据：`preset-plane.spec.ts`（模式留空名单时切模式一次 `recompose` 都不发生 + 官方 `standard` 会话里切 `chat`
  仍收成三件、官方两条注入面成对（chat 都不进 / coding 都在）+ 真 `fs-observation-policy` 行上成对判 policy 拦截）、
  `session-mode.spec.ts`（空名单不碰 registry、当前那份不在名单里就落第一个、名单内的选择不换、退役 `preset` 拒绝装载）、
  `patch.spec.ts`（渲染出的三个模式都不带 `presetsOnly`、装配里不再有 agent preset 行）。
