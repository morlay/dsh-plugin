# 模式的角色与默认模型

状态：已采纳（2026-09-23）

会话模式原本只有一件事：提示词 + 一组能力开关。现在它多两个面——**谁是它的用户**（`role`）与**它默认用
哪个模型**（`defaultModel`）——外加子代理那边的**继承**规则。三件事一起定，因为它们的判据互相牵制。

## 考虑过的选项

- **`role` 只当 UI 过滤用**：那它就该叫 `hidden` 之类；实际语义是"谁能用这个模式"，`main` 是用户选择器，
  `subagent` 是将来"指定 mode"的候选集。缺省给 `["main"]`——没写角色的模式悄悄变成子代理候选是本末倒置。
- **`defaultModel` 写成会话事件（`model/selection`）**：那样它会变成"这个会话的模型选择"，与用户在设置里选
  的那份混成一件事，部署改默认也对已有会话失效。**否**：它是配置事实，只在会话尚无模型事实时兜底。
- **`defaultModel` 无条件覆盖请求路由**：会抢用户的选择（`modelSelection.pending`）与会话已跑过的历史模型
  （`request/header`）。**否**：兜底条件定为"两样都没有"。
- **子代理按 `role: subagent` 选模式（指派）**：需求方明确"暂时不做指派"。**否**：先做继承 + 留接缝。
- **子代理不继承父模式**：那每个子代理都掉回部署默认模式，父子在同一个任务里跑两套工具与提示词。
  **否**：默认继承父当前模式。
- **继承时校验父模式的 `role`**：让 `subagent` 角色成为继承白名单，父在 chat 里派发的子代理会掉回默认。
  **否**：继承不看角色，`subagent` 只表示"可被指定"。
- **继承只改内存、不写日志**：恢复与 fork 会丢掉继承结果，子代理重新变成默认模式——模式决定工具与提示词，
  这条事实必须能重建。**否**：继承写子会话的 `session-mode/selected`（与用户切换同一条通道）。

## 后果

- `select`（用户侧、要求空白会话）与 `applyTo`（内部侧、只要求活着的 agent）是同一条应用路径的两个入口；
  `applyTo` 同时是**将来"指定 mode"** 的接缝，`modesFor("subagent")` 是它的候选集。
- 装配期校验多了三条：`role` 非空、`default` 必须是 `main`、`defaultModel` 要么不写要么 provider + model
  都给全。写错在装载时就失败，不留到某个会话装配时。
- `defaultModel` 依赖上游 `agent/request` 与 `modelSelection` 投影：前者是 `@deepseek-ai/dsh-agent` 的事件面，
  后者由 `@deepseek-ai/dsh-api-session-controller` 声明——**那一行可能没装**（headless 部署），此时按"没有
  用户选择"处理（兜底生效）。
- 已知的未做项：按角色指派 mode、模型侧/配置侧指定 mode 的入口。判据与接缝写进
  [设计 会话模式](../designs/20260924-会话模式.md)。
