# 模式默认模型搬到顶层 volatile 字段

状态：已采纳（2026-09-25）

背景：`@morlay/dsh-session-mode` 的「某个模式默认用哪个模型」原本住在 `config.modes.<id>.defaultModel`
（[ADR 模式的角色与默认模型](./20260923-模式角色与默认模型.md)）。这一轮要给它做**设置页**：让用户在
Plugins 页那张卡片里给每个模式配默认模型。

**决定**

模式的默认模型是 config 的**顶层** `models`（模式 id → `{ provider, model, reasoningEffort? }`），标成
`volatile`；`SessionMode.defaultModel` 删除，`modes.<id>` 里不再有它。

**考虑过的选项**

- **留着 `modes.<id>.defaultModel`，设置页照样编辑它**：设置面（settings 的 `describe()`）只把
  **volatile** 字段挑成可编辑字段（`volatileForm`，`vendor/deepseek-harness/packages/settings/settings/src/schema.ts:37`），
  而 schemastery 的 `validateVolatileSchema` 把 `z.dict` 的 inner 一律当 blocked
  （`vendor/deepseek-harness/vendor/schemastery/src/index.ts:489`）——dict 内部的字段标 volatile 会在解析时
  直接抛错，不标就永远不进设置面。**否**：那条路不通，不是取舍问题。
- **`modes` 整体标 volatile**：那么模式清单（名字、提示词、工具白名单）也成了运行期可改的字段，设置面会给出
  一份改装配数据的通用表单——"改模式清单"这件事我们一直拒绝（见设计 会话模式「取舍」）。**否**：把
  装配事实与运行期事实混成一份。
- **另外开一个 settings namespace（如 `session-mode-models`）装这份映射**：多一个命名空间、多一个行 id 的
  映射表，而配置本体仍得有一份装配层的默认值——两份 home。**否**：单一 home ——运行时读的就是设置页写的那个
  字段。
- **`models` 用 `z.array`**：数组元素不能标 volatile（同样 blocked），且"模式 id → 模型"用映射表达更直接。
  **否**：形状不对，还踩同一条限制。

**后果**

- 设置面能编辑它：settings 的 `volatileForm` 挑出 `models` 这个节点（它是 volatile，路径固定），
  写路径是 `['models', <模式 id>]`（`isVolatilePath` 在 volatile 节点之下继续放行）。
- **装配默认（`cordis.patch.yml` 的 `config.models`）与用户在设置页写的值不是两份配置**：settings 的
  `base`（装配层）与 `user`（设置文档）由它自己的分层叠出同一个字段，运行期读到的仍是一处
  ——`config.models.get()[<模式 id>]`。清空（`{ op: 'unset' }`）回到装配层那份，没有装配层就跟着全局
  `agent-default-model`。
- 它是 volatile **引用**，读的地方必须现场 `.get()`（设置页保存只换引用里的值，这行不重挂）——与
  `llm-openai-compatible` 读 `config.providers` 同一种读法
  （`packages/llm/llm-openai-compatible/src/index.ts:415`）。
- 迁移不破坏任何现有配置：迁移前没有任何部署配过 `defaultModel`（`tool/modes.ts` 里没有，profile 的用户层
  也没有）。`tool/modes.ts` 的 `MODE_MODELS` 是新的真源，当前是空对象。
- 校验跟着挪：`models` 的键必须在 `modes` 里、每条都要给全 `provider` 与 `model`，装配期直接拒绝装载
  （孤儿键是一条"配了但永远不会生效"的配置，不能留到运行期）。
- 代价：`SessionMode` 少一个字段、config 多一个顶层字段；模式定义本身不再自洽地说"我默认用哪个模型"，
  要跨一步看 `config.models`。卡片是按模式列行的，这一步由页面承担。
