# 默认模型住在模式定义里

状态：已采纳

背景：设置面只把 **volatile** 字段挑成可编辑字段，而 schemastery 的 `validateVolatileSchema` 不许 dict 内部再标
volatile（`vendor/deepseek-harness/vendor/schemastery/src/index.ts:488`）。"某个模式默认用哪个模型"因此要找一处
既能上页面、又能跟着模式走的位置。

**决定**

`modes.<模式 id>.defaultModel?: { provider, model, reasoningEffort? }` 是**模式自己的可选字段**：

- 省略就跟全局 `agent-default-model`；
- 只在会话**尚无模型事实**（投影 `modelSelection` 没有 `pending`、`session.requestHeader()` 还没落）时接管请求
  路由，用户选过或会话跑过请求就不再插手；
- 它是**配置事实**，不写会话事件：重启后仍由 config 决定，会话级那次选择才是会话事实。

**考虑过的选项**

- **顶层 `models`（模式 id → 模型）单独标 volatile**：schemastery 拒"volatile 套 volatile"，而路径固定的 volatile
  又只能覆盖 `models` 整段（dict 内部的字段一律 blocked）。**否**：`modes` 本身整段 volatile，模式内的
  `defaultModel` 作为它下面的普通字段自然跟着上页面——它自己不必、也不许再标一层。
- **`provider` / `model` 在 schema 上声明成 `required`**：会让"模式里根本没写 `defaultModel`"也被判成缺值。
  **否**：成对校验交给装配期的 `configProblem`。
- **`defaultModel` 用默认 `{}` 而不是 `.default(null)`**：schemastery 对缺省的对象字段会造一个空对象，那样每个
  模式都会凭空多出一行。**否**：给 `null` 让这个键保持缺失，页面按「非必填」处理（从候选里加成）。

**后果**

- 模式定义自洽：清单里每个模式说清自己的提示词、工具与默认模型；"配了模型但模式不存在"这类孤儿配置不再可能
  ——顶层 `models` 仍声明，但只做一件事：装配期看见它还配着值就报错，提醒挪进对应模式（它 `hidden()`，页面上
  不出现）。
- 生效方式与其它 volatile 字段一致：设置页保存会让这一行重挂（`reconcileProfilePatches`），新定义随重挂生效。
