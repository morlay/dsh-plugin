# 默认模型住在模式定义里

状态：已采纳（2026-09-25）

`@morlay/dsh-session-mode` 的「某个模式默认用哪个模型」是**模式自己的可选字段**：

- `modes.<模式 id>.defaultModel?: { provider, model, reasoningEffort? }` —— 省略就跟全局
  `agent-default-model`；只在会话**尚无模型事实**时接管请求路由（用户选过、或会话已落过 header 就不再插手）。
- 它是**配置事实**，不写会话事件：重启后仍由 config 决定；会话级那次选择才是会话事实。

**为什么可以住在这里（设置面能编辑它）**

设置面只把 **volatile** 字段挑成可编辑字段，而 schemastery 的 `validateVolatileSchema` 不许 dict 内部再标
volatile（`vendor/deepseek-harness/vendor/schemastery/src/index.ts:488`）。这条限制并不挡现在这个形状：
**`modes` 本身就是 volatile**（模式清单要在页面上编辑），整棵子树因此都在设置面的投影里，
`defaultModel` 作为它下面的普通字段自然跟着上页面——它自己不需要（也不许）再标一层 volatile。

**代价与选择**

- `defaultModel` 用 `.default(null)` 而不是默认 `{}`：schemastery 对缺省的对象字段会造一个空对象，那样每个模式
  都会凭空多出一行；给 `null` 反而让这个键保持缺失，页面按「非必填」处理（从候选里加成）。
- `provider` / `model` 在 schema 上**不是** `required`（缺省的那一半由装配期的 `configProblem` 报错拦下）：
  写成 `required` 会让"模式里根本没写 defaultModel"也被判成缺值。
- 退役的顶层 `models`（模式 id → 模型）**仍然声明**，但只做一件事：装配期看见它还配着值就报错，提醒挪进对应
  模式——否则一份"看着像配过"的配置会静静地失效。它 `hidden()`，页面上不出现。

**后果**

- 模式定义自洽：清单里每个模式说清自己的提示词、工具与默认模型；"配了模型但模式不存在"这类孤儿配置不再可能。
- 生效方式与其它 volatile 字段一致：设置页保存会让这一行重挂（`reconcileProfilePatches`），新定义随重挂生效。
