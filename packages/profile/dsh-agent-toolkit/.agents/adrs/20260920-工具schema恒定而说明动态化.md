# 工具 schema 恒定而使用说明动态化

状态：已采纳（实施于 [`guidance` 出口](../../README.md)，设计与取舍见 [设计 工具用法分组](../designs/20260921-工具用法分组.md)）

背景：实现"工具按需注入"有两条路——**裁剪 `tools` schema**（会话内动态增删 / 改序 / 改描述）与
**动态化使用说明**（schema 恒定，变化只走提示）。两者都能表达"当前能调用什么"，但缓存代价差一个量级，
而这个差别不能靠读代码推断（上游只给了一句定性表述：_"A schema or composition change invalidates reuse
from the first altered request token."_），必须实测。

**实测（DeepSeek，2026-09-20）**

实测方法：固定一份冷前缀，逐步发同一会话的请求，只读用量里的缓存命中 token 数；下表是
13 个 case × 5 步的对照（每个 case 都从冷前缀起跑，步与步之间只有该 case 声明的扰动）。

| case                                             | #2 基线命中 | #3 扰动后  | #3 残留 tokens |
| ------------------------------------------------ | ----------- | ---------- | -------------- |
| 对照·全程不带 tools                              | 95.7%       | 95.7%      | 3456           |
| 对照·tools 逐次不变                              | 94.0%       | 94.0%      | 3712           |
| 描述改一个句号 / 描述末尾加空格 / 参数描述改标点 | 94.0%       | **3.2%**   | 128            |
| parameters 加一个可选属性                        | 94.0%       | **3.2%**   | 128            |
| 交换两个 tool 的顺序                             | 94.0%       | **0.0%**   | 0              |
| 末尾追加 tool / 最前插入 tool / 删掉一个 tool    | 94.0%       | **0~3.2%** | 0~128          |
| 标尺·只改 messages 末尾                          | 94.0%       | 93.8%      | 3712           |
| 标尺·只改 user 段开头                            | 94.0%       | 6.5%       | 256            |
| 标尺·只改 system 文本末尾一个标点                | 94.0%       | **0.0%**   | 0              |

三条事实：

1. **与扰动大小无关**：改标点、加空格、加参数、换顺序、增删 tool——八种扰动结果一致，"加一个空格"
   与"删掉一个 tool"等价。
2. **tools 排在 system 文本之后、全部 messages 之前**：三个"标尺"case 把位置读出来——只动 messages 末尾
   仍命中 93.8%（残留 3712），只动 user 段开头残留 256（system 段保住），只动 system 末尾残留 0（比 tools
   更靠前）。prompt 顺序 ≈ `固定模板 + system 文本 → tools → messages`，所以 tools 一变，其后全部
   messages 一起失配。
3. **代价是一次性的，且不清旧档**：再发同一个新 schema 立刻回到 94%~96.6%（新 schema 自己也落盘）；
   切回旧 schema 同样 94%（旧缓存没被变体清掉）。**但工具集若持续抖动，命中率恒为 0**，等于每发全量重算。

**决定**

1. **`tools` 参数在会话内恒定**：不增删、不改序、不改描述文本。本仓库的"短描述压缩"因此实现为
   **装配投影里的固定映射**（同一工具永远映射到同一短描述），而不是会话内可变的东西。
2. **按需能力只改使用说明**，且说明必须走 **append 通道**（`<system-reminder>` user 消息，紧随用户消息），
   不改 system prompt 文本——标尺 case 显示 prompt 前部的任何改动代价都最彻底。
3. **未启用的能力用执行层拒绝兜住**（`tools.guard` + 能力目录标注），而不是把它从 schema 里拿掉。

## 考虑过的选项

- **按需裁剪 catalog**（`tools.restrict({ allow })`）：每次切换都命中一次"schema 扰动"档，等于一次
  全量重算，代价随会话历史增长。
- **就地改写 system prompt 里的使用说明**：位置比 tools 还靠前（只改末尾一个标点就是 0%），
  比裁剪 schema 更差。
- **不做任何动态化**（全量 schema + 上游长描述）：实现最省事，但常驻 token 与注意力占用最大，
  且放弃了"按需"本身。

## 后果

- **说明变化零重算**：`tools` 与 system 文本都不变，只有 append 的说明消息推进历史。
- 代价换成常驻开销：全部工具 schema 一直在请求里（用一行中文短描述压住描述段），以及"模型看得见未启用的
  工具"——由 guard 拒绝与能力目录的状态标注兜住。
- **约束**：工具集变化只允许发生在装配期（重启生效）；使用说明只能整段追加 / 更新（走 reminder），
  不能就地改写 prompt 前部。
- 同类风险：改 system 文本、settings 文本同样让缓存全废且更靠前；任何"就地改写 prompt 前部"的改动
  都要先过这条 ADR。
