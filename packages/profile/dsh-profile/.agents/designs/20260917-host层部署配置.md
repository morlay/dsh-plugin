状态：已实现。行清单是 [`tool/patch.ts`](../../tool/patch.ts)，生成物是包根的 `cordis.patch.yml`。

> 现状（2026-09-23）：本层已收缩成**配置初始化**——patch 里只有按 id 的 `config` 覆盖，禁行/插行交给各能力包
> 自己的 bundle（`@morlay/dsh-sandbox-local`、`@morlay/dsh-web-search-ollama`），app 的 `dsh.profile.bundles`
> 把它们排在本包之前。分工见 [ADR profile 层三分](../../../../../.agents/adrs/20260923-profile层三分（配置初始化与提示词开关与能力清单）.md)。
> 下面这份设计里"按 id 禁用上游行"等段落描述的是收缩之前的形态。


范围：`packages/profile/dsh-profile/` —— **部署级**（与模式无关）的 host 配置：llm 路由、搜索后端、进程沙箱，
以及"哪些上游 host 行不动"。**模式装配**（`coding` / `chat` 的行清单、persona、注入通道）在
[`@morlay/dsh-agent-preset`](../../../dsh-agent-preset/README.md)——那里另有设计文档与 ADR。

约束：不放宽「上游代码不可修改」——只把上游 composition 当数据读、只 patch 装配行。

## 结论摘要

| 议题        | 结论                                                                                                     | 一句话理由                                                                                                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| patch 层级  | 全部装配放本 bundle 的 patch，不用 app 的 patch                                                          | bundle patch 在 dev（web / desktop）与打包形态都生效；app 的 patch 只在打包时作为 seed 的 profile patch 生效                                                                    |
| llm 路由    | `llm-pi-ai` 加 ollama provider，显式只写偏离上游默认的那一项（`requestImageMaxBytes: 2 MiB`）            | pi-ai 的"每张请求版本原始字节目标"默认 1 MiB，llm-deepseek 是 2 MiB，不对齐等于悄悄发更小的图                                                                                   |
| 搜索后端    | 自写 `@morlay/dsh-web-search-ollama`（直连 `POST /api/web_search`），`web` 行切 `searchProvider: ollama` | 上游那条 Messages 后端实测被 Ollama 降级成客户端工具、不执行搜索（上游只认 `web_search_tool_result` 块）                                                                        |
| 沙箱        | 禁用官方 `sandbox` / `fs-sandbox`，插入 `@morlay/dsh-sandbox-local` 并给 `access` 规则                   | 官方策略只有 mode / workspaceRoot，可写路径硬编码，追加可写根与拒绝项没有配置面                                                                                                 |
| office 转档 | **不禁用**官方 `office-to-pdf` 行                                                                        | 它是上游原味能力（Sidebar 的 Office 预览可用）；禁用是"本部署不启用某能力"的全局动作，收益只是省一个后端                                                                        |
| 首次引导    | 覆盖 `ui-settings-general` 行的 `welcomeNoticeVersion` 为上游当前版本                                    | 桌面形态的 client 不是 loopback（自定义 scheme），上游按 `ctx.remote.$host.isLoopback` 决定 settings 持久化——非 loopback 一律 `memory`，「确认过」写不回 host，于是每次打开都弹 |
| 上游两行    | **不再**按 id 禁用 `agent-instructions` / `tool-skill`                                                   | 上游 web-app bundle 自己已把它们设在 preset 平面（本地发现与工具归 preset），host 再禁一次是重复动作                                                                            |

## 事实基线

### patch 层级与放置

patch 层按 `[bundle patches, profile patches, home patches, overlays]` 合并，后应用者整块替换同一行的
`config`：

| 载体                                                                          | 生效范围                                              |
| ----------------------------------------------------------------------------- | ----------------------------------------------------- |
| profile 的 `cordis.patch.yml`（`$DSH_HOME/profiles/<name>/cordis.patch.yml`） | dev 与打包形态都生效，但只属于本机 home               |
| app 的 `cordis.patch.yml`                                                     | 打包（`bundle`）形态：作为 seed 的 profile patch 生效 |
| 一个自有 bundle 的 patch                                                      | 所有形态（随包分发）                                  |

`config` 替换是**整体替换、不是深合并**（`applyEntryPatches` 对同 id 行做 `target[key] = value`），所以覆盖
`web` 行时必须把 `fetchProvider` 一起写全，否则抓取后端凭空消失——`patch.spec.ts` 用上游自己的
`applyEntryPatches` 组合 base + 本 patch 来断言这一点。

### 沙箱

官方沙箱策略只有两个字段：`mode`（`read-only` / `workspace-write` / `danger-full-access`）与 `workspaceRoot`；
`workspace-write` 的可写路径是硬编码的 `[工作区, /tmp, os.tmpdir()]`
（`vendor/deepseek-harness/packages/sandbox/sandbox/src/roots.ts:52-55`），没有追加可写根或拒绝项的配置面。
所以本 bundle 的 patch：

- 按 id 禁用官方 `sandbox`（`ctx.sandbox`）与 `fs-sandbox`（`ctx.fs`）；
- 插入 `@morlay/dsh-sandbox-local`（继承官方实现，只在选中的 runner 参数上追加 `access` 规则），`access`
  就是本包维护的规则文本（`rw /tmp`、`rw {{ env.XDG_* }}`、`-- mise.*.toml`、`-- **/*.pem`）；
- 规则语法与各平台表达能力见 [`@morlay/dsh-sandbox-local` 的 README](../../../../sandbox/dsh-sandbox-local/README.md)。

**为什么住 host**：`sandbox-local` 要覆盖 root realm 的 `ctx.fs` / `ctx.sandbox`，而 agent 的 ctx 解析不到
preset 里 `isolate` realm 的实现（上游为此专门提供 `serviceForAgent` 给 realm 外的读）。同一原因也决定了
"读前置策略"不能在这里禁用——它是模式取舍，由 `@morlay/dsh-agent-preset` 的 `coding` 自己抵消。

### web 搜索后端与图片上限

**搜索**：模型侧的 `web_search` / `web_fetch` 由 preset 的 `tool-web` 行给（host 层的同名行被 web-app
bundle 禁用），而**选哪个后端**由 host 层的 `web` 行决定——base bundle 里写着
`searchProvider: deepseek-official` + `fetchProvider: http`
（`vendor/deepseek-harness/packages/bundle/base/cordis.patch.yml:458-470`）。

**"复用那条 messages 后端、把端点换成 ollama.com" 不成立**——按
[issue #17283](https://github.com/ollama/ollama/issues/17283) 推断过一次可行，真发请求被否：

- `POST https://ollama.com/v1/messages`（body 与上游 provider 完全一致：`tools:[{type:"web_search_20250305",
name:"web_search", max_uses:5}]`、model `deepseek-v4.1-flash`）→ `HTTP 200`、`stop_reason: tool_use`、
  `content` 是 `thinking` + `tool_use`。Ollama 把这个 server tool **降级成普通客户端工具**、不执行搜索，
  要求调用方自己执行后回传 `tool_result`；上游 provider 只认服务端自执行后的 `web_search_tool_result` 块，
  于是报 `WEB_PROVIDER_ERROR`（"returned no web_search_tool_result blocks"）。
- `POST https://ollama.com/api/web_search`（`{"query": …}` + Bearer key）→ `HTTP 200`、
  `{"results":[{title,url,content}]}`。**这才是 Ollama 提供的搜索接口。**

所以自写 [`@morlay/dsh-web-search-ollama`](../../../../web/dsh-web-search-ollama/README.md)（约两百行
provider，直连 `/api/web_search`）：

- **注册行住 host 层**：preset 是每个模式各挂一份 composition，同一个 provider id 注册两次会撞
  `WEB_DUPLICATE_PROVIDER`；`web` 行本来就是 host 行，"选哪个"也只能由这一层决定。
- `deepseek-official` 后端仍在注册表里，改回那一行就是切换（需要 `DEEPSEEK_API_KEY`）。

**真端点的守护**：新包的 `e2e/provider.e2e.spec.ts` 在 `OLLAMA_API_KEY` 存在时真打 `/api/web_search`
（provider 直连一条、装进 `ctx.web` 后选中它再搜一条），key 缺席则整体跳过。它**刻意放在 `src/__tests__/`
之外**（根 vitest 只收 `packages/**/src/__tests__/`），否则环境里恰好有 key 时全量测试会静悄悄打外网：

```sh
mise exec -- pnpm --filter @morlay/dsh-web-search-ollama run test:e2e
```

mock 单测全绿不能替代它：本部署第一版正是"配置指到 Ollama 的 messages 端点"、mock 也全绿，真调用是错的。

**图片上限**：llm 侧有四个旋钮，llm-deepseek 与 ollama 所在的 llm-pi-ai 路由不是同名同默认：

| 层                                         | llm-deepseek                                            | ollama（llm-pi-ai route）                    | 处理                             |
| ------------------------------------------ | ------------------------------------------------------- | -------------------------------------------- | -------------------------------- |
| 上传准入（与供应商无关，attachment-local） | `maxImageBytes` 20 MiB / `maxMessageImageBytes` 200 MiB | 同一份服务，两个供应商共用                   | 不动：单张 20 MiB 与内联预算同值 |
| 请求内联图片预算                           | `maxInlineRequestImageBytes` 20 MiB（base64 长度）      | `maxRequestImageBytes` 20 MiB（base64 长度） | 不写：默认就同值                 |
| 每张请求版本原始字节目标                   | `DEFAULT_REQUEST_IMAGE_MAX_BYTES` 2 MiB                 | `requestImageMaxBytes` 1 MiB                 | **写 2 MiB**：唯一默认不同的那项 |
| 像素预算                                   | 模型级 `imagePixelBudget` 未设（交给 2048² 归一化）     | `requestImagePixelBudget` 2048²              | 不写：默认就同值                 |

只显式写第三项：写同值不改变行为，只是让上游默认一升级这里就不再跟随。

### office 相关

| 内容                                                             | 上游归属                                                                                                                                                                       | 本层能否禁用                                                                              |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `@deepseek-ai/dsh-office-to-pdf`（Office→PDF 转档后端）          | web-app bundle 的 profile 行 `office-to-pdf`（`vendor/deepseek-harness/packages/bundle/web-app/cordis.patch.yml:228`）                                                         | 能，但**不禁用**：上游原味能力，Sidebar 的 Office 预览标签页因此可用                      |
| `@deepseek-ai/dsh-skill-office`（docx / pptx / xlsx 三个 skill） | 桌面宿主命令式装载（`vendor/deepseek-harness/apps/desktop-host/src/office.ts:25`，由 `apps/desktop-host/src/index.ts:69` 在 profile boot 之后 `ctx.plugin(desktopOffice, …)`） | 本层不涉及：不是 profile 行，patch 改不了；桌面形态由 dsh-desktopify 的 host 变体不装载它 |

`@deepseek-ai/dsh-skill-office` 的处置（连同评估并排除掉的七个上游侧口子：命令式装载、空资源、注册表过滤、
禁用 `tool-skill` 行、同名 provider 影子、壳侧不投放资源、环境变量）见
[原设计文档的「office skill 的处置」](../../../dsh-agent-preset/.agents/designs/20260917-预设生成与装配.md)
——结论不变：**不动这些上游面**，桌面化工具侧用自带 host 变体解决（只装载 `workspace-dependencies`、
不装载 officeSkills），桌面里不出现这三个 skill；web / CLI 形态本来就不装载它。

### 禁用 host 行要实测官方 preset

patch 里按 id 禁用的行是**全局**的：官方 standard / ptc / cordis 的 preset 行也活在这份装配里。禁用
`subagent-model-selection-settings` 就是反例——官方那几个 preset 的 `tool-subagent` 行带
`modelSelectionSettings: true`，开关要求 host scope 有 `subagentModelSelection` 服务，禁用即把它们打成
`requires ... in the Host scope`（三个 preset 全 broken）。

所以「我们不用某能力」的正确实现是**自己的 preset 行不带那个开关**（`dsh-agent-preset` 的
`tool-subagent` 行），而不是禁用 host 那行。改完跑 `just profile` 实测，判据见
[本包规范 how-to-verify](./../standards/how-to-verify.md)。

## 取舍

- **沙箱规则放本 bundle 的 patch 而不是示例 app 的 patch**：bundle patch 在 dev（web / desktop）与打包形态
  都会应用，app 的 patch 只在打包时作为 seed 的 profile patch 生效。
- **搜索后端自写 provider，而不是复用上游的 Messages 后端**：真发请求被否（Ollama 只回 `tool_use`、不执行
  server tool）。要让复用成立得有客户端工具回环，那是改上游（红线）；直连 `/api/web_search` 一次 HTTP、
  `max_results` 精确可控。
- **office 转档不禁用**：上游原味能力，且禁用是全局动作（官方 preset 一起失去 Sidebar 预览）；"本部署不装
  某能力"只该针对我们自己的模式。
- **不再重复禁用上游已设在 preset 平面的行**：`agent-instructions` / `tool-skill` / `skill-filesystem` 由
  web-app bundle 自己禁（本地发现与工具归 preset），host 再禁一次只会让"谁在管这一面"变模糊。
- **不放宽 `system-prompt` / `persona` 的部署偏好**：按模式给提示词走各模式自己的 `persona` 行（注册 agent
  作用域同名 section 遮蔽部署级），host 这层不设 persona，也不关 `includeHarnessIdentity` /
  `includeRuntimeContext`——那是所有 preset 共享的部署事实，不该由我们的偏好改写。
