# 工具说明与用法分组的送达（本包的包根运行时）

状态：已实现
范围：`@morlay/dsh-tool-guidance` 的[包根运行时](../../src/index.ts)把工具说明送到模型的**形态**与
**接缝**——工具投影的改写、每组正文的送达方式、上游逐工具说明的处置，以及"哪一侧收窄"。
约束：工具 schema 在会话内恒定（[ADR-工具schema恒定而说明动态化](../adrs/20260920-工具schema恒定而说明动态化.md)）；
上游 `@deepseek-ai/*` 只读；功能行清单归会话挂着的 preset；通道与模式定义分别是
[`dsh-context-assembler`](../../../../context/dsh-context-assembler/README.md) 与
[`dsh-session-mode`](../../../../profile/dsh-session-mode/README.md) 的事——本文只在送达这件事上引用它们。

## 结论摘要

| 议题                  | 结论                                                                                                    | 一句话理由                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 工具描述与参数 schema | 装配**投影**改写：短描述覆盖 `description`、剥掉说明性字段，注册表不动                                  | schema 与短描述都常驻，改投影不触发 `tools/change`                     |
| `base` 组正文         | 本行自挂 `agent/pre-step`，作为一条 user 消息**常驻**送达                                               | 官方注册表只有"按需"一档，通道没有注入扩展点                           |
| 其余组正文            | 注册进官方 `ctx.skills`，目录与加载由官方 `tool-skill` 那一行提供                                       | 技能的官方送达面就是它，本包不自己发目录                               |
| 上游逐工具说明        | `suppressSection` 丢弃，要点吸收进组正文                                                                | 同一份知识只送一次，送的是我们写的那份                                 |
| "首步"的判据          | surface 上同键消息的正文比对，**不用** `step` 号                                                        | 压缩后补发、正文变更重发、重启不重发，三条都是它推出来的               |
| 常驻注入的身份        | 内容块 `<skill_content>`，source kind 用上游 `skill-invocation`，键 = 组名                              | 与按需加载同形态、不新增 source kind、客户端标签直接可用               |
| 正文的工具过滤        | 按**这个会话装配结果里最终可见的工具目录**过滤                                                          | 收窄落在装配投影上、不改注册表；站到装配瀑布最外层才拿得到收窄后的目录 |
| `base` 与官方目录     | **不注册** `base`（避免模型在目录里看到它又去加载一遍）                                                 | 常驻与按需是两种送达，不是两份注册                                     |
| `instructions: false` | **不关**（本行按"常驻就是常驻"定义它，不读那个开关）                                                    | 开关的真源是 `session-mode` 收口的按会话状态，跨包读口是另一笔账       |
| 组数据里的字段        | 身份只有 `BASE_GROUP_KEY` 一处；送达方式与门控都不是数据字段                                            | 没有消费者的字段只会让人以为"改它就能换送达方式"                       |
| policy 拦截           | 归 `session-mode` 的 `modes.<id>.allowPolicies` / `denyPolicies`（policy 名 = 上游 waterfall 名）       | 行清单与豁免政策都不由本包持有                                         |
| chat 的目录           | 默认不注入（`skills` 推导成 false）；显式 `skills: true` 时会列着按需组却加载不了（`skill` 工具被收窄） | 官方目录的判据是注册级工具存在，看不见我们的收窄                       |

## 事实基线

### 本包现在发什么

[`src/index.ts`](../../src/index.ts) 做五件事：装配投影上的改写（`shortenTools` / `slimSchema`）、把每组的
`drops` 交给 `ctx.contextAssembler.suppressSection(...)`、把**按需的三组**注册成官方 skill、把 `base` 组的正文
常驻注入（本行的 `agent/pre-step`）、在装配监听上记下"这个会话最终可见的工具"（本行的
`system-prompt/assemble`；注入的过滤判据就是它，见[接缝设计](#装配目录的记忆)）。行数据（汉化、组表）分族分份住在
[`packs/`](../../src/guidance/packs/index.ts)，汇总与渲染在 [`groups.ts`](../../src/guidance/groups.ts)。
`rows` 出口只发布 [`tool-guidance` 这一行](../../src/rows.ts)（host 平面，装配见
[`session-mode-profile` 的 patch](../../../../bundles/session-mode-profile/cordis.patch.yml)）。

`config.groups` 是**部署级**开关：它只在 `false` 时关掉"用法分组"这一半（本行是 host 平面一行，所有会话共用
一份 config），所以它表达不了"某个模式不要用法正文"。

### 通道只做转换，没有注入扩展点

[`ContextAssembler`](../../../../context/dsh-context-assembler/src/channel.ts) 现在的公开面只剩装配结果
上的文本改写与降级 section 的按步注入：`replaceSection` / `suppressSection` / `isSuppressed` / `replacement` /
`setInstructions` / `collect`（只含降级 section）/ `sync`。**没有**任何"登记内容并让通道按步送达"的入口——
`base` 组正文的常驻送达因此由本行自己实现。

通道仍在系统提示词里常驻一条覆盖规则（[`rules.ts`](../../../../context/dsh-context-assembler/src/rules.ts)）：
"system-reminder 与 skill_content 块…同一条内容的最新一条取代更早的（带 id 的块以 id 为准，其余按来源）"、
"skill_content 是要遵循的技能说明（随请求送来的与你后来加载的一样）"。这条声明由通道的 `keep` 名单保住
（[`defaults.ts`](../../../../context/dsh-context-assembler/src/defaults.ts)），本行的注入不重复解释信封语义。

### 官方 skill 的送达只有一档：目录摘要 + 按需加载

注册面是 [`ctx.skills.register`](../../../../../vendor/deepseek-harness/packages/skill/skill/src/index.ts)：注册项只有
name / description / content / source / invocation / provider，**没有**"常驻 / 自动"这一栏，`content` 是注册时定型的
字符串（不能按会话现算）。注册落在**调用方 ctx 的层**上：host 平面注册即全局，装进某个 agent 的 scope 才只对那个
会话可见（[`skill/src/index.ts:439-467`](../../../../../vendor/deepseek-harness/packages/skill/skill/src/index.ts)；
层解析见 [`index.ts:554-566`](../../../../../vendor/deepseek-harness/packages/skill/skill/src/index.ts)），但可见性只按
**层**分，没有任何"按工具可见性"的过滤谓词。

目录与加载由官方 [tool-skill](../../../../../vendor/deepseek-harness/packages/skill/tool-skill/src/index.ts) 提供：
一条 durable 的 `skill-catalog` 消息（digest 幂等、变更时整份替换，[第 218-250 行](../../../../../vendor/deepseek-harness/packages/skill/tool-skill/src/index.ts)）、
`<available_skills>` 渲染，以及 `skill` 工具（正文用 `renderSkillContent`，带 `<skill_resources>` 段，
[`skill/src/index.ts:170-193`](../../../../../vendor/deepseek-harness/packages/skill/skill/src/index.ts)）。

**目录的开关是注册级判据**：只有 `ctx.tools.get("skill", agent)` 解析到官方那一份注册时才发目录
（[`tool-skill/src/index.ts:220-222`](../../../../../vendor/deepseek-harness/packages/skill/tool-skill/src/index.ts)，
模块注释也写明"a restriction or scoped same-name shadow therefore removes both the schema and its call guidance"）。
我们不用 `tools.restrict`，收窄发生在装配投影上，所以这条判据在 chat 里照样为真——只是 chat 的目录注入被
`skills: false` 丢掉了（见"代价清单"）。

### 会话收窄落在装配结果上，不在注册表上

[`@morlay/dsh-session-mode`](../../../../profile/dsh-session-mode/README.md) 的收口
（[`scope.ts`](../../../../profile/dsh-session-mode/src/scope.ts)，模式行内部持有）把模式的 `allowTools` 落在两处：
`system-prompt/assemble` 里过滤 `assembly.tools` 与 `tool:<名字>` section、执行层 `tools.guard`（挂在
`agent.ctx` 上，拒绝时给该模式的文案）。收窄的那份状态是它私有的（`applied` 是 `WeakMap`），`instructions` 开关
也只是拨给通道的 `setInstructions`，另两条注入面（官方 `agent-instructions` 与 `skill-catalog`）由它在
`agent/pre-step` 上丢。所以**本行读不到"这个会话要不要 instruction / 技能目录"**（那两处状态都是私有的）——
这是下面几个取舍的根。

"这个会话能用哪些工具"本行反过来**读得到**，而且不必去问收口：收窄的结果就摆在装配结果上——本行用 `prepend`
站到装配瀑布的**最外层**（收窄的那条监听注册得比本行早，瀑布里先注册的是外层，它过滤 `tools` 发生在它自己的
返回路径上），`next()` 之后拿到的 `result.tools` 就是这个会话最终可见的目录（见
[装配目录的记忆](#装配目录的记忆)）。

`chat` 模式就是这种形态：白名单只有 `ask_user_question` / `web_search` / `web_fetch`，并且
`instructions: false`、`runtimeContext: false`（`skills` 不写 → 按这三件名单推导成 `false`，
[`mode-sources.ts`](../../../../profile/dsh-session-mode/src/mode-sources.ts)）。

### `agent/pre-step` 的时机

每步一次，且**先装配再走这条瀑布**：`preStep()` 里 `systemPrompt.assemble(...)` 之后才
`dispatch.waterfall('agent/pre-step', { messages, turn, step, signal })`
（[`core/agent-loop/src/agent.ts:267-283`](../../../../../vendor/deepseek-harness/packages/core/agent-loop/src/agent.ts)，
事件签名见 [`core/agent/src/runtime-types.ts:320`](../../../../../vendor/deepseek-harness/packages/core/agent/src/runtime-types.ts)）。
`step` 是 **turn 内**的计数（每个 turn 从 1 起），`turn` 是会话内累计——所以"首步"不能用 `step === 1` 表达。

瀑布是"最先注册的在最外层"：外层在 `await next()` 之后改消息，落点因此靠后
（[`cordis/src/events.ts:234-243`](../../../../../vendor/deepseek-harness/vendor/cordis/src/events.ts)；官方
`tool-skill` 的两条监听就靠注册顺序把目录放在技能正文之前）。本行的落点不依赖别人的注册顺序（见接缝设计）。

首试才落盘：`step()` 里 `if (firstAttempt)` 才把 `decision.messages` 追加进会话
（[`agent.ts:419-423`](../../../../../vendor/deepseek-harness/packages/core/agent-loop/src/agent.ts)），
同一步内的失败重试不重跑 pre-step（[`agent.ts:494-509`](../../../../../vendor/deepseek-harness/packages/core/agent-loop/src/agent.ts)）。

### 送达矩阵

| 内容                                                | 形态                                                                       | 由谁送达                                        | 会话相关吗                                                               |
| --------------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------ |
| 工具 `description`                                  | 装配投影里的一行中文（`SHORT_TOOL_DESCRIPTIONS`）                          | 本行的 `system-prompt/assemble`                 | 是：收窄行在同一条瀑布里过滤工具（过滤与映射可交换，谁先谁后不影响结果） |
| 工具参数 schema 的 `description`/`title`/`examples` | 投影里连键都不留；`type`/`enum`/`required`/`default` 照旧                  | 同上                                            | 同上                                                                     |
| `base` 组正文                                       | 一条 user 消息（`<skill_content>` 内容块），常驻且幂等；正文按装配目录过滤 | **本行自挂 `agent/pre-step`**                   | 是：这个会话最终可见的工具才出现在正文里                                 |
| `flow` / `delegation` / `team` 组正文               | 官方 skill：目录一行摘要常驻、正文按需                                     | 本行注册进 `ctx.skills`，官方 `tool-skill` 发布 | 否：`ctx.skills.register` 是装配期一次                                   |
| 上游逐工具说明 section（`tool:read` 等）            | 丢弃（`suppressSection`）                                                  | 本行                                            | 否：按 section 名，不认会话                                              |
| 组 skill 的目录（`<available_skills>`）             | 官方渲染的 durable `skill-catalog` 消息                                    | 官方 `tool-skill` 那一行                        | 部分：`skill` 工具注册存在才发（注册级）                                 |

**为什么 `base` 不能也走官方 skill**：官方注册表只提供"目录里一行摘要 + 模型主动调 `skill` 才拿正文"这一档，
而 `base` 的工具（read / write / edit / bash / web）是每轮动手都可能要用的基础动作——等模型先花一次往返加载，
第一条任务就要多一轮，这正是
[ADR-提示词注入只有一个通道且按需内容走skill](../../../../context/dsh-context-assembler/.agents/adrs/20260921-提示词注入只有一个通道且按需内容走skill.md)
里"全部按需"被否掉的理由。注册表里没有"常驻"这一栏，也没有按会话现算正文的钩子，所以常驻只能由本行自己发一条消息。

## 接缝设计：`base` 组正文的常驻注入

### 挂点与落点

本行在 `apply` 里挂 `ctx.on("agent/pre-step", ...)`（事件不需要额外服务声明，通道挂在同一个事件上）。落点用
**认领过的消息之后**这个位置，而不是"列表末尾"：`findLastIndex` 找出本步认领的用户消息，把正文插在它后面。
理由是这条位置不随别的监听者的注册顺序漂移——末尾那个位置归官方
`tool-skill` 的目录、上游的 runtime context 等，我们不动它们。

尊重 `signal`（进入前与返回前 `throwIfAborted()`），并沿用 `decision.kind === "reject"` 时不注入。这条注入与组 skill
的注册、`drops` 的丢弃共用同一个开关：`config.groups: false` 时三者都不发生（那一档的语义就是"只要工具预处理"），
它们是同一件事的几半，不各给一个开关。

### "首步"与幂等：surface 比对，不是 `step` 号

判据：**surface 上最近一条同键消息的正文与本次要送的正文逐字相等就不送**（读法：倒着遍历
`agent.session.surface.nodes`，`eventAt(seq)` 取 `user/message`，比 source 里的键与文本；
[`src/index.ts`](../../src/index.ts) 的 `latestInjectText`）。

不用 `step === 1` / `turn === 1` 判"首步"：`step` 是 turn 内计数，每个 turn 都从 1 起，用它要么每轮重发、要么
漏掉"正文已经不在模型眼前"的情形。surface 判据一次给出六种正确行为：

| 场景                        | 结果   | 为什么                                              |
| --------------------------- | ------ | --------------------------------------------------- |
| 会话首步                    | 送一次 | surface 上还没有这条键                              |
| 后续每一步                  | 不送   | 同键最近一条正文逐字相等                            |
| 压缩（早期节点被摘要覆盖）  | 补发   | 那条消息不再在 surface 上，模型真的看不到了         |
| 进程重启后 resume           | 不送   | surface 由完整日志折叠而来，旧条目还在，逐字比得上  |
| 改组表 / 改正文             | 送一次 | 正文变了 → 追加一条新的（同键两条并存，见代价清单） |
| 会话里装了新工具 / 换了收窄 | 送一次 | 正文由这个会话的装配目录现算，目录变了就是正文变了  |

不挂 `agent/request-error` 做重试补发：同一步内的重试不重跑 pre-step，而首试已经把注入落进会话
（[`agent.ts:419-423`](../../../../../vendor/deepseek-harness/packages/core/agent-loop/src/agent.ts)），没有要补的场景。

### 信封与身份

内容块 + 上游的 source kind：

```
<skill_content name="tool-group-base">
<skill_instructions>
- read：读文本文件…
</skill_instructions>
</skill_content>
```

- source 用上游已有的 `skill-invocation`（`{ kind, name, form: "instructions" }`，
  [`skill/src/index.ts:146-153`](../../../../../vendor/deepseek-harness/packages/skill/skill/src/index.ts)），**幂等键就是
  `name`**（组 skill 名 `tool-group-base`，[`src/index.ts`](../../src/index.ts) 的 `injectMessage` / `latestInjectText`）。不新增 source kind：
  客户端的 producer 标签对已知 kind 直接用 `name`
  （[`event-projection.ts:64-70`](../../../../../vendor/deepseek-harness/packages/client/ui-chat/src/client/conversation-nodes/event-projection.ts)），
  未知 kind 会原样显示 kind 字符串。
- 为什么不借用通道的 `context-assembler` kind：那是通道的条目身份；本行借用它，读日志时看不出是谁注入的，而且
  那个类型不在通道的公开面里（借用要新增导出）。
- 为什么不用规则块 `<system-reminder id="tool-group-base">`：那套覆盖语义是为"规则"写的，而这条正文的身份是
  **技能说明**；用内容块还能与按需加载的形态对齐（系统提示词里已声明"skill_content 随提示送来的与你后来加载的
  一样"），模型不会以为"base 还没加载"而再去目录里调一次。
- 正文用组渲染器 `groupSkillBody(group, visible)`（[`groups.ts:27-39`](../../src/guidance/groups.ts)）产出的 markdown 列表。
  信封是**手写**的（不带上游 `renderSkillContent` 的 `<skill_resources>` 段）——那个段对运行时注册的虚拟 skill
  只有一行 provider 提示（"managed by provider "runtime""），是噪音。

### 会话开关：都不关；正文按装配目录过滤

- **`instructions: false` 不关**：那个开关的真源是通道的会话级状态（`setInstructions` 只有写口，读面是私有的），
  `session-mode` 的收口把它拨给通道、没有留下可读的事实。本行要保持"常驻"，就得按"常驻就是常驻"定义它——`chat`
  会话照样收到这条正文，只是正文里只剩它真的能用的那几行（收窄把其余行一起收掉了，见下一条）。
- **正文按这个会话装配结果里最终可见的工具目录过滤**：`groupSkillBody(baseGroup, visible)` 的 `visible` 就是
  "这个名字在不在目录里"（[`src/index.ts`](../../src/index.ts) 的 `visibleTools`），目录由 `system-prompt/assemble` 的监听按 agent
  记下（[装配目录的记忆](#装配目录的记忆)）。于是**任何**让工具不进这个会话目录的机制（模式的收窄、preset 没装
  它、别的开关把它拿掉）都自动反映到正文里——正文与模型手上的工具目录同源。
- **兜底**：某个 agent 还没有装配记录时（正常路径上 `agent/pre-step` 之前必有一次装配，这条留给直接调瀑布的异常
  情形）退回**工具注册表**的判据（`ctx.tools.get(tool, agent) !== undefined`，[`src/index.ts`](../../src/index.ts) 的 `registeredIn`）
  ——认"装没装"，比渲染一份全量正文或空正文都强。
- 按需的三组不在这一档：`ctx.skills.register` 的内容是**装配期一次**定型的字符串，不按会话现算；它们的正文
  里提到的工具是否在这个会话的目录里，由模式收窄决定。

### 装配目录的记忆

`base` 正文要按"这个会话最终可见的工具"过滤，而那个事实只出现在装配结果上。本行因此在
`system-prompt/assemble` 的监听里、`next()` **之后**把 `result.tools` 的名字收进
`WeakMap<Agent, ReadonlySet<string>>`（本行的 `system-prompt/assemble` 监听），`agent/pre-step` 渲染正文时读它。
三点值得写下来：

- **必须站到最外层**（`ctx.on(..., { prepend: true })`）：收窄的那条监听注册得比本行早（host 平面的行先于本行的
  scope），瀑布里先注册的是外层，它过滤 `tools` 发生在**它的返回路径**上。站在内层读 `next()` 拿到的是收窄
  **之前**的目录，正文就会列出 read / write / bash 那些这个会话用不到的行。`prepend` 让本行排到最外层，
  一次装配走完之后手上的 `result` 才是最终结果。本行的投影改写与它共用这条监听，顺序因此也变了：改写现在发生在
  收窄**之后**——两者可交换（只换描述与 schema、不动名字），结果不变。
- **记的是名字集合**：`result.tools` 是投影之后的目录（描述已被本行换成一行中文），名字不受描述改写影响，所以
  收名字就够，不必关心描述。`skills: false` 之类的开关让工具不进目录时，名字自然也不在里面。
- **按 agent 记**（`WeakMap`）：一次装配只刷新它自己那个 agent 的目录，会话收窄变了就在下一次装配时跟着变；
  没有 agent 的装配（诊断）不记，也不影响任何会话。

## 取舍

| 选项                                                               | 为什么否掉 / 保留                                                                                                                                                                           |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `base` 也注册进官方 skill，让模型按需加载                          | 首条任务要先花一轮加载基础用法（旧 ADR 已否掉"全部按需"）；常驻这件事注册表表达不了                                                                                                         |
| `base` 注册进官方注册表**并且**常驻注入                            | 目录里会列一份已经在手上的正文，模型可能再调一次 `skill`（重复正文进历史）；"常驻"与"按需"是两种送达，不是两份注册                                                                          |
| `base` 注册成"仅用户可调用"（`modelInvocable: false`）             | 目录不再列它（官方目录只列 model-invocable），但本行仍要自己实现常驻，多的只是一个用户手势，不值                                                                                            |
| 规则块信封 `<system-reminder id>`                                  | 覆盖语义只对"规则"成立；这条正文的身份是技能说明，且要额外造/借 source kind                                                                                                                 |
| 用官方 `renderSkillContent` 渲染常驻块                             | 少一次手写信封（那本是上游的事实），但每条会多两行 provider 提示噪音（虚拟 skill 没有资源目录，那两行不承载信息）；本行手写、接受"上游改信封时跟着改"这笔小债                               |
| 正文按 `allowTools` 收窄修剪                                       | 收窄是 `session-mode` 收口的私有状态，直接读它得给收口加一个跨包只读口（见下一行）——**不必要**：收窄的结果就在装配结果上，站到装配瀑布最外层就拿到了（见[装配目录的记忆](#装配目录的记忆)） |
| 给收口加一个"本会话可见工具 / 要不要 instruction"的只读口          | 可见工具这一半已由装配结果回答，不必新增跨包接口；"要不要 instruction"那半没有对应的装配事实，仍不读（见代价清单）                                                                          |
| 在装配瀑布的**内层** `next()` 之后记 `result.tools`                | 内层拿到的是收窄**之前**的目录（收窄在外层监听自己的返回路径上做），记下来就是把 read / write / bash 又列回 chat 的正文里                                                                   |
| 按 agent 的 scope 层注册组 skill（`agent/created` 时注册）         | 注册表支持按层隐藏，但内容仍是注册时定型（修剪不了），且要把"注册时机 / 清理 / 目录抖动"这套新复杂度搬进来                                                                                  |
| 本行自己实现 surface 比对（而不是让通道导出 `latestReminderText`） | 那对工具是通道的内部实现；导出会把"信封与幂等"这套知识外泄。自实现的代价是约十行遍历 surface 的代码（两处键不同，不冲突）                                                                   |
| `injection` 字段留着                                               | 它现在只表达"是不是 `base`"（`BASE_GROUP_KEY` 已经在了）；留在数据里会让人以为"改它就能换送达方式"                                                                                          |
| `requires` 字段留着                                                | 现在没有任何消费者（官方注册表按层分可见性、不认工具可见性，正文只按装配目录过滤）；留着一份没有消费者的数据，比删掉它更容易让人误以为门控还在                                              |
| 把 policy 拦截的实现搬进本包                                       | 它归 `session-mode` 的按模式配置（`modes.<id>.allowPolicies` / `denyPolicies`），行清单与拦截判据都在那一层                                                                                 |

## 代价清单

- **`chat` 的目录默认不注入，显式要也会列了却加载不了**：chat 的 `skills` 由工具名单推导成 `false`，所以官方那份
  目录在 `agent/pre-step` 上被丢掉；一旦模式显式写 `skills: true`，会话就会收到一份列着 `tool-group-flow` /
  `-delegation` / `-team` 的目录，而 `skill` 工具不在它的白名单里（投影里没有、真调用会被收口拒）——官方目录的判据
  是"`ctx.tools.get("skill", agent)` 是官方那一份注册"（注册级），看不见我们的收窄。这条代价来自"用官方注册表发布
  目录"这个决定，不是实现疏漏。
- **上游目录的渲染格式与我们无关**：`<available_skills>` 的文案、条目的 digest 幂等与"整份替换"语义都由官方那
  一行定；我们能影响的只有注册项本身（名字、摘要、正文）。
- **按需加载的正文带资源段**：`skill` 工具返回的正文经 `renderSkillContent`，每条都带
  `<skill_resources>` + 一行 provider 提示（运行时注册的虚拟 skill 没有资源目录）。
- **本行的装配监听抢在最外层**（`prepend`）：`next()` 之后才是"最终目录"这件事，只对**不比本行更外层**的收窄
  成立。将来若出现一条比本行还外的收窄（更早注册、且同样 `prepend`），本行记下的又会变成收窄前的目录——那时
  要么再往前排，要么改用别的读法。
- **`instructions: false` 收不住这条常驻正文**：那个开关的真源在通道与收口的私有状态里，本行读不到，所以 chat
  会话照样收到这条正文——只是正文里剩的是它真的能用的那几行（按装配目录过滤）。
- **正文一改，活跃会话各补发一条**：`base` 正文是 durable 消息，改代码或会话里新装一个工具后，每个还在跑的会话
  都会在下一步追加一条新的；压缩之后同样补发。这是"内容变了要重新送达"的必要代价，不是重发。
- **`drops` 不认会话**：`suppressSection` 是按 section 名的一次装配期声明，chat 会话同样被丢弃（它的收窄会先一步
  把 `tool:<名字>` section 滤掉，结果一致，但不是同一套判据）。
- **手写信封跟着上游走**：`<skill_content>` 的形状是上游 `renderSkillContent` 的事实，我们用等价的手写版本；
  上游改信封时本行要跟着改（没有类型或测试跨包钉住它）。
- **policy 拦截不在本包**：它归 `session-mode` 的 `modes.<id>.allowPolicies` / `denyPolicies`（policy 名 = 上游
  waterfall 名），判据在那一层。

## 验证判据

包内测试（[`guidance.spec.ts`](../../src/__tests__/guidance.spec.ts) 在真 agent + 真通道 + 真收口上跑 `pre-step`，
[`guidance-groups.spec.ts`](../../src/__tests__/guidance-groups.spec.ts)、
[`guidance-packs.spec.ts`](../../src/__tests__/guidance-packs.spec.ts)、
[`guidance-inventory.spec.ts`](../../src/__tests__/guidance-inventory.spec.ts)）钉住的是：

- 投影：短描述覆盖 `description` 而执行不受影响、参数说明性字段在投影里连键都不留而注册表照旧、只改投影不碰注册表。
- 注册：`flow` / `delegation` / `team` 三个组 skill 在官方注册表里（`ctx.skills.list({ scope: agent })` 的
  model-invocable 名单）、正文是中文列表且不含上游原文。
- 目录里**没有** `base`：注册表查不到它，模型不会加载一份已经在手上的正文。
- 常驻注入：首步注入一次（信封形态、source 是 `skill-invocation` 且 `name` 是组 skill 名）、落点在本步认领的用户
  消息之后（列表末尾那条不动）、第二步不重发、压缩掉那条注入后补发、正文随装配目录变化重发、正文按**这个会话
  装配结果的最终目录**过滤（真收窄到提问 + 联网三件的会话里 read / write / bash 那几行不在；成对的另一半是不
  收窄的会话里它们都在；还没有装配记录的 agent 退回注册表判据）；`instructions: false` 不关这条正文；
  `groups: false` 时既不注册也不注入，而工具预处理照旧。
- 丢弃：上游逐工具说明不进系统提示词（`renderPrompt` 里搜不到替身正文）。
- 数据：组表齐备、`drops` 一个 section 只归一个组、每个归组工具都有短描述、pack 索引的同名/同 key 当场报错、
  standard 装配引用的工具与说明都有归属。

装配链那一半（模式收窄 + 官方目录）在
[`preset-plane.spec.ts`](../../../dsh-session-mode/src/__tests__/preset-plane.spec.ts)：真 `Loader` + 真上游行上跑
"chat 在我们通道这一侧注入 0 条"、目录由官方 `tool-skill` 那一行发布。那份 spec 不装 `tool-guidance` 行，
所以本行注入的真装配判据就是包内那份 `guidance.spec.ts`。
