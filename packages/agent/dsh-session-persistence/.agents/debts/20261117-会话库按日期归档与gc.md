# 会话库还没有按日期归档 / 删除与 GC

状态：接受中——库的大小**符合预期**（2026-11-17 实测：`t_events` 771,924 行 / 数据 1.73 GB / 706 个会话，
其中 `assistant/message` 1.05 GB、`tool/result` 390 MB 占 84%，是真实内容，不是泄漏）。

位置：`packages/agent/dsh-session-persistence`（SQLite 写入方）。将来落地的形态是**按日期归档 / 删除，然后走 GC**。

**为什么现在不做**

会话是产品数据，删之前要先有「归档到哪、怎么找回」的答案；在归档格式与保留策略定下来之前动删除，等于把用户的历史
直接扔掉。当前规模（几百个会话 / 1.7 GB）不影响使用，只是打开与全表查询会随会话数线性变差。

**将来要回答的三件事**

1. **保留策略**：按 `f_created_at` 还是按「最后活动」；默认保留多久；用户能否覆盖。
2. **归档形态**：搬走的是整个会话（`t_sessions` + `t_events` + `t_session_events` 行）还是导出成一份可读文件
   （`session-log-export` 已经有 `agent/inbox/spliced` 这类事件的导出分支，可复用）。
3. **GC 的触发点**：启动时一次、还是后台周期；以及 `VACUUM`（SQLite 删行不还盘，要显式收缩）。

**销账条件**

库里出现「按日期归档 + 删除 + `VACUUM` 之后 `t_events` 行数下降、且归档件能被 `session-log-export` 读回」的判据时，
删掉这份债。
