# 命令装饰器生产零使用

状态：未销账（`@Command()` 与 `CommandContribution` 存在，仓内无生产使用者）

**现象**

`packages/agent/dsh-command/src/command.decorator.ts` 的 `@Command()` 与 `src/contract/command-contribution.ts` 的 `CommandContribution`，唯一使用者是它自己的 spec：`packages/agent/dsh-command/src/__tests__/command-contribution.spec.ts:47` 的 `GoalCommand`。

仓内三条命令（`dsh-compaction/src/command.service.ts`、`dsh-deepseek-feedback/src/command.service.ts`、`dsh-goal/src/command.service.ts`）都是**上游命令插件的行**：`inject(CommandRegistry)` 后把令牌交给上游 `mount(ctx, undefined, { commands })`，由上游插件自己调 `register`。装饰器在这条链上没有位置。

`CommandRegistry` 本身不是债：它有生产适配器 `CommandRegistryDefault` 与 3 个消费方。

**影响**

按 `dsh-plugin-design` 的接缝判据，`@Command()` 是 0 个适配器的接缝——它没有让任何东西变得可替换，只给「还不存在的自研命令」预留了一种写法。写第一个自研命令的人会看到两条并列路径（手写 `register` 与 `@Command()`），而只有前者有实例可参照。

**触发条件**

新增第一个自研命令贡献类（不依赖上游命令插件、由本仓自己实现 `handler`）时，必须先决定走哪条路径。

**销账条件**

Done when：`grep -rn "@Command(" packages/agent apps | grep -v spec` 有至少一处非注释命中，且对应命令在装配后被 `CommandRegistry.list` 观察到。

**不修的理由**

删掉它要连带削掉 `CommandContribution` 与 `CommandRegistry.register` 的撤销函数语义（`@Command()` 的 `onDispose` 依赖它），而 `CommandRegistry` 是上游 3 个插件行的真实依赖面。没有自研命令时，重写一次的成本高于留着空位；按第一条自研命令的真实形状重写，比现在猜形状省。
