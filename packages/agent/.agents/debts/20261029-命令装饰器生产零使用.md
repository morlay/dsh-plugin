# `@Command()` 与 `CommandContribution` 在生产里零使用

状态：未销账——装饰器已实现、装配期可用，仓内唯一的消费者是它自己的 spec
位置：`packages/agent/dsh-command/src/contract/command.decorator.ts`、`packages/agent/dsh-command/src/contract/command-contribution.ts`；唯一使用者 `packages/agent/dsh-command/src/__tests__/command-contribution.spec.ts` 的 `GoalCommand`

**现象**

`@Command()` 的生产使用者为零。仓内唯一的命令行是 `packages/agent/dsh-compaction/src/command.service.ts`：它 `inject(CommandRegistry)` 后把令牌交给上游 `dsh-command-compact` 的 `mount`，由上游插件自己调 `register`——装饰器在这条链上没有位置。

`CommandRegistry` 本身不是债：它有生产适配器（`dsh-command/src/command-registry.service.ts`）与两个生产消费方（上面那条 compaction 行、`packages/agent/dsh-upload/src/file-upload-store.service.ts`）。

**影响**

按接缝判据，`@Command()` 是 0 个生产适配器的接缝：它没有让任何东西变得可替换，只给「还不存在的自研命令」预留了一种写法。写第一个自研命令的人会看到两条并列路径（手写 `register` 与 `@Command()`），而只有前者有实例可参照。

**触发条件**

新增第一个自研命令贡献类（不依赖上游命令插件、由本仓自己实现 `handler`）时，必须先定走哪条路径。

**销账条件**

Done when：`grep -rn "@Command(" packages/agent apps | grep -v __tests__` 至少一处命中，且该命令在装配后被 `CommandRegistry` 的目录面观察到（spec 断言 `list` 里有它，撤销后消失）。

**不修的理由**

删掉它要连带削掉 `CommandContribution` 与 `CommandRegistry.register` 的撤销语义（`@Command()` 的 `onDispose` 依赖返回的 disposer），而 `CommandRegistry` 是上游两个插件行的真实依赖面。没有自研命令时，按第一个真实命令的形状重写，比现在猜形状省。
