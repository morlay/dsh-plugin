# 包内子域拆分与注册抽象（`packages/agent/*`）

状态：已实现——23 个包的面按「有消费方才开」落地，注册抽象只留 `@Command()` 一个
范围：`packages/agent/*` 包内的面（root / `contract` / `endpoint` / `server` / `ui` / `testing`）各管什么、行与贡献怎么写、注册装饰器做到哪一类
非目标：目录与命名的规范本身（home 在根 [`.agents/standards/ui-module.md`](../../../../.agents/standards/ui-module.md)）；`apps/*` 的装配顺序；框架层（`packages/zephyr/*`）的接缝
关联：根 [`ui-module.md`](../../../../.agents/standards/ui-module.md)（目录与写法）· ADR-20261028-agent层循环依赖 · 设计 20261029-深层模块审计 · 设计 20261109-核心能力与BFF分层 · 债务 命令装饰器生产零使用

## 一、决定

| #   | 议题       | 决定                                                                  | 一句话理由                                                         |
| --- | ---------- | --------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 1   | 面从哪来   | 需要什么面就开什么面；`./testing` 只在有下游消费者时开（当前 5 个包） | 空面就是空壳出口，多一条出口等于把同一份东西列两遍                 |
| 2   | 行与贡献   | **分开**：行装上游插件（`fromCordis` + `mount`），贡献实现我们的契约  | 工具与命令定义的真源在上游插件里，复制一份就是第二份真源           |
| 3   | 注册装饰器 | 只做 `@Command()`；`@Tool` / `@Skill` / `@Policy` 不做                | 后三类在仓内没有贡献方（现有实现全是行），套上去只会造第二份真源   |
| 4   | 无契约的行 | 允许 `fromCordis(上游)` 单参：令牌从插件名派生，不硬造契约            | 契约的价值是「消费方不写上游包名」；没有第二个消费方时它只是间接层 |

## 三、模块边界与接口

| 模块                                      | 拥有（职责与不变量）                                       | 不拥有（明确排除）                 | 依赖方向                                  | 接缝 / 适配器                                                 |
| ----------------------------------------- | ---------------------------------------------------------- | ---------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| 包根 `src/index.ts` + `<name>.service.ts` | 契约聚合、默认实现、`provideXxx()`（仅纯 root 包）         | wire 形状、装配清单、浏览器半      | 基础库与别的域的契约                      | 契约令牌（`@Injectable()` 抽象类）                            |
| `contract/`                               | 进程内端口：注册表 / 目录 / 执行器 / 本域要的外部能力      | RPC 形状（归 `endpoint/`）         | 只依赖类型与 `@morlay/zephyr`             | 令牌；投影契约用 `AssertCovered` 钉住上游面                   |
| `endpoint/`                               | wire 形状：组名 + 方法名 + 请求/响应类型；品牌值的铸造面   | 实现、装配、业务规则               | 只依赖类型                                | `@RemoteGroup` / `@RemoteMethod` 契约类（宿主侧在子类里实现） |
| `server/`                                 | 宿主实现：wire 注册、同进程端口实现、`provideXxx()`        | 浏览器半（React / `.css`）         | root + contract + endpoint + 框架 host 面 | `fromCordis(契约, 上游插件)` 适配器；`registerRemoteGroup`    |
| `ui/`                                     | 浏览器半：store / 位置 / 视图 / 远程面实现、`provideXxx()` | 宿主实现（不引包根）、领域能力本身 | `endpoint` + 框架 client 面               | `fromCordis` 包装上游 client 插件；`Remote` 面                |
| `testing/`                                | fixtures、契约套件（`run*Contract`）、最小装配 helper      | 生产实现、生产装配清单             | 只被下游域的测试与装配面 spec 依赖        | 契约的替身（同一接缝的第二个适配器）                          |

**接口**：一个面给一个 `provideXxx()`，返回 `ProviderList`；装配面只写一行，剔行用 `without(实现类)`。`fromCordis` 三种形态各有用途——`(契约, 上游)` 是标准行、`(上游)` 是无契约行、`(契约)` 是纯实现行；行的 `mount(ctx, config, deps)` 里 `deps` 的键是**上游服务名**，不给容器起别名。

**深度**：删掉 `contract/`，消费方要在装配点写上游包名；删掉 `endpoint/`，wire 组名与方法名散进 ui 与宿主；删掉 `testing/`，下游会各抄一份同形状数据。三件事都在 N 个调用点重新出现，所以这些面有深度；只装一行、没有任何消费方的面（空 `contract/`、空 `testing/`）没有深度——那是空壳。

## 四、行为与边界

- **行装错了上游依赖**：`mount` 的 `deps` 少一项不会在装配期失败，而是上游第一次读到它时 `Cannot read properties of undefined`；写法判据见 [`.agents/standards/how-to-write.md`](../standards/how-to-write.md)。
- **贡献的登记与撤销**：`@Command()` 在装配期把贡献登记进 `CommandRegistry`，`register` 返回的 disposer 归行持有，行卸载即撤销。
- **面之间的 import 越界**：`ui` 引包根会把 node-only 运行时拖进浏览器；`server` 引 `ui` 会把 React 拖进 Node。两条都是「装得上但跑不起来」的错误，靠 `exports` 分隔。

## 六、取舍

- **四个装饰器一次做齐（`@Tool` / `@Command` / `@Skill` / `@Policy`）**：只有命令有真实贡献方，其余三类的现有实现都是行。
- **通用 `@Contribution(注册表)`**：把「是什么」藏进参数里，而四类索引方式不同（`find(name)` vs 触发条件匹配）。
- **给零消费方的包补空 `contract/`**：令牌没有第二处引用，只是多一次跳转。
- **为给 `@Command()` 找消费方把上游命令搬进本仓**：命令名与说明的真源会分叉。
- **把 `provideAgent()` 收进 `./server`**：装配面就装不到「只装 headless」的那一档，所有 spec 都会被逼着拉起 wire。
- **目录扫描自动发现贡献**：隐式注册，与「装配显式」相悖。
- **`dsh-agent-team` 补契约**：它只有一行服务 + 一套上游工具 + 一套上游界面，能力名在装配面由适配类本身承担。

## 八、开放问题

1. **59 处无契约行的门槛**：出现第二个消费方（或跨包替换实现）时才补契约——目前没有这样的消费方。
2. **`dsh-setting` 的 `./contract` 出口**：现在整份转出 `@morlay/zephyr-app`，是否需要收窄成只出 `Setting` 与声明面，等有第二个消费方再定。
