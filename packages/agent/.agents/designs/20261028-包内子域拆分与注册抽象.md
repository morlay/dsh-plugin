# 包内子域拆分与注册抽象（`packages/agent/*`）

状态：已实现（包结构、`@Command`、命名、装配面都是当前形态）
范围：`packages/agent/*` 的目录形状与「按需注册」的统一写法；`apps/*` 只跟随装配。
约束：不改上游 `@deepseek-ai/*`；装配只认 provider 清单（`provide(...)`）；每包自带 spec 可单独跑。

## 结论摘要

| 议题 | 结论 | 一句话理由 |
| --- | --- | --- |
| 包内目录 | 只留 `contract/` `endpoint/` `server/` `ui/` + 包根三件套 | 子域有独立契约与 Module，留在父包里等于把「一组包」当「一个包」用 |
| 其余子域 | 一律独立成包 | 同上 |
| 浏览器半 | 目录名 `ui/`，出口 `./ui` | 与 `server/` 对称，读写各一半 |
| 「行」与「贡献」 | **分开**：行装上游插件，贡献实现我们的契约 | 现有工具行全是 `fromCordis(上游插件)`，工具定义在上游，不在我们这层 |
| 注册装饰器 | 只有 `@Command`，**暂无消费方** | 现有命令与工具全是「行」，装饰器现在套上去只会制造第二份真源 |
| 命名 | 单数；注册表加 `Registry` | `Tools` / `Agents` 既复数又与实体撞名 |

## 事实基线

- **工具行是「装上游插件」，不是「工具定义」**：`dsh-plan-mode/src/server/tool-todo.service.ts`、
  `dsh-web-access/src/server/tool-web.service.ts` 都是 `fromCordis(…)` +
  `mount(ctx, undefined, { tools: … })`，`name`/`schema`/`execute` 的真源在上游插件里。
- **策略行不是工具**：`dsh-tool-policy` 的 `image-offload` / `repeat-tool-reminder` / `timeout-policy` /
  `mcp-resources` 挂在工具调用生命周期上，不进工具注册表。
- **三条命令也是「行」**：`dsh-goal/src/command.service.ts`、`dsh-compaction/src/command.service.ts`、
  `dsh-deepseek-feedback/src/command.service.ts` 都是 `fromCordis(上游插件)` + `mount(ctx, undefined, { commands })`；
  `register` 在 vendor 插件的 `apply` 里（`command-goal/src/index.ts:190`、`command-compact/src/index.ts:85`、
  `command-feedback/src/index.ts:117`），命令名与说明的真源也在那里。
- **结论**：`@Command()` 没有真实贡献方；本仓所有按需注册项都是「行」。
- **注册表方法不是 `register/list/find` 三件套**：上游 `CommandRuntime` 是
  `register(definition) → disposer`、`list(agent)`、`find(agent, name)`（agent 作用域）；
  `ToolRuntime.register` 同样返回 disposer。撤销与作用域不能从契约里抹掉。
- **贡献包也受既有发布规范约束**：`cordis.patch.yml` 出口、`engines.dsh`、`locale/*.json`
  （见 `standards/how-to-write.md`「包出口」一节）。

## 结构

```
<pkg>/src/
├── index.ts            # 聚合 contract + 默认实现 + Module
├── <name>.service.ts   # 默认实现
├── <name>.module.ts    # 装配模块（贡献包也有）
├── contract/           # 进程内端口
├── endpoint/           # RPC 形状（有 remote 才需要）
├── server/             # wire 注册 + 同进程端口实现
└── ui/                 # 浏览器半（有界面才需要）
```

### 形状例外

上面是**默认形状**，不是每包都必须齐。三类例外有判据，不许为了「齐」造空壳：

| 例外 | 谁 | 判据 |
| --- | --- | --- |
| 没有 `contract/` | `dsh-persistence`；`dsh-tool-output`、`dsh-tool-policy`、`dsh-env-tool`（跨域的行包） | 包里只有**行**：令牌就是适配类自身（`fromCordis(上游, 上游)`），或它要登记的目标注册表在别处（`ToolRegistry`、上游 `spillStore` / `tokenMeter`）。造一份空 barrel 只是多一次跳转 |
| 没有 `.module.ts` | `dsh-fs` | 这个域**只有契约**：实现在沙箱域的行里（`FsSandbox` 要 `SandboxPolicy` 才能 mount）。无 provider 的 module 就是空壳 |
| 单域的行不单独成包 | `dsh-skill` / `dsh-goal` / `dsh-job` / `dsh-plan-mode` 的 `src/server/` | 只服务一个域的行放该域的 `server/`，由该域 Module 收进 providers；一个包同时服务多个域（`dsh-env-tool` 的 fs/sandbox/shell/working-directory、`dsh-tool-output`、`dsh-tool-policy`）才独立 |

判据同一条：**没有可装配的东西就不留那个面**；形状是「有什么写什么」的结果，不是先画格子再填空。

### 各包的子域现状

- **四面齐**：`dsh-command`。
- **`contract/` + `server/` + `ui/`**：`dsh-goal`、`dsh-plan-mode`、`dsh-skill`。
- **`contract/` + `server/`**：`dsh-job`、`dsh-web-access`。
- **`contract/` + `ui/`**：`dsh-permission`、`dsh-session`、`dsh-setting`、`dsh-workspace`。
- **只有 `contract/`**（实现在别处或本包就一条行）：`dsh-agent`、`dsh-attachment`、`dsh-auth`、
  `dsh-compaction`、`dsh-fs`、`dsh-ptc`、`dsh-sandbox`、`dsh-session-persistence`、`dsh-session-title`、
  `dsh-shell`、`dsh-storage`、`dsh-subagent`、`dsh-telemetry`、`dsh-upload`、`dsh-working-directory`。
- **只有包根三件套**（纯行或纯令牌）：`dsh-agent-instruction`、`dsh-checkpoint-policy`、
  `dsh-deepseek-feedback`、`dsh-env-tool`、`dsh-persistence`、`dsh-tool-output`、`dsh-tool-policy`。

`dsh-workspace`（会话↔工作区绑定，有 `ui/`）与 `dsh-working-directory`（给 shell / 工具用的 OS cwd）
不同层，不合并。

## 两类东西，两种写法

| | 行（row） | 贡献（contribution） |
| --- | --- | --- |
| 做什么 | 装一个上游插件，把它的服务交给本行 | 我们自己的实现，往某个注册表登记一条 |
| 写法 | `fromCordis(我们的契约, 上游插件)` + `mount(ctx, …, deps)` | `@Command()` 标记 + 实现 `CommandContribution` |
| 真源 | 上游插件 | 这个类自己 |
| 例子 | `plan-mode/src/server/tool-todo.service.ts`、`web-access/src/server/tool-web.service.ts`、`sandbox/src/sandbox.service.ts` | `dsh-command` 的 spec 里那条 `GoalCommand`（唯一的 `@Command` 用例） |

**只有贡献才需要装饰器**。把行也套上 `@Tool()` 会制造第二份工具真源。

## 注册装饰器：只做有真实消费方的那类

| 装饰器 | 注册表 | 现状 |
| --- | --- | --- |
| `@Command()` | `CommandRegistry` | 已实现，**暂无消费方**（见 `债务 命令装饰器生产零使用`） |
| `@Tool()` | `ToolRegistry` | 无贡献方（工具都是行）→ 不做 |
| `@Skill()` / `@Policy()` | `SkillRegistry` / `PolicyRegistry` | 无贡献方 → 不做 |

第一个自研命令出现时直接写 `@Command()`，不再新增机制。

```ts
@Command()
export class GoalCommand implements CommandContribution {
  readonly name = "goal";
  readonly description = "设定或查看当前目标";
  handler(invocation) { … }
}
```

- 注册表契约**只写它真有的方法**：`register(contribution) → disposer`；查询另立只读面
  （`CommandCatalog`：`list(agent)` / `find(agent, name)`），不塞进注册表。
- 装饰器在装配期把贡献登记进注册表，**贡献方不再手写 `registry.register(...)`**；
  包仍然有自己的 `module.ts`，装配层只认 Module。

## 既有约定

1. 文件名与类强相关（`agent-directory.contract.ts` ↔ `AgentDirectory`），一文件一主类。
2. 引用走 `exports` 包名（barrel 与同目录内部除外）。
3. 品牌类型边界转换一次（`endpoint/` 收 `string`，内部 `SessionId`），业务代码无 `as never` / `as unknown as`。
4. 每包自带 spec，只假传输层与外部能力（`LocalRemote`、假 LLM adapter），不假本包服务。
5. 契约成员**必须覆盖上游服务的全部公开成员**（`AssertCovered` 守卫，漏一个编译失败），
   写法是 `abstract class` 逐条声明取 `Upstream["member"]`。
6. 贡献包同样要有 `cordis.patch.yml` 出口、`engines.dsh`、`locale/*.json`。

## 取舍

| 被否掉的选项 | 否掉的理由 |
| --- | --- |
| 四个装饰器一次做齐（`@Tool` / `@Command` / `@Skill` / `@Policy`） | 只有命令有真实贡献方；其余三类的现有实现都是「装上游插件的行」，套装饰器会造第二份真源 |
| 通用 `@Contribution(注册表)` | 把「是什么」藏进参数里；且四类索引方式不同（`find(name)` vs 触发条件匹配） |
| 为给 `@Command` 找消费方而把三条上游命令搬进本仓 | 约 170 行双写，命令名与说明的真源会分叉 |
| 目录扫描自动发现贡献 | 隐式注册，与「装配显式」相悖 |
| 浏览器半目录叫 `client-module/` | 与 `server/` 不对称 |
| `AgentDirectory` 叫 `AgentRegistry` | 它只有 `get`/`list`、没有 `register`，叫 Registry 名不副实 |
| 契约用「空令牌类 + `interface` 同名合并」省行数 | 要开 `no-unsafe-declaration-merging` 豁免，换掉的是「子类漏实现即编译失败」这条保障 |

## 开放问题

1. **`@Tool` / `@Skill` / `@Policy` 要不要做？** 现有代码里没有贡献方（全是行）；等出现第一个自研工具/技能时再定。
2. **`@Command` 的首次使用场景**：已实现但零消费方；等某个命令需要在我们这层实现（而不是装上游插件）时启用。
3. **`dsh-session ↔ dsh-workspace` 那一处真环**要动契约归属，见 `../adrs/20261028-agent层循环依赖.md`。
4. **`Slots.register` 的 props 逐 key 校验**：要把上游 7 个类型参数 + 两个 overload 抄进契约，收益（props 写错编不过）不抵耦合成本，暂不做。
