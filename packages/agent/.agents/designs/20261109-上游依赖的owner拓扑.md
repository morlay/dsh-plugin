# 上游依赖的 owner 拓扑（`packages/agent/*`）

状态：已实现——机械判据当前为 0 冲突；本文只留判据与复核命令，不再维护生成表
范围：`packages/agent/*` 的 `src/`（不含 `__tests__`）直接 import 了哪些 `@deepseek-ai/*`，以及每个上游包唯一归属谁
非目标：扩展层（`packages/agent-ex/*`）的上游面；上游包内部的语义（真源在 `vendor/deepseek-harness`）
关联：设计 20261109-核心能力与BFF分层（三类包与跨域依赖的判据）· 设计 20261028-包内子域拆分与注册抽象（契约写法）

## 一、决定

| #   | 议题                               | 决定                                                                                       | 一句话理由                                           |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 1   | 上游包能被几个本地包直接 import    | 一个                                                                                       | 两个 owner 就是两处要跟着上游改，换实现时还要改两处  |
| 2   | 归属按什么判                       | 按**它服务哪个场景**（能力域），不按包名                                                   | 包名只说明上游把它放在哪，不说明我们的哪个场景要用它 |
| 3   | 上游太散怎么办                     | 在**已有域的契约文件**里按能力 re-export（类型与纯函数跟着能力走），不建转发出口、不建新包 | 一个能力一个名字；转发出口只是把同一份东西列两遍     |
| 4   | 上游实现类（cordis Service）从哪出 | 只从 `./server` 出，不进 `./contract`                                                      | 契约面是「调用方要了解的事实」，不是「实现长什么样」 |

- **归属的三种情形**（按能力包，不按上游包名）：
  1. **同名本地包直接拥有**：`dsh-session` ← `@deepseek-ai/dsh-session`、`dsh-fs` ← `dsh-fs`、`dsh-storage` ← `dsh-storage`、`dsh-workspace` ← `dsh-workspace`、`dsh-sandbox` ← `dsh-sandbox`、`dsh-session-persistence` ← `dsh-session-persistence`。
  2. **归到已有域的契约文件**：词与纯函数进该域的 `*-vocabulary.contract.ts`（如 `dsh-agent` 的 `tool-vocabulary.contract.ts` / `llm-vocabulary.contract.ts`），不新建包。
  3. **BFF 拥有自己场景的端点插件**：会话组（`@deepseek-ai/dsh-api-session-controller`）、日程（`dsh-schedule`）、会话引用（`dsh-session-reference`）、文件引用（`dsh-file-reference-local`）、交付物（`dsh-workspace-changes` 与 `dsh-client-ui-deliverables`）都归 `dsh-conversation`。

## 三、模块边界与接口

| 模块                      | 拥有（职责与不变量）                                                                 | 不拥有（明确排除）                                                   | 依赖方向                        | 接缝 / 适配器                |
| ------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------- | ------------------------------- | ---------------------------- |
| 本地能力包                | 它那一片能力的上游面：契约文件里的类型 / 纯函数 re-export、`./server` 面的上游实现类 | 别的域的上游包；上游源码                                             | 上游包（一个包只归它）+ 框架    | `fromCordis` 适配行          |
| BFF（`dsh-conversation`） | 对话场景的上游端点插件与 client 界面插件                                             | 领域能力包的上游面（会话存储、查询、持久化、权限、上传、工作区文件） | 下层本地能力包 + 本场景上游插件 | 上游行的适配；`provideXxx()` |
| 行包                      | 它装的那一行的上游插件与它要登记的目标注册表                                         | 能力名；上游包的再导出面                                             | 上游插件 + 目标注册表           | 适配类自身即令牌             |

**接口**：本地包对上游的「拥有」通过两种出口表达——`./contract`（词与端口）与 `./server`（实现类）。跨包消费方只认这两个面，不写 `@deepseek-ai/*`。

**深度**：删掉这层归属，上游包名会散进每个装配点与每个 spec；上游改名或换实现时没有单点可改。

## 四、行为与边界

- **两个域都要同一段上游能力**：先问「它服务哪个场景」，归给场景 owner；另一方经本地包取（例：工作区文件读取归 `dsh-workspace`，沙箱与对话域都从它取）。
- **上游新增一个包**：只有在它服务的能力已有本地域时才接入；接进来就归那个域，不新增第二个 import 点。
- **上游改了成员**：该域的投影契约先编译报错（`AssertCovered`），其它域不受影响。

## 六、取舍

- **给每个上游包建一个本地包**：包数与发布面跟着上游涨，而多数上游包只服务一个场景。
- **补一层转发出口（`export *`）**：同一份东西列两遍，且上游结构一变就要跟着改。
- **按上游包名给本地包命名**：名字写的是代理对象而非场景，换实现时包名就错了。
- **让 `agent-ex` 直连上游**：扩展层的替换实现会绕过契约，契约与实现分居两处后没人守得住。

## 七、不做与已知债

- 不维护「上游包 → 本地包」的生成表：表会随上游版本漂，判据与复核命令才是可守的部分。
- `just audit` 的汇总器有一个假绿风险（实测：4 个非 agent 包逐包审计抛 `TypeError`，汇总仍打四项勾）——修在 `devpackages/audit`，不在本层。

## 八、开放问题

1. **`dsh-conversation` 的 34 个上游包里，有多少是「别的域的能力」**：与设计 20261109-核心能力与BFF分层 的开放问题 1 同一条，定完那条判据才能继续唯一化。
2. **`dsh-agent` 的 19 个上游包里含 `dsh-llm-deepseek-api-key` / `dsh-llm-pi-ai`**（provider 配置行）：它们配的是 agent 的模型，归 agent 域；若将来 `dsh-setting` 要直接读 provider 的 `Config`，走 `@morlay/dsh-agent/contract` 而不是上游包。
