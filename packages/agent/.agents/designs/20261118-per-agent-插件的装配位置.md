# per-agent 装配：Provider 声明 scope，装配器按 scope 过滤

状态：①② 已实现（`c8cc7368`：zephyr 的 scope 能力 + 事件字段绑本行 ctx + 事件令牌）；③④（6 个域的
per-agent 化、两处手写订阅）待下一票，方向见「五、下一票的两处形态」。
范围：`@Injectable()` 的 scope 声明、装配器如何按 scope 分派、事件字段绑哪个 ctx、删掉哪几处自造机制。
非目标：上游 `AgentSetup` 的调用细节（见上游 `core/agent/src/index.ts:54`）、`AgentLoop.create` 那条路径（已记债）。

## 一、决定

| # | 决定 |
| --- | --- |
| 1 | **Provider 自带 scope 声明，值是 symbol 不是字符串，且 symbol 不导出**：`@Injectable` 的 `scope` 选项收它；装配器内部的分类键**属于声明方**（agent 域的键在 `dsh-agent` 里，不导出）`Symbol.for("morlay.dsh-agent.scope.agent")`。**为什么是 symbol**：字符串会拼错（`"agnet"`）且无法穷举；symbol 是唯一身份、可作键、`Symbol.for` 让跨包同形。**为什么不导出**：它只是**装配器内部的分类键**，消费方不该碰——能碰就得有人记住「哪些 scope 存在」，那又成了第二个 home。对外只有装饰器。 |
| 1b | **`@AgentScoped()` 是 `@Injectable` 的别名**：`AgentScoped() ≡ Injectable({ scope: <ScopeAgent> })`。**这是外部唯一能表达 scope 的方式**（默认不给 scope 就是 root）。留这个别名是为了可读性，但**不留第二套语义**——它没有额外行为，也不产生额外标记。 |
| 2 | **装配器按 scope 过滤**：装清单时把**声明了 scope** 的挑出来，在**每个 agent 的 `agentCtx`** 上装（上游钩子 `CreateAgentOptions.setup`）；没有 scope 的照旧装应用。装配器**不认识 agent**：它只按 symbol 分组，把装行能力交给宿主（`ScopedRows`）。 |
| 3 | **删掉 `AgentProviderGroup` 与 `entries` 手写清单**：它全仓零读取、与「Provider 自己声明」是同一件事的两份写法。6 个 `provideXxx()` 里的条目随之移除。 |
| 4 | **`@AgentScoped()` 不再是「标记」**：语义从「打个 tag 让诊断能指出」变成「这个 Provider 由 per-agent 装配器装」，与 `Injectable({ scope })` 同一件事——只留一个实现（别名），不留第二套语义。 |
| 5 | **事件字段绑「该行装配时用的那个 ctx」**：`agentCtx` 上装的行 → 令牌的 `bus` 就是 `agentCtx` → 订阅落在该 agent 的 scope。**不需要显式传 ctx**（`onIn` 那条设计作废）。 |
| 6 | **`mountRow` 与 `bootstrapApplication` 走同一个「装一行」实现**：注入怎么填、事件字段绑哪个 ctx、`onInit` 何时跑——只有一处实现（`bootstrap.ts` 的 `mountInstance`），per-agent 装配也调它。 |

## 二、为什么这样最简

- **一个事实一个 home**：Provider 自己说 scope，装配器只按它分派；没有清单、没有第二处列举、没有「声明说 agent、实际装 root」的裂缝。
- **与上游同形**：上游在 `agentCtx` 上 `ctx.plugin(scope)` 就是「装进该 agent 的 scope」，我们只是把「哪些 Provider 该装进去」从**手写条目**换成**Provider 自带的声明**。
- **不需要新 API**：没有 `onIn`、没有 `AgentProviderGroup`、没有 `scopeOf` 的运行时判断——`scopeOf` 可降级为纯诊断。

## 三、已知要一起销的两笔

1. `mountRow` 现在**不给 `EventEmitter` 字段绑 ctx**（只处理 `injectPlaceholderOf`）→ 用它的行一调 `on(...)` 就抛「装配完成前被使用」。决定 6 顺带销掉。（已销，`c8cc7368`。）
2. `bootstrapApplication` 给事件字段绑的是**根 ctx**（`bootstrap.ts:527`），与 `event-emitter.ts:69` 注释的「本行 ctx」不符。决定 5 + 6 顺带销掉。（已销，`c8cc7368`；`42359932` 补的三条 disposer 届时可重新评估。）

## 四、迁移面

- 6 处 `extends AgentProviderGroup` → 删（已删，`c8cc7368`）；对应 Provider 改标 `@AgentScoped()`（**待下一票**：要连着 root 上的消费方一起量）；
- 6 份 `provideXxx()` 里移除这些条目（它们不再装 root）；
- 2 处手写订阅（`tool-guidance.service.ts:179` / `session-mode.service.ts:539`）→ 各做成声明了 scope 的 Provider，`inject` 它的域直接用；
- `zephyr` 的装配器：`fillInjections` 加事件字段绑定 + 按 scope 过滤 + 每 agent 调一次（已完成）。

## 五、下一票的两处形态（走「顺依赖链 per-agent 化」时必须按这两条来）

1. **per-agent 装配的触发点 = 适配行包一层 `kFace` 实例的方法。**
   上游 `AgentRegistry.setFactory` 是独占的（重复注册直接抛 `an agent factory is already registered`），
   `CreateAgentOptions.setup` 又由上游 `api/session-controller` 传入——我们**唯一的缝**是
   `dsh-agent-loop` 的 `AgentLoopDefault` 适配行：就地包装 `kFace`（上游 `AgentLoopService` 实例）上的
   `createAgent` / `resume`，把 `AgentScopedRows.install(agentCtx)` 链到调用方 `setup` 前后。
   先例是 `packages/agent/dsh-conversation/src/server/api-session.provide.ts` 的 `attachWorkspaceOnCreate`
   （同一手法：`upstream.create = async (request) => …`，不改 vendor）。
2. **`fromCordis.mount` 的 owner 要跟着 scope 走。**
   它现在对 cordis `Service` 子类强制用**根 ctx** 构造（`compat/from-cordis.ts:355-358`，理由是「兄弟行沿
   fiber 链到 root 才找得到」）。per-agent 行因此会把服务注册到根，第二个 agent 再装就撞名——走这一票时
   必须改成「用传入的行 ctx（的父）」，与决定 5 同一条：**行注册在装它的那个 ctx 上，作用域就跟着那一层**。
3. **量法的判据**：对每个消费方问一句「同一个 agent 里的两个会话，这个服务该不该共享？」——
   该共享留 root，不该才 `@AgentScoped()`。端点宿主（`JobControllerRow` / `SkillCatalogRow` 这类带
   `remoteDescriptor` 或上游 `Service` 单例的）要单独判，不能跟着工具行一起挪。
