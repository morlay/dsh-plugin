# per-agent 插件的装配位置（`AgentProviderGroup.entries` 的读取方）

状态：已对齐——形态定了，实现另排一票（`zephyr` 与 `agent` 各一半；`create` 那条路径的代价记在「七」）。
范围：`AgentProviderGroup.entries` 与 `@AgentScoped()` 的语义、per-agent 行的装配点、`mountRow` 的事件字段绑定、两处 `agent.ctx` 手动订阅的归属。
非目标：不改上游建 agent 的流程本身；不为「显式传 ctx 的订阅口子」开口子（见六）；`scopeOf` 保留给诊断，不当装配手段。
关联：`packages/agent/dsh-agent/src/contract/agent-scope.ts` · `packages/zephyr/zephyr/src/bootstrap.ts` · `packages/zephyr/zephyr/src/event-emitter.ts` · 上游 `core/scope/src/index.ts`、`core/agent-loop/src/index.ts`、`core/agent/src/index.ts`

## 一、决定

| #   | 议题               | 决定                                                                                                  | 一句话理由                                                                    |
| --- | ------------------ | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1   | `entries` 的读取方 | agent 创建处：`AgentLoopDefault` 覆写 `createAgent` / `resume`，把条目并进 `CreateAgentOptions.setup` | 声明了没人读就是死声明；这里也是唯一拿得到 `agentCtx` 的地方                  |
| 2   | 装配作用域         | 在 `setup(agentCtx, agent)` 给的 `agentCtx` 上逐条 `mountRow`                                         | 那个 ctx 带 agent 的 scope 标记，令牌的 `bus` 因此就是 agent 的               |
| 3   | 标记的语义         | `@AgentScoped()` = 「这个 Provider 由 per-agent 组装配」，不再是「装在 root、内部按 agent 分层」      | 标记与装配位置必须是同一件事，否则清单没法机械核对                            |
| 4   | root 清单          | 组里的条目从各自 `provideXxx()` 移除                                                                  | 同一服务在两个作用域各一份 = 两份状态、双订阅                                 |
| 5   | 两处手动订阅       | 各自收成 per-agent Provider，`inject` 到它的行直接用，调用点不再出现 `agent.ctx` / `scoped`           | 订阅面由装配位置决定，不由调用点传参决定                                      |
| 6   | 共享单例怎么挡     | 按**令牌名**判：某条目的令牌已经在 root 的装配表里、而它没标 `@AgentScoped()`，装配期直接抛错         | 名字才是装配身份（`byName` 就是按名字建的表）；撞名要从运行期两份变成装配期红 |

## 二、现状事实

`AgentProviderGroup` 有 **6 个实现**（工具策略 · 会话端点 · job · skill · 工作目录 · ptc），全仓**零处**读 `entries`：`grep -rn 'AgentProviderGroup' packages --include='*.ts'` 只命中定义与这 6 个类，`isAgentScoped` 也零消费方。

同一批类在各自的 `provideXxx()` 里被显式列出（`provideWorkingDirectory` / `provideToolPolicy` / `providePtc` / `provideApiSession` / `provideSkill` / `provideJob`），所以它们现在**全装在 root**；`agent-scope.ts` 的文件头与 `@AgentScoped()` 的注释都把这件事写成了现行口径（「它不改装配位置」）。

`agent.ctx` 是带 scope 标记的 ctx：上游 `ReactLoopAgent` 构造里 `createScope(loopCtx, this)`，后者 `ctx.plugin(scope)` 再把 `fiber.ctx.extend({ [kScope]: key })`——`agent.ctx = scope.ctx`。所以在它上面 `plugin` 就等于进该 agent 的 scope。

上游给的装配钩子是 `AgentSetup = (agentCtx: Context, agent: Agent) => AgentSetupCommit | Promise<AgentSetupCommit | void> | void`（`CreateAgentOptions.setup`），`commit()` 是发布前的同步校验/回滚点；`AgentRegistry.create(options)` 直接把它转给 `createAgent(ownerCtx, options)`。

`mountRow(ctx, provider, config)` 已导出：按传入 ctx 读服务、在 `ctx.plugin` 里跑 `onInit(child)`。它**不给 `EventEmitter` 字段绑 ctx**（只处理 `injectPlaceholderOf`），所以用它装的 Provider 一调令牌的 `on(...)` 就抛「装配完成前被使用」。

`bootstrapApplication` 那条路给事件字段绑的是**应用根 ctx**（`fillInjections(instance, instances, multi, ctx)` 在 `ctx.plugin` 之前跑），与 `event-emitter.ts` 类注释写的「本行 ctx」不符。

两处仍在手写字符串的订阅都在 `agent.ctx` 上，且都必须是那个作用域：`tool-guidance.service.ts` 的 `scoped`（团队 / schedule 这类行在会话建好**之后**才把工具注册进 agent scope）、`session-mode.service.ts` 的 `agentCtx`（`agent/request` 是 `Scoped<Agent>` 的 scope-filtered dispatch）。

## 三、模块边界与接口

| 模块                                        | 拥有（职责与不变量）                                              | 不拥有（明确排除）                  | 依赖方向                        | 接缝 / 适配器     |
| ------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------- | ------------------------------- | ----------------- |
| `AgentProviderGroup`                        | 条目清单与顺序的声明                                              | 装配执行、实例化                    | 各域 → `dsh-agent`              | 无（纯声明）      |
| per-agent 装配（`AgentLoopDefault` 的覆写） | 读清单、按序装配、失败回滚                                        | 注入解析（归 `mountRow`）、条目内容 | 装配点 → `zephyr` 的 `mountRow` | 上游 `setup` 钩子 |
| `mountRow`（`zephyr`）                      | 单行装配：实例化 / 字段注入 / `onInit` / **事件字段绑传入的 ctx** | 条目清单、清单顺序                  | 装配点 → `zephyr`               | 无                |
| 两处订阅 Provider                           | 该 agent 的订阅生命周期                                           | 事件名与参数表（归令牌）            | agent 行 → 令牌                 | 无                |

接口（`entries` 的语义，调用方需要知道的全部）：

1. **顺序即装配顺序**，同一条目只装一次。
2. 条目在**该 agent 的装配上下文**里实例化——每个 agent 一份，跨 agent 不共享。
3. 条目的 `inject` 沿 `agentCtx` 的父链解析到 root 已就绪的服务；两个 agent 的同名 per-agent 服务互不可见。
4. 条目里的 `EventEmitter` 字段绑到**该 agent 的 ctx**（不是根 ctx）。
5. 装配失败发生在 `commit()` 之前时，整个 agent 创建回滚——不留半个 agent、不留半个 scope。
6. **只列 per-agent 的条目**由写 `entries` 的人负责；机械兜底是装配期检查（见决定 6），报错里给令牌名。

契约变更：

| 契约                      | 现在               | 谁必须跟着改                                                                                          |
| ------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------- |
| `@AgentScoped()` 的语义   | root 标记 + 诊断   | 6 个实现类、`agent-scope.ts` 的文件头与装饰器注释                                                     |
| `mountRow(ctx, provider)` | 只填 `inject` 字段 | `zephyr` 的 `bootstrap.ts` 与它的 spec                                                                |
| `zephyr` 的装配表查询     | 无                 | 新增「这个令牌是否已在 root 装配」的查询面，per-agent 装配点用它做决定 6 的检查                       |
| root 的 `provideXxx()`    | 含 per-agent 条目  | `dsh-agent` / `dsh-agent-loop` / `dsh-ptc` / `dsh-skill` / `dsh-job` / `dsh-conversation` 的 6 份清单 |

## 四、行为与边界

- 正常路径：`createAgent` → `setup(agentCtx, agent)` 里按清单逐条 `mountRow(agentCtx, …)` → agent 的第一次 `pre-step` / `request` 时这些行已经在了。
- 失败与回滚：任一条装配失败，`commit()` 之前的回滚由上游负责；报错要带上条目名与该 agent 的 id。
- 生命周期：`agentCtx` 收起时 per-agent 行随之卸载，令牌订阅跟着停——行自己不必再记 disposer。
- 隔离：per-agent 行看到的是自己 agent 的 scope；root 行看不到它们的服务（事件沿父链只往上，不往下）。
- 漏装的样子：某个 `entries` 没被装，表现是「该 agent 少了一条 section / 少了一个工具 / 模型选择不生效」，失败点离装配点很远——所以判据要断言装配后的服务面，而不是等行为异常。

## 六、取舍

| 选项                                             | 否掉的理由                                                                                                                                |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `EventEmitter.onIn(ctx, …)`（订阅时显式传 ctx）  | 把「隔离」变成「调用点自己传 ctx」——正是框架设计要避免的。它解的是症状（订阅点拿不到 agent ctx），不是病因（per-agent 行没装在 agent 里） |
| 保留 `entries` 死声明、继续 `agent.ctx` 手动分层 | 清单永远是死表；每个域各写一遍分层代码，事件作用域根本不对（两处 `scoped` 就是证据）                                                      |
| per-agent 行继续装 root、靠 `scopeOf(ctx)` 分层  | 状态要自己做 per-agent 表，且 `scopeOf` 只是读标记，换不来事件隔离                                                                        |
| 在 `agent/created` 事件里补装 per-agent 行       | 晚于第一次 `pre-step`（事件在 announce 附近派发），会出现「第一个请求看不到 per-agent 行」的窗口                                          |

## 七、不做与已知债

- 不做 per-agent 的 `without` / `configure`（条目替换）：没有消费方；要做也是装配面的事，不在本设计里。
- 已知缺口（顺带收，同一个病）：`bootstrap.ts` 的 `fillInjections` 给事件字段绑的是根 ctx，与 `event-emitter.ts` 的注释不符；`mountRow` 的事件字段绑定和它是同一件事，判据 5 一起销账。
- 债 [`AgentLoop.create` 起的 agent 没有 per-agent 行](../debts/20261118-AgentLoop.create起的agent没有per-agent行.md)（判据零命中，本笔不覆写 `create`）。
