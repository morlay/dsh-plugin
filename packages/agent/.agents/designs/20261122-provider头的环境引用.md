# provider 头里的环境引用（`Bearer ${OLLAMA_API_KEY}`）

状态：**已实施**。
范围：`llm-pi-ai` 的 provider profile 里 `headers` 值的解析时机与来源；装配层的 ollama 路由。
非目标：设置视图的装配层与脱敏（见[设置视图带装配层与密钥脱敏](./20261122-设置视图带装配层与密钥脱敏.md)）；
凭证服务（这条路由的凭据就是部署给的环境变量，不走 `credentials`）。
关联：[`@morlay/dsh-agent` README](../../dsh-agent/README.md)

## 一、背景

走 `api: "anthropic-messages"` 的第三方网关（Ollama Cloud）认 `Authorization: Bearer <key>`；
pi-ai 的 Anthropic 实现把 `apiKey` 发成 **`x-api-key`**（Anthropic 官方语义），所以只靠
`apiKeyEnv` 会 401——密钥其实取到了，只是放错了头。

那个 Bearer 头不能手写进 `configure(LlmPiAi, { providers })`：装配层是 `settings/describe` 的 `base`，
会随设置页下发到浏览器。先前那次「删掉手写头」的修法因此是对的（密钥不该进行 config），
但没补上「密钥怎么进请求头」这一半。

## 二、决定

| #   | 议题           | 决定                                                                                     | 一句话理由                                                         |
| --- | -------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 1   | 配置里写什么   | profile 的 `headers` 里写**环境引用**：`Authorization: "Bearer ${OLLAMA_API_KEY}"`      | 引用不是密钥：装配层、`settings/describe`、日志里都只是这个字符串   |
| 2   | 什么时候解析   | `LlmPiAi` 在 `mount` 前解析，结果只进**运行期 config**（不进 `rowConfig`/base）        | `settingRow` 的 base 读的是 `rowConfig`，派生值天然不随视图下发    |
| 3   | 从哪读值       | `LaunchEnvironment` 的冻结快照（进程环境 → 项目 `.env` → `$DSH_HOME/.env`），**不走凭证** | 这几条 provider 的 key 是部署给的环境变量；凭证服务是「用户在 UI 里存 key」那条路 |
| 4   | 取不到怎么办   | 这个头**摘掉**（不发），不留 `Bearer `、也不发引用字面量                                  | 半截值只会把 401 变成更难查的 401；摘掉后退回 pi-ai 的默认头        |
| 5   | 解析范围       | 只动 `providers[*].headers` 的字符串值，别的字段里的 `${…}` 原样保留                    | 引用语法只属于请求头；在 `baseURL`/`models` 上做替换是误伤         |

## 三、实现位置

- `packages/agent/dsh-agent/src/llm-pi-ai-headers.ts`：纯函数 `resolveHeaderReferences(config, lookup)`
  （`structuredClone` 后改，输入不动）。
- `packages/agent/dsh-agent/src/llm-pi-ai.service.ts`：`LlmPiAi.mount` 覆写，解析后再交给上游插件。
- `apps/zephyr-custom/src/zephyr.provide.ts`：ollama 路由的 `headers.Authorization` 就是那条引用。

## 四、验收判据

| #   | 判据（Done when）                                                             | 层       | 证据（用例名）                                                                 |
| --- | ----------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------- |
| 1   | 有值就替换，输入对象（装配层那份）仍是引用字符串                               | 纯函数   | `llm-pi-ai-headers.spec.ts`「取得到就替换；输入对象不被修改」                |
| 2   | 取不到 / 空值 / 没有快照 → 这个头被摘掉                                        | 纯函数   | `llm-pi-ai-headers.spec.ts`「取不到（或空值）就把这个头摘掉，不发明细量」     |
| 3   | 非 headers 字段里的 `${…}` 不动                                              | 纯函数   | `llm-pi-ai-headers.spec.ts`「没有引用的头原样保留」                           |
| 4   | 装配层 `base` 里是引用字符串，describe 的响应里没有真密钥                     | 装配级   | `llm-providers.spec.ts`「装配层配的 ollama route 出现在 …」                    |

## 五、取舍

- **不新增 `llm-pi-ai/request-headers` 监听器**：那个 waterfall 是**同步**的，而取值（无论凭证还是快照）
  在同步面外；在 `mount` 时解析一次更短，也不用维护缓存与失效。代价是运行期改环境变量不会热更新
  （本来 `@Setting` 这条路也要重启，见同包 `20261030` 债）。
- **不做通用插值引擎**：只认 `${NAME}` 且只作用于 `headers`。给配置加一门表达式语言，比这个需求大得多。
- **不把这条路由改成 `openai-completions`**：那也会让 pi-ai 发 Bearer，但会换掉线协议（思考字段、图片、
  兼容开关全跟着走），而部署选 `anthropic-messages` 是既有事实。
