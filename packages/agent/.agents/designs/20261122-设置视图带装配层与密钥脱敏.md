# 设置视图带装配层（base）与密钥脱敏

状态：**已实施**。
范围：`settings/describe` 的命名空间视图（`value` / `base` / `user` / `secrets`）、schema 注册表的注册面、
`llm-pi-ai` 的装配值与脱敏。
非目标：配置的**运行期生效**（改完要重启那条债，见同包 `dsh-setting/.agents/debts/20261030-配置变更即时生效.md`）；
UI 的渲染规则（模型页读这些字段的方式由上游 `ui-settings-models` 拥有）。
关联：[`@morlay/dsh-setting` README](../../dsh-setting/README.md) · [包内子域拆分与注册抽象](./20261028-包内子域拆分与注册抽象.md)

## 一、决定

| #   | 议题           | 决定                                                                                          | 一句话理由                                                                     |
| --- | -------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | 装配层进视图   | `@Setting` 的 `settingRow` 注册 schema 时一并交出**行 config**（`configure` 给的 patch），视图多一个 `base`；`value` = schema 默认 ⊕ base ⊕ 用户层 | 模型页按 `value` 的 `settingsPath` 判「provider 配没配」，缺 base 时装配里配好的 provider 永远显示「未配置」 |
| 2   | 注册面形状     | `SettingSchema.register(ns, schema, base?)`：第一个参数从「`toJSON()` 的结果」改成**活 schema**（`Config` 本身） | 脱敏要走活的 schemastery 节点（`role('secret')`），序列化后的 JSON 走不动            |
| 3   | 密钥怎么出     | 三层都过一遍上游 `redactSecrets`（`@deepseek-ai/dsh-settings`），`secrets` 如实给位置与「有没有值」 | 密钥只写不读；不引上游实现就得自己抄一份 100 行的结构行走器                      |
| 4   | 装配里的密钥   | 删掉 `apps/zephyr-custom` 里 ollama 的 `headers.Authorization`，只留 `apiKeyEnv`          | 手写的头等于把密钥抄进行 config，而 base 要下发浏览器；上游按 `apiKeyEnv` 取 key 自己发头 |
| 5   | `user` 的语义 | 仍然只放用户写过的层（`settings.json` 的原值，密钥已抹）                                     | `ui-settings-models` 的 `removable`、`config-form` 的 `draft.user` 都按这个语义判断 |

## 二、现状事实（改前）

- `settings/describe` 的视图只有 `value`（schema 默认 ⊕ 用户层）与 `user`；`secrets` 恒 `[]`，
  `base` 字段不存在。注释把它记成「本装配没有 base 分层、没有密钥脱敏」。
- `llm-pi-ai` 的 provider 路由有两种来源：`settings.json`（用户层）与装配层的 `configure(LlmPiAi, { providers })`。
  模型页 `store.ts` 的 `configured` 判据是「`value` 在 `settingsPath` 处非 undefined」，所以**装配层的路由一律显示「未配置」**，
  只出现在「添加 provider」下拉里；用户改它的 `baseURL` / 模型时要重配一份。
- 装配里 ollama 那条路由把 `OLLAMA_API_KEY` 拼进 `headers.Authorization`。这份值属于行 config，
  一旦 base 下发，密钥就随 `settings/describe` 进浏览器。
- 用户层的密钥（`llm-deepseek-api-key` 的 `apiKey`）此前也**原样**随 `value`/`user` 下发——同一条缺口。

## 三、模块边界与接口

| 模块                                | 拥有                                                       | 不拥有                       | 依赖方向                                  |
| ----------------------------------- | ---------------------------------------------------------- | ---------------------------- | ----------------------------------------- |
| `SettingSchema`（`@morlay/zephyr-app`） | 命名空间 → 活 schema / 序列化 JSON / 默认值树 / 装配层     | 视图的形状（那是端点的）     | ← 各注册行                                |
| `@Setting` 的 `settingRow`（`@morlay/dsh-setting`） | 「读持久化 → mount → 注册 schema」这一条模板               | 具体 setting 项的字段        | ← `SettingSchema`                        |
| `settings/describe`（端点）        | 三层合并、脱敏、`revision`                                | 谁注册了什么（只读注册表）   | ← `Setting` 文档 / `SettingSchema`      |

**接口**（调用方要知道的一切）：

- `SettingSchema.register(ns, schema, base?)`：`schema` 是活的上游 `Config`（要有 `toJSON()` 且节点结构可被脱敏行走）；
  `base` 是装配层，省略即没有。
- 视图字段：`value`（生效值，脱敏后）、`base`（装配层，脱敏后，没有就是 `{}`）、`user`（用户层，脱敏后，没写过就没有这个键）、
  `secrets: { path: string[]; set: boolean }[]`（schema 声明的每个密钥位）。
- 写回仍是 `settings/mutate` 的路径操作（在**内存的完整文档**上改），所以脱敏掉的空值不会覆盖已存密钥。

## 四、行为与边界

1. **三层合并**：`value = mergeTree(mergeTree(默认值, base), user)`，dict 逐键合并（用户的 provider 与装配的 provider 并存）。
2. **装配层可见**：`configure(LlmPiAi, { providers: { ollama } })` 之后，`llm-pi-ai` 视图的 `base.providers.ollama` 与 `value.providers.ollama` 都在。
3. **密钥只写不读**：三层里的 `role('secret')` 字段都不出现；`secrets` 给出 `{ path, set }`。
4. **没写过就是缺省**：`user` 不能拿 base 或默认层冒充（`removable` 判定依赖这一点）。
5. **没有活 schema 的命名空间**（理论上不会出现）按不脱敏原样返回，不退化成报错。

## 六、取舍

- **复用上游 `redactSecrets`**：它是 100 行结构行走器（object / dict / array / union / transform），自己抄一份没有第二个消费者。
  代价是 `dsh-setting` 多一条 `@deepseek-ai/dsh-settings` 依赖，且注册面必须给活 schema（`toJSON()` 不够）。
- **装配层的密钥不落配置**：删掉手写的 `Authorization` 头而不是在 describe 里给它特判脱敏。凭据引用（`apiKeyEnv`）
  是上游认的身份，密钥在请求期由凭证服务解析；把值抄进配置既冗余又不安全。
- **`base` 用行 config，不用「行 mount 后的生效 config」**：后者已含用户层，混进 base 后 `user`/`base` 的分界就没了，
  `removable` 会跟着错。

## 七、不做与已知债

- 不做运行期生效（同包的 `20261030` 债）：改完配置仍要重启。
- `secrets` 只覆盖 `role('secret')`。`llm-pi-ai` 的 `headers` 没有这个标，所以装配里若再手写密钥头，脱敏拦不住——
  这条靠「别把密钥写进配置」守，见第六节。
