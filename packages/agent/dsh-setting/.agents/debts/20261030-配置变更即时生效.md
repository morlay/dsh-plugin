# 配置写入后的「即时生效」还没闭环

- **状态**：已知，未修
- **影响**：改 `llm-*` 的配置后要**重启**才生效；启动时应用持久化值已生效（有 spec 覆盖）
- **现象**：`Setting.onChange` → `fromCordis.remount()` 会撞上游的唯一性校验

  ```
  LlmError: configurable provider "deepseek-official" is already declared
  ```

- **原因**：上游 `LlmRuntime.registerConfigurableProviders()` 的撤销句柄挂在插件自己的 effect 上；
  `remount()` 走的是 `disposeProvider()`（上游 disposer + `fiber.dispose()`），实测旧注册没在
  新 `apply` 之前撤掉，于是第二次声明同名 provider 直接抛错。
- **可能的解法**（按代价排序）

  1. 用上游 `DirectoryRegistrationHandle.replace(entries)`：它是**原子替换**，不重挂载整行；
     代价是要让 `LlmPiAi` / `LlmDeepseek` 这两行把 handle 存下来（上游插件内部创建，得看它是否透出）。
  2. `remount()` 里先 `await` 一轮 `fiber.dispose()` 的收尾（例如 `await Promise.resolve()` 后重试一次）——
     治标，依赖上游清理时序。
  3. 不改运行期：设置页明示「重启后生效」。

- **已尝试并回退**：`Setting.onChange` 广播 + `fromCordis.remount()`（卸载后重挂载）。
  实测两个 llm 行都撞 `already declared`，permission 行则"不报错但也不生效"——说明上游的配置/注册
  生命周期不能靠重挂载绕。相关代码已回退（不留死胡同），本债记录结论。
- **已生效的部分**：[llm-pi-ai.service.ts](../../../dsh-setting/src/llm-pi-ai.service.ts)、
  [llm-deepseek.service.ts](../../../dsh-setting/src/llm-deepseek.service.ts) 的 `onInit` 会先把
  `settings.json` 里的值合进 `providerConfig` 再 `mount`（spec：`setting.spec.ts` 的「启动时应用持久化配置」）。
