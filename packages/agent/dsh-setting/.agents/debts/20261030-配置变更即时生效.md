# 配置写入后的「即时生效」没闭环：改 `settings.json` 要重启才生效

状态：未销账——`@Setting` 的行在 `mount` 时读一次持久化值；运行期改设置只改文档与落盘，不重挂行
位置：`packages/agent/dsh-setting/src/setting.decorator.ts`（`settingRow` 的 `onInit` 读 `Setting.snapshot()[ns]` 后 `mount`）；消费方示例 `packages/agent/dsh-agent/src/llm-pi-ai.service.ts`、`packages/agent/dsh-agent/src/llm-deepseek.service.ts`

**现象**

- 启动时：`settings.json` 里对应命名空间的值会合进这一行的 `Config` 再 `mount`（`settingRow` 的模板），所以**重启后**配置生效。
- 运行期：`Setting.update` / `replace` 只改内存文档、排进 `SettingLoader` 的写盘队列（`packages/agent/dsh-setting/src/setting-loader.service.ts`），**没有任何行被重挂**。所以改 `llm-*` 的配置后，模型面的行为仍是旧配置，直到重启。
- 重挂这条路走不通：上游 `LlmRuntime.registerConfigurableProviders()` 的撤销句柄挂在插件自己的 effect 上，同一行重挂会在第二次 `apply` 撞 `LlmError: configurable provider "<provider>" is already declared`（`vendor/deepseek-harness/packages/llm/llm/src/index.ts`）。

**影响**

改完配置的人会看到「文档里已是新值、界面上仍是旧行为」：模型目录、provider 的 key / baseURL 都要重启一次才生效。写设置的人不会收到任何提示——保存成功、落盘成功。

**触发条件**

要让运行期改 `llm-*` / 其它 `@Setting` 命名空间的配置立即生效时；或在设置页上承诺「保存即生效」之前。

**销账条件**

Done when：`Setting` 文档变更后，对应行的 `Config` 在**不重启**的前提下被重新应用（用一条 spec 断言：`update` 之后该行观察到新值），且没有 `already declared` 报错。

**不修的理由**

三条候选路线的成本都不只是这一处：

1. 用上游 `DirectoryRegistrationHandle.replace(entries)`（原子替换，不重挂整行）——要把 handle 从上游插件内部取出来，得先看它是否透出；
2. 重挂前等一轮 `fiber.dispose()` 收尾——治标，依赖上游清理时序；
3. 不改运行期，在设置页明示「重启后生效」——只是把债换个说法。

现状把「启动时应用持久化值」做到了（`settingRow` 的模板 + `SettingLoader` 的 `initial()`），但那条路径**没有专门的 spec**：`packages/agent/dsh-setting/src/__tests__/setting.spec.ts` 只覆盖文档读写、落盘（「`replace` 落盘；重建整套实例后仍读得回（重启不丢）」）与 `settings/*` 端点，没有一条断言「行在 `mount` 时读到了 `settings.json` 的值」。运行期生效与这条测试缺口是同一处的下一步。
