# 桌面内嵌浏览器面板

状态：设计（Q1/Q2 待与用户对齐：见文末两个岔口）。
范围：`packages/zephyr-desktop/zephyr-desktop-shell/src/`（主进程的 pane 接缝、窗口安全面）与一个新的客户端面板包（侧栏 tab）。
非目标：跨 realm 的 CDP inspector（同 [开发者模式与主进程 Inspector](./20261117-开发者模式与主进程Inspector.md)）；
也**不做**「agent 驱动这个面板」——agent 的浏览器是另一套（见下「三、与 browser-use 的分工」）。
关联：[桌面壳功能面](./20261111-桌面壳功能面.md) · [桌面两包与单进程壳](../../zephyr-desktop-bundle/.agents/designs/20261110-桌面两包与单进程壳.md)

## 一、上游是什么（读的是干净基线 `38a6a5c965`）

上游 `packages/client/ui-sidebar-browser`（`@deepseek-ai/dsh-client-ui-sidebar-browser`，"Sandboxed Web
browser tabs for the right Sidebar"）**没有 host 侧实现**：`src/index.ts` 的 `apply()` 是空函数。它真正要的东西写在
`src/types.ts` 里，是一份 **desktop bridge** 契约：

```ts
interface DesktopBrowserBridge {
  acquire(workspace: string): Promise<{ lease; partition }>; // 主进程批准一块 storage 分区
  release(lease): Promise<void>;
  onOpenRequested(lease, listener): () => void; // guest 里点了链接 → 主进程裁决
}
```

渲染侧有两条实现：`IframeImpl`（同源/开发期）与 `ElectronWebViewImpl`（`<webview>` + 上面的 bridge）。
它的侧栏挂载靠 `dsh.client.inject` 的三行（`ui-sidebar-right` / `ui-session` / `api-workspace-controller`）
与 slot `sidebar.right.pane.tab`——**这一层我们能直接用**（我们已经有同一个 slot：`SessionModePanelView`
就挂在 `sidebar.right.pane.tab`）。

**不能直接抄它的原因**：它假设宿主是上游 `apps/desktop`（有 `webviewTag`、有它自己的 bridge 实现、
有多窗口/多 realm 的假设）。我们的壳是单窗口、`sandbox: true`、`webviewTag` 关着、渲染进程只认
`__DSH_*` 那几个 preload 桥（`ipc.ts` + `preload.ts`），而且窗口的 `setWindowOpenHandler` 一律拒。
所以**客户端那半（侧栏 tab、地址栏、tab 状态）按我们的 slot 重写**，主进程那半按下面的接缝做。

## 二、决定

| #   | 议题             | 决定                                                                                                                                                                                                                                          | 一句话理由                                                                             |
| --- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 1   | 谁创建浏览器实例 | **主进程创建 `WebContentsView`**（渲染进程只报一个矩形）。`webviewTag` 保持 `false`                                                                                                                                                           | 渲染进程不创建原生对象就没有第二条权限面；`webview` 会把「谁能开浏览器」变成页面说了算 |
| 2   | 接缝             | `BrowserPanePort`：`open` / `setBounds` / `close` / `navigate` / `state` / `partition`；适配器 `WebContentsPaneView`（Electron），测试用假适配器                                                                                              | 与 `InspectorPort` 同一条做法：主进程侧可假、渲染侧只发意图                            |
| 3   | 导航归谁         | **主进程**：地址栏、前进后退、外链裁决都在 pane 里；渲染进程只发 `navigate(url)` / `back` / `reload` 这种意图，状态从主进程回推                                                                                                               | 判据只有一处就绕不过去：渲染进程拿不到「任意导航」的能力                               |
| 4   | 允许什么         | 只允许 `http:` / `https:`；`javascript:` / `file:` / `data:` / `about:` 一律拒；外链仍交系统浏览器                                                                                                                                            | 面板是「浏览网页」，不是「在应用里执行任意内容」                                       |
| 5   | 权限与隔离       | pane 用**独立 session 分区**（`persist:zephyr-browser`），`sandbox: true` / `contextIsolation: true` / `nodeIntegration: false` / **不挂 preload**；session 上 `setPermissionRequestHandler` 全拒、`setPermissionCheckHandler` 全假、下载拒绝 | 面板里的页面不该拿到壳的任何入口；权限默认拒绝，需要时再按 origin 开口                 |
| 6   | 生命周期         | 关面板、关窗、`quit()` 都销毁 view（`webContents.close()`）；同一时间最多一个 panel 实例（侧栏只有一个浏览器 tab）                                                                                                                            | 与 Inspector 同一条：退出不留监听/子进程                                               |
| 7   | 外链处置         | 面板里 `target=_blank` / 脚本开窗：**http(s) 交系统浏览器**（`shell.openExternal`），面板自己仍 `deny`；其它协议直接丢弃                                                                                                                      | 面板只有一块：开第二块会带来第二套导航判据；「点了没反应」也不行——所以外抛而不是静默   |
| 8   | state 的出口     | **只有一条**：主进程推 `browserChanged`（`{ id, state }`），渲染侧不推导；面板关闭 / 窗口关闭都退订                                                                                                                                           | 两份推导早晚不一致（地址栏与真实 URL 打架）；退订漏了就是关掉之后还在推                |
| 9   | preload 桥       | `__DSH_BROWSER_PANE__` **只转发**五个意图 + 一条订阅，不带任何判据                                                                                                                                                                            | 判据只有一处（主进程）才绕不过去；桥里放白名单等于给渲染侧第二个真相                   |

## 三、与 browser-use 的分工（不做的事）

agent 的浏览器不在这里：`apps/zephyr-custom/src/zephyr.provide.ts` 的 `provideAgentUse()` 起的是
`agent-browser mcp` 这条 MCP 客户端（外部 CLI，自己带 Chrome + CDP），模型面看到的是 `browser_*` 工具。
**本轮不改它**，也不把面板接进 CDP：

- 面板 = **人**的浏览器（点链接、看文档），生命周期跟着窗口；
- `browser_*` = **agent** 的浏览器（它自己起、自己关、sandbox 按 `SandboxPolicy`）；
- 将来的桥只有一个方向：「把面板当前页交给 agent 的浏览器打开」——实现是给 MCP 侧一条
  `open_url`，**不是**把面板的 `webContents` 暴露成 CDP 端点（那会绕开 agent 侧的 sandbox 判据）。

## 五、行为与边界

- 打开：侧栏 tab → `IPC pane.open({ url? })` → 主进程建 `WebContentsView` 并 `setBounds` 到渲染进程报的矩形。
- 尺寸：面板布局变化 → `pane.setBounds(rect)`（节流到下一帧；`rect` 用窗口坐标系）。
- 导航：地址栏 → `pane.navigate(url)`（主进程判 `browserUrlAllowed`，否则保持当前页并回推错误）；
  页内点链接 → 主进程的 `will-navigate` 判据（http/https 放行，其它拒）；`window.open` 一律拒。
- 状态回推：`did-navigate` / `did-start-loading` / `page-title-updated` → `pane.state`（url、title、canGoBack、loading）。
- 关闭与退出：关 tab / 关窗 / `quit()` 都 `pane.close()`（销毁 `webContents`）。
- 失败：地址非法 / 权限被拒 / 加载失败 → 面板里显示一行原因，不弹原生框、不退出。

## 七、取舍与债

- **不用 `<webview>`**：它要求打开 `webviewTag`（渲染进程能造原生 webContents），与「渲染进程只报矩形」冲突；
  上游那套 `DesktopBrowserBridge`（lease + partition）在我们这里没有对应的主进程宿主，硬接要多一层 lease 语义。
- **暂不做多 tab**：侧栏只有一个浏览器 tab；多 tab 属于面板内部的 UI 决定（真要做，pane 的 key 换成 tab id）。
- **债**：面板的 `bounds` 由渲染进程报（窗口坐标系换算在页面侧）。窗口缩放时若页面侧节流过度会短暂错位——
  真要修就改成主进程按 `BrowserWindow` 的 `contentBounds` 与 DPR 自己算。

## 八、两个岔口（需要用户点头）

- **Q1：面板实例归谁？** (A) 主进程 `WebContentsView`（本设计的选择：权限面最小，但要写 bounds 同步）；
  (B) 渲染进程 `<webview>`（写起来快，等于给渲染进程开了造原生容器的口子）。建议 A。
- **Q2：面板要不要默认出现？** (A) 侧栏 tab 常驻（用户自己点开）；(B) 首次启动就把浏览器 tab 放出来。
  建议 A（打包形态没有开发项，多一个常驻 tab 是产品决定）。
