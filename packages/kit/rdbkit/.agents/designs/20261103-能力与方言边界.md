# 能力与方言边界

状态：已实现（2026-11-03）

范围：本包（`packages/kit/rdbkit/`）。
约束：业务包只拿注入的 `Database`，不接触方言、连接与 SQL 文本；能力不够时下沉到这里，不许散回业务包。

## 结论摘要

| 议题           | 结论                                                                   | 一句话理由                                                     |
| -------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- |
| 业务侧接口     | 表句柄（`select` / `insert` / `update` / `delete`）+ `E.*` 表达式       | 语义由业务表达，SQL 由 rdbkit 算                                |
| 方言相关表达式 | 片段层按 `only(dialect, …)` 分流（JSON 提取、本地日）                  | 两个分支在渲染时二选一，占位符与绑定参数不会串味                 |
| 事务           | 顶层按实例串行 + 事务内嵌套走 `SAVEPOINT`，用 `AsyncLocalStorage` 判嵌套 | 并发调用的上下文不能靠计数器区分                                |
| 值类型         | `bigint` 列 ↔ JS `bigint`；聚合 `number | bigint`                      | int64 / uint64 超过 `2^53` 用 number 会悄悄丢精度                |
| 库级操作       | `objectNames` / `vacuum` / `sqlitePragma` / `setSqlitePragma`          | `PRAGMA`、`VACUUM`、`sqlite_master` 不该出现在业务包里           |
| 测试辅助       | `@morlay/rdbkit/testing`：`openSqliteHandle` / `createPostgresTestDatabase` | 驱动能力留在这一层，业务包不必为测试再依赖 `pg` / `node:sqlite` |

## 事实基线

- 表定义（`defineTable`）是结构与类型的唯一来源：DDL 由 `ensureSchema` 算差异，行类型由 `RowOf` 推导。
- 表达式分两类：条件（`E.eq` / `E.inList` / `E.and` …）与值表达式（`E.coalesce` / `E.add` / `E.localDay` …）。
  两者都能进投影、条件、分组与 upsert 赋值。
- `Database` 之外的连接管理、方言名、`PRAGMA` 都只出现在装配层（`openDatabase`）。

## 决策与理由

### 方言相关的东西必须是片段，不是字符串分支

早期写法是「SQLite 一份 SQL、PostgreSQL 一份 SQL」的字符串三元，散在业务包里。现在这类表达式由 rdbkit
自己的片段承担：`E.localDay` 渲染成 SQLite 的 `date(…,'localtime')` 或 PostgreSQL 的
`to_char(to_timestamp(…))`；`E.jsonText` / `E.jsonInt` 渲染成 `json_extract` 或 `#>>`。两条分支都用
`only(dialect, …)` 包起来，渲染时只保留本方言的那份——**连同它的绑定参数一起丢弃**，所以不会出现「多一个
占位符」的错位。

### 值类型跟着列定义，不跟着驱动

PostgreSQL 驱动把 `int8` 给字符串、把 `numeric` 给字符串；SQLite 的 INTEGER 给 number。若直接透传，同一份表
定义在两种方言下值类型不同，`uint64` 的 ID 还会在 `Number()` 处丢精度。所以：

- `bigint` 列在读取层归一成 **`BigInt`**（`select` 按投影与 join 的表定义判断）；
- 写入时 `bigint` 列接受 `number`（安全整数范围内等价），业务不必到处写 `n` 后缀；
- 聚合（`count()` / `sum()`）的值类型是 `number | bigint`：PostgreSQL 返回 int8（BigInt），SQLite 返回
  number，业务要 number 就显式 `Number(x)`。

### 事务正确性归这里，不归业务包

业务包不该自己维护写队列。`database.transaction` 承担三件事：顶层事务按实例串行（SQLite 单连接、PG
`serializable` 并发会冲突）、事务内再开事务走 `SAVEPOINT`、事务外的写先排队（不落进别人未提交的事务）。
「当前异步上下文是否在事务里」用 `AsyncLocalStorage` 判断——只看计数器会把并发调用误判成嵌套。

### 两条只有跑 PostgreSQL 才暴露的约定

- **upsert 的赋值要带表名**：`ON CONFLICT … DO UPDATE SET "f_turns" = "f_turns" + excluded."f_turns"` 在
  PostgreSQL 上是 `column reference "f_turns" is ambiguous`，必须写 `"t_session_counts"."f_turns"`。
  业务侧用 `E.column(name, table)` 表达（`E.excluded(name)` 提供新值）。
- **分组用列，不要用带参数的表达式**：PostgreSQL 的 GROUP BY 匹配按语法树，`COALESCE(列, ?)` 在 SELECT 与
  GROUP BY 里是两个不同的 Param 节点，会被判成「不在 GROUP BY 里」。分组写列、表达式留在投影里。

### 结构读取的占位符归渲染层

`readShape` 在 PostgreSQL 上原本写死 `$1/$2`，而 `shapeReader` 按 `?` 编参数——渲染时参数接不上，拼出
`table_name = $2$1`。现在方言的查询一律用 `?`，由 `render` 按方言重编号。

## 验证

- `src/__tests__/transaction.spec.ts`：并发事务、保存点、事务内写与事务同生共死；
- `src/__tests__/expr-functions.spec.ts`：两种方言的表达式渲染与占位符不串味；
- `src/__tests__/database-introspect.spec.ts`：`objectNames` / `sqlitePragma` / `vacuum`；
- `src/__tests__/pg.spec.ts`（`TEST_PG_URL`）：建表 / 聚合 / join / 事务 / 迁移差异，外加 `bigint` 列读回
  `BigInt`。
