# 联邦产物里的装饰器不转（构建侧）

**状态**：接受中（打包形态）。**触发**：`dshdev desktop bundle` 之后、浏览器加载到用装饰器的行时。

## 现象

联邦产物（vite build / rolldown 产出的 `<pkg>@<ver>/client.js`）里**留着未转译的装饰器**：

```js
@Remote listProviders() { … }
```

浏览器一加载就是 `Uncaught SyntaxError: Invalid or unexpected token`，那一行的入口整条不执行。web 形态
**看不出来**，只是因为那时还没加载到这些行（它们是打包形态才装进去的行）。

## 查到的

- **vite dev server**（dev 形态）走 vite 自己的 `transformWithOxc` —— 读 tsconfig、装饰器转得掉；
  **vite build** 的 TS 转译在 **rolldown 内部**，这是两条路。
- **rolldown 的 oxc 不看 tsconfig 的 `experimentalDecorators`**：单测里"无 tsconfig + 只给
  `rolldownOptions.transform.decorator.legacy`"**不转**（`transform` 那份**没被 vite 带进** rolldown，
  或键名不对）；而"有 tsconfig"的那条会转——但它是**按被转译的文件就近向上找**，而外置/官方的包住在
  `node_modules/.pnpm/…` 里，向上找不到解析根那份 tsconfig。
- 当前挂着一处**没被读**的配置：`build.rolldownOptions.tsconfig = <解析根>/tsconfig.json`
  （`index.ts` 的 `tsconfigOf()`），以及 `rolldownOptions.transform`（兜底，实测无效）。
- **决定性实验**（单测）：没有 tsconfig 时，`build.rolldownOptions.transform = { target: "es2022",
  decorator: { legacy: true } }` **仍然不转**（`target` 一起给也一样）。所以不是"少了 target"——**这份
  transform 压根没被带进** rolldown 的 input options（vite 里那句 `...rolldownOptions.transform` 的合并，
  看来不在 build 这条路上）。rolldown 认的是 **tsconfig**（就近向上找）。

## 上游的现状（搜到的）

- **Oxc 支持 legacy 装饰器**（`experimentalDecorators` + metadata emitter，[oxc#9170](https://github.com/oxc-project/oxc/issues/9170)、PR 8614/9057）；
  **不支持** Stage 3 / 原生装饰器（[Vite 迁移指南](https://vite.dev/guide/migration) 明说 "the Oxc transformer does not
  support lowering native decorators"，给的 workaround 是 Babel 或 SWC 插件）。我们这边是 **legacy**（cordis 的
  `@Remote`），属于它支持的那一类。
- 社区给的确切开关是 rolldown 的 **`resolve.tsconfigFilename`**（"It seems to not be active without rolldown
  resolving the tsconfig file"）。
- 另一条已知回归（[rolldown#10281](https://github.com/rolldown/rolldown/issues/10281)）：rolldown ≥ 1.1.2 起，
  被 `exclude` 的文件会**丢掉** tsconfig 的 `compilerOptions`（装饰器原样留下）。我们用 1.2.13，在这个范围里。

## 实测（本仓库）

- `build.rolldownOptions.transform = { target, decorator: { legacy: true } }`：**不生效**。
- `build.rolldownOptions.resolve.tsconfigFilename = <别处的 tsconfig>`：**也不生效**（单测守着：包住在没有
  tsconfig 祖先的 `node_modules/…` 下时，产物里仍有 `@Remote`）。
- 而"包住在有 tsconfig 的地方"时会转（另一条单测）——即 rolldown 认 tsconfig，只是**这条 build 路上我们
  递进去的 `rolldownOptions` 没有落到它手里**（vite 8 对 `build.rolldownOptions` 的合并只认部分键 / 或受
  上面那条回归影响）。

## 为什么先接受

产物是**按请求**产出的，装饰器不转只影响用到装饰器的那些包；而 web/dev 形态一切正常，桌面形态目前靠
"那几行恰好是宿主半、浏览器不加载"没有暴露（这条随行清单变化会失效——所以记在这里）。真要收的时候不
该在两处补偿，得先弄清 **vite 8 把 `rolldownOptions` 的哪些键透传给 rolldown**。

## 想收时怎么收（两条路）

1. **找到真正被读的那一层**：读 vite 8 的 build 路径，确认 `build.rolldownOptions` 里哪些键真的落到 rolldown
   的 input options（`transform` 与 `resolve.tsconfigFilename` 都已证伪）。**首选**——一份事实放一处。
   顺带验证是不是 [rolldown#10281](https://github.com/rolldown/rolldown/issues/10281) 那条回归（换 rolldown
   版本对照即可）。
2. **给 rolldown 一份它就近能找到的 tsconfig**：例如把编译设置随产物落到每个 `<pkg>@<ver>/` 旁。代价是
   产物目录里多出与包无关的文件，且"就近向上找"这条仍是隐式的。
3. **官方 workaround**（Vite 迁移指南给的）：在 rolldown 上挂 Babel（`@rolldown/plugin-babel` +
   `@babel/plugin-proposal-decorators`）或 SWC（`@rollup/plugin-swc`），并用 `filter: { code: "@" }` 只处理
   含装饰器的文件。代价是构建链多一个转译器。

判据：**行**（loader 给的 `dsh.client` + client 半）在浏览器里必须**可求值**——装饰器转不掉就不是可求值
（见 [design](../designs/20261013-客户端资源的联邦式预编译.md) 第 2 条）。
