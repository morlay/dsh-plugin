# vite dev server 与宿主同进程

**状态**：接受中（dev 形态）。**触发**：`dshdev desktop`。

## 是什么

这条链把 vite 的 dev server 起在**宿主进程内**（`startViteDev`，middleware 模式，`serve` 直接吃宿主的
`req` / `res`）。好处是零代理、零端口、HMR 与页面同源；代价是**vite 的命运就是宿主的命运**：它的原生绑定
（rolldown / lightningcss）崩一次是 segfault，宿主跟着没了，于是壳报 `backend stopped` 并退出——用户看到
的是"整个服务被打挂"。

同进程还带来第二个症状：宿主的响应最终要被包成 Fetch `Response`，而 `Response` **不接受 304**，
vite 对源码模块正好回 304（`/@vite/client`、`/index.ts`）——那条路会以异常告终。**已处置**：壳在转发请求
时剥掉 `If-None-Match` / `If-Modified-Since`，并让这条链的产物一律回 200（不做协商缓存）。

## 为什么接受

- 只有 dev 形态存在这个风险；bundle 形态用的是打包产物，没有 vite。
- 崩溃是**偶发**的（原生绑定），且重启一次服务即可恢复；把它隔离成独立进程/线程要引入代理层与生命周期
  管理，收益（"崩了不影响宿主"）暂时不足以抵这份复杂度。

## 想收时怎么收（两条路）

1. **独立进程**（`child_process.fork`）：vite 跑在自己的 node 进程里、监听一个**回环**端口，宿主经它转发
   （与 `ws-bridge` 里给 upgrade 用的那条回环端点同一手法）。崩了就重启子进程，宿主不受影响；代理层是
   http，最简单。
2. **worker_threads**：vite 进 worker，宿主把请求经 `postMessage` 代理过去（worker 内用 mock req/res 跑
   middlewares 的写法与现在 `PortlessWebServer` 的 `SyntheticResponse` 同构）。省一个进程，但请求体要
   跨线程序列化，流式响应的转发比进程方案繁琐。

两条路都要先回答一件事：**HMR 的 ws 落在谁身上**（现在是宿主的回环端点，见
[design](../designs/20261013-客户端资源的联邦式预编译.md)「形态差异」一节）。
