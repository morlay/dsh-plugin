# 客户端资源的联邦式预编译（开发态）

**目标**：开发态的 client 资源只有**一条链**——三方（react / zustand / shiki）与仓库里的包**没有本质区别**：
都由"按请求触发、按包产出"的预编译产出，都带版本、都可独立寻址。产物落盘缓存、跨进程共用，浏览器按
URL 取即可（`/@client-modules/<pkg>@<version>/<export>`）。**它取代**了
[`20261012-开发态客户端按文件直访（ESM）`](../../../../../.agents/designs/20261012-开发态客户端按文件直访（ESM）.md)
里的"按文件直访 + `/deps` 预打包"两分形态。

**形态要点**：

1. **地址只有两种**：本地文件 `@/{filepath}`（仓库里的源码文件）、联邦产物
   `@client-modules/<pkg>@<version>/<export>`。**子路径引用保留子路径**（`@oxc-project/runtime/helpers/decorate`、
   `katex/dist/katex.min.css`），**只有包级引用**才按出口表换成 `client.js` / `index.js`；`client` 不是特殊
   身份，就是清单里的一个普通 export。
2. **谁是 client、谁只是被依赖**（这条是上面"出口表"的判据，别自己扫包猜）：
   - **行是显式的**：只有 **cordis loader 的 entries** 里、清单**声明了 `dsh.client`**、且**有 client 半**
     的包才算行（`clientRowsOf` 就是这份事实的读法）。**浏览器只加载行**。
   - **没声明 `dsh.client` 的入口不加载**；这种包若**被行依赖**，就作为**普通依赖**跟进（"被依赖的另说"）——
     它不构成行，也不按它的**根出口**产出产物。
   - **别拿 `exports` 当身份**：`exports` 是 npm 的机制、原封不动（`./client` 只是普通 export）。上游那些
     `@deepseek-ai/dsh-api-*` 有 `dsh.client`、client 半在 `src/client/`，`exports` 里**没有** `./client` 键——
     按"有没有 `./client`"去判身份，就会把它们当成"根出口"打包出**宿主半**（里面带着只有 node 侧才转的
     装饰器，浏览器一加载就是 `SyntaxError`）。
3. **打包 ≠ 加载**：**打包**按"浏览器请求的那个出口"产出（请求 `x.js` 就产出 `x.js`）；**加载**由**引用方
   写下的 URL** 决定——那个出口名是**外置时**定下的。所以"为什么会加载 `index.js`"要问的是**外置时写了什么**，
   不是打包端做了什么。
4. **一条构建链**（`bundle.ts` 的 `bundlePackage`）：vite 的 lib build（`write: false` → 自己落盘），与 dev
   共用同一套插件（CSS / 资产 / `?raw` / node 替身）。入口的来源分两处，之后合流：仓库包按清单 `exports`
   （出口名 → 源文件；子路径没覆盖时按物理路径回退），三方按 node 的解析。
5. **外置与地址改写**：**外置名单 = 行**（loader 给的、声明了 `dsh.client` 且有 client 半的那些包，见第 2 条）——
   每行各有自己的联邦产物，地址由 `output.paths` 交给 `urlOf`，写的是它的 **client 出口**。**不是行的**
   （普通依赖、相对路径、node 内置、虚拟模块）留在产物里**内联**：它们没有自己的联邦产物，也不该让浏览器
   按"根出口"去要宿主半。名单**独占**给 `esmExternalRequirePlugin`（它同时把 CJS 模块里的 `require(外置)`
   转成 ESM import）；**顶层 `external` 不能再列**同一个模块，否则插件整块跳过、产物里留下 `__require(...)`。
6. **缓存按包聚合、按出口命中**：目录键是 `<pkg>@<version>`（版本以**包清单**为准，URL 里那个只是外置时写下的
   提示），`.files.json` 是"这个包产出里有什么"的**唯一真相**（出口产物 + 资产）。指纹没变且**这次要的出口
   都在**才命中；否则重建并把新产物**增量合并**进清单（指纹变了才整包作废）。同一个包的构建**排队串行**——
   首屏那几十个请求是同时在飞的。
7. **入口补偿**（都在 `bundlePackage` 里做，产物侧一致）：
   - **CJS 入口**（`react` 这类 `module.exports = require(…)`）：ESM 的导出必须静态可枚举，所以**求值**入口
     拿到键、生成 `export const X = __cjs["X"]` 的包装文件当入口。用**计算属性**读：静态属性访问会被 rolldown
     按它对 CJS 命名空间的静态理解摇成 `void 0`（`react/jsx-dev-runtime` 就是这么被摇空的）。
   - **CSS 入口**：库模式固定 `cssCodeSplit: false`，`input` 里出现 `.css` 直接报错——包一层 side-effect import。
8. **资产不内联**：库模式默认把所有资产内联（5MB 的 PNG 变成 base64 塞进 JS）。这里走 `threshold` 策略、
   `base` 设成该包的地址前缀、`assetFileNames` 落 `assets/<name>-<hash>.<ext>`，文件落盘并进清单，路由按清单
   服务（顺带挡住凭 URL 读任意文件）。
9. **dev 侧**（`serve-vite` / `vite-plugin`）：插件 `enforce: "pre"`（必须早于 `vite:resolve`——它会先查
   `optimizeDeps` 缓存，命中就改写成 `.vite/deps/…`，于是同一个包两份实例：react 的 `Invalid hook call`）；
   裸说明符 → 联邦地址（三方与 `dsh.dev.exclude` 点名的**非开发模块**），仓库里的**开发模块**仍逐文件走 vite
   （改它要 HMR）；`optimizeDeps` 显式关掉（`noDiscovery`），没有裸说明符需要它。
10. **URL 空间只有 `@` 前缀**：`@/…`（本地文件）、`@client-modules/…`（联邦产物）、`/@fs/…`（仓库里的源码，
   因为 **vite 的 root 收在 `app-boot`**，源码都在 root 之外）、`/@id/…`、`/@vite/…`。兜底只放行这些与页面
   本身，其余一律 404 并打 `[reject]`（带 Referer）——裸的 `/packages/…`、`/vendor/…` 一出现就现形。
   （**不要**用 `base: "/@/"` 去"统一前缀"：vite 会给所有不以 base 开头的绝对 URL 再补一层，联邦地址变成
   `/@/@client-modules/…`。）
11. **缓存策略按"这份产物还会不会变"分**（与 vite 分"预打包依赖 / 源码模块"同一套）：地址里的 `?v=` 是
   **构建器规则指纹**（`BUNDLER_REV`，与 vite 同名的参数；一次会话内所有地址一致——同一个包只有一个 URL，
   多一个 URL 就多一份模块实例）。三方包（`node_modules` 里，dev 期间不变）→ `public, max-age=31536000,
   immutable`；仓库内的包（`dsh.dev.exclude` 点名的，随时可能被改）→ `no-cache` + `ETag`（重复请求走 304）；
   资产（文件名带内容 hash）→ `immutable`。**不做重定向**（vite 也不做）。
12. **宿主专有模块的求值安全替身**：`node:*` 与"被间接拉进 client 图的宿主半代码"都要能求值。替身**两份形态、
   同一语义**：dev 侧 ESM（`app-boot/node-stub.ts`，缺具名导入只是运行期 undefined），构建侧 CJS
   （`app-boot/node-stub.cjs`，rolldown 把"没有该具名导出"当**构建错误**，CJS 的具名导入不校验存在性）；
   被间接拉进来的宿主专有包（`new Worker(new URL(…, import.meta.url))`）则让 worker 走 `es` 格式。

**形态差异（dev 的三种入口）**：

- **web**（`dshdev dev --web`）：宿主是 node http（`src/web.ts`），页面与资源走 `http://127.0.0.1:<port>/`。
- **桌面**（`dshdev dev`）：宿主跑在 Electron 里，页面走**自定义协议** `dsh-…://app/`，请求经壳的字节
  管道进宿主。差异只在两处：进来的 `req.url` 是**完整 URL**（先归一成路径）、页面里的 HMR 客户端只在真的有
  同源 http server 时才注入。
- **bundle 后**：这条链的根是 `$DSH_HOME/profiles/desktop`（dev 态是仓库根，两者都**不**用 `process.cwd()`——
  桌面宿主的 cwd 是 profile 目录）。

**两种形态都跑源码**（部署里不再落 dist 载荷）：宿主入口一律按 node 的解析取 `src/index.ts`（壳用
`--import` 挂着 TS loader —— **命令行参数**不受"打包后禁 `NODE_OPTIONS`"那条限制），我们的包因此都要把
`src` 放进 `files`（否则 `pnpm deploy` 只带走 `dist`）。上游的包仍用它们的发布产物（bundle 时会 seed 一份
官方源码包进 profile）。

**已知限制**：自定义协议下，前端"按 `location.origin` 拼 URL"的 API 拿不到标准语义——`ws://app/api/remote.mux`
就是这么来的（`dsh-…://app` 的 origin 换成 `ws://` 后 host 是 `app`）。当前选择的补法是**在 preload 里给
WebSocket 加一条 IPC 垫片**（复用 `__DSH_DESKTOP_STREAM__` 那条已有的流隧道），而不是让宿主开回环端口——
后者要动壳↔宿主的 wire 协议。

**性能**（每个联邦请求都要做的两件事，都做了缓存）：

- **两张表懒建一次**（版本表 / 出口表）：它们要扫工作区几百个清单与 pnpm store，而路由是**每个请求**都要
  它们——每次重算等于把首屏时间乘以产物数。
- **指纹先攒元信息戳**（名字 + 大小 + mtime）：戳没变就复用上次内容指纹，否则每次请求都要把每个包的源码
  读一遍。实测冷启动（清缓存）首屏渲染 **~2s**，同会话再打开 **~0.6s**。
- 同包的构建**排队串行**是有意的（产物目录包级、重建会清理），跨包并行不受影响。

**判据与坑**：

- `BUNDLER_REV`（`bundle.ts`）：**改解析/改写规则就 bump**，否则复用带旧地址的产物。
- 外置名单只有一个 home（插件），dev 与产物两侧的地址只有一个 home（`urlOf`）。
- 三方包的指纹看它的清单（`root/src` 对 `node_modules` 里的包常常是空目录，所有包会共用一个空哈希）。
- 缓存按出口命中这条是**必需**的：产物目录包级、构建按出口触发，只比指纹会把第二个出口判成命中（404）。
- 地址里的 `?v=` **不能**用"目标包的内容指纹"：产物是**静态字节**，引用方写下的指纹会停在旧值，而别处
  新写的又是新值——同一个包两个 URL 就是两份实例（react 报 `Cannot read properties of null (reading
  'useContext')`）。内容变化交给协商缓存（`no-cache` + `ETag`）。
- `import "@/vendor/…"` 这类**仓库路径**不要写：按包名引（`@deepseek-ai/dsh-x/brand-font.css`），走哪条链
  由解析规则定；写仓库路径等于把 vendor 的目录布局抄进代码，还会把一份样式拆成一串逐文件请求。
