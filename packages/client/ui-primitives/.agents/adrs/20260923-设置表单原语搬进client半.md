# 设置表单原语搬进本包的 client 半，样式改 css-in-js、行为判据照抄上游

状态：已采纳

背景：本仓库后续两个设置卡片（各自一个 cordis 插件页）要复用上游
`@deepseek-ai/dsh-client-ui-primitives` 的 settings-form 原语——暂存式表单模型
（`vendor/deepseek-harness/packages/client/ui-primitives/src/settings-form/form-model.ts`）、
字段控件（`.../fields.tsx`）与表单框（`.../SettingsForm.tsx`），以及它们对应的上游测试
（`.../tests/settings-form-model.client.spec.ts` 等）。

两处约束：上游那套是平台 baseline 模块，插件替换不了（本包与它平行，见
[ADR-css-in-js样式层与官方token消费](./20260917-css-in-js样式层与官方token消费.md)）；它的样式是
CSS Modules，要过一次 lightningcss 预编译，与本包「源码可直接加载、前后端同一份源码」的前提相悖。

**决定**

把这三份源搬进本包 client 半 `src/client/settings-form/`，导出面与上游同形同名（经 `./client` 出口消费），
样式改成本包 css-in-js（`styled` + `dsw`），行为判据照搬上游测试；上游那三份源此后是只读参照，
每次上游升级后对照 diff。

**考虑过的选项**

| 选项                                                  | 为什么否掉                                                                                                    |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 直接 import 上游包的这些导出                          | 上游产物是 CSS Modules 预编译结果；本包要保持源码可直接加载，也不引上游 primitives 的运行时依赖（平行关系）   |
| 搬过来但保留 `.module.css`                            | devkit 的 `cssInlinePlugins` 确实支持（`packages/profile/dsh-session-mode` 就这么用），但那要过一次预编译，违背本包前提 |
| 搬过来只改引用、不管样式                              | 同上                                                                                                          |
| 按我们的口味重设计表单模型接口（换名、换状态形状）    | 消费的两张卡片要和上游设置页同形；重设计等于两份契约各自漂移，还要重写全部上游判据                            |
| 连 `Tag` / `IconInfoOutlineRegular` 一起引上游 primitives | 只为两个微件（徽标、12px 信息图标）引入一个平台 baseline 运行时依赖，且上游那份会拖进 shiki/katex 等整条链    |

**后果**

- 本包 client 半从此含 React 组件（此前只有无状态的引用转换）；`dsh.client.inject` 仍为空——React 与
  `@deepseek-ai/dsh-client-store` 在 client bundle 里都是 external，由平台种子提供（devkit 的 `BASELINE`）。
- 新依赖 `@deepseek-ai/dsh-client-store`（`devDependencies`，与上游同名包的声明位置一致），只为
  `SettingsFormModel.bind()` 的 `createSnapshotStore`：消费方拿到的是同一种 store，`.set()` 与选择器语义与上游一致。
- 同步纪律：上游升级后对照 `vendor/.../src/settings-form/{form-model.ts,fields.tsx,SettingsForm.tsx}` 与
  上游三个测试。`form-model.ts` 逻辑逐行未改（差异只有 oxfmt 的引号/分号风格，以及未用的
  `catch (_error)` 参数按 lint 口径写成可选 catch 绑定）——对照时忽略格式即可；`fields.tsx` /
  `SettingsForm.tsx` 结构同形、样式层不同，diff 只应出现样式相关行与本地徽标/图标替换
  （上游 `Tag` → 两个本地 `styled` 变体，上游 `IconInfoOutlineRegular` → 本地 `InfoGlyph`）。
  导出面与上游根出口逐一对应（`SettingsFormModel` / `SettingsForm` / `SettingsValueField` /
  `SettingsSecretField` / `settingsNumberField` / `settingsTextField` 与 9 个类型）。
- 两个被引用的 token——`--dsw-alias-bg-layer-4`（信息按钮 hover 底色）与 `--dsw-alias-label-error`（保存失败
  文案颜色）——**不在官方主题的定义集里**（`theme.generated.ts` 的 367 个 token 没有它们）。照抄上游的引用、
  不换近义 token，也不加 fallback：官方主题哪天定义它们，这里自动跟着生效，视觉与上游逐帧一致。
- 反转：上游若拆走或改名这套原语、或官方设置页不再用这个模型，这里跟着改；两张卡片若改用官方页面渲染，
  这批原语连测试一起删掉。
