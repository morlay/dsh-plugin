# 完整设计：会话数据面、管理面与表现面（better-session）

状态：已实现——数据面 / 管理面 / 表现面三块落地；16 条业务故事里 15 条落地并挂判据（#1 的批量归档已落地），只剩 #15 的行数上限是部分达成（见第一节功能面表的状态列与[代码结构](../standards/代码结构.md)判据 2）。
范围：`@morlay/better-session` 作为**本仓专用扩展**的完整能力面：宿主半（数据面 / 管理面）与浏览器半（表现面），以及它与 `@morlay/zephyr-rdb`、上游 `dsh-session` 契约的边界。
非目标：第三方复用与 API 稳定承诺（契约绑定上游）；跨进程写仲裁（不承诺，用位点守卫 + 冲突码）；routing/鉴权（上游网关的职责）。
关联：[RDB 复用边界与 Remote 端点形状](./20261106-RDB复用边界与Remote端点形状.md)、[会话查询直读 RDB 读面](./20261109-会话查询直读RDB读面.md)、[对话管理页](./20260929-对话管理页.md)、[会话读写与失败面的健壮性](./20261120-会话读写与失败面的健壮性.md)、rdbkit 的[完整库设计](../../../../zephyr/zephyr-rdb/.agents/designs/20261120-完整库设计.md)。

## 一、决定

| #   | 议题             | 决定                                                                                                                                                                                                                                                                                                                                                                                                                        | 一句话理由                                                           |
| --- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | 定位             | 本仓专用扩展：契约绑定上游，不承诺第三方复用；内部按库标准（明确接口与不变量、可替换、判据齐）                                                                                                                                                                                                                                                                                                                              | 真正通用化要先抽象掉上游契约，成本与收益不成比例                     |
| 2   | 功能面归属       | 宿主半拥有三件事：数据面（落盘 / 事件 / 分支编辑）、管理面（查询读面 / 导入导出 / 用量 / 整理）、存储接管（KV 域同库 + 投影检查点）；浏览器半同包（表现面）                                                                                                                                                                                                                                                                 | 同一份库、同一个事务是硬理由；拆包只会多一层跨包事务                 |
| 3   | 记录结构         | 记录按「数据面 / 管理面 / 表现面」三块写各自的不变量与判据，不混成一个能力面                                                                                                                                                                                                                                                                                                                                                | 三块的变更节奏与判据不同                                             |
| 4   | 与 rdbkit 的边界 | 通用机制下沉（同进程同库写串行、库身份、错误分类、方言表达式、`first` / `affected` / 列引用 / 投影类型四个原语）；会话域语义留本包（事件形状、折叠规则、统计口径、编辑计划）                                                                                                                                                                                                                                                | 库不该知道会话；域层不该重造通用原语                                 |
| 5   | 串行粒度         | 承诺**同进程同库**（rdbkit 按库身份共享写队列）；跨进程不承诺，用位点守卫 + `SESSION_CONCURRENT_WRITER`                                                                                                                                                                                                                                                                                                                     | 域层已自建过这一层，上移能删掉自建；跨进程锁成本高且与「不承诺」一致 |
| 6   | 库身份           | rdbkit 提供最小库身份面（读/写/版本不匹配即拒绝），SQLite 用 pragma、PG 用库与 schema 探测；域层只声明「dsh-session、格式 v3」                                                                                                                                                                                                                                                                                              | PG 部署现在没有「这是不是同一个库」的判据                            |
| 7   | 错误分层         | 域错误 `SessionStoreError`（带域码，`cause` 链到 `DbError`）；rdbkit 不认识会话语义；端点只转发域码不翻译                                                                                                                                                                                                                                                                                                                   | 一个能力一个 owner                                                   |
| 8   | 数据模型清理     | 删 `t_schema_meta`（空表，与 `t_schema_migrations` 重复）**不走迁移**，直接从 catalog 移除；三张统计表与 `t_session_projcache_row` 标注「可销毁重建」；删内容相同的 `postgresTableDefs` 死代码                                                                                                                                                                                                                              | 一个事实一个 home；派生表的可重建性是它们的契约                      |
| 9   | 漂移口径         | 「库里有、catalog 没有」的表由结构漂移报告列为 orphan（`kind: "orphan"`、`fix: "manual"`），**只报告不自动删**：`runMigrations` 把 `ensureSchema` 的 `drift` 原样交回，`data/store/open.ts` 收下后只打一条汇总 warn、不阻塞打开；判据在 rdb 的 `migration.spec.ts`（「结构对齐的漂移随结果一起返回：库里有、catalog 没有的表只报告不删」）与本包 `data/__tests__/schema-drift.spec.ts`（SQLite / PostgreSQL 各一条 orphan） | DDL 的破坏性动作由人决定                                             |

## 二、现状事实

- 唯一消费方关系：本包是 rdbkit 的唯一生产消费者，只用「表句柄 + `E.*` + `count/sum` + `transaction` + 库级操作」；`Database.read/iterate`、`classifyError`、`planSchema`、CTE/集合运算、`onQuery` 零使用（盘点结论）。
- 自建物（缺口信号，不是设计）：写者位点守卫 `src/data/write-guard.ts`、16 处「取首行就 return」、44 处 `Number()`、14 处 `.toFragment()`、41 处字符串列名。写队列与库身份由 rdbkit 提供（`serialQueueFor` / `identity`），本包只声明「dsh-session、格式 v3」。
- 数据模型：10 张表（`t_schema_meta` 已从 catalog 移除，不写迁移）；统计三表与投影检查点表为派生；`t_storage_units` / `t_storage_records` 属 KV 接管。
- 多进程：写者位点守卫覆盖 append 与 rewind；`flush()` 屏障不完整；PG 侧无库身份校验。

## 三、模块边界与接口

目录名与面的对应：数据面 `src/data/` + `src/editor/`、管理面 `src/admin/`、存储接管 `src/storage/`、表现面 `src/ui/`；`contract/` / `endpoint/` / `server/` 按出口与装配分，不按功能面分。

| 面       | 拥有（职责与不变量）                                                                                   | 不拥有（明确排除）                 | 依赖方向                            | 接缝 / 适配器                                              |
| -------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------- | ----------------------------------- | ---------------------------------------------------------- |
| 数据面   | 落盘五方法、事件与桥接行、head/revision、撕裂尾部、分支与编辑（fork/rewind/seed/replay）、写者位点仲裁 | 查询语义（归管理面）、UI           | ← `SessionPersistence` 契约、rdbkit | `SessionPersistence` 令牌；`SessionBranch` 端口            |

接口（调用方必须知道的）：

- 写冲突以 `SessionStoreError("SESSION_CONCURRENT_WRITER")` 报出，不自动重试；调用方决定是否重放。
- 派生表可销毁重建；`organize()` 是唯一的重建入口，且自身拒绝在有运行中会话时清表。
- 端点错误只有域码一条通道；客户端按码分派，不解析文案。
- 表现面不直读库；页面需要的只读投影也必须做成端点。

## 四、行为与边界

1. 正常路径：写经句柄批量落库（同事务内事件 + 桥接 + head）；读经管理面端点，live 先 flush 再读库。
2. 错误：域码表覆盖 NOT_FOUND / LIVE / NOT_ARCHIVED / CONCURRENT_WRITER / EVENT_REJECTED / IMPORT_* / QUERY_*。
3. 取消：契约方法收 `AbortSignal`，wire 上暂无取消面（记债）。
4. 生命周期：卸载先排水再关句柄；`flush()` 是真屏障（含 live 缓冲）。
5. 并发：同进程同库写串行；跨进程靠位点守卫拒绝并给码。

## 六、取舍

- 否掉「拆成数据包 / 管理包 / UI 包」：同一份库与同一个事务会把它们重新绑在一起。
- 否掉「跨进程写队列」：需要文件锁或常驻 DB 锁，与「桌面 + CLI 靠位点守卫」的既有语义冲突。
- 否掉「删表写迁移」：库是开发版本且表是空的，写迁移等于给一张空表留历史。
- 否掉「漂移报告自动删 orphan 表」：DDL 的破坏性动作由人决定。
- 否掉「扩展 `DbError.kind` 承载域码」：库层不该知道「会话」。

## 七、不做与已知债

- 已知债：[导入与整理没有取消面](../debts/20261120-导入与整理没有取消面.md)、[`SESSION_EVENT_REJECTED` 域码与上游契约断言冲突](../debts/20261120-SESSION_EVENT_REJECTED域码与上游契约断言冲突.md)、[库身份切换导致旧库不兼容](../debts/20261120-库身份切换导致旧库不兼容.md)、[标题前缀搜索用不上 idx_sessions_title](../debts/20261120-标题前缀搜索用不上idx_sessions_title.md)。导入覆盖已是原子替换（判据 `import-replace.spec.ts`），剩下的跨进程那一段留在「开放问题」。
- 不做：wire 取消面、用量 wire 两份形状合一、列表虚拟化（每页 20 行）、软删除与撤销。

## 八、开放问题

- 跨进程导入覆盖：一个进程正在写、另一个进程覆盖导入时，除位点守卫外是否需要「导入目标有活跃写者就拒绝」的显式检查（现由 `hasOpenHandle` 覆盖的只是本进程）。
- 表现面的「长任务可取消」依赖 wire 取消面，是否值得为导入/整理单独开一条流式端点。
