# 配置来源与替换形态（`sandbox.toml`、`fromCordis` 与三块结构）

状态：**已实现**——`{DSH_HOME}/sandbox.toml` 启动时读一次；两个替换实现走 `fromCordis` + deps；装配面 `without(SandboxDefault)` / `without(FsSandbox)`。
范围：配置从哪来（文件、六个字段、默认文件、坏文件口径、可注入的读面）、替换形态（两层类、类名、注入字段的写法、清单顺序），以及本包的结构（为什么没有 `server/` / `endpoint/`）。
非目标：规则语义与平台降级（[设计 20260929-可配置沙箱的规则面与平台降级](./20260929-可配置沙箱的规则面与平台降级.md)）；官方两个实现的内部（归 `packages/agent/dsh-sandbox` / `packages/agent/dsh-fs`）。
关联：根规范 [`describing-facts.md`](../../../../../.agents/standards/describing-facts.md) 的「exports 与代码布局一一对应」；[ADR-替换官方进程沙箱与 fs 围栏以支持额外可写根与拒绝项](../adrs/20260917-替换官方进程沙箱与fs围栏以支持额外可写根与拒绝项.md)；装配面判据在 `src/__tests__/assembly.spec.ts`。

## 一、决定

| #   | 议题                   | 决定                                                                                                         | 一句话理由                                                                               |
| --- | ---------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| 1   | 配置来源               | 启动时读一次 `{DSH_HOME}/sandbox.toml`，落成不可变的装配事实；行 config 不带任何字段                         | 本部署没有配置页，`volatile()` 那套「页面改了下次编译就是新值」只剩成本                  |
| 2   | 文件缺失               | 默认读面**写一份默认规则**再返回它（写不进去就用内置那份）                                                   | 一条 `rw` 都没有时只有工作区可写，症状是 agent-browser 起不来、`XDG_CACHE_HOME` 写不进去 |
| 3   | 坏文件                 | 整份按「没有规则」处理 + 一条点名 warn，**不阻断启动**                                                       | 用户写坏一份 toml 不该让宿主起不来；挑一半字段生效比一条都不生效更难查                   |
| 4   | 读文件                 | `SandboxFile` 契约 + `SandboxFileDefault`，测试注入假件                                                      | 否则开发机上真用户的 `sandbox.toml` 会顶掉用例输入                                       |
| 5   | 替换形态               | 内层继承官方实现（`LocalSandboxProvider` / `LocalFileSystem`），外层 `fromCordis(契约, 内层)` 成 DSL 条目    | 装配面的 `provide([...])` 只收 DSL 形态，`without(实现类)` 也按条目定位                  |
| 6   | 依赖交给上游实例的方式 | 经 `mount(ctx, config, deps)` 的 deps 注入，不用全局单例                                                     | 上游实例按 `ctx.get("sandboxRules")` 读到的是本行那份；同一进程两份装配各持自己的规则    |
| 7   | 目录结构               | 只有「契约 + 实现 + 装配」三块：`src/contract/**`、`src/*.service.ts`、`src/configurable-sandbox.provide.ts` | 本包没有 wire 面：有 `endpoint/` 才有 `server/`                                          |

## 二、现状事实

- **字段与默认值**（`src/sandbox-rules.service.ts` 的 `SandboxSettings`）：`access`（规则条目，数组或多行文本）、`runnerCommand`、`runnerFailureSignatures`、`probeTimeoutMs`（缺省 5000）、`cwd`（缺省 `process.cwd()`）、`diffBasisMaxBytes`（缺省 10 MiB）。
- **解析与退化**：`SandboxRulesDefault.onInit()` 读一次 `SandboxFile.read()`；`undefined` 直接返回（用默认值 + 空规则）；坏 TOML / 未知顶层字段 / 字段类型不对 / 条目语法不对 → 整份退回默认值 + 空规则，并 warn 一条点名（文件路径 + 坏在哪）。`KNOWN_KEYS` 是认得的顶层字段全集。
- **默认文件**：`src/defaults.ts` 的 `DEFAULT_SANDBOX_TOML`——临时目录、agent-browser 与 XDG 的缓存 / 状态 / 数据可写，XDG 配置只读，`mise.*.toml` 与 `**/*.pem` 拒绝；文件由 `SandboxFileDefault.read()` 在 ENOENT 时用 `flag: "wx"` 写出（并发启动撞 `EEXIST` 就读回别人写的那份），写不进去时只 warn 并用内置那份。
- **默认读面**：`src/sandbox-file.service.ts` 的 `SandboxFileDefault`——`path = dshHomePath("sandbox.toml")`；非 ENOENT 的读错误直接抛（权限 / 路径是目录属于环境问题，读成「没配规则」会让沙箱静默退回官方行为）。
- **内层两个实现**：`src/sandbox.service.ts` 的 `ConfigurableSandboxProvider`（`extends LocalSandboxProvider`，构造 `(ctx, config)`，从 `ctx.get("sandboxRules")` 取规则源）与 `src/fs.service.ts` 的 `ConfigurableFileSystem`（`extends LocalFileSystem`，从 `ctx.get("sandboxRules")` / `ctx.get("sandboxPolicy")` 取）。
- **外层两个条目**：`ConfigurableSandbox`（`fromCordis(Sandbox, ConfigurableSandboxProvider)`）与 `ConfigurableFsSandbox`（`fromCordis(FileSystem, ConfigurableFileSystem)`），`onInit` 里 `mount(ctx, upstreamConfigOf(settings), deps)`；`upstreamConfigOf` / `upstreamFsConfigOf` 只挑官方基类认的字段。
- **清单**：`src/configurable-sandbox.provide.ts` 的 `provideConfigurableSandbox()`——`SandboxFileDefault` → `SandboxRulesDefault` → `ConfigurableSandbox` → `ConfigurableFsSandbox` → `SandboxRuntimeContexts`（读配置 → 解析规则 → 两个替换实现 → 接管运行时文本）。
- **注入字段的写法**：外层两个 Provider 用普通 `private` 字段（装配期回填注入走 `Object.keys(instance)`，`#` 私有字段不可见）；内层两个官方子类用 `#` 私有（只是避免与包在外面的 Provider 字段撞名，依赖从构造参数拿）。
- **类名**：内层保留上游语义的名字（`ConfigurableSandboxProvider` / `ConfigurableFileSystem`），外层是装配条目（`ConfigurableSandbox` / `ConfigurableFsSandbox`，与官方的 `SandboxDefault` / `FsSandbox` 对称）。

## 三、模块边界与接口

| 模块                                   | 拥有（职责与不变量）                                                                                 | 不拥有（明确排除）                          | 依赖方向                                                   | 接缝 / 适配器                                                   |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| `SandboxFile` / `SandboxFileDefault`   | 「从哪读、怎么读」、首次启动写默认文件、读错误的分级                                                 | 解析与校验（归规则面）；路径之外的策略      | 依赖 `@morlay/zephyr-app` 的 `dshHomePath` 与可选 `Logger` | 契约可注入：测试用 `src/__tests__/support/fake-sandbox-file.ts` |
| `SandboxRules` / `SandboxRulesDefault` | 六个字段的解析与默认值、坏文件的一口径退化、规则源的唯一 owner                                       | 规则的编译与判定（归 `rules.ts`）；平台能力 | 依赖 `SandboxFile` + `smol-toml`                           | `settings()` / `source()` 两个读口                              |
| `ConfigurableSandbox`（DSL 条目）      | 装配清单里能被 `provide` 列出、能被 `without` 定位；把配置与规则经 deps 交给上游实例；装配期降级告警 | 官方 runner 探测 / 选择；规则判定           | 依赖 `SandboxRules` + `Logger`                             | `fromCordis(Sandbox, ConfigurableSandboxProvider)`              |
| `ConfigurableFsSandbox`（DSL 条目）    | 同上；把 `sandboxRules` / `sandboxPolicy` 两个读面交给上游实例                                       | 官方 diff / 版本 / 解析细节                 | 依赖 `SandboxRules` + `SandboxPolicy`                      | `fromCordis(FileSystem, ConfigurableFileSystem)`                |
| `provideConfigurableSandbox()`         | 本面的行清单与顺序                                                                                   | 装配面的 feature（`without` 由调用方写）    | 被 `apps/zephyr-custom` 的装配清单引用                     | zephyr 的 `provide(list, [features])`                           |

**接口**（调用方要知道的）：

- `provideConfigurableSandbox(...features)`：要剔某行用 `without(实现类)`；要改配置没有配置项——改 `{DSH_HOME}/sandbox.toml`（或 `configure(SandboxFile, …)` 换实现）。
- 采用方必须同时剔掉官方两个实现（`without(SandboxDefault)` + `without(FsSandbox)`）：只剔一个时另一个令牌仍由官方兑现，规则在那一侧没有生效点。
- `SandboxRules.settings()` 是不可变快照：改文件要重启这一行；`source()` 给编译前的规则源（环境变量已展开）。

## 四、行为与边界

1. **正常路径**：`onInit` 读文件 → 解析 → `Object.assign` 到 `settings` / `rules` → 两个替换实现 `mount` 时拿这份快照。
2. **文件缺失**：默认读面写一份默认规则并返回它；并发启动撞 `EEXIST` 时读回已存在那份。
3. **坏配置**：整份退回「没有规则」+ warn；不认识的顶层字段也算坏（多写一个键说明这份文件不是本版本认的形状）。
4. **写不进去**：只 warn，内置那份规则仍生效——规则面缺失是产品问题，文件写不进去是环境问题。
5. **读错误分级**：`ENOENT` 才走默认文件；权限 / 路径是目录这类直接抛，不静默当成「没配规则」。
6. **装配顺序**：清单顺序即依赖——规则源在两个替换实现之前就绪，运行时文本接管在最后。
7. **取消与并发**：读一次即固定，没有运行期重载；同一进程两份装配各持自己的 `SandboxRules` 实例（deps 注入，不是全局单例）。

## 六、取舍

- **不要行 config**：`volatile()` 存在的理由是可改配置页，本部署没有页面；改成文件后规则源不可变，缓存键也不必把 `access` 拼进去。
- **文件缺失时写一份默认**：空规则会让沙箱静默退化成「只有工作区可写」，比写一份能跑的最小集合更难查。
- **未知字段算坏**：挑一半字段生效（比如 `runnerCommand` 拼错被静默丢弃）比一条都不生效更难查——**可查**优先于**多用一点**。
- **两层都要**：内层保留 `super(ctx, config)` 的官方装配逻辑，外层用 `fromCordis` 包成 DSL 条目——装配面要能列出它（`provide`）也要能剔它（`without`）。
- **外层注入字段不用 `#`**：装配期回填注入走 `Object.keys(instance)`，`#` 私有字段不可见——用了就是「注入没发生，运行期 `this.#rules` 是 `undefined`」。
- **不引 `ctx.isolate`**：多一层作用域与卸载时序，收益只是省掉一次 `without`——而装配面本来就是 `without(...)`。
- **不放 `server/`**：本包没有 `@RemoteGroup`；`server/` 在本仓的语义是「wire 端点实现的宿主面」，放内部服务会把「有 API」读成「有个服务」。

## 七、不做与已知债

- 没有 UI 半（不引 react / css），出口只有 `.`。
- 没有 `./rows` 出口：本仓不生成 `cordis.patch.yml`，装配就是代码里的清单。
- 运行期改 `sandbox.toml` 不生效：要重启（这一行读一次即固定）。

## 八、开放问题

- `sandbox.toml` 的字段集合要不要跟着上游 `sandbox-local` / `fs-local` 的 Config 走：现在只透了 6 个字段，上游新增字段（例如更细的 temp 策略）时这里不会自动出现。
- 多部署共用一份 `{DSH_HOME}` 时规则无法按部署区分：现在一个 `DSH_HOME` 一份规则，要不要支持按 profile 覆盖。
