# 投影检查点落 RDB，以及 storage 接管的两个名字

状态：**已实现**——`storage-takeover.spec.ts`、`projection-cache.spec.ts`、`workspace-registry.spec.ts` 全绿；整包 38 文件 / 377 通过。
范围：`sessionProjectionCache` 这一行落在哪个介质上、写回时机与失败兜底；`rdb` storage 后端为什么必须 `register` **和** `provide` 两件事都做；`storages/*.json` 的一次性导入件归谁。
非目标：会话落盘本身（[设计 20261106-RDB复用边界与Remote端点形状](./20261106-RDB复用边界与Remote端点形状.md)）；读路径口径（[如何写读路径](../standards/rdb-读路径.md)）；`workspace` 域的归档语义（归 `packages/agent/dsh-workspace`）。
关联：上游 `storage-domain` 的 `apply` 用 `ctx.inject([...], …)` 等后端就绪（`vendor/deepseek-harness/packages/storage/storage-domain/src/index.ts`）；服务键构造函数来自 `packages/agent/dsh-storage/src/contract/storage.contract.ts`（再导出上游 `storageBackendServiceKey`）；词义见[会话数据面术语表](../../../../agent/dsh-session/.agents/GLOSSARY.md)（live / cold / 闭合边界）。

## 一、决定

| #   | 议题                   | 决定                                                                                                                              | 一句话理由                                                                      |
| --- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1   | 检查点存哪             | `t_session_projcache_row`（`src/rdb/storage-takeover/repository.ts` 的 `loadProjcache` / `putProjcache` / `pruneStaleProjcache`） | 与事件行同一个库：撤回要按同一水位截断缓存，跨库就跨事务                        |

## 二、现状事实

- **storage 接管行**：`src/rdb/storage-takeover/storage-takeover.service.ts` 的 `StorageTakeoverDefault`——注入 `Storage` / `SessionPersistence`，用 `asRdbStore(persistence).storageRepository()` 拿同一个库的句柄，`register` 之后 `ctx.effect` 里注销并关后端，再用 `ctx.reflect.provide(storageBackendServiceKey(RDB_STORAGE_BACKEND), backend)` 发布服务名。
- **为什么发布服务名**：上游 `vendor/deepseek-harness/packages/storage/storage-domain/src/index.ts` 的 `apply` 把 `config.backend` 与 `config.routes` 映射成 `storageBackendServiceKey(...)`，再用 `ctx.inject(backendServices, (domainCtx) => domainCtx.provide("storageDomain", …))` 等它们。只 `register` 时那条 fiber 永远在等一个没人 provide 的名字——症状是 `ctx.storageDomain` 恒 `undefined`，`Workspace` / `Schedule` / 审批授权这些行整类挂不上。
- **检查点服务**：`src/rdb/storage-takeover/projection-cache.service.ts` 的 `SessionProjectionCacheRdb`——`cachedSnapshot` 只读进程内镜像；`write()` 先比检查点差异；`truncateTo()` 按新水位丢弃超出 head 的投影单元；`hydratePrepared` / `coldSnapshot` 给冷读用；`onInit` 先 `loadProjcache()`，**有行才** `pruneStaleProjcache()`（空库不写，避免共用库文件的并发实例在装配期抢写锁）。
- **写回订阅**：`installWritePath()` 订阅 `session/event`（排进同一 tick 的队列）、`session/created`、`session/disposed`；`queueMicrotask` 合并同一 tick，`onDispose` 清队列。
- **读镜像**：`cachedSnapshot(meta, keys)` 与 `cachedPredecessorTitle(meta)` 只读镜像，删掉介质里的行不影响进程内镜像（判据见 `projection-cache.spec.ts`）。
- **撤回后写回**：`src/rdb/branch/index.ts` 的 `refreshProjectionCache` 在**调用时**按名字 `lookup("sessionProjectionCache")`（装配顺序不保证）；live 走 `write`，cold 走 `truncateTo`（不 fold 日志），写失败按新水位截断兜底。
- **导入件**：`src/rdb/storage-takeover/import-storages.ts` 的 `importStorages` / `PROJCACHE_UNIT_VERSIONS`（`7` 与 `3`–`6`）/ `WORKSPACE_UNIT_VERSIONS`（`2`）；workspace 文档写 `putDomainRecord` + `writeDomainGlobal`，投影检查点写 `putProjcache`，两个单元都先 `insertUnitVersion`。
- **workspace 域与归档标记**：`createStorageRepository` 的 `syncSessionFlags()` 把域 global 里的 `archivedSessionIds` / `pinnedSessionIds` 写穿到会话行（`f_archived_at` / `f_pinned_seq`）；列表与删除读的是会话行，归档集合的真相仍在 workspace 域。

## 三、模块边界与接口

| 模块                          | 拥有（职责与不变量）                                                                         | 不拥有（明确排除）                                                  | 依赖方向                                                              | 接缝 / 适配器                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------- |
| `StorageTakeoverDefault`      | `rdb` 后端的注册**与**服务名发布、卸载时注销并关后端                                         | KV 域的语义（归 `storage-domain`）；会话语义                        | 依赖 `Storage`（hub）与 `SessionPersistence`（拿同一个库）            | `storage.backend.register` + `ctx.reflect.provide`              |
| `SessionProjectionCacheRdb`   | 检查点的增量写回、进程内读镜像、撤回后的截断、冷读的写回                                     | 投影怎么折（归 `SessionProjectionStore`）；事件怎么落库（归写路径） | 依赖 `SessionPersistence` / `SessionProjectionStore` / `SessionStore` | `SessionProjectionCache` 契约 + 上游驼峰别名                    |
| `repository.ts`（storage 面） | KV 域的通用行存储（`(域, 表, 键)` → 一行）、单元版本、投影检查点行、workspace 索引与标记写穿 | 域的业务规则（workspace 的排序 / 钉住语义归域层）                   | 依赖 `Database`（同一个库）                                           | `StorageRepository` 类型（`src/rdb/storage-takeover/types.ts`） |
| `import-storages.ts`          | `storages/*.json` 的读取、版本集合校验、把文档搬进 RDB                                       | 是否该搬（一次性脚本，调用方决定）；装配行                          | 依赖 `StorageRepository`                                              | 包根导出的纯函数                                                |

**接口**（调用方要知道的）：

- `storageRepository()` 是异步口：后端打开后才可用；投影检查点与导入件都经它拿句柄。
- `cachedSnapshot()` 的命中要求身份匹配（header-only 的生命周期身份或带继承前缀的完整身份）；不命中返回 `undefined`，调用方走冷读。
- `write()` 是幂等的：检查点与已存行相同就不写；`truncateTo(meta, inheritedEventCount, headSeq)` 只丢水位超出新 head 的单元。
- `importStorages()` 对版本不在接受集内的文档抛错（不静默跳过整份文件）。

## 四、行为与边界

1. **正常路径**：装配期 `onInit` 等持久化就绪 → 取同一库的 storage 面 → 读回已有检查点（有行才清 → 再读一次）→ 装写回订阅。
2. **写回**：`session/event` 排进同 tick 队列 → `write()`：先 `sessions.flush`（失败只 warn）→ 比检查点差异 → 有变化才落库。
3. **撤回**：live 会话按内存 log 重算检查点再写；cold 会话只截断到新水位（不 fold 日志）；两条都失败时按水位截断兜底。
4. **错误**：装配期取不到库 → 缓存关掉并 warn，装配继续；写回失败 → warn，缓存停在旧水位但读路径仍可用。
5. **生命周期**：`onDispose` 置 `disposed` 并清队列；`StorageTakeoverDefault` 的 effect 注销后端并关连接。
6. **并发**：同一库文件的多个实例共享写锁——装配期不写（空库直接跳过清理），写回只在有变化时发生。

## 六、取舍

- **检查点与事件同库**：跨库就跨事务，撤回时两边会不同步；代价是 KV 域也被拉进同一个库（见下一条）。
- **KV 域一起接管**：只接管会话表时 `dataDir/storages/` 会继续被创建与写入，撤回/导入里两套存储一起写就不可能同事务。
- **写回不用攒批参数**：上游接口有 `writeEveryEvents` / `writeIntervalMs`，RDB 版填 0 且不参与决策——判据是「检查点有没有变」，不是条数或时间。
- **装配期清库只在有行时做**：空库不必写；共用同一库文件的并发实例不该在装配期抢写锁。
- **撤回后的检查点以内存 log 为源**：那是派生状态重算，不是查询读；落库失败也要写回，否则读路径停在撤回前。
- **storage 服务名必须显式发布**：上游的 fiber 等的是 `storage.backend.rdb`，不是注册表里的 `"rdb"`；这不是风格问题，是它能不能激活的问题。

## 七、不做与已知债

- 投影检查点不提供「跨进程共享的读镜像」：镜像在进程内，删掉介质里的行不影响它，多实例各自加载各自的。
- `importStorages` 是一次性脚本，不挂装配行：源部署跑过一次就不再写 `storages/`，重复搬没有意义。
- 投影检查点的上游攒批参数（`writeEveryEvents` / `writeIntervalMs`）在本实现里恒为 0：形状对齐上游，语义不成立。

## 八、开放问题

- 多实例共用同一个库文件时，检查点镜像可能落后于另一个实例写入的行；目前只靠 revision / 身份匹配让读路径回落到冷读。要不要做跨实例失效通知，等真有这种部署再定。
- `storages/*.json` 的版本集合（`PROJCACHE_UNIT_VERSIONS` 含 3–6）是手写清单：上游再出旧世代时要不要扩，取决于是否还要搬那种库。
