## 三、模块边界与接口

| 模块                      | 拥有（职责与不变量）                                                          | 不拥有（明确排除）                                            | 依赖方向                                     | 接缝 / 适配器                             |

| `data/store/branch/**`    | 截断的前置条件、边界与 seed 长度收缩、写句柄水位回退                          | 并发写者的所有权（归 `WriteGuard`）                           | ← `BranchPort`                               | `BranchPort.guardHead`                    |

| `admin/query.ts`          | 读面的配平口径：live 不补合成 closer、冷读补；detached 会话的解释器从注册表取 | 日志怎么落库（归写路径）                                      | ← `SessionPersistence.load` / `SessionStore` | `loadLog` / `sessionOf`                   |
| `editor/service.ts`       | 编辑动作的前置条件：没有重放入口就不动日志                                    | 重放怎么跑（归 agent 目录面）                                 | ← `SessionAgentControl`                      | `SESSION_EDITOR_REPLAY_UNAVAILABLE`       |
| `admin/import-export/**`  | 导入件的行账目与血缘：种子长度、根会话 header                                 | 事务与 head 复位（归写路径 `replaceSessionLog`）              | ← `ImportHost`                               | `persistImport`                           |
| `data/errors.ts`          | 域码表与错误对象：码、可读消息、`dbErrorOf` 的归一                            | 码到页面文案的映射（归 `ui/conversation-manager/failure.ts`） | ← 各写路径                                   | `SessionStoreError` / `sessionStoreError` |

接口（调用方要知道的）：

- `branch.rewind(id, boundary)` 在「本实例认领过旧位点、之后别的写者提交过」时拒绝（错误文案含 another writer），库保持原样。
- `listSnapshots` 跳过坏行并各 warn 一条；它不是「整份要么全有」。
- `drainLive` 失败后事件留在缓冲里，按退避自动重试；`close()` 之后不再重试。
- `readSession` / `observeSession` 对 live 会话给的就是库里的日志：没有合成事件，`cursor` 等于库 head；冷读才有 `turn/end {reason: "interrupted"}` 这类 closer。
- 编辑动作在「有用户输入要重放、但没有重放入口」时整条失败（码 `SESSION_EDITOR_REPLAY_UNAVAILABLE`），日志一条都不改；`recall` / `rewind` 与助手消息的「截断 + 手写回合」不受这条限制。
- 导入落库的会话在库里没有 `parentSession` 也没有 `origin`：它按根会话列出、统计计入人类会话。
- `flush()` 之后库读与内存读等价：live 会话的缓冲、还没建好的写句柄、失败态会话都在这一次屏障里结算；失败报 `SESSION_FLUSH_FAILED`（原因在 `cause` 的 `AggregateError` 里）。
- `organize()` 在还有写句柄的会话存在时拒绝（`SESSION_ORGANIZE_LIVE`），清表与重算都不发生；调用方先停会话再来。
- `checkConsistency(database)` 只读、不自动修；`repairDerivations(steps)` 不抛，把失败的步骤与原因交回。
- 失败面：端点只转发 `error.code`，不猜页面文案；页面侧的错误码映射与呈现见[对话管理页](./20260929-对话管理页.md)。

## 四、行为与边界

1. 生命周期：`close()` 清掉重试定时器并置 `disposing`，之后的失败不再排重试。
2. 并发：同一会话的截断与另一实例的追加由写者位点守卫仲裁；被拒绝的一方不产生副作用。
3. 读面：live 会话先 `session/flush` 再从库读，读到的就是库里那份日志（正在跑的轮次保持打开）；冷会话的日志尾部未闭合时补合成 closer，`cursor` 因此可以越过库 head。
4. 编辑：没有运行中的 agent 时，`edit` / `retry` / `reroll` 在截断之前失败，日志与派生状态都不动；有 agent 时行为不变（先停 loop、截断、再把用户输入排进重放队列）。
5. 导入：一次事务替换整段日志；`f_seed_length` 跟着新 head 走（未种子的导入件把旧的种子长度清成 `NULL`），父引用与子代理标记不落库。
6. 派生状态：删除 / 回收之后的两步重算各自跑完（统计行、用量引用标记），失败进返回值并 warn；留下的漂移正是 `checkConsistency` 报的那几类。
7. 整理：先排水再判「运行中」；被拒时不改库。排水里的失败只 warn（它们各自已经有归属的错误记账），不阻断整理本身。
8. 失败面：宿主拒绝带 `code` 回 wire；页面据 `code` 选文案（`failure.ts`），成功与失败分别落 `role="status"` / `role="alert"`，动作在途禁用确认按钮——呈现与焦点细节归[对话管理页](./20260929-对话管理页.md)。

## 六、取舍

- 否掉「截断前重新 flush 并对齐位点」：对齐等于替另一个写者认账，用户要的是「有人改过，先别动」。
- 否掉「live 也补 closer」：把正开着的轮次读成已中断，页面会把「正在跑」显示成「中断」，`cursor` 还越过库 head。
- 否掉「没有重放入口时把首条用户输入写成裸 `user/message` 落库」：日志里会多一条没人应答的用户消息（下一轮请求会带上它），「已截断」与「已排队」在接口上仍然分不清。
- 否掉「导入保留父引用」：`origin: "subagent"` 加父会话不在库里就是 `organize` 的孤儿判据，导入的会话会在下一次整理时被删掉。
- 否掉「一致性校验比较两侧的整段相等」：撤回不回退统计、fork 共享事件行，两侧刻意可以不相等；只报「少了」的方向才没有假警报。
- 否掉「`organize()` 等运行中的会话自己关掉」：等不到头的等待比一条明确的拒绝更难解释；拒绝的码告诉调用方先停会话。
- 否掉「删除的重算失败抛出去」：会话行与桥接行已经提交删除了，抛错会让调用方以为什么都没发生；结果进返回值。
- 否掉「页面猜宿主文案」：端点只给 `code`，文案与呈现归页面（`failure.ts` + 共享 `Feedback`）；宿主改文案不该改到用户看到的措辞。

## 七、不做与已知债

- 已知债：[导入与整理没有取消面](../debts/20261120-导入与整理没有取消面.md)。
- 不做：把每个端点错误码都映射成专属文案（页面只认会改变用户下一步的那几个，其余保留宿主原文）。
- 不做：替调用方恢复会话。编辑动作要求「有运行中的 agent」这个前置条件由装配面对用户兑现，本行只在没有时拒绝。
- 不做：导入连父会话一起搬。跨库保留真实血缘要一份「整棵树导入」的能力，单条会话的导入按根会话处理。

## 八、开放问题

- `SessionEditor.recall` 等动作的失败只区分「true/false」；要不要把宿主的错误码带到行内文案。
- 编辑在冷会话上的失败要不要由 UI 自动「恢复会话再重试」，而不是把失败直接摆给用户。
- 单条会话的导入要不要带父会话（否则跨库的 fork / 子代理血缘永远丢失）。
