# 库身份切换导致旧库不兼容

状态：触发中——`application_id` 换成库身份指纹之后，手里有旧库的人升级即被拒，没有迁移入口。
位置：`packages/agent-ex/better-session/src/data/version.ts`（`SESSION_PERSISTENCE_SQLITE_APPLICATION_ID = identityFingerprint("dsh-session") | 0`，即 `-80036999` / `0xfb3abb79`）、`packages/agent-ex/better-session/src/data/store/open.ts`（`claimLibrary` 比对指纹与版本 → `SESSION_STORAGE_INCOMPATIBLE`）、`packages/zephyr/zephyr-rdb/src/database/library.ts`（`identityFingerprint`，FNV-1a 32 位）。

**现象**

- 库身份不再是一个手写常量：SQLite 的 `application_id` 存 `identityFingerprint("dsh-session") | 0`，版本另存 `user_version` = 3；两个方言用同一个身份名。
- `claimLibrary` 在指纹或版本对不上时直接抛 `SessionStoreError("SESSION_STORAGE_INCOMPATIBLE")`，消息里给出库里存的 application id 与期望值；不改写身份、不搬行、不猜。
- `application_id` 为 `0x44534850`（`"DSHP"`）的旧库，即使表与 `user_version` 都对得上，也在打开这一步被判不兼容。

**影响**

正在用旧库的人升级后打不开库：页面 / CLI 只看到 `SESSION_STORAGE_INCOMPATIBLE`。数据还在文件里，但要自己决定「回退旧构建」还是「放弃这份库重来」——没有迁移入口，也没有「怎么把旧库变成新库」的提示。

**触发条件**

有用户已经在用旧库时（本机之外还有别的数据根、或构建已经发给别人）必须先还；纯开发机上删库重来即等价于迁移，不算触发。眼下这是开发版本的默认处境，所以记「触发中」。

**销账条件**

Done when：旧库要么有显式迁移入口（把 `application_id` 认领成指纹并保留原有的行，命令带确认并要求先备份），要么确认真实用户的旧库数为 0 之后删掉这条。判据：一个 `application_id = 0x44534850` 的夹具库经显式迁移后能打开且数据完整，而默认路径仍然拒绝不认识的库。

**不修的理由**

库是开发版本，这一轮优先让「这是不是同一个库」有唯一判据（身份名指纹 + 版本）；写迁移等于给魔数时代留一条永久的兼容分支，而认领旧库是破坏性动作，归人决定。
