# 预设生成与装配（dsh-preset 的设计与取舍）

状态：已实现（`dist/presets/{standard,chat}` 由 tsdown `build:done` 生成——行由 `tool/presets/*.ts` 声明，`cordis.patch.yml` 也由同一次生成写出；装配见 [README](../../README.md)）
范围：`packages/preset/dsh-preset/` 的 preset 来源、提示词分层与装配机制；被插入的插件自身行为不在本文。
约束：不放宽「上游代码不可修改」——只把上游 composition 当数据读、只 patch 装配行。

## 事实基线

### 产物与生成器

产物由 [`tool/presets/*.ts`](../../tool/presets/index.ts) 的**显式行清单** dump 而成：`js-yaml` 用 include 的
`entryListSchema` 解析与输出，`!!js` 表达式由 `jsExpr()` 从一个无参函数取函数体——平台开关这类运行期判断
因此仍是编译器检查过的代码，而不是手拼字符串（产物在构建机上生成，不能固化成静态值）。

行清单是我们**按需列**的，不再从上游 composition 派生。派生只在上游默认集合就是我们要的时候才划算；
现在定制已经很多（不装 planning / agent-instructions / tool-skill / 外部 agent CLI codex 与 claude-code /
ralph / plugin-manager，还要追加五行注入相关的行），派生等于每次都在「读上游 → 禁用/收窄」，产物里堆一串
`disabled: true`。上游改动改由覆盖性测试提醒：清单里的行必须仍在上游存在。

产物落在 `dist/`，由 tsdown 的 `build:done` hook 在每次 `pnpm build` 时生成（`tsdown.config.ts` 挂
`presetHooks()`）。必须挂 `build:done` 而非 `build:prepare`——tsdown 时序是 `build:prepare` → `clean()`
（清空 outDir）→ rolldown → `build:done`，写在 clean 之前会被删掉。

脚本先**整目录清空**输出目录再生成：产物完全派生自清单，残留目录（改过 id、旧命名）不该留下——否则
discovery 会把它们当有效 preset 扫出来。`src/__tests__/generated-presets.spec.ts` 断言产物逐字等于清单、
清单里的 `@deepseek-ai/*` 行在上游确实存在、除平台开关外没有 `disabled`，并断言输出目录里没有清单之外的目录。

生成器显式设 `quotingType: '"'`：`yaml.dump` 默认单引号而仓库 oxfmt 偏好双引号，不指定会让生成器与
formatter 来回改；产物在 gitignore 的 dist 里，本就不参与 fmt。

发布判据：`package.json` 的 `files` 必须含 `dist`（preset 在其中）与 `tool`，否则发布产物缺内容。

### roster 与展示名

patch 设 `includeShippedRoot: false`，官方 `minimal` / `cordis` 等不再出现在 roster；本包 `dist/presets/` 作为
唯一 root 提供 `standard` / `chat`（`default: standard`）。`includeShippedRoot` 是上游 `dsh-agent-presets` 的
正式配置项，不是 hack。

产物目录名 = 生成器里的 preset id（与上游 source 解耦：两个产物都源自上游 `standard`）。`presetDisplayText` 对
`trust: system` 且 id 命中 `BUILT_IN_PRESET_KEYS` 的行走客户端语言字典，因此 `standard` 的展示名自动本地化
（zh「标准模式」/ en「Standard mode」），`preset.yml` 的 `name` / `description` 会被字典遮蔽；自造 id
（`chat`）不进字典，展示名直接用 `preset.yml` 的中文名。`preset.yml` 的 `order` 决定 roster 排序。

### 提示词分层

个人提示词只在 `cordis.patch.yml` 的 `system-prompt` 行维护一份（关掉 harness identity
与 runtime context 快照，`personaPrefix` / `personaSuffix` 由该行给出）。

preset 自带的 `persona` 行会在 agent scope 注册 `deployment:persona-prefix` 并**按 scope 遮蔽**部署级值（上游
`vendor/deepseek-harness/packages/core/system-prompt/tests/scoped.spec.ts` 固化了该语义），所以生成器把那一行
**删掉**，而不是复制一份改过的 persona——同一份文案只维护一处。

`personaPrefix` 位于 order 0（prompt 最前，紧跟被关掉的 harness identity 之后）：声明指令优先级（直接用户指令

> 工作区 `AGENTS.md` > 本系统提示词）与执行协议。其中点名 `AGENTS.md` 是**强制约束**——官方
> `agent-instructions` 注入模板的措辞（"may be relevant" / "as guidance" / "do not override…"）是上游的通用保守
> 表述，会让模型把仓库规则当参考而不是规则，所以这里显式反制。协议一行覆盖：动手前读相关 `AGENTS.md`、过程自检、
> 交付前核对红线与验证证据、无法遵守时明确说明、派发子代理时把约束写进任务说明。

`personaSuffix` 位于 order 10200（prompt 最后）：一句话复述「结束任务前对照本提示词与 `AGENTS.md` 自检」。
长 prompt 里中段指令会被稀释，首尾各放一次最关键的约束，用近因位置兜住遵循度；细节只在 prefix 维护，避免两处
重复。

自建 preset 仍然必要，但只为别的事：`includeShippedRoot: false` 之后需要一份自己的 roster（id 沿用官方名以走
客户端语言字典），以及桌面形态下 preset 必须落在 dsh 包的 `config/agent-presets` 挂载点（见
[dsh-desktopify 的 `dsh.desktop.agentPresets`](../../../../desktop/dsh-desktopify/README.md)）。

### 工具说明降级为 reminder

上游把每个工具的跨调用说明（`tool:bash`、`tool:read`、…）、Agent Teams 协作规则、harness 源码位置、Web GUI
说明都注册成系统提示词的 section。本部署实测它们占 9200 字符里的约 7400：条数多、篇幅大、挤在上下文最前面，
稀释真正要遵守的那几行纪律。`cordis.patch.yml` 因此在 host plane 插一行
（`@morlay/dsh-context-assembler`，行为与配置见
[该包 README](../../../../context/dsh-context-assembler/README.md)）。

一处定义覆盖全部 preset（standard / chat 以及后续新增的）——这是与具体 preset 无关的部署级策略，preset
composition 不各自带这一行，生成器也就不必碰它。该插件是**注入的唯一通道**：注册在 root scope，会收到每个 agent
的装配与 pre-step 事件（含子 agent）。装配时按 `keep` 名单留下部署 persona，其余 section 按处置分流——丢弃
（平台运维说明）、改写（两段中文文案）、或降级捕获（要点写进 skill 正文是各注入方自己的事）；pre-step 时把要送的内容**逐条**
以 `<system-reminder>` user 消息注入，紧随本轮用户消息之后（每条按文本幂等，只有变化的那条重发）。内容与可用
条件由分发方（`preset/dsh-context-tool-guidance`）在装配期登记，机制与取舍见
[ADR-20260921-提示词注入只有一个通道且按需内容走skill](../../../../context/dsh-context-assembler/.agents/adrs/20260921-提示词注入只有一个通道且按需内容走skill.md)
与该包 README。

### 工作区指令

preset 里的 `agent-instructions` 行是官方 `@deepseek-ai/dsh-agent-instructions`：baseline 按官方语义作为 user
消息注入一次。生成器只覆盖该行 config 的两个字段——`instructionFileCandidates: ["AGENTS.md"]`（上游默认还含
`CLAUDE.md`）与 `localInstructionFileCandidates: ["AGENTS.local.md"]`（上游默认还含 `CLAUDE.local.md`），
即**不读 CLAUDE 系列**（本部署不需要 CLAUDE 兼容）；`maxBytes` 等其余字段跟随上游。

### 装配表达式

`agent-presets.roots` 指向本包的 `dist/presets/`。因为该目录随包分发，位置只能在运行期解析：`cordis.patch.yml`
用 `!!js` 表达式从 profile 的 `baseUrl` 起 `createRequire` 解析包路径（`ctx.baseUrl` 即 root include 所在目录
= profile 根），并把该 root 声明为 `trust: system`。

用 `process.getBuiltinModule` 而非裸 `require` / `import`：求值环境是 `with (ctx) { eval(expr) }`，只有全局对象
稳定可用。表达式含 `'` 与换行，`--dump-config` 会把它输出成 folded scalar，往返后语义不变（已实测）。

`trust: system` 与 shipped root 同级：preset 是一份完整 composition，授予的能力等价于 shell 访问，只应来自受控
的安装包。

### patch 层级与放置

patch 层按 `[bundle patches, profile patches, home patches, overlays]` 合并，后应用者整块
替换同一行的 `config`：

| 载体                                                                          | 生效范围                                              |
| ----------------------------------------------------------------------------- | ----------------------------------------------------- |
| profile 的 `cordis.patch.yml`（`$DSH_HOME/profiles/<name>/cordis.patch.yml`） | dev 与打包形态都生效，但只属于本机 home               |
| app 的 `cordis.patch.yml`                                                     | 打包（`bundle`）形态：作为 seed 的 profile patch 生效 |
| 一个自有 bundle 的 patch                                                      | 所有形态（随包分发）                                  |

本 bundle 的规则类装配（禁用官方沙箱两行 + 插入 `sandbox-local` 行 + `access` 规则、禁用官方
`fs-observation-policy` 行）因此放在**本 bundle 的 patch** 里，跨 dev（web / desktop）与打包形态一致；app 的
`dsh.profile.bundles` 不需要再列一层。禁用官方 `office-to-pdf` 行同理放在这一层：它是
「本部署不启用官方某行」的策略，与具体 app 形态无关。

### web 搜索后端与图片上限

**搜索**：模型侧的 `web_search` / `web_fetch` 由 preset 的 `tool-web` 行给（host 层的同名行被 web-app
bundle 禁用），而**选哪个后端**由 host 层的 `web` 行决定——基础 bundle 里它写着
`searchProvider: deepseek-official` + `fetchProvider: http`
（`vendor/deepseek-harness/packages/bundle/base/cordis.patch.yml:458-470`），对应的注册行是
`web-search-deepseek`：Anthropic Messages 的 `web_search_20250305` server tool，吃 `DEEPSEEK_API_KEY`。

**"复用那条 messages 后端、把端点换成 ollama.com" 不成立**——这条我按
[issue #17283](https://github.com/ollama/ollama/issues/17283) 推断过一次，真发请求被否，实测：

- `POST https://ollama.com/v1/messages`，body 与上游 provider 完全一致（`tools:[{type:"web_search_20250305",
name:"web_search", max_uses:5}]`、model `deepseek-v4.1-flash`）→ `HTTP 200`、`stop_reason: tool_use`、
  `content` 块是 `thinking` + `tool_use`。Ollama 把这个 server tool **降级成普通客户端工具**、不执行搜索，
  要求调用方自己执行后回传 `tool_result`；上游 provider 只认服务端自执行后的 `web_search_tool_result` 块，
  于是报 `WEB_PROVIDER_ERROR`（"returned no web_search_tool_result blocks"）。Ollama 文档里
  "hosted web search are not fully supported" 就是这个意思，issue 里的 `WebSearchAnthropicWriter` 拦截
  只发生在本地 server 的 cloud 模型路径上。
- `POST https://ollama.com/api/web_search`（`{"query": …}`、Bearer key）→ `HTTP 200`、
  `{"results":[{title,url,content}]}`。**这才是 Ollama 提供的搜索接口。**

所以新增 [`@morlay/dsh-web-search-ollama`](../../../../web/dsh-web-search-ollama/README.md)（约两百行
provider，直连 `/api/web_search`），并在本 bundle 的 patch 里把 `web` 行的 `searchProvider` 切到 `ollama`：

- **注册行住 host 层**：preset 是每个 agent 各挂一份，同一个 provider id 注册两次会撞
  `WEB_DUPLICATE_PROVIDER`；`web` 行本来就是 host 行，"选哪个"也只能由这一层决定。
- **`config` 是整体替换，不是深合并**（`applyEntryPatches` 对同 id 行做 `target[key] = value`），
  所以覆盖 `web` 行时必须把 `fetchProvider` 一起写全，否则抓取后端会凭空消失。测试
  `src/__tests__/patch.spec.ts` 用上游自己的 `applyEntryPatches` 组合 base + 本 patch，断言组合后
  `searchProvider` 是 `ollama`、`fetchProvider` 仍是 `http`。
- `deepseek-official` 后端仍在注册表里，改回那一行就是切换（需要 `DEEPSEEK_API_KEY`）。

**真端点的守护**：新包 `e2e/provider.e2e.spec.ts` 在 `OLLAMA_API_KEY` 存在时真打 `/api/web_search`
（provider 直连一条、装进 `ctx.web` 后选中它再搜一条），key 缺席则整体跳过（CI 没有这个 key，它是带凭据环境
的证据）。它**刻意放在 `src/__tests__/` 之外**：根 vitest 的 include 只收 `packages/**/src/__tests__/`，默认
`just test` 不会收集它——否则环境里恰好有 key 时，全量测试会静悄悄打外网：

```sh
mise exec -- pnpm --filter @morlay/dsh-web-search-ollama run test:e2e
```

mock 单测全绿不能替代它：本部署的第一版正是"配置指到 Ollama 的 messages 端点"、mock 也全绿，真调用是错的。

**图片上限**：llm 侧有四个旋钮，llm-deepseek 与 ollama 所在的 llm-pi-ai 路由不是同名同默认：

| 层                                         | llm-deepseek                                                     | ollama（llm-pi-ai route）                    | 处理                                   |
| ------------------------------------------ | ---------------------------------------------------------------- | -------------------------------------------- | -------------------------------------- |
| 上传准入（与供应商无关，attachment-local） | `maxImageBytes` 20 MiB / `maxMessageImageBytes` 200 MiB          | 同一份服务，两个供应商共用                   | 不动：单张 20 MiB 与下面的内联预算同值 |
| 请求内联图片预算                           | `maxInlineRequestImageBytes` 20 MiB（base64 长度）               | `maxRequestImageBytes` 20 MiB（base64 长度） | 不写：默认就同值                       |
| 每张请求版本原始字节目标                   | `DEFAULT_REQUEST_IMAGE_MAX_BYTES` 2 MiB                          | `requestImageMaxBytes` 1 MiB                 | **写 2 MiB**：唯一默认不同的那项       |
| 像素预算                                   | 模型级 `imagePixelBudget` 未设（交给 attachment 归一化的 2048²） | `requestImagePixelBudget` 2048²              | 不写：默认就同值                       |

按「config 只写偏离上游默认的项」的既有约定（`tool/presets/standard.ts` 同一条），只显式写第三项；
另外两项写进去也不改变行为，只会让上游默认升级时不再跟随。

### office 相关

两类 office 内容归属不同，只有转档后端能从本层禁用：

| 内容                                                             | 上游归属                                                                                                                                                                       | 本层能否禁用                                                                                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `@deepseek-ai/dsh-office-to-pdf`（Office→PDF 转档后端）          | web-app bundle 的 profile 行 `office-to-pdf`（`vendor/deepseek-harness/packages/bundle/web-app/cordis.patch.yml:228`）                                                         | 能：本 bundle 的 patch 用 id 覆盖 `disabled: true`                                                                     |
| `@deepseek-ai/dsh-skill-office`（docx / pptx / xlsx 三个 skill） | 桌面宿主命令式装载（`vendor/deepseek-harness/apps/desktop-host/src/office.ts:25`，由 `apps/desktop-host/src/index.ts:69` 在 profile boot 之后 `ctx.plugin(desktopOffice, …)`） | 本层不涉及：不是 profile 行，patch 改不了；桌面形态由 dsh-desktopify 的 host 变体不装载它（见「office skill 的处置」） |

禁用转档后端后，Sidebar 文档预览的 Office 标签页回落成 `unavailable`：该渲染器要客户端 remote
`remote.officeToPdf`（`vendor/deepseek-harness/packages/client/ui-sidebar-documentpreview/src/client/office/index.ts:64`），
行禁用后 remote 不存在，读取路径停在该文件 :36-40 的兜底实现。office skill 与转档后端无关
（skill 资源只有 `packages/skill/skill-office/assets/{office-docx,office-pptx,office-xlsx}/SKILL.md`
与 `assets/scripts/check_office.py`，不引用转档服务）；两者现在都不启用——转档后端由本 bundle 的 patch 禁用，
office skill 由 dsh-desktopify 的 host 变体不装载。

## 取舍

- **禁用官方 preset 而不是改它**：官方 roster 里没有本部署要的 `standard` 形态（工具说明进系统提示词、
  persona 由 preset 自带）；`includeShippedRoot: false` 是上游配置项，不需要触碰上游代码。
- **每个模式一份清单**：`standard` 列标准形态的行，`chat` 只列对话要的那几行（工具三个、`context-scope` 收白名单并关
  掉 instruction、不要用法分组）。两份清单各自声明，不从一个上游 composition 派生。
- **id 沿用官方名而不是全自造 id**：`standard` 沿用官方 id 以走客户端语言字典；`chat` 没有对应官方 id，
  展示名由 `preset.yml` 的中文名给出。
- **按需列行而不是派生上游 composition**：派生只在上游默认集合就是我们要的时候才划算；定制已经很多时，
  它退化成「读上游 → 禁用/收窄」。代价是上游新增行不再自动跟随——换成覆盖性测试（清单里的行必须仍在上游
  存在、产物除平台开关外无 `disabled`）来提醒复核。
- **reminder 用独立插件而不是 `persona` 行的 `complete: true`**：`complete` 会连 suffix 一起丢，且子 agent 自己
  注册同名 persona 时 `complete` 语义消失，保留 / 降级会不一致；插件按 `keep` 名单匹配 section 名，两种 agent
  行为一致。
- **reminder 装配在部署级而非 preset 内**：与具体 preset 无关的策略，一处定义覆盖全部 preset（含后续新增）。
- **沙箱规则放本 bundle 的 patch 而不是示例 app 的 patch**：bundle patch 在 dev（web / desktop）与打包形态都会
  应用，app 的 patch 只在打包时作为 seed 的 profile patch 生效；规则语法与各平台表达能力见
  [`@morlay/dsh-sandbox-local` 的 README](../../../../sandbox/dsh-sandbox-local/README.md)。
- **搜索后端自写 provider，而不是复用上游的 Messages 后端**：先用 issue 推断过可行，真发一次请求被否——
  Ollama 只回 `tool_use`、不执行 server tool（详见「web 搜索后端与图片上限」）。要让复用成立，得有客户端
  工具回环，那是改上游（红线）；直连 `/api/web_search` 一次 HTTP、`max_results` 精确可控，也不依赖兼容层行为。
- **图片上限只显式写偏离默认的那一项**：与 preset 清单同一条约定（值与默认相同就该删掉）。写同值不改变行为，
  只是让上游默认一升级这里就不再跟随；反过来漏写偏离项就是悄悄发更小的图。

## office skill 的处置

`@deepseek-ai/dsh-skill-office` 不是 profile 行：上游桌面宿主命令式装载它
（`vendor/deepseek-harness/apps/desktop-host/src/index.ts:69` → `apps/desktop-host/src/office.ts:25`），仓库里也没有
任何 bundle / preset patch 出现这一行（只出现在测试快照
`vendor/deepseek-harness/snapshots/session/office-skills/cordis.yml:3`）。所以**本包（以及任何 bundle / preset
patch）都没有旋钮**。评估并排除掉的上游侧口子：

1. **用 profile patch 禁用某行**——不存在这一行：装载是命令式的，不经过 loader。
2. **给 `skill-office` 一个「空资源」配置**——`Config` 只有 `assetRoot`
   （`packages/skill/skill-office/src/index.ts:15-21`），`apply` 无条件注册三个 skill（同文件 :12 的名字表、
   :49-59 的候选、:69 的 `ctx.skills.registerProvider`）；资源缺 `scripts/check_office.py` 时抛错，直接让宿主
   启动失败（同文件 :46-48，上游 `vendor/deepseek-harness/apps/desktop-host/src/office.ts:12` 的注释也这么约定）。只给 `SKILL.md` 的最小
   目录仍然是「三个 skill 已启用」。
3. **在注册表侧过滤**——`SkillRegistry.Config` 只有 `collectCacheMaxEntries`
   （`packages/skill/skill/src/index.ts:277-281`），公开面只有 `registerProvider` / `register` /
   `list` / `snapshot` / `get`（同文件 :390-506），没有注销 / allow / deny；`dsh-tool-skill` 的唯一配置是
   `catalogDescriptionMaxLength`（`packages/skill/tool-skill/src/index.ts:61-69`）；`dsh-skill-filesystem`
   的配置是 roots 与 watch 相关（`packages/skill/skill-filesystem/src/index.ts:49-69`）。三层都没有按名字排除的口子。
4. **禁用 preset 的 `tool-skill` 行**——过于宽泛：它同时是模型侧 `skill` 工具的来源
   （`dist/presets/standard/agent.cordis.yml:26-27`），禁掉等于砍掉全部 skill（含非 office 的）。
5. **用同名 provider 影子覆盖**（机制上可行，不采纳）——同一 layer 内同名 candidate 按 `rank` → `providerOrder`
   取胜（`packages/skill/skill/src/index.ts:807-811`），`modelInvocable: false` 的候选不进模型目录
   （`packages/skill/tool-skill/src/index.ts:226`），所以本包可以注册一个 rank 更低的 provider 抢占
   `office-docx` / `office-pptx` / `office-xlsx` 三个名字并标成不可调用。不采纳：那是「把上游 skill 替换成
   占位物」而不是「不启用」，要跟着上游 skill 名单维护，还在注册表里留下假条目。
6. **壳侧不投放 office 资源**——被候选 2 的校验挡住：资源缺失让桌面宿主启动失败，不是「不启用」。
7. 桌面宿主与 `skill-office` 两侧都没有环境变量开关（各自的 `process.env` 无命中）。

**采取的做法**：不动这些上游面，改在桌面化工具侧解决——
[dsh-desktopify](../../../../desktop/dsh-desktopify/README.md) 的自带 host 变体只装载 `workspace-dependencies`、不装载
officeSkills（`office-skills` 资源也不随包），所以桌面里不再出现这三个 skill；web / CLI 形态
本来就不装载 `skill-office`（唯一依赖它的包是上游 `vendor/deepseek-harness/apps/desktop-host/package.json:22`）。副作用与 `office-to-pdf`
一致：Sidebar 文档预览的 Office 标签页回落 `unavailable`。

仍然开放（若上游要给开关）：把桌面 office 组合做成装配行（`desktop-office` 行，`config` 就是 `office.ts` 现在从
argv 取的两个目录），或给 `SkillRegistry.Config` 加 `disabledProviders?: string[]`。
