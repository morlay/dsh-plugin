# 工具按需注入（dsh-tool-gating 的设计与取舍）

状态：已实现（`packages/preset/dsh-tool-gating/`，装配行由 dsh-preset 生成器写进每个 preset 产物）
范围：`packages/preset/dsh-tool-gating/`（新包）与 `packages/preset/dsh-preset/`（生成器插行 + 模式列表）
约束：不放宽「上游不可修改」——只用上游公开面（`agent/created` 事件、`agent.ctx.tools.restrict()` /
`agent.ctx.tools.register()` / `agent.ctx.systemPrompt.section()` / `ctx.commands.register()`），不碰 vendor。

## 结论摘要

| 议题        | 结论                                                                                  | 一句话理由                                                                  |
| ----------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 目录        | **恒定**：不裁剪 schema，全部工具始终在请求里                                         | tools 排在请求最前，任何裁剪都让该请求整段重算；恒定则档位切换零重算        |
| 档位判定    | 执行层：`tools.guard` 拒绝归组但未启用的工具，并给出解锁路径                          | 目录不再承担约束，约束必须落在执行点；未归组的工具一律放行                  |
| schema 说明 | 用一行中文**短描述覆盖**上游 `description`（参数 schema / 执行体 / 渲染转发上游定义） | schema 常驻，描述只讲"做什么"，用短描述压住常驻开销                         |
| 提示词给法  | **上游逐工具的说明一律遮蔽**（静态清单）；启用某组时给**该组一整段**中文用法提示      | 逐工具说明碎片化且占位最大；一组一段与「组」这个授权单位对齐                |
| 提示词通道  | 能力目录与按组提示注册成 section，在 **agent scope 遮蔽上游说明**                     | 空文本被 `dsh-prompt-reminder` 跳过，两插件无顺序耦合，也不占系统提示词前缀 |
| 模型侧升级  | 常驻元工具 `enable_tools(groups[])`，只做并集；目录与回执用中文                       | 归因清晰；档位变化不再付出缓存代价                                          |
| 用户侧切换  | `/tools [groups...]` 命令，集合语义（可关）；落一条带结构的 user 消息                 | 用户要能立刻改档位；消息进 surface，重建与 rewind 天然一致                  |
| 模式        | 从上游 `standard` 生成两个 preset，差别只在 `config.initial`                          | 模式 = 起始档位，不是第二套装配；PTC preset 已下线                          |
| 单调性      | 模型侧只增，用户侧可切                                                                | 模型反复增减是噪声；用户是显式决策者                                        |
| 装配层级    | 每个 preset 产物末尾一行，`config.initial` 表达该模式的默认能力                       | agent plane 天然按 preset 隔离；一条事实（模式默认）只有一个 home           |
| 档位重建    | 重放 surface 上的切换记录：命令消息 = 设定，`enable_tools` = 并集                     | resume 不丢、rewind 自动回退，不需要额外持久化                              |
| 子 agent    | 从起始档位起步（不继承父档）                                                          | 子任务由基础组覆盖，协作类工具在子代理里本就不该用                          |

## 事实基线

### 接缝（全部是上游公开面）

- **`agent/created`**：`AgentRegistry.announce` 以 agent 的 carrier 派发
  （`vendor/deepseek-harness/packages/core/agent/src/index.ts:547`），因此**注册在 preset scope 上的 listener 只收到该
  preset 的 agent**——这是「只影响本模式」的结构性依据，不靠运行时判断 preset id。
- **`agent.ctx`**：agent 自己的 scoped context（`agent-loop/src/agent.ts:79`），`agent.ctx.inject(['tools','systemPrompt'], …)`
  是其上的注册面；`packages/context/file-reference-local/src/index.ts:69` 是上游现成模板（按工具是否存在渲染 section 文本、
  fiber 管生命周期）。
- **`tools.restrict(filter)`**（`packages/core/tools/src/index.ts:1077`）：per-scope 过滤**继承面**（global + 祖先 scope），
  正是 preset 注册的工具（preset 是 agent 的祖先 scope）；要求 scoped ctx、名字必须在 `restrictableNames` 里否则抛错、
  返回精确 disposer。agent 自己 own 层注册的工具不受过滤。
- **`systemPrompt.section()`**：scoped 同名 section 遮蔽祖先/global 同名 section——上游测试固化了该语义
  （`dsh-prompt-reminder/src/__tests__/prompt-reminder.spec.ts:138`「agent scope 上的 persona 按同名保留」断言部署级文本消失）。
- **`commands.register()` / `commands.execute()`**（`packages/interaction/commands/src/index.ts:285`、:361）：命令按 scope
  分层的注册表；`execute(agent, line, attachments, signal)` 返回归一化结果，并把 `command/run` / `command/done` 写进
  会话日志（`recordInput` 默认记录参数）。
- **`system-prompt/assemble`（每 step）**：模型可见工具目录就是 `assembly.tools`，由 `ToolRuntime` 构造时注册的
  `ctx.systemPrompt.tools(context => this.wireSchemas(context.scope))` 生成（`packages/core/tools/src/index.ts:832`），
  其内容 = `view(scope).visible`，即**受 restriction 影响**。这保证「限制可见性」与「模型目录」是同一事实。

### 缓存代价（设计围绕它收敛）

- 工具定义走请求的 `tools` 参数（`agent-loop/src/agent.ts:557`、`:614`），且**实测**其位置在
  「system 文本之后、全部 messages 之前」（见 [ADR-工具schema恒定而说明动态化](../adrs/20260920-工具schema恒定而说明动态化.md)：
  只改 messages 末尾仍命中 93.8%，只改 system 末尾残留 0）。
- catalog 变化 → `toolsChanged()`（`agent.ts:263`）→ `project()` 收到 `startsSeries: true`（`agent.ts:365`）→
  `SystemPromptProjection.project` 走 **normalize** 分支：重写历史最前的 `system/message` 并清空后续节点
  （`agent-loop/src/runtime-context.ts:88`）。
- 上游 README 的定性表述（`packages/core/agent-loop/README.md:160`）：_"A schema or composition change invalidates
  reuse from the first altered request token."_ 实测把这句量化了：schema 的任何扰动（改标点、加空格、加参数、
  换序、增删）都把命中率从 94% 打到 **0~3.2%**，与扰动大小无关；代价一次性（下一发恢复 94%+），
  但工具集持续抖动则恒为 0。数据与判定见
  [ADR-工具schema恒定而说明动态化](../adrs/20260920-工具schema恒定而说明动态化.md)。
  这一点在三种协议上没有区别：`openai-completions` / `openai-responses` 是自动前缀匹配，
  `anthropic-messages` 虽有显式 `cache_control` 断点（`llm-pi-ai/src/catalog.ts:421` 的
  `supportsCacheControlOnTools`），但断点缓存的前缀同样包含 tools，改 tools 依旧让断点及其之后全部失效。
- 反向杠杆：**只改系统提示词文本、不动 tools** 时投影走 append 分支（`runtime-context.ts:96`），已有前缀不失效。
  能力目录与按组提示都走 `<system-reminder>` user 消息通道，所以说明侧的按需代价近乎零。
- **由此得到的结论（本版设计）**：既然 schema 侧没有"追加"这条路，就让它**恒定**——档位不再裁剪 catalog，
  约束改由执行层承担。代价是 schema 常驻（用短描述压缩），收益是档位切换**零重算**。
  （上一版按档位 `tools.restrict()` 裁剪 catalog：每次切换都会付一次全量 prefill，长会话里不划算。）

### 提示词通道

`dsh-prompt-reminder` 把非 `keep` 的非空 section 从系统提示词移到紧随用户消息的 `<system-reminder>`；**空文本 section 被跳过**
（`dsh-prompt-reminder/src/index.ts:30`）。于是：

- 能力目录与按组提示（中文，随档位变）→ 被降级为 reminder，档位变化时按 reminder 的「变化增量」重新注入；
- 上游逐工具说明（`IGNORED_SECTIONS`，静态清单）→ agent scope 遮蔽成空文本 → 既不进系统提示词，也不进 reminder；
- 三者都不需要与 reminder 争监听顺序，也不占系统提示词前缀（本部署路由没有 `in-history`，系统提示词就地替换会从头失效）。

被忽略的只有"工具用法说明"这一类；`plan:policy`（计划模式的行为约束）保留——遮蔽它会让计划模式静默失效，
它约束的是行为而不是某个工具的调用方式。`team:policy`（Agent Teams 协作规则）同理保留：`tool-agent-team`
在 **agent 作用域**注册它（`tool-agent-team/src/index.ts:160-164` 的 `scoped.systemPrompt.section`），
遮蔽会撞同层重名——这条边界由「忽略清单不含上游按 agent 作用域注册的说明」的扫描断言兜住。
它与档位联动：team 组启用时，投影把 `team:policy` 换成本仓库维护的中文版规则；未启用时换成空串（等于不注入），
这样"未启用的能力"不会带着它的规则一起出现在提示词里。

**遮蔽清单的边界（一次真实故障的教训）**：遮蔽靠 agent 作用域的同名空文本 section 生效，因此清单只能列
**注册在 preset 作用域**（比 agent 更远）的说明。上游 `tool-subagent` 用 `tool:${toolName}` 模板在
**agent 作用域**注册 `tool:subagent` / `tool:subagent_fork`（`tool-subagent/src/index.ts:599`，注册在
`runtimeCtx` 上以便按 scope 判断可见性）——把 `tool:subagent` 放进清单会在同一层重复注册，抛
`prompt section "tool:subagent" is already registered in this scope`，整场 session 创建失败。
它本来就自渲染（`runtimeCtx.tools.get(toolName, context.scope) === undefined ? '' : …`，同文件 :602），
工具被门控隐藏时自然不给，因此**不需要也不能**遮蔽。

由此得到两条实现约束：清单只收 preset 层说明；遮蔽注册可重入（`inject` 回调在 dev HMR 下会重跑，先释放再重建）。

## 机制

### 四组（中文描述面向模型）

| 组     | 中文名   | 工具                                                                                                                                                                     |
| ------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `base` | 基础     | read / write / edit / glob / grep / bash（或 pwsh）/ ask_user_question / job_* / read_image / web_fetch / skill                                                          |
| `flow` | 流程     | todo_write / exit_plan_mode / get_goal / create_goal / update_goal / present                                                                                             |
| `web`  | 联网检索 | web_search                                                                                                                                                               |
| `team` | 协作编排 | subagent / subagent_fork / list_subagent_models / workflow，以及队友协作全套（list_agents / send_message / wait_agent / interrupt_agent / spawn_teammate / team_task_*） |

三条划分依据：

- `job_*` 进 `base`：`run_in_background` 是 `bash` 的参数，只给启动不给收结果是残缺能力；
- `web_fetch` / `read_image` / `skill` 进 `base`：它们是"读"的延伸，不属于需要额外授权的对外行为；`web_search`
  才是真正会外发查询的那个，单独成组；
- 队友协作与派发（`list_agents` / `send_message` / `wait_agent` / `interrupt_agent` / `spawn_teammate` /
  `team_task_*` / `subagent` / `subagent_fork` / `workflow`）都进 `team`：本部署的 agent-team 插件默认开启，
  那些工具**已经注册**，但注册不等于可见——门控决定它们是否出现在模型目录里。因此标准模式不会一上来就带着
  派发与编排，「协作模式」的差别也只是把这一组预先打开。

### 曾经绕开门控的东西（own 层豁免），与我们的处理

`tools.restrict()` 过滤的是**继承面**（global + 祖先 scope），**不过滤 scope 自己贡献的 own 层**——上游注释写明这是
刻意的：作用域自己的机制不能被继承面过滤器剥掉（`packages/core/tools/src/index.ts:1181-1200`）。

`tool-subagent` 在 standing scope 且 `modelSelectionSettings: true` 时走 `installScoped`：它经
`candidate.ctx.inject(['tools','subagents','systemPrompt'], runtimeCtx => install(runtimeCtx, …))`
把 `subagent` 注册进 **agent 自己的作用域**（`tool-subagent/src/index.ts:677` → `:380`）。
后果是 `subagent` 的工具定义与说明 section 都绕过门控、始终可见——第一版实现因此把它如实列进 `base`
（`subagent_fork` 走 `install(ctx, …)` 没有这个问题）。

**本部署的决定**：不要这个例外。生成器从 `tool-subagent` 行删掉 `modelSelectionSettings`
（`generate-presets.ts`，行在 `delegation` group 的嵌套 config 里，查找要递归），子代理一律**继承父会话的模型**；
配套在 bundle patch 里禁用提供者行 `subagent-model-selection-settings`（Plugins 设置页的子代理模型卡片随之消失）。
于是 `subagent` 注册回 preset 层，工具与它的说明都回到门控之下，并进 `team` 组。

代价与防护：失去「按会话限制子代理可用模型」这一策略。产物测试断言两份产物的 `tool-subagent` 行都不含
`modelSelectionSettings`（上游开着、产物没有），忽略清单测试断言 `IGNORED_SECTIONS` 不与 agent 作用域注册的说明重叠——
谁把配置加回来，测试就红。

每组还带一份 `guidance`（中文用法提示）：启用该组时整段给，替代上游逐工具的说明。

### 模式与起始档位

生成器从上游 `standard` 生成两个 preset，`config.initial` 表达差别：

| preset 产物     | 展示名   | `config.initial` |
| --------------- | -------- | ---------------- |
| `standard`      | 标准模式 | 空（只有基础组） |
| `collaboration` | 协作模式 | `["team"]`       |

模式只影响起始档位，两种模式的切换能力完全相同。`initial` 出现未知组名时装配抛错（misconfiguration fails loud）。

### 档位判定（执行层）

目录恒定，所以约束落在执行点：`tools.guard` 在 agent 作用域注册，闭包读 state 里的档位（因此切换档位
不需要重注册，也不需要动 catalog）：

```
groupOfTool(name) === undefined      → 放行（未归组的工具：enable_tools、host plane 机制工具、上游新增未归组的）
groupOfTool(name).key === base       → 放行
已启用组                             → 放行
其余（归组但未启用）                 → 拒绝，文案写明属于哪一组、用 enable_tools 或 /tools <key> 解锁
```

- 未归组一律放行是刻意的：档位只管理"归了组的工具"，拒绝未知工具只会造成静默失效（与上一版的
  白名单策略相反——那时目录裁剪要防"未知工具默认可见"，现在目录恒定、拒绝未知工具反而更危险）。
- 覆盖性测试保证 standard 装配的工具与说明都归了组，所以"未归组"实际只可能是 host plane 的机制工具。

### schema 短描述覆盖

工具 schema 常驻，所以 `description` 值得压。改写发生在**装配投影**，不写注册表：

- 在 `system-prompt/assemble` 的 waterfall 里改 `assembly.tools`：按短描述表替换 `description`，
  其余字段（参数 schema）原样保留。模型请求用的是 waterfall 之后的 `assembly.tools`
  （`agent-loop/src/agent.ts:380` 传入 `buildRequest`），所以投影就是模型看到的那份。
- **为什么不注册同名工具**：在 agent 作用域 `tools.register` 会**同步** emit `tools/change`，而上游
  `tool-subagent` 用该事件做 composition reconcile（`tool-subagent/src/index.ts:710`）——它的 reconcile 又会
  注册/拆除工具，两边互相触发，装配风暴式重入，实测把 session 创建卡死。投影改写不碰注册表，没有这个回响。
- 短描述是"做什么"的一行中文（`SHORT_TOOL_DESCRIPTIONS`），参数细节留在 schema、用法留在按组提示。
- 顺带的好处：晚注册的工具（provider 就绪后才出现的）每次装配都过同一份投影，不像注册方案那样漏掉。
- 回归防线：用例断言**注册表里仍是上游的长描述**，只有投影里是短描述。

### 两条切换路径

- **模型侧 `enable_tools`**：注册在 preset scope，任何档位下都可调用；只做并集，返回中文说明
  （已启用组 + 当前档位 + "下一步可调用"）。参数 schema 的 `enum` 只收四个组 key——未知组名由参数校验拦下，
  比"静默忽略"更早暴露。
- **用户侧 `/tools`**：命令不带参数回到基础组，带组名即把档位设为这些组（可增可减）；拒绝未知组名；
  成功后 `agent.session.append` 一条 `source.kind === "tool-gating"` 的 user 消息，正文是中文档位说明、
  `source.groups` 是结构化档位。

### 档位重建

`unlockedFromSession(session, initial)` 以 `initial` 起步，按 surface 上的 seq 顺序应用每次变更：

| surface 上的记录                                | 语义             |
| ----------------------------------------------- | ---------------- |
| `user/message`（`source.kind` 为本插件）        | 设定（替换档位） |
| `tool/result`（关联成功的 `enable_tools` 调用） | 并集             |

只认**当前 surface**：rewind 把节点移出 surface 后，那次变更随之消失。这与
"model-visible ⟺ logged" 的约束一致——档位影响模型可见工具集，所以它必须能从会话记录重建。

## 取舍

- **目录恒定而非按档位裁剪**：上一版用 `tools.restrict()` 裁 catalog，代价是每次切换一次全量 prefill
  （schema 落在请求最前）；改成恒定后切换零重算，代价换成 schema 常驻 + 短描述压缩 + 执行层拒绝。
  长会话里这笔账划算，短会话里差别不大。
- **执行层拒绝而非目录隐藏**：目录不再承担约束，模型看得见未启用的工具；换来的是缓存稳定。拒绝文案必须
  给出解锁路径，否则模型只会反复重试。
- **未归组工具放行**：拒绝它们会变成静默失效（host plane 的机制工具、上游新增未归组的工具）；
  档位只管理归了组的工具。
- **短描述覆盖上游 `description`**：只换描述、转发执行与渲染，压住常驻开销。代价是描述与上游语义脱钩
  （上游改职责时要跟，改参数不用跟）。
- **按组给提示而不是沿用上游逐工具说明**：授权单位是「组」，所以提示也应该以组为单位——一组一段，模型在启用时
  一次读全该组的用法；逐工具说明碎片化且总量最大。代价是这段文案由本仓库维护（上游改工具行为时要跟着改）。
- **遮蔽上游说明而不是在 `system-prompt/assemble` 里裁剪**：裁剪方案要求我们的 listener 排在
  `dsh-prompt-reminder` 之前（否则 reminder 已把文本捕获进 captured），是脆弱的顺序耦合；同名遮蔽与顺序无关。
- **遮蔽清单静态、按组提示动态**：被忽略的说明不随档位变化（一次注册），档位切换只改提示文本与 guard 读到的档位。
- **模型只增、用户可切**：模型侧的并集语义让它不必权衡「该不该关」（也避免它在能力上"反复横跳"）；
  用户是显式决策者，`/tools` 是集合语义。
- **模式用 `initial` 而不是第二份装配**：模式之间的差别只有起始档位，复制一份 composition 会让同一事实有两处 home。
- **`initial` 未知组抛错而不是忽略**：配置错误应在装配点失败，而不是静默降级成一个不像预期的模式。
- **命令切换落 user 消息而不是自定义 session 事件**：档位必须可重建；一条带结构化 source 的消息即可满足，且顺带
  让模型知道档位变了，不需要新增会话格式类型。
- **不提供「按闲置自动降级」**：档位是单调的模型侧语义 + 用户显式切换；自动回收只会让能力在会话中途消失。

## 已知限制

- **全量 schema 常驻**：省不了工具定义本身的开销（含参数 schema），只是让它稳定；短描述只压住描述那段。
- **模型看得见未启用的工具**：约束靠 guard 与能力目录的标注，模型偶尔会碰壁一次并消耗一轮。
- **短描述与按组提示是本仓库维护的文案**：上游改工具职责时要跟着改 `SHORT_TOOL_DESCRIPTIONS` / `guidance`。
- **覆盖只发生在装配时**：晚注册的工具（provider 就绪后才出现）用上游原描述，直到下次装配。
- **忽略清单与组表要跟随上游**：上游新增工具或改说明 section 名时，覆盖性测试变红，必须把新 section 加进忽略清单
  或豁免表。源码里没有字面量的动态工具名由装配行扫描补上，改由源码默认值生成的名字抓不到。
- **目录与提示在 reminder 里**：两者都不占系统提示词，因此每次档位变化会多一条 user reminder。
- **子 agent 不继承父档**：父已启用的派发能力不会传给子代理；子代理可用 `enable_tools` 或父派发时的任务说明自取。
