# 压缩事务在重写时补回

状态：已采纳

背景：压缩（`compaction/start` → `compaction/summary` → `user/message` checkpoint（`surfaceOp: replace`，
source 为 `{ kind: "compact-checkpoint", compactionId }`；v3 旧日志是 `{ kind: "plugin", plugin: "compact" }`，
两种形状都认）→ `compaction/end`）是**已生效的历史**：它把被摘要遮蔽的消息从模型上下文里拿掉，压缩点之后
的对话都建立在摘要之上。而就地编辑 / 撤回的 rewind 边界只按轮次找（`precedingContentIndex` 取「前一个内容
轮」），「压缩后的第一条用户消息」的边界因此落在**压缩之前**的 `turn/end`——压缩四件套随目标轮一起被截断。

**决定**

rewind 仍然只截断到 `turn/end` / `user/message` 边界（不改 provider 的边界契约）；编排层按**轮次切分**
重写：目标之前的压缩事务随前序保留，**整段落在 `[keepFrom, 目标事件)` 区间的事务重排为 standalone 形态**
（`compaction/start` 的 `turn: null`）的连续 seq，`surfaceOp` 的 range、metering 事件的
`shadowedRange` / `shadowedSeqs` / `sourceEventSeqs` 同步重编号，保证 metering 事件与相邻 replace 仍成对。
补回位置在保留前缀之后、手工回合 / 重放输入之前（编排层 `appendSeedSuffix`），`edit` / `retry` /
`reroll` / `recall` 四条路径一致。

**范围**：保留规则是结构性的（`keptOutsideTurn`）——只排除轮结构（`turn/start` / `turn/end` /
`step/start` / `step/end`）与轮正文（人发的 `user/message`、`assistant/message`、`tool/*`），其余事件
（配置、请求头、上下文注入、队伍、`todo/write`、上游插件新增类型…）默认按原顺序保留，不需要逐类登记。
轮内 followup 撤回时保留前缀尾部是未闭合轮，补 `turn/end(interrupted)` 闭合。

**考虑过的选项**

- **把 rewind 边界扩到 `compaction/end` 或目标事件、让未闭合轮原样留在前缀里**：前缀会停在未闭合轮次上，
  之后的轮次导航与续跑都落在孤儿轮上；要么由 provider 补合成 closer（越界到持久化层），要么交给每个
  消费方自己修。现在由编排层在重写时补 `turn/end(interrupted)`，provider 的边界契约不动。
- **不补回**：摘要失效（上下文退回未压缩形态）+ 日志里留下未闭合的 `compaction/start`，上游据此判定压缩
  仍在进行、之后再也压不了。
- **按事件类型白名单补回**：上下文注入 / 队伍 / 配置等每来一类上游事件都要登记一次，上游增删即失配；改为
  只排除核心稳定的「轮结构与轮正文」，其余默认保留。
- **把压缩 checkpoint 当作「内容轮」参与 `closedTurns`**：会改变轮次导航与「可重试轮次」的口径
  （checkpoint 的 `source.kind` 是 `compact-checkpoint`（旧日志 `plugin: "compact"`），不是用户消息）。

**后果**

- 压缩在重写后仍是历史的一部分：重放只重放目标输入，界面上的摘要节点（`CompactionItem`）与上下文占用都
  保持压缩后的形态；`closedTurns` / `retryableTurns` / `editableMessages` 与轮次号不受影响（重放仍复用
  原轮号）。
- 边界类型没有扩：`session-rdb` 的 rewind 仍只接受 `turn/end` / `user/message` 两类边界；未闭合轮的闭合
  由编排层在截断之后追加。
- `compaction/prune` 作为前序事件原样保留：它的 replace range 引用更早的历史，不在切点之后，不需要重算；
  链式压缩（第二个事务遮蔽第一个 checkpoint）按 `moved` 映射处理，暂无专门 fixture。
