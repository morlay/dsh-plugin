# 撤回边界只认存储坐标

状态：已采纳

背景：撤回（`edit` / `retry` / `reroll` / `recall`）原先在 `readEvents` 里**优先读 live 会话的内存 log**。
但撤回的边界最后是拿去做 `ctx.sessionBranch.rewind(id, boundary)` 的，而这一步的校验查的是**存储**里那条
`f_sequence` 的事件类型（`session-rdb` 的 `getEventTypeAt`）。两边不是同一份坐标：

- 内存 log 的 seq 由上游 `Session.append` 用 `log.length` 自增，是「内存条目序号」；
- 存储的 `f_sequence` 由写路径按 head 递增分配，是「落库条目序号」。

两者只在「内存 log 恰好是存储的镜像」时相等。内存落后于存储时（覆盖导入、取消与截断之间的竞态），
内存算出来的边界会点到存储里不存在的位置，表现为 `rewind boundary N does not exist in session "<id>"`
或 `所选消息不属于已落定回合。`——而重启之后没有 live 会话，同一操作读的是存储，于是「自己好了」。

**决定**

撤回的目标判定与边界计算**只认存储**：`readEvents` 恒走 `ctx.sessionBranch.readRawEvents`（持久化的
稠密坐标），不再有 live 分支；`seedStart` 也按存储口径（配平后的保留前缀长度）算，不读 `live.seq`。

配套的不变量：**内存 log 必须是存储前缀的镜像**。`session-rdb` 的 `rewind` 在「内存条目数 < 保留长度」
时不再对内存做长度运算（`log.length = n` 会在尾部补出空洞，之后每次 `append` 的 seq 都与存储错位），
改为按存储前缀整体重建（`replaceLiveSessionLog`），folds / derived / surface 这些派生缓存随之清空；
内存与存储同源时仍走 `truncateLiveSession`（同样重置派生缓存）。两条分支都继续失效投影单元缓存、
token meter 与 inbox。

**考虑过的选项**

- **保持内存优先（现状）**：快，但边界坐标与校验坐标不一致，竞态下必错，且错了以后要靠重启恢复。
- **两边都读、不一致再报错或取其一**：多一次全量读，还要额外约定「信谁」；而校验那侧已经固定在存储上。
- **把内存 seq 改成存储坐标**：`Session.append` 属上游实现（用 `log.length`），改它等于 fork 上游；
  而且内存 seq 与事件顺序本来就该一一对应，缺的是「内存不能落后于存储」这条不变量，不是编号方案。

**后果**

- 撤回路径多一次全量读（读存储）；撤回本来就要重放历史，读的是同一批数据，不引入新的量级。
- 「内存落后于存储时按存储重建」只在异常态付代价；正常路径仍按长度截断，不读日志。
- 回归守护：`session-rdb` 的「rewind 之后的 memory log 镜像」用例（内存落后时重建后 seq 仍连续）与
  `ui-conversation-message-actions` 的「内存 log 落后于存储时，撤回目标与边界仍按存储判定」用例——
  后者在旧实现下抛 `所选消息不属于已落定回合。`。
