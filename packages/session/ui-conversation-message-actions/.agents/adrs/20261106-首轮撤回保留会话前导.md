# 首轮撤回保留会话前导

状态：已采纳

背景：`recallBoundary` / `retryPlan` / `rerollPlan` 落在首轮（没有前一个已落定回合）时给出边界 `-1`，
`session-rdb` 的 `rewind(id, -1)` 按契约把整个日志删掉、head 置 `-1`。而编排层此前对 `-1` 另有一段特判：

```ts
const preserved = boundary === -1 ? [] : keptOutsideTurn(events, keepFrom, targetSeq);
```

于是首轮撤回 / 编辑连**会话前导**一起丢：第一条 `turn/start` 之前写下的 `permission/preset`、
`sandbox/mode`、`approval/policy`、`agent-preset/selected`、工作目录这些会话级事实都被清掉。投影随
header 的创建默认值重算——`agentPreset` 从用户选的非默认预设回退到 header 里的创建默认（issue #10：
chip 从「空白对照」跳回「标准模式」），而 agent 的实际 composition 并没有跟着变，只有日志与 UI 记错；
直到 agent 重建（重启宿主 / 冷恢复 / 换客户端 resume）才真的按默认预设装配，对照实验的条件中途静默漂移。
第二回合及以后走 `keptOutsideTurn()`，同样的事件会被补回，所以只有首轮中招。

**决定**

`boundary === -1` 不再清空前导：`preserved` 与 `droppedCompactions` 在两处入口（`branchOperation` 与
`recallOperation`）都无条件按 `keptOutsideTurn(events, 0, targetSeq)` / `droppedCompactions(…)` 计算，
`appendSeedSuffix` 把它们按原序重写回保留前缀之后（live 与 cold 两条落写路径都不变）。`rewind(-1)` 的
数据层契约不改：它仍是「清空」，前导的找回由编排层在这一步之后补写——这样 `-1` 的含义在
`@morlay/session-branch` / `@morlay/session-rdb` 那一层保持单一。

`keptOutsideTurn` 的排除面已经保证这条区间安全：轮结构（`turn/start` / `turn/end` / `step/start` /
`step/end`）、轮正文（人发的 `user/message`、`assistant/message`、`tool/*`）与压缩事务都不在保留集合里，
所以不会把逐请求产物（`system/message`、`request/header` 之类若落在轮内也按既有规则处理）与空回合带回来。

**考虑过的选项**

- **recall 直接 `rewind(firstUserMessageSeq)`（issue 的备选方案）**：`user/message` 是合法边界，前缀自然
  保留；但 edit / retry / reroll 走这条路会留下 `turn/start` 造成空回合（`recallBoundary` 的注释已经说明
  这个坑），两个入口的边界口径也会分叉。
- **在 `session-rdb` 的 `rewind(-1)` 里保留前导**：改的是数据层通用语义，fork / 导入 / 其他调用方都受影响；
  `rewind(-1)` 的契约是「清空」，让它悄悄留一段就不是清空了。
- **上游在会话重开为空时补写一条 `agent-preset/selected`**：composition 是 agent 状态、不是日志状态，
  能补出来的只是「当前实际用的预设」，补不回权限 / 沙箱 / 审批这些同样丢掉的会话前导。

**后果**

- 首轮撤回后 `head_sequence` 不再必然为 `-1`：库里留下前导那段（若本来就没有前导，仍然是空的）。
- `agentPreset` 等会话级投影在撤回后保持不变，新回合的 `request/header` 与 chip 显示重新一致。
- 回归守护：`recall.spec.ts`「首轮撤回保留会话前导」（cold，前导四条按原序重编号）、「停止运行中的 loop」
  用例（live，保留 `request/header`），`edit.spec.ts`「首轮编辑保留会话前导」（cold）与「编辑首轮后重放
  排队输入」（live）；第二回合及以后的 `keptOutsideTurn` 用例保持通过。
