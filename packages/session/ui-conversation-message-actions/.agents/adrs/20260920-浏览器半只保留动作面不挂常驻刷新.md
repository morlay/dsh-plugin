# 浏览器半只保留动作面，不挂常驻刷新

状态：已采纳

背景：rewind 把会话日志的 seq 回退了，客户端窗口里**已渲染的旧节点不会自己消失**（被裁剪的消息残留、
新消息也追加不进去），而删除无法经 append-only 事件流表达——`ProjectionsFace` 只有 `faceOf`，没有投影
截断入口。另一方面，消息渲染面真正用到的只有两个动作（`retry` / `recall`），门控全部来自上游 chat node
的 props。

**决定**

浏览器半只保留消息渲染面用到的动作（`retry` / `recall`），刷新只由动作驱动：动作成功后先探测
`binding(id).session.resync()`（上游 ClientSession 的重建入口，类型面 `SessionFace` 没暴露，所以逐个
探测）→ 拿不到时退而 `sessions.refresh()`（只刷列表元数据）→ 都没有就记一条 warn。**不整页重载**
（打断用户），也不做投影截断。撤回回填的文本由渲染面给出**该消息的全部文本块**。浏览器半不常驻订阅会话
列表 / 快照，也不拉任何读取面。

**考虑过的选项**

- **常驻订阅会话列表 / 快照 + 全量读取面**：刷新策略由「快照抖动」而不是「用户动作」定义——编辑 / 重试 /
  撤回触发重放（agent 持续运行 → 快照与列表高频变化），访问过 N 个会话时一次列表更新就是 N 次请求。
- **靠上游事件流自行收敛、不重建窗口**：实测被裁剪的消息会残留在窗口里、新消息也追加不进去，所以重建这
  一步是必须的。
- **整页 `reload()` 刷新**：打断用户。
- **投影截断（`projections.truncate(-1)`）**：`ProjectionsFace` 没有截断入口。

**后果**

- 请求只剩动作 POST；`SessionEditorFace`（[`src/client/controller.ts`](../../src/client/controller.ts)）
  只有两个方法。
- 撤回的文本来源是消息自身内容：多文本块消息不再丢块。
- 撤回后视口无条件回底（窗口重建落定之后等两帧写 `[data-conversation-scroll]`）——上游 `ChatView` 只在
  读者已经贴底时才自动跟随（`tipMoved && atBottom`），而撤回的下一步是改完再发；重试不参与。
- 守护：`client-controller.spec.ts`（动作 POST + 窗口重建、全部文本块回填、失败不阻塞下一次操作、列表 /
  快照变化不发任何请求）。
- 接版本导航时用**按需拉取**，不要恢复常驻订阅；`conversation.session.header.utilities` 目前没有注册方。
