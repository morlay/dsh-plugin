## 结论摘要

## 事实基线

### 现状与落点

| 诉求              | 现状                                                                                                                                                                | 处置                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 引用无法表达      | 官方 `ContentBlockMap` 无资源块；`file` 块只有 sha256 附件引用；ACP `resource_link` 入站即文本化                                                                    | 引用走 text 块里的文本形态，统一解析（见下），不新增块类型 |
| 用户输入被预处理  | composer 无 ContentBlock 模型：引用只是文本，没有能携带行号范围的形态                                                                                               | 「文本即真相」：引用就是文本                               |
| 正文进消息文本    | 把文件内容 / skill 正文内联进消息与官方「选中不读内容」的取向相反，也重复付费                                                                                       | host 后注入                                                |
| 思考块无 Markdown | 上游 `ReasoningRow` 的展开正文已是 `MarkdownText`（`.../ui-chat/src/client/chat/ReasoningRow.tsx:72`），折叠摘要仍由上游 `replaceAll('**','')` 生成（同文件 `:57`） | 我们不复制该文件，跟随上游                                 |

一个支撑事实：**host 侧的队列与落库本身没有丢失结构**——排队输入就是同一个 `UserMessage`（同 id、同
`ContentBlock[]`），step 边界 claim 时同一条消息被 append 成 `user/message`
（`vendor/deepseek-harness/packages/core/agent-loop/src/inbox.ts:109-113` 的 `claim`、
`.../agent-loop/src/agent.ts:421` 的 append）。丢结构的一直是 client 的输入表示与渲染投影。

### 引用：统一解析（解析与渲染分离）

所有书写形态都用 markdown 解析器（`mdast-util-from-markdown` + GFM + 我们的 micromark/mdast 扩展）归一
到同一个结构——**host 与 client 共用同一份 `findReferences`**：

| 书写                                | 归一                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------- |
| `skill:xxx` / `@skill:xxx`          | `{ protocol: 'skill', path: 'xxx' }`                                          |
| `@xxx`（手打的裸路径）              | `{ protocol: 'file', path: 'xxx' }`                                           |
| `@xxx#L12-L40`                      | 同上 + `lineStart: 12, lineEnd: 40`                                           |
| `@xxx:1:2`                          | `{ protocol: 'file', path: 'xxx', lineStart: 1, column: 2 }`                  |
| `@"my file.ts"`                     | `{ protocol: 'file', path: 'my file.ts' }`（引号内空格是路径的一部分）        |
| `@"my file.ts"#L12-L40`             | 同上 + `lineStart: 12, lineEnd: 40`                                           |
| `[label](src/a.ts)`                 | `{ protocol: 'file'（默认）, path: 'src/a.ts', title: 'label' }`              |
| `[label](src/a.ts#L12-L40)`         | 同上 + `lineStart: 12, lineEnd: 40`                                           |
| `[label](https://example.com/a.ts)` | `{ protocol: 'https', origin: 'example.com', path: '/a.ts', title: 'label' }` |
| `@[label](dsh-session:…)`           | `{ protocol: 'dsh-session', path: '…', title: 'label' }`（官方语义原样保留）  |

```ts
export interface Reference {
  readonly protocol: string; // 默认 "file"
  readonly origin?: string;
  readonly path?: string;
  readonly title?: string;
  readonly lineStart?: number;
  readonly lineEnd?: number;
  readonly column?: number;
}
```

- `protocol` **默认 `file`**：无 scheme 的相对路径 link 也是 file 引用；http(s) 走同一套（`origin` +
  `path`）；
- 裸形态由 micromark 扩展认领（词边界起手；`@` 起手的路径无行号也认领、`#L12-L40` fragment 一并吃掉——本
  UI 没有 cue 人，`@handle` 一律当路径；非 `@` 的裸形态必须已知 scheme，`x:y` 不会被吃掉）；link / mention
  形态由 mdast 转换层认领（label → `title`；`@` 紧邻时并入 span）；
- 代码块与 inline code 内的同形文本由解析器天然排除——**不做文本层全局正则替换**；
- 生成侧按**预定形态**写出：file / folder 是 `@src/a.ts`（含空格 `@"my file.ts"`，目录 `@src/dir/`，
  `formatReferenceMention` 产出），skill pick 是 `skill:code-review`（`insertTextOf`）；行号 / 列号不是生成
  侧的产物，由手写形态认领（`#L12`、`#L12-L40`、`#L1C2`）。形态由解析器 / 格式化器这一份规则定义，谁产出
  的都归一到它。

### 输入、提交与回填

- **插入**（菜单 pick）：conversation 输入汇把引用源给出的字符串解析回结构化引用，再按预定形态归一
  （[`src/client/input/reference-text.ts`](../../../ui-conversation/src/client/input/reference-text.ts) 的 `referenceTextOf` /
  `insertTextOf`），facade 的 `insertReference` 把它当**普通文本**替换 pick span（尾随空格规则沿用）——
  **不创建 chip 节点**，草稿里没有结构化引用状态；
- **粘贴**：只落 `text/plain` 原文，上游的剪贴板改写路径没有复制；
- **提交**：草稿原文即模型文本的一个 text 块（`sinkSerialized` 回到上游实现：有 chip 时按 codec splice），
  不再切块；
- **回填**（编辑 / 撤回）：消息各 text 块按空行拼成 raw markdown 落回输入框（`restoreDraft(draft)`）；
- **输入框不做引用渲染**：编辑器里显示原文，pick / 粘贴路径都不建 chip 节点、不装饰；编辑器仍注册
  `ReferenceChipNode`，但它只服务历史草稿的 occurrence 回填（见「开放问题」）；
- **命令路径不变**：`/command` 仍走 `remote.commands.execute`，不产生 `user/message`。

### host 后注入

引用正文由 host 的 `agent/pre-step` 边界注入，形态与官方 `/name` 手势一致：

- `protocol === 'skill'` 的引用 → `@morlay/dsh-reference` 用 `ctx.skills.get` 取定义并渲染
  `<skill_content>`，作为 instructions 形态的 user 消息追加在本步已有注入之后
  （`source.kind = 'skill-invocation'`）；判定与官方手势一致（未知 / 不可调用 → 保持普通文本）；
- 解析复用 client 面同一个 `findReferences`（手写的 `` `skill:x` `` 由 `parseReferenceToken` 再兜一次）；
- file 引用的正文按 read 信封注入（裸路径与带行号范围都注入，读不出——不存在 / 目录 / 二进制——就保持普通
  文本），见 [设计 20260920-文件引用内容注入](../../../../context/dsh-reference/.agents/designs/20260920-文件引用内容注入.md)。

### 渲染

一个渲染入口，两处复用：`ReferenceMarkdown`（= 统一解析 → 本地引用切片转 token → 官方 `MarkdownText` +
`fileMentions` → chip）。

- **不 fork 渲染器**：官方包公共面只有 `MarkdownText` / `CodeBlock` / `extractMarkdownPlainText`，
  `renderBlocks` 不在公共面，且官方包在 client 侧是平台 baseline external（模块表按精确包名注册，子路径
  require 必 miss）；官方唯一的 chip 钩子是 `fileMentions`（只认 inline code），所以转换规则是：本地引用
  （非 http / https / mailto）的原文切片换成 token，http(s) 等外部地址保持 link 原文；
- chip **显示文本省略 protocol**（图标已表示协议）：有 label 就用 label（`[实现](src/a.ts#L12-L40)` →
  `实现`），否则用 path + 行号范围（`file:mise.toml` → `mise.toml`、`skill:code-review` →
  `code-review`）；hover 与 aria-label 是完整引用；图标由官方 `LinkIcon` / `classifyLinkPath(显示文本)`
  决定；
- 判定不靠文本形态：转换同时产出「显示文本 → Reference」映射给 `fileMentions.resolve`，所以没有路径特征的
  skill 名也能成 chip，普通 inline code 不会误判；
- 点击 file → `openFile`、skill → `openSkill`（owner props，打开右侧栏）——**keyed 渲染器也要从 owner props
  取这两个动作并透传**，否则点击无反应；没有 `actions` 时照常渲染但点击无效果；
- 两处消费点：[`src/client/chat-node/MessageItem.tsx`](../../src/client/chat-node/MessageItem.tsx)
  （keyed shadow，user / steering 气泡含 pending 与提交 echo，实际生效的那份）与
  [`ui-conversation` 的 `QueueDock.tsx`](../../../ui-conversation/src/client/queue/QueueDock.tsx)
  （队列行与本地 echo，无 actions）——官方 `AssistantMarkdown` 侧不消费引用渲染；
- `MarkdownLabels` 适配（`markdown-labels.ts`）在 `@morlay/dsh-client-ui-primitives` 里一份，两处共用。

## 取舍

- **新增 content block 类型（或 XML 资源块）表示引用**：官方 `ContentBlockMap` 没有资源块，加块要么改上游
  要么让消息里出现上游不认识的形态；引用留在 text 块里，host 与 client 就能用同一份解析。
- **草稿里维护结构化引用（chip 节点 + 序列化）**：composer 的模型是 `draft: string` + `occurrences`，把结
  构化引用塞进草稿就得自己维护一套状态与提交时的切块规则；「文本即真相」让草稿、提交与渲染认同一份形态。
- **把引用正文内联进用户消息**：与官方「选中不读内容」的取向相反、重复付费，且引用一旦变化就与消息内容脱
  节；后注入把正文的取值时机钉在 `agent/pre-step`。
- **队列用上游的 inline edit**：编辑 = 撤回该条到输入框是刻意的体验选择（撤回后能在完整输入框里带着上下文
  改），上游哪怕支持 in-place 编辑也不回退；理由与同步口径见
  [债务 20260917-临时接管上游对话UI的client半](../../../ui-conversation/.agents/debts/20260917-临时接管上游对话UI的client半.md)。

## 开放问题

1. 其它 protocol（`dsh-session` 等）的 chip 显示文本与点击目标（当前显示 path、无点击目标）；
2. 目录 token（`@src/dir/`）的 folder 图标：官方 `classifyLinkPath` 按扩展名判定，当前是通用纸张图标；
3. 手打 `/name`（官方 skill 手势）在 markdown 渲染下的 chip 外观；
4. 编辑器内的 chip 节点机制（`chip-node.tsx` / `ReferenceChip.tsx` / `projection.ts` 的 chip 分支 /
   `Occurrence` 契约）在 pick 改落文本后已没有产生新 occurrence 的路径，是否连同
   `slash/input-insert-reference` 的 chip 语义一起清理。
