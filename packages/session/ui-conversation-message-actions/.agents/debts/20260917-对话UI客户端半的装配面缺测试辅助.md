# 对话 UI 的槽注册面缺真装配用例

状态：未销账（障碍已解除：fork 删除后不再有 TS2717 冲突，上游 client harness 可用但未接）

**现象**

`@morlay/ui-conversation-message-actions` 的 client 半有两处槽注册，覆盖程度不一样：

- `conversation.composer.dock` 的 id `stats` 覆盖注册（`src/client/composer-stats/register.ts`）**有**真运行时用例：
  `composer-stats.spec.ts` 直接驱动真实的 `SlotCore`（`@deepseek-ai/dsh-client-ui-slots`，纯注册表，不需要浏览器
  运行时）——声明槽、注册官方同 id 行、再跑我们的注册，断言赢家 id / priority / locale / 组件。
- `conversation.chat.node` 的 `user` / `steering` 覆盖注册（`src/client/chat-node/register.ts`）**没有**：现有的
  `chat-node-actions.spec.tsx` 直接渲染组件并传入 faces，覆盖的是编辑 / 重试的门控与确认行为，注册本身的
  key / priority / locale / `inject` 面无人守护。

此前真正的阻塞在类型层：fork 的 `Context.input` 收窄声明与官方 `ui-conversation` 类型撞 `TS2717`，任何把官方
client 类型拉进同一 program 的 harness 都会让 `just lint` 变红（接线一度只能靠 fork 的 `upstream-wiring.spec.ts`
对着上游源守）。**该 fork 已于 2026-10-01 删除**
（[ADR-不fork上游前端组件只做插槽扩展](../../../../../.agents/adrs/20261001-不fork上游前端组件只做插槽扩展.md)），
冲突不复存在。

**影响**

改 `src/client/chat-node/register.ts`（换 key、调 priority / locale、改 `inject` 面）时没有回归保护：错误只会
表现为 GUI 里那一格不渲染或渲染两次，得人工跑界面才发现。

**触发条件**

动 `src/client/chat-node/register.ts` 之前——尤其是上游 `ui-chat` 的 keyed 槽声明变动、或我们要再加一个 key 时。

**销账条件**

Done when：`conversation.chat.node` 的注册有真运行时用例（断言 key = `user` / `steering`、priority、locale、
`inject` 面在真实注册表里生效），并同步更新[本包规范 how-to-verify](../standards/how-to-verify.md) 的接缝清单。

harness 的接法（上轮已验证可行，障碍解除后即可用）：上游 0.1.7 起提供
`@deepseek-ai/dsh-client-test-runtime` 的 `SlotTestRuntime`
（`vendor/deepseek-harness/packages/test-support/client-runtime/`）；按 vendor 的 `tsconfig.base.json` paths 把上游
**client 半**解析回 TS 源码（host 半仍走构建产物——其源码含标准装饰器，vite 的 oxc 在 esnext 下不转译），
vitest 的解析 alias 要**精确匹配** key（字符串 find 是前缀匹配，会吃掉 `.../renderer/src/client/bind.ts` 这类
深路径），且只覆盖 client 面。

**不修的理由**

行为面（用户看得见的那部分）已由 `chat-node-actions.spec.tsx` 覆盖，注册面窄且稳定；接 harness 要先铺一套
client 源码解析的测试基建，本轮（删 fork + 基础面内联）不顺手做。
