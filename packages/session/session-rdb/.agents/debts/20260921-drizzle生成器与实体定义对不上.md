# drizzle 生成器与实体定义对不上，迁移只能手写

状态：未销账（`pnpm db:generate` 的 diff 不能直接应用；最近几次表结构变更都是手写迁移）

**现象**

`pnpm db:generate`（`drizzle-kit generate`，schema 源是 `src/drizzle/sqlite-v3.ts` / `postgres-v3.ts`）当前不能
直接产出可用的迁移：

- **SQLite**：diff 混着与改动无关的 `t_event_usage` 重建（`CREATE __new_t_event_usage` → 拷贝 →
  `DROP TABLE` → `RENAME`），重建在几十万行的库上要重写整表，不能应用。tokens 列的 `default: 0` 已经补在实体上
  （`src/entities/v3/event-usage.ts`，与既有 DDL 的 `DEFAULT 0 NOT NULL` 对齐），触发点剩下两处**表示差异**：
  `f_event_id` 的主键表示（生成器写 `text PRIMARY KEY`，既有 DDL 是 `text PRIMARY KEY NOT NULL`）与
  `f_created_at` 的方言映射（实体是 `bigint`，生成器 SQLite DDL 写 `integer`，既有 DDL 是 `bigint`；
  `drizzle/sqlite/20260923120000_v3_usage_materialized/migration.sql`）。
- **PostgreSQL**：读既有快照直接失败（`data is malformed`），生成中断。JSON 本身合法（`JSON.parse` 通过），
  是**结构**不被当前 drizzle-kit（`1.0.0-rc.5-ab785fc`）接受；该快照 `version: 8`
  （`drizzle/postgres/20260918120000_v3_event_usage/snapshot.json`），而 SQLite 侧快照是 `7`
  （同日期 sqlite 目录）。
- 两个方言的 drizzle 视图（`src/drizzle/*-v3.ts`）都已导出统计三张表（`tEventUsage` / `tSessionUsage` /
  `tSessionCounts`）：漏导出时生成器会直接产出 `DROP TABLE`，比重建危险。

**影响**

新加列 / 表时，迁移 SQL 要**手写**：改 `src/entities/` 的 TableDef + 写 `drizzle/{sqlite,postgres}/` 里的迁移
（按惯例判断是补既有迁移还是新开一个目录），并自己检查生成器想做的其余改动是否该应用——最近几次
（`20260921075900_v3_agent_preset`、`20260922090001_v3_pinned_seq`、`20260922093001_v3_last_event_at`、
`20260923120000_v3_usage_materialized`）都只保留了真实改动，被略过的重建段写在文件注释里。手写迁移没有
`drizzle-kit` 的静态校验，列名 / 类型写错要到运行时或 PG 契约用例才暴露。

**触发条件**

- 下一次表结构变更（加列 / 加表 / 改类型）之前：要么先把生成器修到能产出可用 diff，要么明确按手写迁移走并
  在迁移文件里注明略过的段。
- 升级 drizzle-kit 或 drizzle-orm 之前：先把 PG 快照的读取问题解决，否则升级后 `db:generate` 仍然跑不完。

**销账条件**

Done when：`pnpm db:generate` 在两个方言上都成功，且产出的 diff 只包含本次真实改动（无 `t_event_usage` /
其它表的整表重建、无 `DROP TABLE`）——即实体与生成器的期望一致（主键 `NOT NULL` 与 `bigint` 两处表示差异
定性清楚，PG 快照能被当前 drizzle-kit 读取）。

**不修的理由**

当前收益只有「少写几行 SQL」：表结构变更频率低（迁移目录共 9 个 / 方言），手写迁移有 `migrate.spec.ts` 与
PG 契约用例兜住形状与数值；而修生成器要先把实体表示差异与 drizzle-kit rc 版本的快照格式一起定性，
改实体还会影响既有 DDL 的生成结果（有整表重建风险），不值得在表结构不动的时候做。
