# 会话列表逐行读投影：量级评估后不批量化

状态：未销账（已量级评估，判为边际；不是待修的 bug）

**现象**

上游 `session/list` 对每行调一次 `sessionProjectionCache.cachedSnapshot(header)`（没有批次边界可挂），
我们每次落到 `repository.readProjcacheDirect(id)` —— 一次 `(f_session_id, f_key)` 唯一索引上的单行查；
标题缺失时再 `readSessionTitleDirect(id)` 一次（多数行不会进这一支，因为 checkpoint 通常自带 `title`）。
40 个会话 ≈ 40–80 次单行索引查，量级 ~10µs/次，合计 **0.4–0.8ms**。

（对照：用量表与活动计数表**刻意分开提交**——两条派生统计线各自 best-effort，一条失败不该把另一条一起回滚。
这不是待修的写放大，见下。）

**影响**

不修的代价是每次列表刷新多几百微秒；修了要付：

- 批量预取要**跨调用保留一批内存态**（`listSnapshots` 预取 → 逐行 `cachedSnapshot` 命中），生命周期挂在
  「上一次列表调用」上。一旦失效漏掉，读到的是旧投影——比 N 次单行查贵得多，也正是
  [ADR-撤回边界只认存储坐标](../../../ui-conversation-message-actions/.agents/adrs/20261028-撤回边界只认存储坐标.md)
  与 [ADR-投影检查点按值差异写回](../adrs/20261028-投影检查点按值差异写回.md) 想要避开的形态。
- 试过把两张统计表合进一个事务：8 条 `usage.spec.ts` 转红（活动计数没落库）。**这条不修**——用量与计数是
  两条独立的派生统计线，各自 best-effort 才是想要的语义（一条失败不该连坐另一条）。

**扫过但不算多读的地方（留档）**

- `client/dsh-client-modules` 的 `readFile`（模块版本、`.files.json`、缓存代码）是**按请求读一次**，靠磁盘
  page cache 与 HTTP 缓存吸收；不是「一次操作里读同一份数据两遍」。
- `session-query` 的 `hydratePrepared` 只在观察面被调用（`observation.ts`），加载热路径不 fold 两次。

**触发条件**

- 列表页出现可感知的延迟（先量：`session/list` 的 P95 与单次 `readProjcacheDirect` 耗时），或单次列表
  会话数上千（40 → 1000 时 N 次查才到十几毫秒）。

**销账条件**

Done when：`session/list` 的投影读取是一次批量查（或上游给出批次边界），且没有引入跨调用的内存态。

**不修的理由**

批量预取要留跨调用内存态、修复方向与「读写都走库」相冲突；真出现热点时再按上面的触发条件重新评估。
