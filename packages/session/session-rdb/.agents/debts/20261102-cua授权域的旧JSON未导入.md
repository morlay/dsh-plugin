# cua 授权域的旧 JSON 文件未导入

状态：未销账（按现状接受：换介质后会话级决定需重新授权）

**现象**

`importStorages`（`src/import-storages.ts`）把 `$DSH_HOME/storages` 的 `workspace.json` 与
`session_projcache/` 导进 rdb 语义表，**不含** `cua_permissions_<profile 真实目录 sha256>.json`（官方 JSON
介质的 single 文档：`{ unit: { name, version: 1 }, global, tables: {} }`）。在官方 JSON 后端里授予过的
Computer Use 权限，切到本 bundle（`storage-domain` 路由 `rdb`、`storage-json` 被 patch 禁用）后不会出现在
`t_storage_records`：

- 应用级 `allowedApps`（profile 配置）仍会由上游 `CuaPermissionStore` 在 global 缺省（`migrated: false`）
  时一次性导入，**这一条不会丢**；
- 只存在旧 JSON 文档里的**会话级决定**（`sessions[conversation]` 的 allow / deny）与**撤销代次**
  （`revoked`）读不到，需要重新授权或重新拒绝。

**影响**

从纯官方 JSON 介质迁到本 bundle 的用户，升级后第一次用 Computer Use 会重新问一遍；已撤销的应用可能被
重新允许（用户手动决定的那一次），不是静默放行已撤销的身份——撤销代次丢失后，授权页会按新状态显示。

**触发条件**

- 有用户/发行版真的从 JSON 介质切过来，且不能接受重新授权（例如企业批量部署、撤销记录需留档）。

**销账条件**

Done when：`importStorages` 扫描 `cua_permissions_*.json` 并把 `global` 原样写进 `t_storage_records`
（行键就是文件名里的域名），且有测试证明导入后上游 `CuaPermissionStore` 能读回应用级与会话级决定。

**不修的理由**

本次报障路径下没有旧文件可导：rdb 从未服务这个域，第一次访问就以 `serves only` fail loud，`storages`
目录里不会出现 cua 文档；而上游升级指南本身接受「升级后会话许可需重新授予一次」。等触发条件成立再做，
那时要先确认旧文档的版本集合（当前只有 v1）再写映射。
