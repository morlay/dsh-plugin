## 事实基线

### 上游的规则

- 上游 `KNOWN_SESSION_EVENT_TYPES` 是**由上游仓库里 `SessionEventMap` 的声明生成的**：只有那些类型才是
  「已知」的（`vendor/deepseek-harness/packages/core/session/src/known-event-types.ts`，外部插件的事件按构造
  就在表外）。
- 持久化校验（`validateStoredEvents`）只放行两种事件——已知类型，或**带 `ignorable: true` 信封的未知类型**；
  其余一律 fail loud（判据是「很可能是更新的 harness 写的日志」）。
- `ignorable` 是**落库那一刻**写进事件信封的标记（`SessionEvent.ignorable`），不是读取时的判断：它声明
  「不认识这个类型的读者可以安全跳过它」。

### 本包的实现

1. **落库前补信封**：`appendBatch` 在 `validateStoredEvents` 之前调 `sealOwnEvents(events)`
   （`src/index.ts:941`）——凡 `OWN_EVENT_TYPES` 里的事件类型，落库的那一份带上 `ignorable: true`。
   canonical log 里的形状不变（补的是 `materializeAppendBatch` 的 JSON 快照副本，`src/index.ts:348`）。
2. **读回时兜底**：`needsShapeAdoption` 把「含自造事件类型」也算作需要归一的记录（`src/log.ts:559`），
   `normalizeToCurrentShape` 顺手给它们补信封（`src/log.ts:478`）。这一半覆盖库里**已存在、信封缺失**的行。
3. **登记表就是白名单**：`OWN_EVENT_TYPES` 列出本仓库自造、上游不认识的事件类型——当前在写的
   （`session-mode/selected`）与只出现在既有日志里的（`session-branch/version`）都在其中（`src/log.ts:552`）；
   版本效果事件本身的写侧行为见
   [ADR-20260920-删除版本树投影并停止写版本效果](../../../session-branch/.agents/adrs/20260920-删除版本树投影并停止写版本效果.md)，
   模式选择事件的语义见 [`@morlay/dsh-session-mode`](../../../../profile/dsh-session-mode/README.md)。
4. **判据**：`legacy-shape.spec.ts` 的「marks our own event types ignorable, whoever wrote them (retired or
   current)」（写入含该类型的批次 → 读回 → 事件带 `ignorable`）与真装配探针
   [`verify-session-mode.mts`](../../../../desktop/dsh-desktop-host/tool/verify-session-mode.mts)
   的「抽读已存会话」那条。

## 取舍

- **让事件类型进上游已知表**（否）：那张表由上游仓库的声明生成，外部插件进不去（vendor 只读）。
- **读取时统一放行未知类型**（否）：等于把「更新的 harness 写的日志」也读成残会话——上游拒绝这件事是对的。
- **绕开 `Session.append`，由写方直接构造带信封的事件落库**（否）：那要求每个写方自己碰持久化句柄；
  模式的选择事件本来就是 canonical log 的一部分（决定模型看到的工具与提示词），该走正常的 append 路径。
- **把白名单做成「当前在写的类型」的自动推导**（否）：白名单的价值在「写侧不产出版本效果事件之后，旧库里那些
  类型仍要能读出来」，自动推导会把只存在于既有日志里的类型漏掉。

## 开放问题

- 上游若给 `Session.append` 开口子承载 `ignorable`，这一笔可以回到写方，持久化层就不必认识自造类型——
  上游没有这个口子前不动。
