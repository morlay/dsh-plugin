# backend 合并方案：组合 + 工厂（试过继承，不行）

状态：已实现（2026-11-03）

（落地形态见 [设计 结构审计](20261103-结构审计.md)；本文是当时的方案记录，文件归并细节以现状为准。）

## 目标

删掉原先两个方言后端类（各自一套读写实现），只留：

- `openSqlite(options)` / `openPostgres(options)`：连接 + 建表（`ensureSchema`）+ 迁移（`runMigrations`）+
  identity，返回 `{ database, storage, readModel, storeIdentity, close, transaction, vacuum? }`；
- `createRdbBackend(opened)`：一个 `Backend` 实现，方法全部委托 `read-model` / `session-ops`，
  `open` / `close` / `transaction` / `vacuum` 由 `opened` 提供。

## 为什么继承不行

试过 `abstract class RdbBackendBase implements Backend` + `SqliteBackend extends RdbBackendBase`，把读方法上移。
失败点集中在**构造时序**：

1. 子类构造必须先 `super()`，但 `storage` / `readModel` / `rdb` 依赖构造参数与「打开连接」之后才有的东西；
2. 基类用 `#storage` + `attach()` 延迟注入，`super()` 之后、连接打开之前的调用（`open()` 里的 identity /
   迁移）会读到未设置的 `storage`；
3. 实测 176 条用例失败（`Must call super constructor`、`storage` 为 `undefined`），修起来要把 `open()` 拆成
   「连接 → 构造 → 打开」三段，改动面比组合方案大。

## 打开期的两个特例（实测）

工厂化时有两处不能直接用异步的 rdbkit 实例：

1. **SQLite 的 identity 读写**（`doOpen`）：此时 `dbReady` 还没 resolve，`iterateRaw` 会永久等待——第一次
   改完测试直接 5s 超时。只能在同步连接（`opened.$client`）上查。
2. **PostgreSQL 的 identity 读写**（`doOpen`）：`this.rdb` 的 `iterate` 依赖 `opened`，而 `inTransaction` 又
   依赖 `this.rdb`，同理会自锁；这一步保留在 drizzle 的 `db.transaction` 里。

因此 `openSqlite(options)` / `openPostgres(options)` 工厂的返回值里要带上**同步连接**（SQLite 的
`DatabaseSync`、PG 的 `Pool`），identity 这类「打开期」操作走它，其余在 `database` 上走 rdbkit。

## 采用方案（下一步）

组合 + 工厂，`Backend` 的生命周期保持「先构造、后 `open()`」：

```ts
// index.ts
function createBackend(config): Backend {
  let opened: OpenedBackend | undefined;
  const backend: Backend = {
    kind: config.type,
    open: async () => {
      opened = config.type === "sqlite" ? await openSqlite(config) : await openPostgres(config);
      Object.setPrototypeOf(backend, createRdbBackend(opened));
    },
    // …其余方法转发到 backend（`this` 在 open 后是 RdbBackend 的实例）
  };
  return backend;
}
```

判据：`sqlite.ts` / `postgres.ts` 只剩两个打开函数（各 ~200 行），读写方法只有 `RdbBackend` 一份；
`drizzle-orm` / `pg` 从本包依赖里移除（`pg` 留给 rdbkit）。
