# 迁移到 rdbkit：切片与判据

状态：已实现（2026-11-03，收尾见 [设计 数据库交互经 rdbkit](20261103-数据库交互经-rdbkit.md)）

## 目标

`packages/session/session-rdb` 只保留**业务语义**（会话、分支、投影、用量），数据库操作全部走
`@morlay/rdbkit`：

- 删掉 `sqlite.ts` / `postgres.ts` 里重复的两套查询实现（同一个语义写两遍）；
- 删掉手写的 `drizzle/` 迁移与 `adapters/`（结构与 DDL 由表定义生成，`ensureSchema` 负责升级）；
- 查询、写入、迁移都不再出现手写 SQL（`fragment(...)` 是唯一逃生口）；
- `Database` 作为注入项，方言只在装配层出现。

## 现状（rdbkit 已具备）

表定义 → DDL / 迁移（只增 + 破坏性开关）、投影强类型查询（`AsyncIterable`）、join 变体、CTE/UNION、
聚合、`RETURNING`、`ON CONFLICT` 表达式、`IN (SELECT)` / `EXISTS`、行锁（PG）、错误分类、查询观测、
PG 真游标。

还缺、但本包暂时用不到：多数据源（adapter 选择）、可序列化过滤模型、ER 提取、时间/JSON 类型糖。

## 切片（每片都保持现有 spec 绿，再进下一片）

1. ✅ **装配层**：`SqliteBackend` / `PostgresBackend` 打开时构造 rdbkit `Database`（catalog = 现有
   `entities/v3` 表定义），把 `dbx()` / `this.db` 之外的读写逐步改成 `database.read/run/iterate`；
   删 `adapters/`（`schema.ts` 若仍要用 drizzle 表对象，改用 rdbkit 的 `createSchema`）。
   判据：全部既有 spec 绿，且 `storage-takeover.spec` 的域层用例不改断言。
2. ✅ **存储域**：`storage-takeover/repository.ts` 的通用域读写（版本账本、`t_storage_records`、
   workspace 索引、归档/钉住写穿）改成 rdbkit 的 `table(...)`；`workspace-documents.ts` 的清理同改。
   判据：`storage-takeover` / `schedule-row` / `workspace-registry` / `cua-permissions` / `deletion` / `gc`。
3. ✅ **会话读**（`getSession` / `getEventRows` / `getEventTypeAt` / `getEventTypesBefore` / `listSessions` 全部走 `storage-takeover/read-model.ts`，两后端共享同一份）：`listSessions` / `listSnapshots` / `load` / `stat` 改成投影查询 + 迭代器；列表的
   workspace 标题仍按文档索引（rdbkit 已具备）。
   判据：`read-path`（读放大）、`session-query`、`rows`、`session-title`。
4. **会话写**：`create` / `append` / `flush` 用 `insert(...).returning(...)` 与
   `upsertExpr({ f_revision: expr('"f_revision" + 1') })`；事务边界与现有 `writeAtomically` 对齐
   （SQLite `BEGIN IMMEDIATE`、PG 串行化 + 队列）。
   判据：`rdb`、`write-guard`、`busy-timeout`、`multi-instance`、`branch`。
5. **派生**：projcache 的行级 upsert/删除、用量聚合（group by / sum）、GC 与删除路径。
   判据：`projection-cache`、`usage`、`gc`、`deletion`。
6. **迁移收口**：`ensureSchema` 替换 `drizzle/`；v2 → v3 的数据回填（标题 / 事件时间 / 钉住 / 派生统计）
   用查询构造重写（原先是手写 SQL），补回 `migrate.spec` 跳过的用例；删 `drizzle` 依赖、`drizzle*.config.ts`、
   `db:generate` 脚本。
   判据：`migrate.spec` 全绿；`just build` 不再产出 drizzle 迁移目录。

## 风险

- **v2 升级回填**：原迁移 SQL 里有数据修复，切片 6 之前不能删 `drizzle/`；迁移期两套结构定义并存时要保证
  `ensureSchema` 与 drizzle 迁移对同一份库的假设一致（都以 `entities/v3` 为准）。
- **并发写**：rdbkit 的 `transaction` 在 SQLite 是 `BEGIN IMMEDIATE`、PG 是 `BEGIN ... COMMIT`；本包现有的
  `writeAtomically` 还带「按介质串行队列」与 PG 的 `serializable`，切片 4 要把这两层对齐，不能只换成
  rdbkit 的裸事务。
- **同步读**：`cachedSnapshot` 等同步路径依赖 SQLite 直读；rdbkit 的读是异步迭代器，切片 5 要给这些路径
  保留同步入口（或改成预取 + 内存镜像），不能直接替换。

## 最终形态（第 34 轮）

迁移完成。两套 backend 是**薄壳**：SQLite 与 PostgreSQL 的类里只剩「连接、方言配置、事务（同步 / 自管 +
串行队列）、旧表搬运、`VACUUM`、同步直读」，加上每个方法一行「转发到 `session-ops` / read model」的委托。

重复的**实现**为 0：读（`read-model.ts`）、写/删除/孤儿回收/标记重算/累加/统计回填与重建（`session-ops.ts`，
9 个共享操作）、会话列表与用量总览（`session-ops.ts`，五段查询）都只有一份。委托方法保留在两类里是
TypeScript 接口实现的必然（`implements Backend` 要求方法在类上），运行期混入或继承都会牺牲类型安全或重排
`open()` 时序——取舍见下一节。

## 骨架合并的取舍（第 33 轮）

两套 backend 的**重复实现已归零**：30+ 个方法体都只剩「调用 `session-ops` / read model」的一行委托，
`this.db` 的引用只落在连接、事务、旧表搬运、`vacuum`（PG）与 `dbDirect`（SQLite 同步直读）上。

没有把这一行委托也抽成基类，原因是**构造时序**：`storage` 依赖 `database`，而 `database` 由子类在
`open` 前用方言连接创建；基类构造拿不到它，`readonly storage` 又不能在子类构造里赋值。可行的两条路都不划算：

1. 静态工厂 + 基类构造注入（`super({ rdb, readModel, storage })`）——把两个 `open()` 拆成「连接 → 构造 →
   打开」三段，事务与 identity 的时序要重排，风险高于收益；
2. 组合式操作包（`createBackendOps({ rdb: () => this.rdb, … })` + `Object.assign(this, …)`）——用 getter
   绕开构造时序，但把类型检查换成运行期混入，`Backend` 接口的实现从编译期变成约定。

当前形态（两个薄壳类、委托方法各自一行）在可读性与类型安全上更好，重复的**逻辑**已经为 0。若以后要真正
合并骨架，先改 `open()` 的时序再抽基类。
