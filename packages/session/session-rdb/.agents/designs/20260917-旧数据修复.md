状态：已实现
范围：旧格式行的读取 / 导出视图修复与写打开时的落库迁移；表结构级迁移见
[设计 表结构](20260917-表结构.md)，修复管线与顺序见 [设计 读路径](20260917-读路径.md)。

## 事实基线

### 库里旧格式行的形状（读取视图要兼容的形状）

- `f_data` 可能是**纯 `data` 形状**（旧行只落 `event.data`），也可能是完整事件（当前形状，
  type/seq/time/data/ignorable 四键）；兼容判定在 `rowToEvent` 与 `physicalEvent`
  （`src/log.ts:97`、`src/legacy.ts:29`）。
- `f_surface_op` 里 replace 的端点字段名可能是 v2 时代的 `start` / `end`，读取时按 `startSeq` / `endSeq`
  归一（`normalizeSurfaceOp`，`src/log.ts:9`）；旧写入器重编号事件后，range 还可能是旧坐标空间的残留，
  由 `repairSurfaceOps` 夹取或降级（[设计 读路径](20260917-读路径.md)）。
- `assistant/message` / `assistant/attempt` 可能缺 `stream`（旧行没有流式记录），由
  `repairAssistantSettlement` 补 `[]`——上游 seed 校验要求 turn / step / stream 齐备。
- `request/header` 可能是 v3 之前的形状（带 `header.system` / 空 `tools` / 空 `adapterDefaults`），
  由 `repairRequestHeaders` 归一——v3 起 system prompt 由 surface 上的 `system/message` 承载。

### 表结构级迁移（手写迁移）

表结构版本策略、迁移执行方式与 v3 diff 内容见 [设计 表结构](20260917-表结构.md)。

### 混合世代 log 的回退读取

旧写入器只在建会话时落一次 `f_version`，之后跟随上游演进继续追加事件：同一个 log 可能是**混合世代**
（早年的行 + 新版本字段，如 `permission/preset.origin`、`subagent/descriptor` version 2），不是任何单一
已发布格式。严格的上游迁移链（v0 → v1 → v2 → v3 → v4）对这种 log 必然拒绝。

`readLog` 因此先尝试迁移链（真旧格式数据，含 `assistant/chunk`、旧消息形状），拒绝后回退
`adoptLegacyRows`（`src/legacy.ts:77`）：

1. header 版本归一到 `SESSION_FORMAT_VERSION`（其余 header 字段来自存储行）；
2. 按稠密 seq 采用行数据（`rowToEvent` 兼容纯 data 形状、归一面字段名）；
3. 继承前缀收缩到实际事件数（`min(f_seed_length, 事件数)`）；
4. `repairRequestHeaders` 把旧格式 `request/header` 归一为当前格式——必须发生在调用方
   `validateStoredEvents` 之前，否则会话加载失败；
5. 交给读取视图修复（`repairReadView`）：补 `assistant/message.stream`、越界 replace 按 metering 数量夹取
   或降级、metering range 对齐、provenance 重算、孤儿 inbox splice 改写——这一步由 `readLog` 的调用方执行
   （`src/index.ts:1243`），不在 `adoptLegacyRows` 里。

回退不放松 fail-loud：旧事件类型（`assistant/chunk`、`compact/*` 等）仍由 `validateStoredEvents` 拒绝；
已提交区的 seq gap / 不可解析行仍由 `scanRows` 拒绝（`src/log.ts:666`）。

### 写打开时落库迁移（坐标对齐）

迁移链会**生成 / 合并事件**（继承切点的 `session/end-seed`、无 message 的 `assistant/attempt`、chunk 合并），
迁移视图的事件数因此可能与存储桥接行数不同。读坐标与写坐标（存储 head）不一致时，`append` 按 head 重编号
会撞上已有行或写坏 log。

因此 `open(id, "write")` 检测到「迁移视图事件数 ≠ 存储行数」时，在同一事务内执行 `rewriteMigratedLog`
（`src/index.ts:748`、`src/index.ts:1134`）：并发写者校验 → 删光本会话桥接行（`deleteBridgeTail(id, 0)`）→
按迁移视图重建（新事件行，完整信封 + 桥接行）→ 更新 head 与 revision。此后该会话是普通当前格式会话，
读写同坐标；被换掉的事件行成为孤儿（引用标记落回 0，本会话汇总按新事件重算
`rebuildSessionStats`），由 GC 通道回收
（[ADR-删除不再清孤儿与vacuum独立成gc通道](../adrs/20260918-删除不再清孤儿与vacuum独立成gc通道.md)）。
混合世代回退视图（`adoptLegacyRows`）与存储行同坐标，不触发落库迁移。

### 数据格式级修复（导出即修复）

表结构已是当前版本、但数据仍是旧格式（`f_data` 纯 data 形状、`f_surface_op` 旧字段名）或 surface
**语义**损坏（非法 replace 导致 seed 校验失败）时，修复并入读取 / 导出路径（`readRaw`），导出即修复：
读取会话全部事件行（`rowToEvent` 兼容纯 data 形状）→ 应用 `repairReadView` 容错修复（含继承前缀收缩，
明细见 [设计 读路径](20260917-读路径.md)）→ 重算 replace provenance → 序列化为 JSONL artifact
（`toJsonlArtifact`，`src/log.ts:715`）。产出的 artifact **完备可用**：导入（`parseJsonlArtifact`，
同样防御性收缩，`src/import.ts:19`）后无需任何修复即可加载。

修复只作用于读取 / 导出视图，**不落库**（存储行与 revision 在读取 / 导出前后完全一致）。

### rewind 收缩 seedLength（根因处理）

根因与修复见 [设计 分支能力](20260917-分支能力.md)：rewind 截断后在事务内把 `f_seed_length` 收缩到保留事件数
（只收缩、不扩张），并同步 live write handle 的继承前缀（否则下一次 append 会把旧值覆盖回去）。

## 取舍

- **原地修复数据行**（否）：破坏「写路径零转换」不变量，修复逻辑与写路径耦合，历史加载失败的会话也无法修复
  （[ADR-旧数据导出即修复而非原地迁移](../adrs/20260917-旧数据导出即修复而非原地迁移.md)）。
- **单独维护一个修复脚本**（否）：解析逻辑与导出路径重复一份，用户还得知道何时运行。
- **回退视图放松 fail-loud（未知类型一律放行）**（否）：那等于把「更新的 harness 写的日志」也读成残会话，
  未知类型必须保持拒绝（[ADR-混合世代日志回退为当前格式视图](../adrs/20260917-混合世代日志回退为当前格式视图.md)）。
- **回退视图重实现 payload 转换**（否）：payload 转换是上游 v0→v1 迁移链的职责，回退视图只做字段级归一。

## 开放问题

- 纯 v0 / v1 的 pre-step 会话（消息无 id、旧 payload 形状）当前仍不可读：要不要在回退视图里补一段
  payload 转换，取决于是否还有这类数据需要打开。
