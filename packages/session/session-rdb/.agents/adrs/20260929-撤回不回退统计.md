# 撤回不回退统计

状态：已采纳

背景：撤回（rewind；「编辑 / 重试 / 撤回」三条动作的最后一步都走它）原先在截断之后重算该会话的两张汇总表，
并**全量**重算 `t_event_usage` 的引用标记。真实库（1GB：`t_events` 23.6 万行、`t_event_usage` 3.96 万行）
实测这条尾巴是**固定 1401ms**（全表 UPDATE 3.96 万行）+ 按会话重算 508ms / 10,248 事件（会话越小越便宜），
与会话大小无关地摊在每次编辑、每次重试上。

**决定**

撤回不碰统计：`rewind` 不重算 `t_session_usage` / `t_session_counts`，也不刷新 `t_event_usage` 的引用标记。
统计记的是**真实发生过的消耗**——请求已经发起就已经消耗过，撤回只是把对话重放一遍，不该把已消耗的 token
从报表里抹掉；重放再跑一次会按写路径再累加一次（那也是真实消耗）。

**考虑过的选项**

- **全表刷新标记**（原实现）：语义错（撤回后消耗凭空消失）且固定 1.4s。
- **只刷被截断的那批事件**（精确增量）：性能能接受，但语义还是错——被撤回的那笔消耗一样会退出统计。
- **只重算该会话汇总表、不刷标记**：按会话行回落、总量不变，但两张表的口径从此不一致（同一次撤回，
  总量还留着、按会话行已经扣掉），读数会互相打架。

**后果**

- 「编辑 / 重试 / 撤回」的耗时只剩撤回本身的写成本（删桥接行，与截断掉的事件数成正比：中位会话 378 事件
  全程 113ms）。
- 撤回后该会话的统计不回落（按会话行 = 该会话历史真实消耗，不是「当前内容」的消耗）；被截断的事件行成为孤儿，
  由 GC 通道回收后从统计消失（那是一次显式清理，见 ADR-删除不再清孤儿与vacuum独立成gc通道）。
- 全量刷新只留在「会话删除」与「旧日志重写」两处低频路径上；撤回与 fork 都不再触发它
  （fork 侧见 ADR-fork不继承统计）。
