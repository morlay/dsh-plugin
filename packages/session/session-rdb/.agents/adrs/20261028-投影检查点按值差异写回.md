# 投影检查点按值差异写回

状态：已采纳

背景：投影检查点（`t_session_projcache_row`）此前是「按事件条数 / 时间攒批」写回：`session/event` 每来一条
就 `pending += 1`，到 200 条或 5 秒（`writeEveryEvents` / `writeIntervalMs`）才 `flush` 一次，且每次写都是
「删掉这个会话的全部行 + 重新插入全部行」。两个后果：

- 攒批参数是**猜测出来的节奏**，与「投影值有没有真的变」无关：`request/header`、流式结算这类不进任何
  投影的事件也会把计数推上去；
- 真到写的时候，一次事务全量重写几十行。

而缓存要的是「值对不对」，不是「水位最新」：上游 checkpoint 行里的 `seq` 是「最后折入的事件」，
**每个事件都会推进它**，拿它当变化判据等于每个事件都写一次。

**决定**

写回判据改成**比值**：`ver` + `val` 相同就跳过（不比 `seq`），没变化**既不写库、也不推 `flush`**。
调度上取消攒批参数：`session/event` 到达即排一次微任务做「取 checkpoint → 比差异 → 有变化才写」，
同一 tick 的多条事件合并成一次比对（这不是攒批：比对是内存操作，落库仍然即时）。

事件落库的节奏不动：仍是上游 handle 的 200ms 批量窗口（[设计 写路径](../designs/20260917-写路径.md)
「否掉的选项」里已否掉逐条落库——长回答下会放大到每秒数十次事务）。我们只在检查点真的要写时顺带
`flush` 一次。

同时删掉 `projectionCache` 配置项（`writeEveryEvents` / `writeIntervalMs`）：它们唯一的作用就是攒批节奏，
判据换了之后没有语义。这两个键从未被任何 profile / 部署配置写过，删掉不涉及迁移。

**考虑过的选项**

- **保留攒批参数、只是把判据换成值**：参数还在就要有人调；而「有变化才写」本身已经给出上界（值变化的频率），
  再叠一层攒批只是把写往后拖，读侧水位更旧。
- **比 `seq` 也算变化**：每个事件都会推进 `seq`，等于回到「每事件写一次」，写放大最严重的一版。
- **只在 `turn/end` 写**：长回答里中途的投影（标题、outline、inbox）会长时间停在旧值，列表页读到旧标题。
- **把落库节奏也改成逐条（读写全直连、无任何批量）**：与上游 200ms 窗口的设计取舍冲突，且没有用户可见收益——
  事件本身不参与任何判定（撤回边界读库，见
  [ADR-撤回边界只认存储坐标](../../../ui-conversation-message-actions/.agents/adrs/20261028-撤回边界只认存储坐标.md)）。

**后果**

- 回归守护：`projection-cache.spec.ts` 的「投影没有变化时不写库」——追加一条不进任何投影的事件后，
  库里的行快照必须一字不差；`read-path.spec.ts` 的「write-through」——`append` 返回后另开只读句柄
  不调 `flush` 也能读到全部事件（`append` 的事务提交即持久）。
- 写量上界从「事件条数 × 全量行」降到「值变化次数 × **变化的行**」：写回走
  `StorageRepository.patchProjcache`（同一事务内先删这些 key 的行、再插变化行），未变化的行一行都不碰；
  `putProjcache`（整份替换）只留给导入这类「一次性整份写出」的场景。
- 配置面少两项：老配置里写了这两个键也不会被拒（schemastery 保留未知键），只是不再生效。
