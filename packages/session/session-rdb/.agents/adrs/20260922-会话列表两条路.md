# 会话列表两条路：官方 list 排除归档，管理面走自有路由

状态：已采纳

背景：上游只有一条会话列表——`session/list`（`@deepseek-ai/dsh-api-session-controller` 的 remote）→
`ctx.sessionQuery.listSessions()`（本包接管）→ 上游按 header 组装 summary。它的契约是「完整逻辑语料」：
**归档与否不影响返回**，归档可见性由 client 用 workspace registry 的 `archivedSessionIds` 过滤。本部署要的是
「列表默认干净」（归档是收起来的会话，不该混进日常列表与搜索），而同一份数据又是「对话管理」页
（`@morlay/ui-conversation-manager`）的工作对象——它需要**完整集合**（含归档），还要标题与最后活动时间。

**决定**

**两条路分开**：官方 `session/list`（本包在 `listSessions` 里覆盖）**默认排除已归档**；本包另给一条
`POST /api/session.rows`（`/api/session.*` 族）返回**完整语料** + 标题 + 最后活动时间 + 工作区归属，供我们自己
的管理面使用。「对话管理」页的数据面用这条路由（`useWorkspaces` 仍用于工作区归属）。

**分页与搜索也在后端**：请求 `{ query?, includeSubagents?, page?, pageSize? }`（`pageSize` 默认 20、上限 200），
响应 `{ items, total, page, pageSize }`；`query` 同时匹配标题与**工作区标题**（会话行与工作区归属在 host 侧
join），`includeSubagents` 决定是否连子代理派生会话一起要。排序键是会话行的 **`f_last_event_at`**（写路径在
提交批次时把本批最大事件时间推上去，只增不减；老数据由迁移一次性回填，没有事件的会话留 NULL，读时回落
`f_created_at`）。

**考虑过的选项**

- **接管上游 `session-controller`，给 `session/list` 加 `includeArchived`**：能保住「参数化」，但要子类化一个
  50+ remote 的大服务并长期跟住它的 remote 面；而且上游 client 不会传该参数，「只看归档」视图照样空，
  收益只剩「参数好看」。
- **只过滤、不给自有路由**：管理页的归档集直接消失（它的行依赖 summary），等于废掉本仓库的归档操作面。
- **在消费侧过滤（保持上游契约不动）**：等于把策略散到每个消费者，官方那条对任何人都是脏的；本部署的客户端
  不止一个。
- **给 summary 加 archived 标记、仍返回全部**：列表集合没变，「默认干净」这个诉求没解决。
- **一次返回全量、页面自己分页 + 搜索**：那条 SQL 对每行算一次「该会话最后事件时间」的相关子查询，真实库
  243 行要 **4.2s**；加 `LIMIT 20` 仍要 383ms（排序要求全表先把时间算出来），物化到会话行后同一条分页查询
  是 **0.2ms**。
- **范围过滤用 `now - N × 24h` 的滚动窗口**：与统计侧「本地日零点」口径不一致，两处数值会漂
  （[ADR-统计衍生表物化归属与汇总](20260923-统计衍生表物化归属与汇总.md)）。

**后果**

- **上游 UI 的归档派生视图会空**：`ui-workspace` 的 `ArchivedFilter`（默认隐藏 / 显示 / 只看）拿不到归档行
  ——这是「默认干净」的代价，本部署用「对话管理」页承担归档集的查看与动作。
- 搜索同样不含归档（搜索走同一 `listSessions`）。
- 管理面这条路由要跟着 `archived` / `title` 的口径走：`archived` 读会话行的 `f_archived_at`，`title` 读
  `f_title`，`updatedAt` 取「创建时间与该会话最后事件时间的较大者」（对齐上游 summary 的
  `max(createdAt, lastPromptAt)` 口径）。
- 归档集合的权威仍是 workspace registry；`f_archived_at` 是它的存储投影，两边由本包的 storage 接管保持同步
  （[ADR-接管storages到rdb语义表](20260917-接管storages到rdb语义表.md)）。
