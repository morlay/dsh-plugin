# 统计衍生表物化归属与汇总

状态：已采纳

背景：统计报表（对话管理页「统计」视图，`POST /api/session.usage`）在真实库（788MB：`t_events` 18.2 万行、
`t_session_events` 18.1 万、`t_event_usage` 3.05 万、`t_sessions` 262）上单次全范围要 **~230ms**
（sqlite3 CLI 实测：按会话行 124ms、总览+桶 84ms、活动计数 22ms），每次切时间范围重付一遍。
慢点全在「用量行没有读侧维度」上（[设计 表结构](../designs/20260917-表结构.md)）：

- `t_event_usage` 只有事件键、时间、模型与 5 个 token 列——**没有会话归属、没有本地日、没有「是否被会话引用」**，
  于是每条查询都现算：`EXISTS(t_session_events)` 判引用、相关子查询 JOIN `t_sessions` 判 subagent；
- 按会话聚合只能回连 `t_session_events`（执行计划 `SCAN t_session_events` 18 万行）；
- 活动计数与会话集合靠 `hasUsageSession(EXISTS …)` 把 `t_event_counts` 和用量表拼口径。

物化实验（同一副本，先给用量行补上物化列再测等价查询）：总览 84ms → **10ms**、桶 → **18ms**、
全量回填一次性 **183ms**；而「按会话行」即使有物化列仍要回连事件表 **119ms**——因为「一个事件行属于多个会话」
（fork 派生）这一维只有事件表有；若把归属压成用量行上的单列，则降到 9ms，但**丢掉 fork 继承前缀口径**。

**决定**

统计读侧只读三张**可销毁重建的衍生表**，全部读侧维度在写入时物化：

1. `t_event_usage` 补三列——`f_day`（host 本地日）、`f_referenced`（被任何会话桥接行引用）、
   `f_subagent`（被任何 `origin = 'subagent'` 的会话引用）。事件级去重口径（fork 共享行计一次、孤儿行不计）
   与天×模型桶只读它，不再有 `EXISTS` 与相关子查询。
2. 新增 `t_session_usage`（会话 × 本地日 × provider × model → 5 个 token 列）：**按会话的行**读它，
   从而保住「含 fork 继承前缀」的口径而不回连事件表。
3. `t_event_counts`（会话 × 日 × 类型）换成 `t_session_counts`（会话 × 日 → 轮次 / 步骤 / 用户输入 / 工具调用
   四列）：活动计数一次读成四项，不再在读取时按类型折。

配套规则：

- **时间范围起点按本地时区对齐到零点**（`day` / `week` 不变；`7d` / `30d` / `90d` 变成「最近 N 个自然日，含今天」）。
  事件级表按毫秒 `f_created_at >= since` 过滤，会话汇总表按本地日 `f_day >= 起点日` 过滤——起点是本地零点时
  两者严格等价，两处数值不会打架。
- **写路径**：事务内新事件行的用量行直接带 `f_day` / `f_referenced = 1` / `f_subagent`（会话是否 subagent）；
  事务提交后**旁路累加**两张会话汇总表（失败只 warn，同既有活动计数旁路）。
- **重建**：fork / rewind 之后按会话重算该会话的两张汇总行，并**全量重算** `t_event_usage` 的引用标记；
  删除会话后同样全量重算标记（引用消失要让孤儿行退出统计，GC 之外的窗口也必须正确）。
- **回填**：打开库时任一衍生表为空 → 从事件表全量重算（幂等）。迁移对这三张表**先 DROP 再建**
  （纯衍生数据，不写 ALTER / 数据搬迁）。
- **不 bump `SCHEMA_VERSION`**：理由同 [ADR-用量统计走专用用量日志表](20260918-用量统计走专用用量日志表.md)——
  迁移由 `__drizzle_migrations` 驱动，bump 只会让既有的 v3 库被判不兼容而打不开。

**考虑过的选项**

- **只补物化列、不做汇总表**：改动最小，但按会话行仍 119ms（要回连 18 万行事件表）；
  压成用量行单归属列则丢 fork 继承前缀口径（各行之和会等于总量），用户明确要保口径。
- **再加一张日聚合表**（day × provider × model × subagent）：总览/桶能降到 μs 级，但 3 万行聚合实测
  10–18ms 已不可感知，多一层旁路累加与前缀重建不划算（YAGNI）。
- **引用标记做精确增量维护**（rewind 只重算被截断的事件、fork 只置 1）：截断/删除后「是否还有别的会话引用」
  要跨会话判定，调用点还得在桥接行删除前捕获事件集合；低频路径上省不下可感知的时间，值不当的复杂度。
- **范围过滤保留 `now - N × 24h` 的滚动毫秒窗口**：起点不是本地零点，汇总表的 `f_day` 过滤就与事件级的
  毫秒过滤不等价（边界日差 ≤1 天），两处口径会漂；按本地日对齐后语义更贴界面文案「近 N 天」。
- **`t_event_counts` 保留按类型存**：读取时还要折四项、行数 ×4；改成四列同价且更直白。

**后果**

- 读侧从「现算 + 回连事件表」变成 4 条小表查询。真实库副本（18.4 万事件行 / 3.09 万用量行 / 262 会话，
  788MB）端到端实测：全范围 **30.6ms**、近 7 天 **16.3ms**、本日 **1.7ms**（改造前 SQL 层就 ~230ms，
  其中按会话行 124ms、总览+桶 84ms）。
- 同一副本上逐项交叉核对，新旧口径数值一致：总量 6 848 020 587、subagent 143 万 / human 539 万、
  按会话 262 行、桶 38 行全部相同；`f_day` 与现算 `localtime` 零差异；活动计数与「从事件表重算」逐行一致。
- 派生表可在任何时候清空重算；代价是 fork / rewind / 删除会话各多一次按会话重算与全量标记重算
  （标记 UPDATE 实测 183ms），都在低频路径上、且不参与写事务（失败只 warn，下次重建自愈）。
- **首次打开旧库付一次全量回填**：实测 2.4s（用量行 1.9s + 两张汇总表 0.5s），加上迁移删表重建，
  端到端 `open` 3.7s；此后每次打开不再发生。回填的大头是逐行 `json_extract`，要再压只能改事件存储形态
  （不在本次范围）。
- `7d` / `30d` / `90d` 的数值会与旧口径略有差异（起点从「此刻往前 N×24h」变成「今天零点往前 N-1 天」）；
  `day` / `week` 与总数/按会话的相对关系（各行之和 ≥ 总量）不变。
- 迁移 `20260923120000_v3_usage_materialized` 对四张统计表（含旧 `t_event_counts`）先 `DROP` 再按新结构建，
  首次打开旧库多一次全量回填。
