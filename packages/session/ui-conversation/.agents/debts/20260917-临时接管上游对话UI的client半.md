# 临时接管上游对话 UI 的 client 半

状态：未销账（`@morlay/dsh-client-ui-conversation` 是官方 `ui-conversation` 行的**薄壳 fork**、由我们维护；
装配里官方该行 `disabled: true`，insert 我们的一对一行）

**现象**

对话外壳的改造点全在组件内部——粘贴决策与插入路径在编辑器与 InputBar 里、队列行自己算文本——而插件面只有
「整格 shadow keyed slot」，没有 wrap 上游组件的机制。所以这一行由我们接管，**我们是它的发布方**。

装配在 `packages/session/better-session/cordis.patch.yml`：官方 `ui-conversation` 行 `disabled: true` + insert
我们的 `ui-conversation-fork` 行。`disabled` 停掉的是官方那行的装配（槽声明与渲染），它声明的 22 个
target-neutral 槽（`main.conversation` … `conversation.input.model`）由我们的 `client/apply.ts` 同形承担
（`children` 既声明子槽也授权 `renderSlot`）；槽、locale 命名空间与设置命名空间都与上游同名同形。上游已发布包
反过来依赖 fork 的槽面（`ui-subagent` 的 `conversation.content` 工厂、`ui-sidebar` 的
`conversation.session.header.leading`、`ui-agent-preset` 的 `conversation.hero.agentPreset`），fork 少声明一个席
就静默失效。

形态是**薄壳**：只复制我们**有意改过**的文件，其余上游文件不复制——保留文件里指向它们的 import 走相对路径指向
`vendor/deepseek-harness/packages/client/ui-conversation/src/...`，构建时由 tsdown 内联进 `dist/client.cjs`
（发布物自包含，`files: ["dist"]`），开发态由 `dev-client-bundles` 现场打包。包级写法约束（根 `tsconfig.json`
保持 `composite: false`、合并接口只能一份实例）见[本包规范 how-to-write](../standards/how-to-write.md)，测试口径见
[本包规范 how-to-verify](../standards/how-to-verify.md)。

## 同步口径

- fork 的 `src/` **不是**上游的逐字快照：同步按差异项逐条判定「有意偏离」还是「落后于上游」——有意偏离保留我们的
  实现，落后项跟随上游；
- 与我们的改动冲突时**保留我们自己的实现**，不回退、不迁就上游当前形态；只有「上游已支持」或「我们不再需要偏离」
  才执行上面的回退动作；
- 回写粒度按能力项（上面的四项），不按文件；每次同步注明当时的 `DEEPSEEK_HARNESS_VERSION`（基线见根 `mise.toml`）。

## `turn-tail` 不能承载覆盖（当前结论）

keyed 格子的 `children` 既是子槽声明也是 `renderSlot` 授权：官方 `conversation.chat.node` 的 key `turn-tail`
那一格已声明 `conversation.chat.turnTail` / `conversation.chat.assistant-actions`（消费者 `ui-deliverables` /
`ui-plan` / `ui-message-feedback`）。同 key、同优先级再注册即 fail loud：

```text
slot "conversation.chat.turnTail" is already declared (by an entry in "conversation.chat.node")
```

带 `children` 覆盖撞「already declared」，不带 `children` 覆盖则丢这两个槽的全部贡献。因此这一格只能沿用官方实现；
可用的覆盖面是 list 槽按 id shadow——编排层在 `conversation.composer.dock` 的 id `stats`（priority −1）上覆盖官方
同 id 行，就是这样承载它自己的统计行的。

## 已知冲突：官方类型可见时的 TS2717

`client/index.ts` 在 `declare module "@deepseek-ai/cordis"` 里把 `conversation` 收窄成
`Omit<IConversation, "input"> & { input: SessionInputResolver }`（`ui-conversation-message-actions` 靠它改写
草稿）。模块增强没法表达「属性类型收窄」：官方 `@deepseek-ai/dsh-client-ui-conversation` 的类型一旦与这段声明
同处一个 program，TS 就按「同一属性的两次声明类型不同」报 TS2717（`conversation` 一条；`uiConversation` 一条是
「同名类型两份实例」）。运行期官方 `ui-conversation` 行是 disabled 的、同一 scope 里只有 fork 这一份服务，所以
冲突只在类型层。

**后果**：任何把官方 ui-conversation 类型拉进同一 program 的东西都会让 `just lint` 变红——包括上游 0.1.7 起
提供的 client 测试 harness（`@deepseek-ai/dsh-client-test-runtime`，vendor 的
`packages/test-support/client-runtime`：它的 `fixtures.ts` 引官方包类型）。所以**装配面的行为用例还开不了**，
接线改由 [`upstream-wiring.spec.ts`](../../src/__tests__/upstream-wiring.spec.ts) 守（落点见本包规范
how-to-verify）。

试过并排除的两条路（免得下次重试）：

- **把声明搬进 `.d.ts` 靠 `skipLibCheck` 覆盖**：tsgolint 不把 `/// <reference>` 或
  `import type {} from "./x.d.ts"` 指到的声明文件纳入 program → 收窄直接失效（`QueueDock.tsx` 当场报
  `restoreDraft` 不存在）；
- **就地加 `@ts-ignore`**：报错压住了，收窄类型同时失效（同上）。

真要开装配面行为用例，得先把收窄从「占用官方属性名」改成 fork 自己的服务 / 类型面（契约变更，落 ADR）。

（附：让 client 侧用例跑起来的另一半——按 vendor `tsconfig.base.json` 的 paths 把上游 **client 半**解析回 TS
源码，host 半仍走构建产物（其源码含标准装饰器，vite 的 oxc 在 esnext 下不转译）——改法已验证可行：vitest 的
