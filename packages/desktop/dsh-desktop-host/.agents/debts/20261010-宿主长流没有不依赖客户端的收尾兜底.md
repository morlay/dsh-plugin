# 宿主长流没有不依赖客户端的收尾兜底

状态：触发中（两条真实取消路径已收口，但没有「客户端什么都不做」时的兜底）

**现象**

桌面宿主里的长流（`session/follow`、`job/attach` 这类）只有两条收尾路径：客户端显式取消（cancel 帧 →
`Request.signal` abort → `streamHandler` 的 `cancel()` → gateway 的 signal abort → 上游 follow 的 `finally`），以及
响应自己写完（`response.end()`）。**没有空闲超时，也没有「同一会话新开取代旧开」**——上游
`SessionHistoryController.closeFollowers` 只在 controller 卸载时触发
（`vendor/deepseek-harness/packages/api/session-controller/src/history.ts`），同会话再开一条 follow 不会动旧的。

客户端彻底不取消时（页面卡死/崩溃，或注入脚本被改回「丢下迭代器不 cancel」），那条流就一直挂着，
`DSH_MEMORY_REPORT=1` 那行的 `active` 只增不减。

**读数（打包形态 + 干净 DSH_HOME + 复制的会话库；现场临时探针：对同一会话开 12 条 follow 后丢掉迭代器，探针不进树）**

| 姿态                             | 报告行                                                        |
| -------------------------------- | ------------------------------------------------------------- |
| 12 条丢下、不 cancel（修复前/后） | `active=12 opened=12 failed=0 items=13 bytes=7MB heapUsed=386MB` |
| 补发 cancel（修复前）            | `active=12`（不动）`heapUsed=387MB`（不动）                   |
| 补发 cancel（修复后）            | `active=0 opened=12 failed=12 heapUsed=152MB`（回落）          |

**影响**

残留流的代价是**常驻**，不是 churn：每条 retain 一份会话观察（`observeSession` 的 observation）、一份 opening
snapshot 的记录数组，以及一个随会话活动无界增长的事件缓冲。上表 12 条 ≈ 200MB heapUsed 常驻——GC 收不掉
（修复前的对照里 `heapUsed` 停在 387MB 不动），要等 signal abort 才释放。

**触发条件**

- 客户端不发 cancel 帧：页面崩溃、渲染进程卡死，或注入脚本的收尾又被改回「只处理 abort、丢下迭代器不 cancel」
  （本次已在 `packages/desktop/dsh-desktop-host/src/transport.ts` 的 `close()` 里统一收尾，并有测试钉住）；
- 上游若把 follow 的收尾改成依赖别的信号（`client-modules` 的 `responses` 缓存、心跳），这条链的第三环要重新对表。

**销账条件**

Done when：上游在服务端给一条不依赖客户端动作的收尾（follower 空闲超时、或「同一 address 的新开取代旧的订阅」），
或我们自己在宿主里加兜底，并有一条「客户端什么都不做」的真实场景钉住它。

**不修的理由**

现在两条真实取消路径（abort 与 return）都已经收口，兜底要先有一条「谁都不取消」的可复现场景。宿主侧「无人拉取」
在无端口管道下没有可靠观测点——`response.write()` 返回 `true` 只说明合成缓冲没满，客户端的读取进度要等壳把字节
读走才可见；照这个加空闲超时会误杀慢客户端（大 snapshot 的第一帧本来就要写一会儿）。
