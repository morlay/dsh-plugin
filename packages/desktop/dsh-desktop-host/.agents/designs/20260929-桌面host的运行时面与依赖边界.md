# 桌面 host 的运行时面与依赖边界（dsh-desktop-host）

状态：**已实现**（desktop profile 由本包启动，无端口 `webServer` 替身与管道传输已跑通）
范围：`packages/desktop/dsh-desktop-host/` 在运行时做什么、以及它对 `@deepseek-ai/*` 的依赖边界；门面与用法见该包
[`README.md`](../../README.md)。传输形态、窗口与标记、启动链的取舍见
[`设计 桌面无端口传输与窗口对齐`](../../../dsh-desktopify/.agents/designs/20260920-桌面无端口传输与窗口对齐.md)。
约束：上游只读；本包是上游 `apps/desktop-host`（`private: true`，外部装不到）的变体，argv / IPC 契约与
`lib/index.js` 入口路径照旧。

## 结论摘要

| 议题          | 结论                                                                      | 一句话理由                                                                   |
| ------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 载波          | 宿主内 `webServer` 替身 + FD 3/4 字节管道，不监听端口                     | 桌面档没有网络入口，登录要的回环回调也进不来                                 |
| Office 组合   | **整个不挂**（原先那份 `src/office.ts` 已删除）                           | 桌面不需要捆绑载荷，挂了只会多出一个没人用的工具                             |
| 账号 / 登录面 | 桌面 patch 按 id 停掉整条（`deepseek-account` 等四行）                    | 无端口下登录没有入口，装着只撞死路；模型路径不受影响                         |
| 产品遥测面    | 桌面 patch 按 id 停掉（`desktop-product-telemetry`、`product-analytics`） | 两行靠构建期 `DSH_CLIENT_VERSION` 填必填项，自研壳不传；本地部署没有上报对象 |
| 依赖面        | 清单只声明**这份代码真正用到**的包；官方闭包由部署步骤提供                | 上游 app manifest 里的组合依赖属部署，不该由变体包声明                       |

## 事实基线

### 运行时做的事

1. 官方那两步装配 `desktop` profile：`loadProfileDirectory` 读 profile root 的清单（打包形态是工具种出的
   `$DSH_HOME/profiles/desktop`，dev 形态是 app 目录本身——见
   [设计 dev 形态的 profile root 就是 app 目录](../../../dsh-desktopify/.agents/designs/20261010-app目录即profile-root.md)），
   `runProfile` 起树（保住 profileContext / proxy / fail-loud / appReady / shutdown 语义）；
2. 桌面 patch 禁用上游 `webserver` 行，插入本包的 `webServer` 替身——同一份路由面
   （`register` / `registerFallback` / `registerUpgrade` / `tapIndex` / `renderIndex` / `collectIndexInjections` /
   `port` / `host`），请求由 `dispatch(Request)` 从管道喂进来；
3. 接管浏览器认证：页面由壳独占、没有网络入口，`connection` 的 `requestRejection` 与 `authorizeIndex` 被改写为
   放行（理由与代价见
   [`债务 桌面宿主覆写connection认证方法`](../../../dsh-desktopify/.agents/debts/20260920-桌面宿主覆写connection认证方法.md)）；
4. 注入客户端 transport（`__DSH_TRANSPORT__ = { ownsHost, openStream }`）并注册 `/.dsh/remote-stream`
   （双向 NDJSON：请求体首行定 endpoint/payload、后续行是上行项，响应体是下行帧 →
   `typertGateway.wireStream.open`）；
5. 桌面 patch 还按 id 停掉整条**账号 / 登录面**（`deepseek-account`、`account-controller`、`llm-deepseek-account`、
   `ui-settings-account`）：登录要的回环地址回调在无端口下没有入口，装着只会撞死路——理由与代价见
   [`ADR 桌面档不含登录与账号面`](../adrs/20260928-桌面档不含登录与账号面.md)。模型路径不受影响
   （`credentials` + `llm-pi-ai` 的 `ollama` 路由），同包 `tool/verify-desktop-account-plane.mts` 装配一次真
   desktop profile 判这两件事；
6. 同一份 patch 也停掉**产品遥测面**（`desktop-product-telemetry`、`product-analytics`）：两行只在 `desktop` profile
   激活、靠构建期 `DSH_CLIENT_VERSION` 填必填的 `serviceVersion`，自研壳不传那个变量，留着只会是「行配置校验失败 →
   产品分析行 pending → 页面拿 502 → 前端抛未捕获错误」——理由与代价见
   [`ADR 桌面档无产品遥测`](../adrs/20261008-桌面档无产品遥测.md)。

### 一条桌面流的取消契约

长流（`session/follow`、`job/attach` 这类）在宿主里没有超时，也没有「同一会话新开取代旧开」——上游
`session/follow` 的 follower 只在**它的 signal abort** 时 dispose（`SessionHistoryController.closeFollowers` 只在
controller 卸载时触发，见 `vendor/deepseek-harness/packages/api/session-controller/src/history.ts`）。所以收尾是三方接力，
断一环那条流就一直挂在宿主里（连带它留住的会话观察与事件缓冲）：

1. **页面**：注入脚本的生成器只有一处收尾（`close()`）——`signal` abort（窗口重建）与消费方提前退出
   （`return()` / `break`，切会话时上游丢下迭代器就走这条）都调它，`carrier.cancel()` 幂等；
2. **壳**：`carrier.cancel()` → IPC `streamCancel` → `HostProcess.cancelResponse` 发一条 cancel 帧
   （`src/host-process.ts`）；
3. **宿主**：cancel 帧 → `PendingRequest.abort.abort()` → 合成请求的 `aborted`
   （`src/webserver.ts` 的 `createRequest` 把 `Request.signal` 翻成 node 请求的中止）→ `streamHandler` 的
   `cancel()` → `typertGateway.wireStream.open` 的 `signal` abort → 上游 follow 的 `finally` 跑完
   （`disposeEvent` / `disposeCreated` / `disposeAssistantStream`）。

`DSH_MEMORY_REPORT=1` 那行报告就是量这条链的：`opened` 与 `active` 的差就是「开了没收」的条数，`items/bytes`
是下游真读走的量。链路断在 2/3 之间时，`opened` 线性涨而 `items/bytes` 不动。

### 出口

`.`（启动入口）、`./webserver`（无端口 `webServer` 服务，供 patch 行加载）、`./wire`（管道分帧，壳构建时内联，
部署里不需要单独解析它）。

### 依赖边界

`@deepseek-ai/*` 全部由**部署自己的** `node_modules` 提供（与上游同边界）：

- `dependencies`：本包入口与替身真正 import 的 `@deepseek-ai/dsh`（含 `./profile-boot` 子路径）、
  `@deepseek-ai/dsh-app-boot`、`@deepseek-ai/dsh-host-webserver`（`renderIndexInjections`）、
  `@deepseek-ai/schemastery`（替身的 Config schema）；
- `peerDependencies`：`@deepseek-ai/cordis`；
- 类型面 `@deepseek-ai/dsh-client-connection` / `@deepseek-ai/dsh-api-gateway` 只在 devDependencies
  （空 import 带 Context merge，构建后即被擦除）；
- 不再声明 `@deepseek-ai/dsh-home-paths` 与 `@deepseek-ai/dsh-tool-workspace-dependencies`：前者只被删除的
  Office 组合用来算安装目录，后者就是那个组合装载的载荷工具。

清单只声明**这份代码真正用到**的包：上游那份 app manifest 里的组合依赖（`@deepseek-ai/dsh-skill-office`、
`dsh-agent`、`dsh-jobs`、`dsh-tools` …）属于部署的官方闭包，由 `@morlay/dsh-desktopify` 的部署步骤按 profile 提供。

## 取舍

- **不做第二套启动路径**：复用上游 host 的纯 node 实现（`loadProfileDirectory` + `runProfile` + 同一份 profile），
  装配只换 profile root 与 overlay，升级时跟随 vendor 版本即可。
- **不保留端口 + 反向代理**：桌面档没有网络入口，代理只会把认证面重新引进来。
- **不声明官方闭包依赖**：那是部署的事，写进变体包会让两处清单互相漂移。
- **去掉 Office 组合与随它的 primary runtime 载荷**：桌面自己定义能力面，不留没人消费的 argv 格、打包步骤与
  依赖声明；代价是桌面会话没有 `load_workspace_dependencies`，要用 Office 文件的人得自己装那条行。

## 开放问题

- `webServer.port` 固定为 `0`：上游若新增读者，需要重评这个替身的契约面。
