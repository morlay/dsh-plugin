# 桌面标识取自 app 名（自定义协议与后端进程名）

状态：已实现（2026-09-21）
范围：Electron 壳对外自称的两处标识——页面用的自定义协议 scheme，与后端 host 子进程在 `ps` 里的名字。
约束：`vendor/**` 只读；app 名只有一个来源（app 工作区 `package.json` 的 `name`，经 `appconfig.json` 递给壳）；不新增配置文件字段。

## 结论摘要

| 议题        | 结论                                                                                                                                                         | 一句话理由                                                                                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 协议 scheme | 由 app 名派生：去 scope 前缀（`@morlay/x` → `x`）、转小写、非法字符换成 `-`；派生不出合法 scheme 则启动即报错（原生错误框 + `app.exit(1)`）                  | 写死的 `dsh-app` 会与官方桌面应用撞名；app 名是壳本来就有的唯一身份（`appconfig.json` 的 `name`，即工作区 `package.json` 的 `name`）                                         |
| scheme 传递 | 主进程顶层 `await` 读 `appconfig.json` → `desktopScheme(name)` → 顶层 `registerSchemesAsPrivileged`；页面的 `additionalArguments` 把它递给 sandboxed preload | `registerSchemesAsPrivileged` 只有「`ready` 之前」一个窗口期，而 Electron 会等入口模块的顶层 await 跑完才 emit `ready`；preload 是 sandboxed（读不到文件），只能从 argv 认领 |
| 后端进程名  | 壳给 host 子进程加 `node --title=<app name>-server`                                                                                                          | `ps` 里原来是一串 `node …/lib/index.js`，桌面后端与别的 node 进程无法区分；名字由壳（唯一知道 app 名的一侧）给，host 包不必新增契约                                          |
| hostname    | 仍是 `app`（`<scheme>://app/*`）                                                                                                                             | 只换 scheme 就能错开官方；路径面（`protocol.handle`、`assertDesktopSender`、preload 的 `location.hostname`）一个字都不用动                                                   |

## 事实基线

- 改前 scheme 写死在 `src/ipc.ts`（`SCHEME = "dsh-app"`），`index.ts` 的 `protocol.registerSchemesAsPrivileged` / `protocol.handle` / `APPLICATION_URL` / `will-navigate` 与 preload 的 `location.protocol` 判断都读它。
- 上游桌面（`vendor/deepseek-harness/apps/desktop`）与 Web 前端都不读 scheme，host 只把 URL 透传（`wire.ts` 的 `url`、`webserver.ts` 只取 `pathname`/`search`）——所以 scheme 完全是壳的自称，换名不需要动 host 与协议版本。
- app 名已随 `appconfig.json` 落在壳手里（`cli/dev.ts` 与 `cli/bundle.ts` 都写 `manifest.name`），scheme 再写一份就是第二个 home。

## 取舍

- **派生而非新增配置字段**：`appconfig.json` 只留 `name`，scheme 是它的一次纯函数变换；加字段会让「改名忘了改 scheme」变成可能。
- **规范化而非拒绝非法名**：包名允许 scope 与下划线，scheme 不允许——去 scope + 转 `-` 让 `@morlay/dsh_custom` 也能起；但派生结果若不以字母开头（`1app`、空名）仍大声失败，不猜一个前缀。
- **顶层 `await` 而非同步读**：`node/no-sync` 是本仓的 lint 规则；Electron 明确「入口模块的顶层 await 跑完才 `ready`」，所以 await 同样能赶在 `registerSchemesAsPrivileged` 的窗口期之前。
- **`--title` 而非 host 侧读环境变量**：随包 Node（24.17.0）与 dev 的系统 Node 都支持 `--title`，host 包零改动；代价是该 flag 成了壳与 Node 之间的一个隐性依赖（node < 21.2 会启动失败，属于大声失败）。
- **只给 Electron 壳的子进程改名**：`dev --web` 起的 `dsh web` 是浏览器形态的另一条路（不起壳、不起 host），本次不动。

## 实施结果

| 落点                                                                 | 内容                                                                                                                                                                 |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/desktop/dsh-desktopify/src/ipc.ts`                         | `SCHEME` 常量 → `desktopScheme(name)`；`DESKTOP_SCHEME_ARGUMENT`（主进程与 preload 共用参数名）；`assertDesktopSender` 收 scheme                                     |
| `packages/desktop/dsh-desktopify/src/index.ts`                       | 顶层 await 读 `appConfig`（打包分支的 userData 设置复用这一份，不再二次读）→ `SCHEME`；窗口 `additionalArguments` 把 scheme 递给 preload；host 启动带 `processTitle` |
| `packages/desktop/dsh-desktopify/src/preload-app.ts`                 | scheme 从 `process.argv` 的 `--dsh-desktop-scheme=` 读回                                                                                                             |
| `packages/desktop/dsh-desktopify/src/host-process.ts`                | `options.processTitle` → `args` 里的 `--title=<title>`                                                                                                               |
| `packages/desktop/dsh-desktopify/src/directory-picker.ts`            | `installDesktopDirectoryPicker(getWindow, scheme)`（发送者校验用运行期 scheme）                                                                                      |
| `packages/desktop/dsh-desktopify/src/__tests__/ipc.spec.ts`          | 派生规则、非法名报错、发送者校验不再认 `dsh-app://`、参数名一致                                                                                                      |
| `packages/desktop/dsh-desktopify/src/__tests__/host-process.spec.ts` | `processTitle` 落在 `--title`、且不影响既有 argv 顺序                                                                                                                |

证据（本次运行）：`pnpm exec vitest run packages/desktop` 31 文件 / 161 用例全绿；`pnpm exec oxlint packages/desktop` 0 错；
`pnpm --filter @morlay/dsh-desktopify build` 重建壳产物（`dist/index.mjs` 的顶层 await 与 `registerSchemesAsPrivileged` 顺序保持）。
真实起壳（dev 形态，本机受限环境加了 `--no-sandbox --disable-gpu`）：`curl 127.0.0.1:9222/json/list` 里页面 URL 为
`dsh-custom-next://app/`，壳日志 `[dsh-shell] stream session/control → 200` 说明 preload 从 argv 认到 scheme 并暴露了流载体，
`pgrep -fl dsh-custom-next-server` 命中后端进程；随包 Node（24.17.0）`--title=dsh-custom-next-server -p process.title` 回显一致。

## 开放问题

- 两处标识都取自 `name`；若将来要按 `dsh.desktop.id`（反向域名）派生，`id` 已经是合法的 scheme 形状，但会与 `name` 分成两套叫法，需要重新取舍。
- Windows 上 `process.title` 的可见性（任务管理器 / `tasklist`）未实测。
