# 桌面无端口传输与窗口对齐（dsh-desktopify + dsh-desktop-host 的运行形态）

状态：已实现（2026-09-20：桌面 dev 形态跑通——host 无任何应用端口监听，窗口与平台标记已对齐官方；管道分帧、替身路由、transport 装配有单测守护）
范围：桌面形态（Electron 壳 + host 进程）的**传输**与**窗口观感**两件事——把当前「host 监听端口 + 壳认证反向代理」换成「宿主内接管 `webServer` + 框架化字节管道」，并让窗口与平台标记对齐官方桌面。
约束：`vendor/**` 只读；插件注册面统一走 `webServer`（不再有 `connection.fetch` 双注册）；改动只落在这两个包与桌面专属记录。
本文引到的 `apps/…` / `packages/…` 路径**都是上游真源**，位置在 `vendor/deepseek-harness/`（本仓库自己的包一律写 `packages/<family>/<pkg>`）。

## 事实基线

**无端口的既有机制（上游 alpha.1）**

- `git show dsh-v0.1.6-alpha.1:apps/desktop-host/src/index.ts`：无 listening socket，自建 `assetHandler`（dist + `webserver/index-inject` + `renderIndexInjections`）、`remoteStreamHandler`（POST `/.dsh/remote-stream` → `typertGateway.wireStream.open`，NDJSON）、`/api` 直连 `connection.createSharedFetchHandler('/api')`；分帧在 `...:apps/desktop-host/src/wire.ts`（FD 3/4、64 KiB chunk、协议 3）。
- alpha.2 已改成 web server + 端口 19387（`vendor/deepseek-harness/apps/desktop-host/src/index.ts:24,73-74`），vendor 里没有留下开关。
- 上游自己也有「不监听」的形态：`packages/experimental/webworker-runtime/src/node/builtin_modules/implemented/http.ts:16,95-100`（假 `node:http`，虚拟端口 3080）+ `src/transport/synthetic-http.ts:51-157`（合成 req/res），`packages/host/webserver/src/index.ts:102-114` 也为「res 无 socket」留了口。

**当前桌面形态（要改掉的）**

- host：`runProfile` 起 web 应用，`args: ['--no-open','--port','19387']`，就绪后把 `connection.authenticatedUrl('http://127.0.0.1:<port>')` 与 `webServer.collectIndexInjections()` 经 IPC 报给壳（`packages/desktop/dsh-desktop-host/src/index.ts:33,110-117`）。
- 壳：本地 dist 出 index + 注入 `__DSH_BOOT_READY__`（`src/web-document.ts:10,16-44`）、`fetch(ready.url)` 换 cookie（`:46-54`）、其余请求带 cookie 反向代理（`:56-78`）、WS 头重写（`src/index.ts:315-348`）、preload 暴露 `dshDesktopBoot`（`src/preload-app.ts:6-13`）。

**客户端为何必须换装配**

- `apps/web/src/main.ts:20-35`：仅当 `globalThis.dshDesktopBoot` 存在时注入 `{ownsHost:true, streamBaseUrl}` 并应用 IPC 的 injections → 无端口下 `streamBaseUrl` 无处可指，且会覆盖 `openStream`。
- 注入脚本一旦带 `openStream`，`connection.rpc.open` 存在（`packages/client/connection/src/client/rpc.ts:61-67`），Gateway 便**不启动** WS mux（`packages/api/gateway/src/client/index.ts:161,166,170`）；`client/web/src/boot.ts:55` 等 `__DSH_BOOT_READY__`，由 `renderIndexInjections` 的 `READY_MARKUP`（`packages/host/webserver/src/injections.ts:86,104`）在服务端渲染时 settle。

**路线 B 的前提**

- `web-app` 的 `web-runtime` 行 `inject:['webServer']`，内部挂 `frontend-static`（`packages/bundle/web-app/src/index.ts:41,226,232`）→ 替身一到位，dist 静态、index 渲染（含 `<base href="/">`）、注入行、`/plugins` bundle 服务全部照常。
- `connection` 行在 `ctx.inject(['webServer'])` 内注册 `/api` 前缀路由（`packages/client/connection/src/index.ts:134-154`），handler 先 `requestRejection`（Host/Origin 栅栏 + cookie，`src/rpc-host.ts:97-100`、`src/api-request-trust.ts:91-118`、`src/browser-auth.ts:289-302`）再走 `connection/request` waterfall → `bridge`。
- `session-rdb` 的五条 `/api/session.*` 与 `ui-conversation-message-actions` 的 `/api/session-editor` handler 内部自查 `requestRejection`（如 `packages/session/session-rdb/src/export.ts:38-46`）。
- `frontend-static` 的 index 分支先 `ctx.connection.authorizeIndex(req,res)`（`packages/host/frontend-static/src/index.ts:139`）。

## 取舍

- **路线 B（替身 webServer）而非路线 A（照 alpha.1 禁用行）**：A 会让所有「注册到 webServer 的插件」静默 404 或 PENDING（`dev-client` 的即时打包直接没有挂载点），且要禁用 `connection` 行之外的关联行、改写 `connection.inject`。B 只替换 listen 那一环。
- **B-full（所有路径走替身路由表）而非 B-hybrid（`/api` 直连 shared handler）**：既然插件注册面统一到 webServer，就不要再开第二条道；`/api` 走路由表后 `connection/request` waterfall 等语义也在。认证用「宿主接管」而不是自铸 cookie（少一层签名/cookie 管道，且与「认证不需要」一致）。
- **仍用 `runProfile` 而非回到手写 `boot()`**：手写会丢 `profileContext`（插件页）、proxy、fail-loud、`appReady`、`shutdown` 五件事（`apps/cli/src/profile-boot.ts:257-260,292-294,325-329`）。
- **替身自写路由表而非 `extends WebServer` 覆盖 `[Service.init]`**：后者依赖 TS 私有成员 `match`，上游重构会静默破坏；自写约 200 行并复用公开导出（`renderIndexInjections`、`serveStatic`）。
- **不暴露 `dshDesktopBoot` 而非给 `apps/web/src/main.ts` 打本地 patch**：不改上游就成立；代价是页面级失败上报回到 control 台/壳对话框（alpha.1 也如此）。
- **不动 `client-hmr`/`open-in-app`/`directory-picker-auto` 行**：B 下它们照常工作（`/plugins/events` SSE、`open-in-app` 路由、picker 选择读 `webServer.host`）。

## 后续变化（2026-09-22）

**注入脚本的取消语义补全**（`packages/desktop/dsh-desktop-host/src/transport.ts` 的 `DESKTOP_TRANSPORT_SCRIPT`）。

现象：桌面端「编辑并撤回」确认后，动作已生效（壳日志 `recv POST /session-editor → 200`、输入框回填被撤回的文本），
但对话区仍留着被撤回的消息；web 端同一操作正常。

根因：`openStream` 的 `onAbort` 原先只调 `cancel()`——解绑 IPC 监听、通知主进程取消，**却不唤醒正挂在等待上的迭代**
（`await new Promise(resolve => { wake = resolve })`），且监听已解绑，主进程随后推来的 end 帧也不再被处理。而
上游 `RemoteStream.dispose()` 会 `await iterator.return()` 等生成器真正结束，于是
`ClientSession.resync()` 卡在 `await events?.dispose()` 上永不落定：既不开新 follow 流（页面看不到新的
`[dsh-desktop] openStream`），也不抛错（`SessionEditorController` 的重建分支没有 warn 可打），窗口就停在 rewind 之前。
web 端不走这段注入脚本（走上游自己的 transport），所以没有这一环。

修法：`onAbort` 置 `ended=true` 并 `notify()` 唤醒迭代（队列剩余数据仍先交付，上游的 abort 判断会丢弃），
`addEventListener` 之后再对已经 abort 的 signal 补一次 `onAbort()`。守护用例在宿主包的
`src/__tests__/transport.spec.ts`（abort 后迭代立即结束、signal 已 abort 时消费即结束、end 帧交付后结束）。
