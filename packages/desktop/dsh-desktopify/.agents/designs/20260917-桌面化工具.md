# 桌面化工具（dsh-desktopify 的打包机制与取舍）

状态：已实现（`dev` / `bundle` 两条路径可用，命令表见 [README](../../README.md)）
范围：`packages/desktop/dsh-desktopify/` 这份 CLI——命令面、工作区契约、官方依赖闭包、种子与指纹、随包运行时、dev / bundle 的运行时语义。
约束：壳复用上游 `vendor/deepseek-harness/apps/desktop` 的形态与产物；host 变体以上游 `apps/desktop-host/src/*` 为源（本地适配，不改 `vendor/**`）；工具内不写死任何 app 路径或名字（一律由 node 解析）；工具的构建依赖不进 app。

壳与 host 的运行形态（传输、窗口、启动链、壳产物的依赖边界）见[设计 桌面无端口传输与窗口对齐](./20260920-桌面无端口传输与窗口对齐.md)；壳包与工具的边界见[设计 壳独立成包](../../../dsh-desktop-shell/.agents/designs/20260924-壳独立成包.md)。

## 结论摘要

| 议题             | 结论                                                                                                                             | 一句话理由                                                                                                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 工具形态         | 只发 CLI（`bin` + `./dev-client-bundles`）；壳住 [`@morlay/dsh-desktop-shell`](../../../dsh-desktop-shell/README.md)             | 一个包不该同时是「npm 消费者眼里的工具」与「Electron 眼里的应用」，见[设计 壳独立成包](../../../dsh-desktop-shell/.agents/designs/20260924-壳独立成包.md) |
| 官方依赖闭包     | registry 面交 pnpm 装（`deploy/package.json`），本地源码包与后端载荷由闭包复制补齐                                               | 文件集语义由包管理器负责；带 `workspace:` 的包在部署项目里解析不了                                                                                        |
| 种子与指纹       | 种子 = 不可变 runtime + 初始 profile；`.seed-hash` 覆盖 app 白名单 / lockfile / 本地包产物 / 安装产物清单 / 种子自己生成的文件   | 版本号不变而内容会变（本地源码包、工具选哪些文件进闭包、生成出的 manifest），指纹变化时壳重种 profile 并重装                                              |
| 运行时与 profile | runtime 留在应用只读 resources，`DSH_HOME` 只放 profile；host 的解析锚点指向 runtime                                             | profile 里只装外部插件，官方包与 dsh 由 runtime 提供（对齐上游桌面形态）                                                                                  |
| profile 安装     | 随包 pnpm 离线装 profile 的 `file:` 依赖；profile 本地包的依赖（普通与 `workspace:` 都算）由 `overrides` 以 `link:` 指回 runtime | profile 因此是 pnpm 能接管的真项目，安装不访问 registry，Web 插件页的安装 / 卸载 / 启停才能在打包产物里工作                                               |
| 桌面 preset      | 不由工具物化：agent preset 是官方 shipped 的（registry 的默认指向 `standard`），模式是它的会话级扩展                             | 工具只管打包输入，preset 与模式的装配归 bundle（[`session-mode-profile`](../../../../bundles/session-mode-profile/README.md)），工具物化出来没人读        |
| XDG 路径         | `dshHome` 三态：`xdg` → `xdg.DataHome/<name>`、`env`、绝对路径；`DSH_APP_DSH_HOME` 可覆盖                                        | 走平台 XDG 约定，壳与 host 共用同一 home，dev 的 `--home` 复用同一份解析                                                                                  |
| shell 注入       | Unix 上经 `$SHELL -c 'source ~/.bashrc; exec …'` 启动 host                                                                       | 继承用户终端环境（API key 等），`exec` 保持同进程与进程组终止语义                                                                                         |

## 事实基线

### 工具形态

源码与 CLI 全 TS。开发形态 `bin` 直指 `src/cli/index.ts`（Node 原生类型剥离直接执行）；`exports` / `bin` /
`main` 由 `tsdown.config.ts` 的 `exports` 选项在构建期收敛进 `package.json`——开发形态指 `src/*.ts`，发布形态
经 `publishConfig` 指 `dist/*`。对外出口是 `bin` 与 `./dev-client-bundles`（另有 `./package.json` /
`./locale/*.json` 这类包元数据出口）。

### 命令面

| 命令                                                     | 作用                                                                              |
| -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `dsh-desktopify dev [--web] [--home <spec>] [workspace]` | 启动 Electron 壳（不打包）；`--web` 改为在浏览器里跑 `dsh web`；`--home` 换数据面 |
| `dsh-desktopify bundle [--dir] [--install] [workspace]`  | 构建当前平台的静态、无签名桌面应用                                                |

工作区取首个位置参数（缺省当前目录），CLI 把它写进 `DSH_DESKTOP_WORKSPACE`（`src/cli/index.ts` 的
`resolveWorkspaceArg`）。

- **数据面**：dev 两种形态共用工作区的 `.dsh-store`（`src/cli/workspace.ts:160` 的 `devStoreHome`），profile
  名 `desktop` / `web` 互不冲突；只有 Electron 的浏览器数据落在
  `<workspace>/node_modules/.dsh-desktopify/development/electron-user-data`（`src/cli/dev.ts:323-325`）。
- **`--home <spec>`** 换数据面根，取值与 `dshHome` 同构，解析只有一份
  （[`dshhome.ts`](../../../dsh-desktop-shell/src/dshhome.ts) 的 `resolveConfiguredHome` / `resolveDshHome`）：

  | `--home` | 数据面                                               |
  | -------- | ---------------------------------------------------- |
  | 缺省     | `<workspace>/.dsh-store`（工作区内，与打包形态隔离） |
  | `xdg`    | 打包形态那同一个目录（`<平台数据目录>/<app 名>`）    |
  | `env`    | 环境里的 `DSH_HOME`（没设就 fail loud）              |
  | 绝对路径 | 原样使用                                             |

  「打包形态才复现」的问题用 `just custom dev --home=xdg` 就能让 dev 跑真实数据；`DSH_APP_DSH_HOME` 仍是壳里的
  最高优先覆盖。

- **`--web`** 把 web profile 装配清单（profile `package.json` 的 `dsh.profile.bundles`）刷成工作区定义的那份
  （`src/cli/dev-web.ts:29-53`）：清单决定 patch 层的顺序，profile 里种子留下的旧清单会让后装 bundle 插的行
  打不到前面层的配置（只 warn 后跳过）。
- **壳产物不重建**：壳包的 `dist/` 由 `pnpm build` 生成，dev / bundle 只校验它在（`src/cli/shell.ts:9-54` 的
  `SHELL_ENTRY` 与「产物比源码旧」告警）。随包 Node / pnpm 载荷的准备与校验、profile 种子生成是 `bundle` 的
  内部步骤，不单独暴露命令。
- 本仓库示例工作区：`just custom desktop`（dev）/ `just custom bundle`（打包）——app 的
  [`justfile`](../../../../../apps/dsh-custom-next/justfile) 会先刷新 `bundles/*` 的生成 patch。

### 工作区契约（`package.json`）

解析在 `src/cli/workspace.ts`（`dshVersion`、`desktopConfig`、`appProfileBundles` 与 `mergedProfileBundles`），实例见
[`apps/dsh-custom-next/package.json`](../../../../../apps/dsh-custom-next/package.json)：

- `name`：壳对外自称的两处标识的来源（自定义协议 scheme、后端进程名，
  [设计 桌面标识取自 app 名](./20260921-桌面标识取自app名.md)），也是 `dsh.desktop.name` 的缺省值；
- `dsh.version`：`@deepseek-ai/dsh` 的依赖 spec——`workspace:*`（从 vendor 源码解析）或具体版本（从 registry
  安装）；缺省时回退到工作区已解析的 dsh 版本。配 `workspace:` 时工具不把它落成版本号（本地源码可能尚未发布），
  而是指向解析到的包目录；打包时工作区没有的官方包按这个版本钉住装进部署项目。`workspace:` 与缺省都不行时，
  只能靠工作区自己装齐官方包；
- `dsh.profile.bundles`：必填，非法即失败（`src/cli/workspace.ts:101-108`）；
- `dsh.desktop`：`id`（缺省 `ai.deepseek.dsh.custom`）、`name`（桌面应用的对外名字 = electron-builder 的
  `productName`，缺省用工作区包名）、`icon`、`dshHome`（缺省 `xdg`）、`window`（宽高与最小宽高，壳读它）。

### 前置条件

- pnpm workspace（dev 依赖 `findWorkspaceRoot` 装配临时项目；bundle 依赖 `pnpm deploy` 导出 app 闭包，工具不改写
  工作区清单 / lockfile）。
- `vendor/deepseek-harness` 已构建（`just vendor prepare`：dev 需要 dsh CLI；后端变体
  [`@morlay/dsh-desktop-host`](../../../dsh-desktop-host/README.md) 运行期从部署载荷的 `node_modules` 解析上游
  `@deepseek-ai/*` 包）。
- 工具、壳包与后端变体都已构建（`pnpm build`）：dev / bundle 用壳包的 `dist/index.mjs`（`dev` 起的 Electron
  按它的 `main` 加载）与 `@morlay/dsh-desktop-host` 的 `lib/index.js`。
- 前端静态资源来自闭包内 `@deepseek-ai/dsh-web-frontend/dist`（`dsh` → `dsh-web-app` 的传递依赖），壳按
  `<runtimeDir>/node_modules/@deepseek-ai/dsh-web-frontend/dist` 读取。

### 打包

electron-builder 经 Node API 在 `src/cli/electron-builder.ts` 内配置（无独立配置文件）。壳以最小 app 目录
（`dist/` + 入口 manifest，版本取工作区版本）打包，工具自身的构建依赖不进 app；`--dir` 产出未打包的应用目录，
不签名、不 notarize。

### 官方依赖内部维护与闭包装配

`@deepseek-ai/*` 依赖清单（dsh、cordis-plugin-group 及约 20 个 peer 包）由工具内部维护（`src/official.ts`），
app 只声明自己的依赖、`dsh.version` 与 bundles。包位置一律由 node 解析（`src/cli/official-deps.ts`）：app 工作区
优先、工具自身安装兜底，不写死 `workspace:`；**后端载荷是唯一例外**——它由工具自己的依赖
（`@morlay/dsh-desktop-host`）解析，因为变体才是要跑的后端。

官方依赖分两条路进闭包：

- **registry 面交给 pnpm**：按工作区已解析版本写进 `deploy/package.json` 再 `pnpm install`（工作区没装的
  `@deepseek-ai/dsh*` 按 app 的 `dsh.version` 钉版本；独立版本线如 `cordis-plugin-group` 1.x 不猜版本），文件集
  语义由 npm/pnpm 负责（`files` 不会裁掉 `main` / `bin` / README / LICENSE）；
- **本地源码包与工具依赖的后端载荷**仍由闭包复制补齐（它们带 `workspace:` 依赖，在部署项目里解析不了）。

装之前部署项目先继承工作区的安装设置（`minimumReleaseAge` 等，`pnpm deploy` 只带走 `allowBuilds` /
`patchedDependencies` / `overrides`）。工作区的清单与 lockfile 始终只读。

### 随包运行时载荷

`dev` 与 `bundle` 都在 `<buildRoot>/runtime` 下准备随包载荷（`src/cli/prepare-runtime.ts`、`src/cli/bundle.ts`）：

- **`node/`**：按 Node 官方 `SHASUMS256.txt` 校验下载的随包 Node；`bin/` 是指向它的相对链接（Windows 下复制
  `node.exe`），作为 pnpm 子进程 `PATH` 的前置目录（Host `argv[5]`）。
- **`pnpm/bin/pnpm.mjs`**：pnpm 入口，壳作为 Host `argv[4]` 交给 `profileContext.packageManager`。pnpm 12 的
  npm 包只是 wrapper：入口会 spawn 同包装的 `@pnpm/exe.<platform>-<arch>` 原生二进制（约 35 MiB），所以载荷按
  入口实际加载的闭包复制 wrapper（约 3.5 MiB），并把平台包放进 `<runtime>/pnpm/node_modules/`；两处复制都要
  dereference（否则符号链接指向仓库 store，打包后断链）。准备完立即用随包 node 跑 `pnpm.mjs --version` 与
  manifest 版本比对。
- **`versions.json`**：`{schemaVersion: 1, node, pnpm}`（纯增量字段，形状与上游桌面一致）。
- **`appconfig.json`**。**不带 `office-skills/`**：那份资源唯一的读者是上游命令式装载的 `officeSkills`，
  本部署的 host 变体不挂它，随包只会让打包多一个解析不到的 `@deepseek-ai/dsh-skill-office` 硬依赖。

跨平台打包被拒绝：载荷只含构建主机平台的 `@pnpm/exe` 二进制，`DSH_DESKTOP_TARGET_PLATFORM` /
`DSH_DESKTOP_TARGET_ARCH` 指向别的平台时在任何写入之前就失败（`desktop runtime: bundled pnpm carries the
<host> native binary, which cannot serve <target>`）。

### 运行时与 profile 分离

- **runtime**（`seed/runtime`）：deploy 闭包的副本（`package.json` + `node_modules`，保留 pnpm 虚拟存储与相对
  链接），随包留在应用的只读 resources 里。它同时是 host 的 dsh 安装（解析锚点 = Host `argv[2]` 的 runtimeDir）、
  前端静态资源（`@deepseek-ai/dsh-web-frontend/dist`）与 profile `overrides` 指向的包源。
- **profile**（`seed/profiles/desktop`）：只带 app 自己声明的 bundle。manifest 里这些包是
  `file:./vendor/<name>`（`vendor/` 是从 runtime 闭包 deref 复制出来的源），外加 app 白名单文件与
  `pnpm-workspace.yaml`（`nodeLinker: hoisted`、`autoInstallPeers: false`、从工作区继承的 `allowBuilds`）。
  官方 bundle 与 dsh 不进 profile，由 runtime 提供；manifest 不带 app 的 `dsh.version` / `desktop` / `dev`
  （那些属于打包输入）。
- **替换逻辑的例外**：profile 的 `cordis.patch.yml` 是**用户数据**（settings 面板写在那里），所以种子带 app
  那份（新机器有默认装配行），但重种**不替换**它：`ensureSeedProfile` 在整目录替换前把用户那份读出来、种完放
  回去（[`seed.ts`](../../../dsh-desktop-shell/src/seed.ts)）。代价是 app 层装配行日后的修改送不到老用户
  （见[债务 profile 的 `cordis.patch.yml` 豁免替换](../debts/20260922-profile的cordis.patch.yml豁免替换.md)）。
- **安装**：壳在种出 profile 后，先按种子写的 `desktop-runtime-packages.json` 把 `overrides`
  （`"<dep>": "link:<runtime>/<package path>"`）写进 `pnpm-workspace.yaml`，再用随包 node 跑随包 pnpm 的
  `install --prod --ignore-scripts --offline`。报告覆盖 profile 本地包的**每一条**依赖（普通范围如
  `zod@^4.4.3` 与 `workspace:` 协议都算）；漏掉普通依赖时 pnpm 会回 registry 解析范围，离线只能查 metadata
  镜像并失败（打包产物首次启动报 `profile install exited with 1` 就是这个原因）。peer / optional 找不到就跳过
  （`autoInstallPeers: false`），普通依赖找不到则打包直接失败。依赖全部由 `file:` 源与 `link:` 覆盖满足，安装
  不访问 registry，profile 里的包也与 runtime 共享同一份实例。
- **peer 闭包**：`pnpm deploy --prod` 不装 peerDependencies，desktop-host boot 依赖的 `@deepseek-ai/*` peer
  包由工具注入为具体版本依赖（`dsh.version` 锚定 dsh，其余取已解析版本；desktop-host 以 `link:` 注入），随
  deploy 复制进闭包。

### bundles 自动合并

官方 bundles（`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`）+ app 的 `dsh.profile.bundles` 自动合并进
dev 项目与种子 profile。

### 运行流程

- **dev 数据面**：`dev`（Electron）与 `dev --web` 的 `DSH_HOME` 都是工作区的 `.dsh-store`，profile 名不同
  （`desktop` / `web`）互不冲突；只有 Electron 的浏览器数据留在 `<buildRoot>/development/electron-user-data`。
- **dev**：链接工作区依赖闭包 + 后端载荷（`@morlay/dsh-desktop-host`）到临时项目（dsh 包以真实副本装入），
  host 用系统 node 直载工作区 TS 源码——仅当工作区装有 tsx 时才加 `--import=tsx/esm`（否则不注入 loader），
  profile 目录由 host 自己解析（`loadProfileDirectory`，Host `argv[3]` 的 projectDir）；`--web` 则准备 `web`
  profile 后启动 `dsh web`。
- **bundle**：`pnpm deploy --prod` 导出 app 闭包（工作区清单与 lockfile 只读）→ 部署项目继承工作区安装设置；
  官方 registry 面由 pnpm 装进部署项目，本地源码包与后端载荷由闭包复制补齐 → 种子（`seed/runtime` +
  `seed/profiles/desktop` + `.seed-hash`）→ 随包 pnpm 与运行时载荷 → 下载校验随包 Node 二进制 →
  electron-builder 静态打包。指纹覆盖 app 工作区白名单、根 lockfile、闭包内每个本地源码包的产物内容、每个安装
  产物的文件清单，以及种子自己生成的文件（runtime manifest、profile manifest / pnpm 设置 /
  `desktop-runtime-packages.json`、vendor 的包路径清单）。闭包内 `@morlay/*` 的 exports 切到 publishConfig 的
  dist 产物（打包环境没有 tsx）。

### 产物布局（打包形态）

`Resources/` 下两棵互不覆盖的树：

- `runtime/`：随包运行时——`node/`（随包 Node）、`pnpm/bin/pnpm.mjs`（随包 pnpm 的入口，壳把它作为 Host
  `argv[4]` 交给 `profileContext.packageManager`；该 npm 包只是 wrapper，入口会 spawn 同平台
  `@pnpm/exe.<platform>-<arch>` 的原生二进制，所以载荷带上那个平台包）、`bin/`（pnpm 子进程的 `PATH` 前置目录，
  Unix 下是指向 `../node/node` 的相对链接）、`appconfig.json`、`versions.json`；
- `seed/`：`runtime/`（不可变闭包 = host 的 dsh 安装锚点与前端静态资源）+ `profiles/desktop/`（初始 profile：
  app 自己的 bundle 以 `file:` 指向 `vendor/` 副本、`pnpm-workspace.yaml`、`desktop-runtime-packages.json`、
  `.seed-hash`）。

用户的 `DSH_HOME` 只放 profile（`profiles/<name>`）：种出 / 替换后由壳用随包 pnpm 离线安装它，官方包与 dsh
始终取自 `seed/runtime`。

### 运行时语义

- **XDG 路径**：`dshHome: xdg`（默认）→ `xdg.DataHome/<name>`（macOS `~/Library/Application Support`、
  Linux `$XDG_DATA_HOME`）；`DSH_APP_DSH_HOME` 可覆盖（开发 / 测试）。
- **shell 注入**：Unix 上 host 经 `$SHELL -c 'source ~/.bashrc; exec …'` 启动（bash/zsh），继承用户终端环境
  （API key 等）；`exec` 保持同进程，进程组终止语义不受影响。
- **单个 app id 单实例**：Electron 的单实例锁落在 userData 目录；被强杀或 PID 复用后残留的 `SingletonLock`
  会让新实例直接退出（无输出、退出码 0），清掉 `<userData>/Singleton*`（macOS
  `~/Library/Application Support/<app id>/`）即可恢复。
- **未覆盖面**：Electron 主进程 / preload 与 `src/cli/{bundle,dev}.ts` 的私有逻辑没有自动化测试——要整套
  Electron mock 面；纯 node 的命令面、协议、配置 / 路径推导、种子与部署按接缝测（判据与未覆盖清单见
  [本包如何验证](../standards/how-to-verify.md)）。

## 取舍

- **官方依赖的 registry 面交 pnpm 而非自己复制**：文件集语义（`files` 不裁 `main` / `bin` / README / LICENSE）
  由包管理器负责；自建复制要跟住上游每个包的 manifest。
- **runtime 与 profile 分离、profile 交给 pnpm 装**：profile 必须是 pnpm 能接管的真项目，Web 插件页的安装 /
  卸载 / 启停才能在打包产物里工作——把 deploy 闭包当 profile 时，pnpm 的依赖图与磁盘不一致（手工复制进闭包的
  包不在图里），任何包操作都会把那些包 prune 掉；理由与代价见
  [ADR 运行时与 profile 分离且由随包 pnpm 安装](../adrs/20260918-运行时与profile分离且由随包pnpm安装.md)。
- **`overrides` 用 `link:` 指回 runtime，而不是把包复制进 profile**：profile 里这些包的 `@deepseek-ai/*`
  依赖因此共享 runtime 的同一份实例（cordis 尤其），也不再多占一份闭包；代价是 `pnpm-workspace.yaml` 的
  `overrides` 由壳在种出 profile 时写入（种子里的设置保持静态），空列表时不碰文件，以免覆盖手写内容。
- **随包 pnpm 而不是内置包管理器实现**：与上游桌面同源——Electron 的 Node 模式 + 随包 pnpm 作为
  `profileContext.packageManager`，插件页的包操作与官方桌面走同一条路。代价是载荷要带平台原生二进制
  （见「随包运行时载荷」），跨平台打包因此被拒绝。`allowBuilds` 里保留 `pnpm: true`：pnpm 包的 install 脚本
  正是把包内 shim 重链接到那份原生二进制的那一步。
- **后端变体独立成包，而不是塞进工具产物**：工具只管打包，载荷的身份（`@morlay/dsh-desktop-host`）、入口路径
  （`lib/index.js`）与依赖清单（只声明它真正用到的）都归那个包；从上游 app manifest 抄依赖会把变体不挂的
  `dsh-skill-office` 之类变成部署的硬要求。该包的清单与产物互相覆盖由 `manifest.spec.ts` 守住。
- **壳产物由 `pnpm build` 生成、dev / bundle 只校验不重建**：壳构建是独立一步（`dist/index.mjs` + preload），
  工具不替壳管构建；源码形态下产物比源码旧只打印警告。
- **工具内不写死 app 路径与包名**：包位置一律 node 解析（工作区优先、工具安装兜底），换工作区不改代码。
