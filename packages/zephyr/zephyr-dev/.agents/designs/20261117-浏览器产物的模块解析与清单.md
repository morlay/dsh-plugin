# 浏览器产物的模块解析与清单

状态：已实现（票 01-06）。真实应用 `zephyr build` 绿：可达地址零缺口、270 个包产物、`katex` 两份副本各有产物、runtime 聚合产物为空（残余为零）。
范围：`zephyr-dev` 的三处实现——`federation/prebundle-plan.ts`（枚举）、`federation/bundle.ts`（转译与地址）、`build/compile.ts`（编排与落盘）——以及它们产出的静态目录。
非目标：静态投递（`StaticClientAssets`）、dev 期按请求预编译的时序、CJS 互操作的字节层面、桌面包。
关联：[开发构建与产物布局](../../../.agents/designs/20261113-开发构建与产物布局.md) · [客户端资源的联邦式预编译](../../zephyr-app/.agents/designs/20261013-客户端资源的联邦式预编译.md) · [预编译时序与令牌表](../../zephyr-app/.agents/designs/20261114-预编译时序与令牌表.md) · [CJS 互操作与依赖预构建](../../zephyr-app/.agents/designs/20261114-CJS互操作与依赖预构建.md)

## 一、决定

| #   | 议题         | 决定                                                                                                                                                    | 一句话理由                                                                       |
| --- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 真相         | 浏览器面需要哪些模块，由**从应用 client 入口出发的模块图**决定；产物里出现的地址只在兜底一步被引用，不用来反推新包                                           | 浏览器的加载行为由这张图解释；反推出来的条目没有归属，谁负责它说不清              |
| 2   | 副本         | 图里每个包按**实际安装的副本**（包根清单）各出一条目标；同名多版本各一份，地址带各自版本                                                                  | pnpm 的严格布局下同名多版本是常态，按包名去重会让其中一个版本的地址永远 404      |
| 3   | 入口条件     | 一个出口的入口按 `browser` → `import` → `module` → `main` 解析，并校验文件真实存在                                                                  | 产物跑在浏览器里；CJS 的那份（UMD）既不是浏览器那份字节，也要额外求值包装才能打    |
| 4   | 地址         | 地址末段 = 磁盘上的**产物文件名** = 由**产物形态**决定：JS 产物是 `<出口名>.js`，资产（图片/字体等）原样保留扩展名                                       | 一条规则两个消费者；两者不同形就是 404，而这类 404 在构建期看不出来              |
| 5   | 外置         | 只有**能按 exports 解析到入口**的说明符才外置成地址；解析不到的（`包名 + 源码路径` 这类）内联进当前产物                                                  | 外置意味着「浏览器会按这条地址再取一次」；取不到的东西不该变成地址               |
| 6   | 共享运行时   | 合并成**一个虚拟聚合产物**（不落地为可安装包），只出一个 `index.js`，成员按具名平铺                                                                     | 共享运行时只有一份实例、一条地址，hooks 一类按实例判等的机制才不会分家           |
| 7   | runtime 成员 | 只装**解析不到引用方声明**的依赖（peer、转译器注入、上游传递运行时）                                                                                      | 「声明过」的包有自己的 owner 与自己那条地址；剩下的才是无主的残余               |
| 8   | 兜底         | 编译末期把「清单里没有出口」的地址统一指向 runtime 的 `index.js`                                                                                        | 残余不需要逐个解释，它们只需要一个确定的去处                                     |
| 9   | 兜底上限     | runtime 只兜**连副本都解析不到**的地址；有副本的一律按副本出独立产物（即使没有声明）                                                                     | 兜底不是「吞掉多版本」的袋子；副本是解析事实，事实优先于「有没有声明」           |
| 10  | 导入形态     | 共享运行时**只允许具名导入**；出现 default 导入（`import React from "react"`）即构建失败并指出源文件                                                    | 一份模块只有一个 default，两个共享运行时不可能都占它                             |
| 11  | 下潜范围     | 枚举时读四个出口 `./client` / `./ui` / `./client-module` / `./index`                                                                                | 宿主面与 client 面可能互相引用；下潜窄了会把依赖悄悄漏掉                         |
| 12  | 判据         | 判据按「**从页面入口可达**」的地址集合算；不可达的产物**留在目录里**，判据只要求可达子集与磁盘一一对应                                                    | 宿主面产物在目录里无妨，它们不会被任何页面加载                                   |
| 13  | 失败面       | 兜底之后，可达集合里仍有**编不出来**的地址 → 构建失败，点名「地址 / 引用方 / 副本 / 打包器原话」                                                          | 宁可构建红，也不要发一份会白屏的应用——白屏在生产环境里没有任何线索               |

## 二、现状事实

- **枚举**在 `federation/prebundle-plan.ts`：正则扫静态 / 副作用 / 动态 import 与相对 import；只对 `@morlay/*` 与 `@deepseek-ai/dsh-client*` 下潜读源码；记录**按包根副本**建键，出口入口复用 `bundle.ts` 的 `browserEntryOf`（条件表在 `internal/resolve.ts`）。
- **转译与地址**在 `federation/bundle.ts`：`bundlePackage` 用 rolldown；外置按**逐条说明符**判定（`externalizableSpecifiersOf`：能按 exports 解析到入口才外置）；产物文件名由 `productFileNameOf` 一处决定，`urlOf` 与 `entryFileNames` 共用它。
- **编排与落盘**在 `build/compile.ts`：`prebundleAll` 逐包编译 → 删构建中间物 → 剥掉清单里的构建机路径 → 写页面骨架。
- **生产态**只做静态投递（`zephyr-app` 的 `StaticClientAssets`）：地址没有对应产物就是 404。
- **实测**（某应用）：静态目录里从页面入口可达 486 个模块，其中 52 个地址没有产物，分三类——同名多版本的另一个副本、转译器注入的说明符（`react/jsx-runtime`）、被外置的「包名 + 源码路径」。构建全绿，页面白屏。
- **清单不是一次枚举定稿**：下潜只走 `@morlay/*` 与 `@deepseek-ai/dsh-client*`，那些「只被三方产物引用」的传递依赖（`micromark`、`@lexical/*`、`scheduler`、`@shikijs/core`、`katex@0.16` 一类）不在首批清单里；它们在编译末期由「可达产物里引用、且有副本」的目标按副本补齐（真实应用上两轮共 49 个包）。判据因此落在**可达产物的引用**上，而不是「枚举一次就完整」。

## 三、模块边界与接口

| 模块         | 拥有（职责与不变量）                                                     | 不拥有（明确排除）                     | 依赖方向             | 接缝 / 适配器                     |
| ------------ | ------------------------------------------------------------------------ | -------------------------------------- | -------------------- | --------------------------------- |
| 枚举         | 从入口文件到**目标清单**：副本分组、出口名、下潜范围、解析基准               | 转译、地址、磁盘布局                   | → 转译与地址（复用入口条件） | `planPrebundle({ entry, include? })` |
| 转译与地址   | 一条目标 → 产物字节 + 它的地址；外置判据                                 | 该枚举哪些目标、目录怎么摆             | → rolldown           | `bundlePackage(options)`          |
| 编排与落盘   | 迭代到固定点、兜底到 runtime、可达性判定、页面骨架                        | 枚举规则与地址规则（都是上面两块的）   | ← 上面两块           | `compile(options)`               |

## 四、行为与边界

1. **枚举**：从应用的 client 入口出发走模块图；每进一个包按它**自己的清单**解析说明符，命中哪个副本就记哪个副本；下潜读四个出口的源码继续走。
2. **编译**：按副本分组，每份副本一次编译；出口的入口按浏览器条件解析（决定 3）；外置只对能解析到入口的说明符生效（决定 5）。
3. **兜底**：编译产物里出现、但清单里没有对应出口的地址，统一改写成 runtime 的地址（决定 8）；有副本却没出产物的，按副本补一条目标（决定 9），不再兜底。
4. **可达性**：从页面入口地址开始 BFS 产物的 import 语句；只有这条链上的地址参与判据（决定 12）。
5. **失败面**：兜底之后可达集合里仍有缺口 → 报错并点名现场（决定 13）。
6. **共享运行时的导入形态**：出现 default 导入即失败并指出源文件（决定 10）。

静态目录的形态不变（`client_modules/` + `index.html` + 按包产物 + `.files.json`），见[开发构建与产物布局](../../../.agents/designs/20261113-开发构建与产物布局.md)。

## 五、验收判据

| #   | 判据                                                                 | 证据                                                                 |
| --- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 1   | 同名多版本各有一条地址、各有产物                                      | 夹具里两个引用方各看到一份；两条地址都能取到                          |
| 2   | 转译器注入的说明符落到 runtime                                        | 产物里没有指向缺失包产物的地址；runtime 的 `index.js` 有一条 `export *` 转发到该成员地址（具名由成员提供，runtime 自己不写具名） |
| 3   | 「包名 + 源码路径」不再外置                                           | 产物里不出现 `<pkg>@<ver>/src/…` 形态的地址                          |
| 4   | 从页面入口可达的地址**零缺口**                                        | 真实应用：可达 270 个包产物零缺口、runtime 聚合产物不出现；遍历可达集合逐个取产物全部命中 |
| 5   | default 导入共享运行时 → 构建失败并指出源文件                          | 夹具里写一条 `import React from "react"`，构建报错含该文件名         |
| 6   | 兜底仍编不出来 → 构建失败并点名                                        | 夹具里放一个原生模块依赖，构建报错含地址、引用方与打包器原话          |
| 7   | 入口按浏览器条件解析                                                  | 双面入口的包（`exports` 同时给 require/import）取到的是 import 那份  |

## 六、取舍

- **一个 `index.js` + 只许具名导入**：换取「共享运行时一份实例、一条地址」；代价是 default 导入不能进共享运行时（由构建期报错兜住）。
- **不可达产物留在目录里**：换取实现简单（不用两遍落盘）；代价是分发体积与「一一对应」判据放宽成「可达子集」。
- **兜底指向一处**：残余不进清单、不逐个解释；代价是 runtime 的内容只能从产物或构建日志看出来。

## 七、不做与已知债

- **不做 AST**：枚举仍用正则扫 import；假说明符（CSS 片段、模板字符串里的示例）靠「解析不到」过滤。销账条件：出现「正则扫到了却不是 import」的真实误判。
- **不删不可达产物**：静态目录里会有页面永远不加载的宿主面产物。销账条件：分发体积成为实际问题，或静态目录要交给第三方核对。
- **runtime 的内容不可审查**：它由兜底决定，没有源码面与清单。销账条件：需要「这个包里到底有什么」时，把成员表落进 `.files.json` 的扩展字段。
- **兜底改写是持久的**：缺口被改写成 runtime 地址后落在磁盘字节上；若那个缺口后来被修掉，旧产物仍指向 runtime，直到该包因源码变化重编。当前没有影响（build 每次清空产物目录、dev 不走这条链）。销账条件：出现跨轮复用的产物目录时，改写要落在内存产物，或在清单里标成易失。
- **通配出口不做逐条存在性校验**：`exports: { "./src/*": "./src/*" }` 这类没有可枚举实例（仓库里 `@deepseek-ai/dsh-api-*` 都这么写），
  外置判据只能按模式放行，于是仍可能放出一条没有产物的地址。销账条件：把外置判断挪进 `resolveId` 钩子，逐个说明符带 IO 校验。
