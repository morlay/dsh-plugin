# 类型约束（跨包边界上的类型纪律）

状态：草稿——判据与分批已成形，未实施。
范围：本仓跨包 / 跨端边界上的类型纪律：品牌 id、`any`/`unknown`、契约面的 `import type`、装配清单的类型级校验、导出面类型测试。
非目标：运行期校验（归装配内核与各域服务）；上游类型定义本身（`vendor/**` 只读）；生成型 wire 类型；渲染层类型。

## 一、决定

| #   | 议题         | 决定                                                                                                                                     | 一句话理由                                                                 |
| --- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | 品牌 id      | 跨包 / 跨端边界的实体 id 一律用上游 `Branded<…>` / `BrandedNumber<…>`，且**只经同名工厂函数铸**（`SessionId(raw)`）；禁 `as XxxId`       | 两个都是 string 的 id 混用不会报错，品牌是唯一编译期防线                   |
| 2   | 裸 `string`  | 只许三类：wire 声明（生成口径）、`src/endpoint/**` 的线上字段、非实体字符串（路径 / 包名 / 事件名 / serviceName）                        | wire 是线格式，铸点在解包处；其余字符串不是实体                            |
| 3   | 铸点         | 每个 id 只在**入口三处**铸：wire 解包、DB 行读回、用户输入解析；域内不再出现裸 string                                                    | 铸点越少，「这个 string 是哪来的」越好回答                                 |
| 4   | `any`        | 归零；例外只留三类（TS2545 的 mixin 构造签名、rdb 的列引用、覆盖检查里放弃判定的条件类型），每处带 `oxlint-disable-next-line` + 一行理由 | 现存 `any` 只有 7 处（5 文件）且都有理由，可以直接开规则                   |
| 5   | `unknown`    | 只作边界输入；导出面（contract / endpoint）的成员类型不许出现 `unknown` / `any`                                                          | 导出面的 `unknown` 会把窄化责任推给每个消费方                              |
| 6   | 双断言       | `as unknown as` 只许出现在**边界桥**文件（白名单住 `rules.ts`）；测试不受限                                                              | 生产 239 处里绝大多数不是边界桥，先用白名单挡增量                          |
| 7   | 契约面取上游 | 类型一律 `import type`；**值**只许来自上游的 `/types`、`/client`、`/endpoint` 子路径或无宿主依赖的纯值（错误类 / 纯函数 / 品牌工厂）     | 契约面两端共用，一条上游**包根**值边就把宿主行拖进浏览器（本仓现状 56 条） |
| 8   | 契约面取框架 | 本包 DSL 走包根（两端共用，不分面）；上层的浏览器面与装饰器面由上层文档指定                                                              | 本包没有第二个说明符；上层的宿主面与浏览器面是两件事                       |
| 9   | 清单校验     | `ProvidersCoverage` 的覆盖面写进判据：只判单值 `inject`；multi / optional 用装配用例守，不假装编译期能判                                 | 类型层只收集 `inject` 的品牌，写清比扩能力便宜                             |
| 10  | 导出面测试   | 每条契约同时钉两层：**成员存在**（`AssertCovered`）+ **签名可赋值**（新增 `AssertCovers`）                                               | 现在只比 `keyof`，上游改签名不红                                           |

## 二、现状事实

**品牌类型全部来自上游，本仓不自造**：上游 `@deepseek-ai/dsh-brand` 提供 `Branded<B>` / `BrandedNumber<B>` 与 `brandString` / `brandNumber`，每个 id 有同名工厂。本仓 `export type <X>Id` 的数量是 **0**；生产代码铸品牌 **437 处**（`grep -rnE '\bSessionId\(|\bWorkspaceId\(|\bToolCallId\(' packages apps`，去 `node_modules`）。

**品牌逃逸 13 处，全部在一个扩展包的 rdb 层**（SQL 行 → 域对象）：12 处生产 + 1 处测试；另 4 处是测试里的 `as ResolveId`（非 id）。**裸 `sessionId: string` 100 处**：endpoint 39（线格式，合法）、contract 2、其余 59（ui 面直接吃裸 string）。

**`any` 只有 7 处（5 文件）且都有理由**：`command.decorator.ts`（2 处 `...args: any[]`）与 `setting.decorator.ts`（1 处）是 TS2545 的 mixin 构造签名硬要求（已带 `oxlint-disable-next-line` + 理由）；`zephyr-rdb/src/table/types.ts` 的 `ColumnRef<any>`（2 处）是列引用的值类型擦除；`coverage.ts` 的 2 处是条件类型里对宽条目**主动放弃**判定。`as any` 为 0。

**`unknown` 是常态**：`: unknown` 1089 处（测试 300+，生产 700+）；契约面只有 16 处，是唯一要求收紧的地方。

**双断言 `as unknown as` 543 处**（测试 304 / 生产 239）。生产集中：`bootstrap.ts` 19 与 `compat/from-cordis.ts` 17（cordis ctx 的边界桥，设计如此）、一个行修复文件 17（要拆）。

**`as never` 277 处**，生产代码 41 处集中在一个渲染槽位文件（把动态字符串 key 传给上游的泛型接口）。

**契约 / 端点面的非 type 包导入 174 条 / 85 文件**（上层各包的面，读数是本仓口径）：上游 63（**包根值 56**、子路径值 7）、本包包根 **58**（`Injectable` 56 / `EventEmitter` 2 / `inject` 2；正常——包根两端共用）、上层两个宿主面包根合计 **51**（归上层迁移）、其它 2。契约 / 端点面 **没有** `node:` 导入。

**装配清单的类型级校验只有 `coverage.ts` 一处**：`Uncovered<L>` 从清单字面量收集 `inject` 打下的 `Required<T>` 品牌再比对。它能保证：缺单值提供者 → 编译错（`assembly.spec.ts` 有 `@ts-expect-error` 钉住）。它**不看** `inject.optional`（返回 `T | undefined`，无品牌）、**不看** `inject.all`（返回 `T[]`）、**不判** `without()` 剔掉的条目（类型沿用 `L`）、宽类型条目（`...provideXxx()` 展开成 `ProviderEntry`）按 `any` 放弃。

**`ConfigOf` 三态**（`provider.ts`）：`static Config` → 构造参数 → `unknown`。构造参数分支是 `new (config?: infer C, ...rest: never[]) => unknown`，只匹配单参构造；**适配行与上游插件落到 `unknown`**，于是 `configure(Adapter, {...})` 接受任何 patch（`DeepPartial<unknown>` 仍是 `unknown`）。`toCordis` 的 `Config` 是 `(input?: never) => unknown`，与 `ConfigOf` 不联动。

**导出面测试**：上层的契约覆盖断言（`AssertCovered` / `AssertTrue`，45 个文件在用）判据是 `Exclude<keyof Upstream, "name" | keyof Contract>`——**只比键名**：上游新增成员会红，上游改签名 / 变可选 / 变只读不红。`@ts-expect-error` 全仓只有 7 处。

**判据现状**：`.oxlintrc.json` 已开 `node/no-sync` 与 `typescript/no-explicit-any`（`typeAware` / `typeCheck` 同开）；`devpackages/audit` 只判面边界与依赖声明。除这两条，类型纪律靠 `strict` + 代码评审。

## 三、模块边界与接口

| 模块                                                          | 拥有（职责与不变量）                                                             | 不拥有（明确排除）                                 | 依赖方向                     | 接缝 / 适配器                                        |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------- | ---------------------------------------------------- |
| 品牌与铸点（上游 `dsh-brand` + 各域入口）                     | id 的类型身份与唯一铸点（工厂函数）；「哪个 string 已是哪个 id」                 | id 的取值合法性（归域服务）、序列化格式（归 wire） | ← 上游 brand 工具            | 工厂函数就是适配器：裸 string → branded 只此一个入口 |
| 契约面（`src/contract/**`）                                   | 面形状、令牌身份、只吃 branded 的类型签名                                        | 上游实现细节、宿主能力、运行期解析                 | ← 本包包根 + 上游 `/types`   | `import type` 是这里的默认，值导入是例外             |
| 端点面（`src/endpoint/**`）                                   | wire 的线格式（id 在这里是 `string`）、远端方法名                                | 域内的 id 身份（解包后立刻铸）、传输实现           | ← 上游 `/remote`、框架装饰器 | 解包函数 = wire→域 的适配器                          |
| 装配清单类型（`coverage.ts`、`provider.ts`）                  | 单值 `inject` 的覆盖检查、配置类型推导（`ConfigOf`）                             | multi / optional 的覆盖、运行期预检                | ← 令牌与清单                 | `ProvidersCoverage` 是 options 上的额外必填字段      |
| 导出面测试（`contract-coverage.ts` + 契约套件）               | 「上游有而契约没列」的编译判据                                                   | 签名兼容、语义一致                                 | ← 上游类型                   | `AssertTrue` 把失败摊成类型错误                      |
| 边界桥（`bootstrap.ts`、`compat/from-cordis.ts`、rdb 行映射） | 与 cordis / SQL 行 / wire 三类外部形状的转换；双断言与 `as never` 的唯一合法住处 | 域语义、业务判断                                   | ← 上游形状                   | 一个桥一个文件，白名单按文件登记                     |

**接口**（调用方要知道的）：

- 铸品牌只经工厂（`SessionId(raw)`），不经断言；断言只出现在边界桥，且必须能指出「桥的另一头是什么外部形状」。
- 契约面的签名只接受 branded id；端点面只接受 `string`——两者之间的转换**有且只有** endpoint 的解包函数。
- `configure` 只对能推出 `ConfigOf` 的实现（有 `static Config` 或单参构造）有类型约束；适配行的 patch 不受约束，这是已知缺口。

契约变更（只加强制，不改签名）：

| 契约            | 现在                                     | 谁必须跟着改                                      |
| --------------- | ---------------------------------------- | ------------------------------------------------- |
| `AssertCovered` | 只判成员存在                             | 新增 `AssertCovers`（签名级）后，各契约套件逐个接 |
| `ConfigOf`      | 适配行 → `unknown`（`configure` 不校验） | 收紧后清单里对适配行的 `configure(...)` 要写对    |

## 四、行为与边界

- 正常路径：wire 收到 `{ sessionId: string }` → endpoint 解包处 `SessionId(raw)` → 之后每一层签名都是 `SessionId`，编译期挡住跨 id 误用。
- 错误：未铸品牌的 `string` 传给契约（如 `archive(sessionId: SessionId)`）→ 编译错，不等到运行期「列表里查不到」。
- 边界桥例外：`bootstrap.ts` / `from-cordis.ts` / rdb 行映射里允许 `as unknown as`，因为另一头是 cordis 的 ctx、上游插件对象或 SQL 行——不是域类型。
- 缺口（运行期才红）：`inject.all` 少一个实现、`inject.optional` 有提供者但没就绪——这两类只由装配用例守，编译期不判。
- 顺序：铸点在**解包之后、进域之前**，不允许「域里先收 string 再在某处补铸」。
- 包面不变：本包不按运行环境分面，类型规则对两端同一套（见[包出口](./20261113-包出口.md)）。

## 六、取舍

- **否掉「全仓禁 `as unknown as`」**：生产 239 处，其中 36 处是设计上的边界桥，其余一次改完必伤行为；改白名单 + 增量 + 分批。
- **否掉「用 zod / io-ts 在运行期验 id」**：品牌是编译期的事，运行期再验一遍等于同一事实两个 home；值合法性归域服务自己的校验。
- **否掉「本地自造一套 branded 类型」**：上游 `dsh-brand` 已经给了 `Branded` / 工厂函数，自造会让同一个 id 有两个类型身份。
- **否掉「直接开 `typescript/no-unsafe-*` 全家桶」**：typeAware 对上游 `.d.ts` 的 `any` 面误报很多，先只开 `no-explicit-any` + 双断言审计。
- **否掉「把 `ProvidersCoverage` 扩到 multi / optional」**：那要在类型层模拟清单的多值语义，收益远小于复杂度；写清覆盖面即可。

## 七、不做与已知债

- **ui 面的裸 string id（59 处）**：从 props / URL 进来的 id 在组件层还是 `string`，铸点在传输解包层；要收得改解包层（跨包）。销账条件：契约面「`archive(sessionId: string)`」类签名清零。
- **`as never` 41 处集中在渲染槽位文件**：上游按泛型键约束、我们的 key 是运行期字符串；要治得让上游开「动态键」入口。
- **`zephyr-rdb` 的 11 处 `as`**：列引用 / 聚合的类型断言，等 schema 推导成型再收。
- **`toCordis` 的 `Config` 与 `ConfigOf` 不联动**：行入口只给部署用，生产装配面不写 `Config`；先记债。
- **生成型 wire 类型**：`sessionId: string` 是生成口径，不在本设计的修改范围。

## 八、开放问题

- `AssertCovers` 的判据要不要含参数个数与 optional 位？倾向：**要**（`Parameters` / `ReturnType` 逐成员比较 + `@ts-expect-error` 反例），但不引入 `expect-type` 这类新依赖。
- 契约面的「上游包根值」审计规则挂哪：`devpackages/audit` 新增一项（面边界之外），还是本包的静态用例（像 `entry-shape.spec.ts`）？倾向 audit——它在扫全仓源码。
- `unknown` 在导出面的边界：`InjectionToken<unknown>` 这类「没有服务类型的值令牌」算不算导出面的 `unknown`？倾向：算例外，但要求 `T` 写真实类型。
