# 契约面转发方案（2026-10-23）

**要解决的问题**：`fromCordis(契约, 上游)` 的适配行要把**契约声明的面**（`register`/`admitConnection`/`mount` 这类方法）
暴露给消费者，但实现活在上游实例上。当前的三种做法都有问题：

| 做法 | 问题 |
| --- | --- |
| 让适配类手写转发（`this.register = (r) => this.providerContext.webServer.register(r)`） | 要拿上游实例 → 只能靠 `providerContext` 越狱；每个契约都要手写一遍 |
| 把上游原型的方法**复制**到 `this` | 覆盖了上游自己的 `provide`/`start`/`stop`，打断 `published` 收集与占位回填（10 条既有用例被打红） |
| `Proxy` 转发**全部** miss 的键 | 每次属性访问多一层 trap；且 `Reflect.has(target, prop)` 命中面变了，上游内部状态（`providerScope`/`published` 相关）被绕过 |

## 两个方向，两个 Proxy（先分清）

适配行夹在两套消费者之间，**一进一出**，各有一个 Proxy，别混：

```
        上游插件                      适配行（AdaptedBase）                   我们的消费者
  ┌──────────────┐   (入) providerCtx      ┌──────────────┐   (出) face        ┌────────────┐
  │ apply(ctx)   │ ──────────────────────► │  mount(ctx)  │ ────────────────►  │ inject(契约)│
  │ 读 ctx.<dep> │   读依赖 → 我们的 deps   │ 持有 instance │   读面 → 上游实例   │ 调 register │
  └──────────────┘                         └──────────────┘                    └────────────┘
```

| 方向 | 对象 | 谁读谁 | 白名单来源 | 已有状态 |
| --- | --- | --- | --- | --- |
| **入** | `providerCtx`（`createServiceScope`） | 上游插件读**我们的依赖** | `deps`（行内 local）+ 名字视图 + 根 ctx | 已实现（`readNames` + `permissiveRead`） |
| **出** | `face`（Proxy on 上游实例） | 我们的消费者读**上游的面** | 上游实例「固有 + `inject` deps」 | 待实现 |

- 入的 Proxy 解决的是「上游插件不知道我们的 DI，要用 cordis 的方式读到依赖」；
- 出的 Proxy 解决的是「我们不想把上游实例整个暴露给业务方」；
- 两者互不影响：改出的白名单不会改变入的读面（上一版把两者混在一起，才出现「10 条既有用例被打红」）。

## provide 多重时的限制（定稿）

**根名字视图是我们自己的机制，上游 `provide` 一律不进根。**

| 上游做了什么 | 落点 |
| --- | --- |
| `ctx.provide("session-query-sqlite", …)`（非契约名） | 只进**行内 local**（同一行内其它上游插件可读）；**不进根名字视图** |
| 契约名（`getTokenName(token)`，如 `session-query`） | 进根名字视图 + 令牌指向 `face` |
| 一次 provide 多个名字 | 全部只进行内 local；根上仍只有契约名 |
| 面与名字指向同一实例 | 同一个 `face`，不重复包 Proxy |

理由：根是**全局命名空间**，只有我们的机制（`provideService` / `publishServiceName`）能往里写；上游插件的内部命名
（`*-sqlite`、`*.backend.json` 这类）是它的实现细节，外泄就会让业务方依赖上游的内部命名，上游一改名我们就崩。

## 功能边界

- **要暴露**：契约 token 原型链上声明的成员（抽象方法/访问器）+ 适配类自己声明的（`inject` 字段、覆写方法）。
  `WebServer.register`、`Connection.admitConnection`、`UiRenderer.mount` 都是这一类。
- **不暴露**：上游自己的内部成员（`provide`/`start`/`stop`/`providerScope`/`providerInstance`/私有字段）。
  它们属于 `AdaptedBase` 的实现细节，消费者不该看到，也不该被覆盖。
- **上游内部自调用**（`api-gateway` 在构造里 `this.register(...)`）走**上游实例自身**，不经过适配行；
  需要观测/包装时包 `providerInstance`（受保护的框架面），不包 `this`。

## 方案

**A. 初始化时一次性定义 getter（推荐）**

`mount` 结束、`providerInstance` 就绪后，遍历「契约 token 原型链上的成员名」，只对 `this` 上**还没有**的键
定义转发（`Object.defineProperty` 一次，之后是普通属性访问）：

```ts
const contractProto = (token as { prototype?: object }).prototype;
for (const key of contractMemberNames(contractProto)) {
  if (key === "constructor" || key in this) continue;
  Object.defineProperty(this, key, {
    configurable: true,
    value: (...args) => this.providerInstance[key](...args),   // 方法
  });
}
```

- **性能**：转发只在 mount 时定义一次；运行期零 trap、零额外分配（优于 Proxy）。
- **边界**：只碰契约面，不覆盖上游内部成员 → 不打断 `published`/占位（既有 10 条用例的前提）。
- **时序**：mount 完成后才定义；`published` 的收集在 `callPluginWithInstance` 之前完成，互不影响。

**B. Proxy（不推荐，仅在 A 不可行时）**

`new Proxy(this, { get })` 每个属性访问都要进 trap；`Reflect.has` 的判定面一旦包含上游内部键，
就会改变 `providerScope`/占位回填的语义（这次 10 条回退的根因）。除非「契约方法在 mount 之后才动态出现」，
否则没有理由付这个成本。

**C. 面对象（推荐，替代 A）**

A（把转发定义到适配实例上）有个隔离漏洞：`defineProperty` 写的是**适配实例本身**的公开属性，
于是「消费者看到的对象」和「框架持有的适配实例」是同一个——上游内部的东西（`providerInstance`、
转发闭包）与业务面共享同一个对象，卸载时还得逐个 `delete` 才能断开对上游实例的引用。

改成：**契约令牌指向一个独立的面对象**，适配实例本身不挂任何转发。

```ts
// mount 末尾：只把「契约面」装进面对象，令牌指向它
const face = Object.create(null) as Record<string, unknown>;
for (const key of contractMemberNames(contractProto)) {
  face[key] = (...args) => (called.instance as Record<string, unknown>)[key](...args);
}
unpublishAll.push(provideService(context, token, face));
// 卸载时：面对象清空 + 解除令牌，适配实例与上游实例的引用随之断开
```

- **隔离**：消费者 `inject(契约)` 只拿得到面对象；`providerInstance`/`providerContext`/适配实例本身都不外露。
- **性能**：每个适配行一个面对象、方法闭包数量等于契约成员数（通常 1～4 个），比「每实例 defineProperty + 每访问闭包」更省；没有 Proxy trap。
- **生命周期**：面对象在 `mount` 末尾生成、卸载时清空；上游实例由 `providerInstance` 持有，随行卸载释放。
- **边界**：上游内部自调用（`api-gateway` 构造里的 `this.register`）不经过面对象；要观测就包 `providerInstance`（框架面）。

**D. 面对象 = 上游实例的 Proxy + cordis 的「固有 + inject」白名单（最终选型）**

C 要预先枚举契约成员（`contractMemberNames` 反射），而这件事**可以交给 Proxy 惰性做**。
白名单不用自己发明——**cordis 已经有明确的两类键**：

- **固有**：实例自身的键 + 原型链上的成员（`Service` 基类的方法、上游类声明的方法/访问器）；
- **inject 的 deps**：上游 `inject: [...]` 声明的服务名（`ctx.<dep>` 的读面）。

```ts
// 白名单来源：固有（自身 + 原型链）+ inject 声明的名字
const intrinsic = new Set<string>([
  "constructor",
  ...Object.keys(subject),
  ...prototypeChainNames(Object.getPrototypeOf(subject)),
  ...(upstream as { inject?: readonly string[] }).inject ?? [],
]);
const face = new Proxy(subject as object, {
  get(target, prop) {
    // 白名单 = 实例自身的键 + 原型链成员 + 上游 `inject` 声明的 deps keys（cordis 的"固有 + inject"面）。
    if (typeof prop === "string" && !intrinsic.has(prop)) return undefined;
    const value = Reflect.get(target, prop);
    return typeof value === "function" ? value.bind(target) : value;
  },
});
unpublishAll.push(provideService(context, token, face));
```

- **实现量**：不需要为每个成员准备闭包，也不需要 `defineProperty`；`get` 时按需转发，**取不到就是 `undefined`**。
- **隔离**：白名单只放「固有 + inject deps」；`providerInstance`/`providerContext` 这类框架私有成员
  （不在实例、不在原型链、不在 inject 声明里）读不到。
- **性能**：每个跨行调用过一次 `get` trap（只在业务调用路径上）；白名单是 `Set.has`，O(1)。比 C 的「每成员一个闭包」更省内存，比 B 的「无白名单全域转发」更安全。
- **卸载**：令牌解除即断开；面对象随行释放，无需逐个 `delete`。
- **`constructor` 不进绑定**：白名单里保留 `constructor`（`isAdaptedPlaceholder` / `instanceof` 要读它），
  但它是唯一不 `bind` 的函数——绑定会丢掉原型链，`face instanceof Service` 与占位判定都会失真。

## 选型

**D**。

- A（defineProperty 到 `this`）：业务面与适配实例同体，隔离靠约定；
- B（无白名单 Proxy 转发全部 miss）：`Reflect.has` 面覆盖了上游内部键，改变占位/回填语义（10 条回退的根因）；
- C（预生成面对象）：正确但要多一次反射 + N 个闭包；
- D：惰性转发 + 白名单隔离，实现量与内存都最小。

## 兼容性（必须确认）

- 既有消费者是用 `inject(契约)` 拿**令牌**的：`provideService(context, token, face)` 与既有的
  `provideService(context, token, value)` 同一路径，语义不变（只是值从「上游实例」换成「面对象」）。
- 若有消费者直接 `app.get(契约)` 后读**契约面以外**的成员（例如 `providerInstance`），那本来就在越狱——
  D 会让它拿不到，这是**正确**的收紧。
- 单参形态（无契约原型）同样生成面对象；面来源见形态二下面的「面来源」——只有上游什么都没 `provide`
  又没有实例时才没有面。

## 判据（落地后必须绿）

- `from-cordis.spec`（15 条）、`adapter-placeholder.spec`（2 条）、`bootstrap.spec` 的适配用例、`api-gateway.spec`；
- `adapter-matrix.spec` 的 B4（`inject(契约)` 拿到的面对象能调 `register`）与 B5（包 `providerInstance`
  能记录经面对象的调用）；
- 守门：A5（dispose 后根名字清理）与 B11（上游内部名不进根）；
- 「不经过 trap」的性能护栏属于方案 A，选型 D 就是 Proxy，不再适用。

## 举例：`token` 是什么、两种形态各发布什么

`token` = `resolveToken(适配类的 ctor) ?? 适配类自身`。它是**契约令牌**（`@Injectable` 沿继承链记下的那个 abstract class），
决定了「根上发布什么名字」和「`inject(...)` 用什么读」。

### 形态一：双参（有契约，生成面对象）

```ts
@Injectable()
abstract class SessionQuery {
  abstract query(id: string): string;
}

@Injectable()
class SessionQueryDefault extends fromCordis(SessionQuery, upstream) {
  protected override async onInit(ctx) { await this.mount(ctx); }
}
```

- `resolveToken(SessionQueryDefault)` → `SessionQuery`；
- `getTokenName(SessionQuery)` = `session-query` → **根上发布 `session-query`**；
- 上游 `apply` 里 `ctx.provide("session-query-sqlite", …)` → 只进行内 local，**不进根**；
- 契约有原型（`query`）→ 生成 `face`（白名单 = 上游实例固有 + `inject` deps），令牌指向 `face`；
- 消费者：`inject(SessionQuery)`（或按名 `session-query`）拿到 `face`，调 `face.query("x")`。

### 形态二：单参（无契约，不生成面对象）

```ts
@Injectable()
class UiPrimitivesClient extends fromCordis({ apply, inject }) {
  protected override async onInit(ctx) { await this.mount(ctx); }
}
```

- `resolveToken(UiPrimitivesClient)` → `undefined` → `token = UiPrimitivesClient`（**适配类自身**）；
- `getTokenName(UiPrimitivesClient)` = `ui-primitives-client`（类名连字符）；
- 上游 `apply` 里 `ctx.provide("locale", …)` / `ctx.provide("theme", …)`（多个名字）→ 只进行内 local，**不进根**；
- 契约**没有原型成员**（适配类只有 `onInit`）→ 白名单退化成「上游实例固有 + `inject` deps」；
- **同样生成 `face`**，令牌指向 `face`——单参也转发，上游实例一点不外露；
- 对象插件没有实例时，面来源退到它 `provide` 出的值（见下「面来源」）；**一个值都没有 → 令牌 `undefined`**
  （它本来就没有「面」可给）；
- 但注意（方案 A）：**对象插件形态的上游行不能再被 `inject`**——要 `inject` 就必须给它写双参契约，
  那时面来源存在、`face` 也就能生成。

### 面来源（落地定稿）

`mount` 末尾按这个顺序取面来源，有值才生成 `face` 并发布：

1. `published.get(getTokenName(token))`——上游自己 `provide` 了与契约名同名的值（`Greeter` 这类「provide 出实现对象」的形态）；
2. `called.instance`——上游是 `Service` 子类 / 类插件，有实例；
3. `published` 里第一个值——对象插件只 `provide` 了实现对象、没有实例（`session-query-sqlite` 这类）。

「契约名同名的 provide 值」优先，是因为上游可能既 `super()` 注册自己（`Service` 的构造），又 `provide`
一份实现对象给契约面；这时契约面是后者。三者都没有 → 令牌与根名字都不发布（`app.get(适配类)` 仍抛
`is not available`）。


### 单参也转发（定稿）

隔离不能有例外：**只要上游有实例（`Service` 子类），令牌就指向 `face`**，不直接给实例。
单参时白名单没有契约原型可参考，就用「实例固有 + 原型链 + `inject` deps」——这与双参的白名单来源一致，
区别只是双参多一层「契约原型声明的成员」。

## 隐患点：`provide("locale")` / `provide("theme")` 这类跨行服务

上游两行的实现：

```ts
// locale/src/client/index.ts
ctx.provide('locale', locale)        // LocaleRuntime 实例
// ui-theme/src/client/index.ts
ctx.provide('theme', theme)          // ThemeRuntime 实例
```

而 `publishServiceName(ctx, name, value)` 的实现是 `tableOf(ctx).names`，`tableOf` 用 **`rootOf(ctx)`** ——
**任何一次 `publishServiceName` 都写根表**。所以现状是：

- `locale`/`theme`/`session-query-sqlite`/`storage.backend.json`… 这些**上游内部名全进了根**（污染全局）；
- 而 `layout` 的 `inject: ['slots','theme','locale','shortcuts']` 又**确实要跨行读**这些名字。

结论：**跨行要用的上游名，必须由我们定义契约**（`@Injectable() abstract class Theme` / `Locale` / `Slots` / `Shortcuts`），
行适配写成 `fromCordis(Theme, uiThemePlugin)`，根上只出现契约名（`theme`/`locale`/…）；上游内部名只留行内 local。

这与「根上只能通过我们的机制注册」一致：**根上的每个名字都必须有对应的契约**。

## 收窄：可被 `inject` 的必须是契约

**判据**：`inject(X)` / `inject.all(X)` / `inject.optional(X)` 里的 `X` 必须是 `@Injectable()` 标记的契约类。
没有标记的类、上游内部名字符串、`InjectionToken` 之外的裸值都**不是**注入目标。

落地两层：

- **类型层**：原计划让 `@Injectable()` 的返回类型带品牌（`InjectableToken`）、`inject` 只接受它。落地时确认
  **本仓做不到**：类型检查走 `experimentalDecorators`（legacy），装饰器返回类型不会带回类类型上
  （`typeof SomeContract` 上拿不到品牌，`inject(SomeContract)` 全仓报 TS2345）。品牌类型因此不引入。
- **运行时**：`createInjectPlaceholder` 里校验 `getTokenMeta(token) !== undefined`，否则抛
  `inject() 的目标必须是 @Injectable() 契约：<name>`。这是唯一落地的判据，也让「上游内部名不能 inject」
  有了确定的错误面。

配套（同一条规则的另一面）：

- 上游 `provide(name, value)` 的名字**不进根名字视图**（只进行内 `local`）；
- 跨行要读的上游名，必须由我们定义契约（`Theme`/`Locale`/`Slots`/`Shortcuts`），根上只出现契约名；
- 契约名 = `getTokenName(契约)`（连字符），是根名字视图里**唯一**由上游行贡献的名字。
