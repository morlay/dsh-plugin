# 上游服务类适配成强类型令牌

状态：已采纳

背景：dsh 的行按 Cordis 字符串服务名工作（`ctx.web`、`ctx.sandboxPolicy`），但我们自己的 Provider 不应写 `inject: ["web"]` 这类字符串。上游服务已由 profile 行装载，也不能为我们再挂一份插件。上游包不一定提供稳定的静态服务名（`WebRuntime` / `SandboxPolicyService` 都没有）。

**决定**

- `fromCordisService<T>(ServiceClass)` 生成适配令牌；`attachProvider` 在行 ctx 的 Cordis 服务表里按 `instanceof` 扫描实例，取运行时 `Impl.name` 注册到令牌表，回填 `inject(令牌)`；不手写服务名。
- 仍按名字直接读 `ctx.<service>` 的上游 Service 类用 `providerContext(ctx)`（名字视图 + 原生 provide）；它在行 ctx 上转发，不要求行 fiber 手写 inject。
- 官方行 id 从上游 `package.json` 包名 / 插件名派生：`@deepseek-ai/dsh-<row>` → `<row>`；`officialPlugin(plugin)` 基于 `fromCordis(plugin)` 生成运行期可装配的适配型 Provider，并带 `officialRowId`；包名放在 `@Module.dsh.packages` 的构建期映射里。
- `toCordis()` 不输出字符串 `inject` 数组。

**考虑过的选项**

- 静态 `inject: string[]`：消费侧退回字符串，且服务名要手写。
- 给行 fiber 的 `inject` 补声明：cordis 的 inject 是「待就绪声明」，补进去会触发 `inactive context`，它不是访问许可。
- 每个上游类重写一份 Provider：会与 profile 行重复注册，服务名冲突。

**后果**

- 上游服务类必须运行期可导入（peer 依赖）；类扫描有 5s 超时。
- 同一服务类出现多个实例时取第一个；当前不支持多实例。
- `providerContext` 只给需要名字视图的上游类；我们自己的 Provider 用 `inject(令牌)`。
- 官方行适配的行 id 依赖「包名最后一段去掉 `dsh-`」这条上游命名约定；不满足时要显式覆盖。
