# 上游行的依赖面与装配顺序

状态：机制已实现并闭环（`fromCordis` 的读面替换 + root ctx 归属 + `assertInjectedDepsSatisfied`）。子服务那一档的判据见第五节。
范围：`fromCordis` 适配行如何满足上游行的依赖、这些依赖如何参与装配排序、缺依赖时在哪一层失败。
非目标：上游各包内部的注入写法（源码即真源，见[上游同步技能](../../../../.agents/skills/zephyr-upstream-sync/SKILL.md)）；bootstrap 的拓扑排序实现（见 `bootstrap.ts`）。

## 一、事实：上游行读依赖的三条路

| 读法         | 例子                                                                           | 谁解析                                                                          |
| ------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 按名读 store | `ctx.get('sessions')`、`ctx.sessions`                                          | cordis 的 store（全局）                                                         |
| 声明的注入   | `export const inject = ['sessions', …]`                                        | cordis 的 fiber 启动检查（**本仓不消费**：`fromCordis` 不走上游的 plugin 调度） |
| 子服务       | `super(ctx, 'uiSession.sessionStatus')` 注册、`ctx.uiSession.sessionStatus` 读 | `uiSession` 实例**自己的 ctx** 按全名解析 store                                 |

第三条是关键：读 `ctx.a.b` 时 cordis 会转成 `Reflect.get(ctx, 'a.b')`，按 **`reflect.props`** 查表——而那张表是**每个 ctx 一张**。所以决定"读得到读不到"的不是 deps 有没有那个键，而是**提供方与消费方在不在同一张 props 表上**。

## 二、我们的机制：deps 读面替换

`fromCordis` 给上游 apply 的 ctx 是一层代理（`withDeps`）：deps 里有的**名字**直接返回本行给的值，其余回落到真 ctx。
所以包装行要做的一件事是：把上游要用到的每个名字显式放进 `mount(ctx, config, deps)`。

第三条路（子服务）**不能靠包实例解决**：把服务实例包成 `getTraceable` Proxy 确实能让读命中，但上游
服务里有 `#private` 字段，Proxy 上访问会抛 `Private element is not present on this object`
（真机症状：新建会话失败、skill 根目录 skipped）。已回退，任何情况下都不包实例。

正解是**属性读的 ctx 归属**：应用根的行把上游建在 **root ctx** 上（同一张 `props` 表），
`@AgentScoped()` 的行仍建在行 ctx（注册落点必须留在 `agentCtx`）。同时 `withDeps` 的代理把
`fiber` 指回**行** fiber（`fiberOf` 参数）——ctx 换成 root 之后 `ctx.fiber` 会变成 root fiber，而上游
按 fiber 记状态（`mcp-client` 会因此抛"previous connection cleanup is incomplete"）。

deps 仍按名字替换（deps 命中直接返回原值）；deps 没交、名字带点（`a.b`）时按名字宽松读一次
（`ctx.get(name, false)`），与 `ctx.a.b` 命中同一个 store 条目。

## 三、决定

0. **令牌只来自继承**：适配行的基类 `extends` 契约（`InjectionToken` 造的也是类），`@Injectable()` 无参复用父类元数据。
   `InjectableOptions.token` 已删——不存在"手工指定令牌"这一档；令牌是上游类时（`fromCordis(X, X)`）会 `extends` 上游类
   并跑它的构造，属于错写法，已在本仓清零（4 处改成单参或组合）。

1. **子服务面在本仓建令牌**，令牌名就是上游的子服务名（`uiSession.sessionStatus` → `UiSessionStatus`）。
   - 提供行：`fromCordis(UiSessionStatus, 上游行)`——`faceFromStore` 按令牌名从 store 取到上游实例，`bindFace` 把它绑进令牌表。
   - 消费行：`inject(UiSessionStatus)`，并把值放进 deps 的名**字面键**（`"uiSession.sessionStatus"`），让上游 apply 里的直接读也命中。
   - 令牌边同时承担排序：提供行的令牌先进 `instances`，消费行的 placeholder 让它排后。
2. **不**让上游名字参与排序（早期试过：给适配行加"上游 `inject` 名字边"）。理由：那是把上游内部命名当成我们的装配契约，上游改名时只会静默错序；而令牌是显式契约。
3. 子服务读**必须**由提供者先注册（store 里先有该名字），且提供方与消费方必须在**同一张 `props` 表**上
   （应用根的行都建在 root ctx 上，天然满足）。这两条都只能靠装配保证，deps 替换对属性读无效。

## 四、缺依赖的失败点

`assertInjectedDepsSatisfied`（`from-cordis.ts`）：上游 `inject` 声明的名字若既没在 deps、也不在 store，`mount` 直接抛错并列出缺的名字。
判据用例：`packages/zephyr/zephyr/src/compat/__tests__/from-cordis.spec.ts`（缺 → 失败；store 已就位 → 通过）。

这条判据把"浏览器白屏"提前成"装配期一条明确失败"，0.2.3 同步期间实际抓到了 `web-search-deepseek` 缺 `deepseekAuth`。

## 五、判据

`ui-session-status` ↔ `ui-workspace` 这一组是这条机制的现场样本：令牌 `UiSessionStatus`（名 = 上游子服务名）
由 `SessionStatusSlots` 提供、`WorkspaceSlots` 注入并放进 deps；属性读由"应用根的行建在 root ctx 上"
保证；整链装配通过。

判据用例：

- 框架层：`packages/zephyr/zephyr/src/compat/__tests__/from-cordis.spec.ts`（上游 `Service` 构造里读
  `ctx.parent.child`，deps 交 `parent` + `"parent.child"`）；
- 应用层：`apps/zephyr-custom/src/client/__tests__/assembly.spec.ts`（装 `appClientProviders()` 整链，
  断言 `connection` / `client-connection` / `uiSession` / `uiSession.sessionStatus` 都可读）。

仍待补：一条"子服务名必须有提供行"的预检（目前靠上面两条用例覆盖，不是装配期的通用判据）。

排查用的探针留在两处，默认零输出：`ZEPHYR_DEBUG_PROXY=1` 打开 `withDeps` 代理的读日志（带点名字与
`uiSession*`）以及 `mount` 结束时打印 `face.tracker.ctx` 的身份。
