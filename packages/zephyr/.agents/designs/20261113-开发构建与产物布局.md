# 开发构建与产物布局（`zephyr-dev` 的边界、产物目录的形状）

状态：已对齐——方案定稿，代码未动；实施按票推进。
范围：谁拥有「开发运行时 + 最终构建」、`zephyr build` 产出的目录形状、dev 与 prod 的前端形态、
部署值怎么递进产物里。
非目标：联邦产物的格式与缓存算法本身（见[预编译时序与令牌表](../../zephyr-app/.agents/designs/20261114-预编译时序与令牌表.md)与
[CJS 互操作](../../zephyr-app/.agents/designs/20261114-CJS互操作与依赖预构建.md)）；目录语义与可删性
（见[目录契约](../../zephyr-app/.agents/designs/20261114-目录契约.md)）；桌面壳的打包细节（桌面包级记录）。
关联：[框架层](20261113-框架层.md) · [构建期前端预编译](../../zephyr-cli/.agents/designs/20261114-构建期前端预编译.md) · [如何写](../../../../.agents/standards/how-to-write.md)

## 一、决定

| #   | 议题            | 决定                                                                                                                                                               | 一句话理由                                                                        |
| --- | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 1   | 新包            | 新建 `zephyr-dev`，拥有**开发运行时与最终构建**的浏览器侧全部：vite HMR 旁路、联邦预编译、前端产物落盘                                                             | dev 与 build 共用同一份解析规则与同一条产物算法，合成一个模块才不会长出第二条链   |
| 2   | `zephyr-app`    | 剥离开发构建，只剩**运行时**（宿主与浏览器双态）；不再依赖 `vite` / `chokidar` / `lightningcss`                                                                    | 运行时不需要构建器；同一包里混着两套依赖，浏览器面就得靠 external 表硬挡 rolldown |
| 3   | 产物根          | `server.outputDir`（相对配置文件或绝对），缺省 `target/<应用名>/`；`runBuild` 每次整目录重建                                                                       | 产物是「可分发的一份应用」；落哪归应用配置，与 vite 的 `build.outDir` 同一习惯    |
| 4   | 产物形状        | `client_modules/`（前端联邦产物 + 页面骨架）、`node_modules/`（`pnpm deploy --prod` 闭包）、`src/server.ts`（源码面入口）、`package.json`、`zephyr.json`（部署值） | 一个目录就是一份可运行的应用，拷到别处不改任何路径也能起                          |
| 5   | 前端形态        | **dev 与 prod 都是联邦**：页面只有一个很小的入口，其余按包从 `client_modules/` 取                                                                                  | 一种形态，不存在「dev 能跑、打包不能跑」                                          |
| 6   | dev 的 HMR 旁路 | 可选：点名 `@morlay/*` 走 vite 逐文件（改它要热更），其余一律联邦                                                                                                  | 热更是开发期的局部收益，不该成为整条链的第二形态                                  |
| 7   | 缓存            | 联邦缓存与产物目录**同一语义、只换目录**：dev 写 `<dataDir>/cache/client-modules`，build 直接写 `<outputDir>/client_modules`                                       | 一份算法两处落点，读代码的人不必先分辨「这是哪种缓存」                            |
| 8   | node 侧入口     | **源码面** `src/server.ts`，由 `@morlay/dsh-oxc-node` 直接跑；不再打 `entry.mjs` 单文件                                                                            | 闭包里本来就有 loader；少一次 rolldown，也少一份「只有打包时才炸」的错位          |
| 9   | 页面骨架        | `index.html` 进 `client_modules/`，`src/` 只留 server 侧源码                                                                                                       | 前端产物自包含在一个目录里                                                        |
| 10  | 部署值          | `<outputDir>/zephyr.json`：启动时读它（数据根、端口、形态）                                                                                                        | Finder 启动没有命令行与环境变量，部署值必须随产物走                               |

## 二、现状事实

- 构建三步在 `zephyr-cli/src/build/builder.ts`：`buildClient`（vite build → `layout.dist`）、`buildRuntime`（`pnpm deploy --prod` → `layout.runtime`）、
  `bundleEntry`（rolldown 单文件 → `runtime/entry.mjs`），另有第四步 `buildPrebundle`。
- **`dist/` 是死产物**：`serve.service.ts` 的 `replyPage` 读的是 `appBootDir/index.html` 并注入 `/@fs/…/index.ts`，
  preview 形态仍在跑 vite 服务源码，没有任何代码读 `layout.dist`。
- `zephyr-app/package.json` 的 `dependencies` 含 `vite` / `chokidar` / `lightningcss`，`rolldown` 在 `peerDependencies`；
  而 `zephyr-cli` 的 `vite` 只在 `devDependencies`（`builder.ts` 里却 `await import("vite")`）。
- 实测规模：`pnpm deploy --prod` 闭包 **928M / 923 个包**；现行 `dist/` **14M**。
- 实测可行性（本机探针）：`bundlePackage({ input: { client: apps/zephyr-custom/src/client/app-boot.ts } })` 产出 **6.8KB** 的 `client.js`，
  外部依赖 9 条 `/_zephyr/@modules/…`，无相对 import、无 assets/chunks 引用——应用入口可以是一个普通联邦目标。
- 实测可行形态：`target/<app>/{package.json, node_modules → 闭包, src/, client_modules/}` 里用
  `node --import <loader> --input-type=module -e 'await import("./src/server.ts")'` **能加载**（导出 `default` 是函数）。
- loader 在闭包里：`runtime/node_modules/@morlay/dsh-oxc-node` 存在，所以产物自带启动器。
- vite 8 下「循环 re-export 报错」这条理由**不成立**（vite / rolldown / esbuild 里都没有该措辞，构造的循环包两种形态都不报），
  见 `.scratch/dev-build-research/notes.md`；`dev.include` 因此只剩「哪些包要 HMR」这一条产品含义。

## 三、模块边界与接口

| 模块         | 拥有（职责与不变量）                                                                                                   | 不拥有（明确排除）              | 依赖方向          | 接缝 / 适配器                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ----------------- | ------------------------------------------------------------------------------- |
| `zephyr-dev` | 浏览器侧的唯一构建者：解析规则（alias / define / 装饰器）、联邦预编译、dev 的 HMR 旁路、build 的前端产物落盘           | 宿主装配、命令树、node 侧闭包   | ← `zephyr` 的 DSL | `compile(options)` / `serve(options)`：清单进、产物出                           |
| `zephyr-app` | 运行时（宿主与浏览器双态）：web / http / connection / remote / api-gateway / 渲染骨架 / `AppEnv`；**一条静态资源契约** | 任何构建行为、vite 依赖、预编译 | ← `zephyr` 的 DSL | `ClientAssets.serve(req,res)`（dev 接 `zephyr-dev`，prod 读 `client_modules/`） |
| `zephyr-cli` | 命令与编排、工作区配置解析、布局与数据根、运行模式（部署值）                                                           | 构建算法细节                    | ← `zephyr-dev`    | `layoutOf` / `resolveDataDir`                                                   |

**布局**（`ZephyrLayout` 的目标形状；根由 `server.outputDir` 给，缺省 `target/<应用名>/`）：

```
<outputDir>/
  client_modules/      前端：index.html + 按包的联邦产物（<pkg>@<ver>/… + .files.json）
  node_modules/        宿主闭包（pnpm deploy --prod，含 @morlay/dsh-oxc-node）
  src/server.ts        宿主入口（源码面，由闭包里的 loader 直接转译）
  package.json         应用清单（type: module、files）
  zephyr.json          部署值（数据根 / 端口 / 形态）
```

**契约变更**：

| 契约                        | 现在                                      | 谁必须跟着改                                                                  |
| --------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------- |
| `ZephyrServerConfig`        | `{ entry }`                               | 加 `outputDir`（缺省 `target/<应用名>`）：产物根从它算，不再写死在 `layoutOf` |
| `ZephyrLayout`              | `{root, dist, runtime, cache, entry}`     | `zephyr-cli`（`layoutOf`）、`zephyr-desktop-bundle`（打包输入）、`preview`    |
| 静态资源投递                | `ServeDefault` 直接持 `ViteHandoff`       | `zephyr-app`（改成 `ClientAssets` 契约）、`zephyr-dev`（实现 dev 侧）         |
| `AppEnv.appBootDir`         | `<profileDir>/src/client`，由运行时读页面 | 页面改从 `client_modules/` 取；`appBootDir` 降为「dev 的 vite root」          |
| `zephyr/dev*.ts` 的装配函数 | 在 `zephyr-app` 的 `client-modules` 里    | 迁到 `zephyr-dev`；应用装配清单改为从 `@morlay/zephyr-dev` 取                 |

## 四、行为与边界

- **dev**：`zephyr dev` 起宿主；前端请求先到 `ClientAssets`，命中 HMR 名单的包走 vite 逐文件，其余按包返回
  `client_modules/` 的联邦产物（未命中则现算并落缓存）。改源码 = 该包产物失效重编译，页面整刷。
- **build**：`rm -rf <outputDir>` → `pnpm deploy --prod --config.inject-workspace-packages=true` 到 `node_modules/` →
  联邦编译应用入口与整棵 client 图到 `client_modules/` → 写 `zephyr.json` → 删 `src/client`（产物已在 `client_modules/`）。
- **preview**：只吃 `<outputDir>`，启动前校验 `client_modules/` 齐全（缺则 `CliError`，不回退到现场编译）。
- **错误**：清单为空 / 缺已知包 / 产物缺失都是构建失败，不静默降级。
- **回收**：`<outputDir>` 整目录可删；`<dataDir>/cache/client-modules` 整目录可删（下次按需重建）。

## 六、取舍

- **不用 `pnpm deploy` 之外的办法解决 node 侧**：已经完全打通过一次，闭包 928M 是体积代价但换来「零自研模块装载」；
  全打包成单文件实测 16.2MB 仍留 `koffi` / `node:sqlite` / `@vitejs/devtools/*` 逃逸，反而多一份名单要维护。
- **不打 `entry.mjs`**：闭包里本来就有 loader，源码面入口少一层 rolldown，也让 stack trace 指向真实文件。
- **prod 也用联邦**（而不是 vite build 出一个打包后的静态面）：接受首屏请求数多，换 dev/prod 只有一种形态。
- **保留 HMR 旁路**：不追求「纯粹一种形态」到丢掉热更；旁路是开发期的局部，不参与产物。
- **vite 的 optimizeDeps 不作为主链**：它的 key 是裸说明符字符串，同名多版本会塌成一份（`zod@4.4.3` 静默变成 4.6.6），
  而我们要把版本写进 URL；CJS 具名导出也依赖「请求方由 vite 转译」这一条。详见调研笔记。

## 七、不做与已知债

- 不做「node 侧零 node_modules」的打包（见取舍）。
- 已知债：`target/` 里 `node_modules` 928M，分发体积大；销账条件是出现按包增量装载的方案。
- 已知债：dev 的联邦缓存与 build 的产物目录是两份字节（同算法不同落点），磁盘占用翻倍；
  销账条件是 build 能直接复用 dev 的缓存目录而不破坏「target 自包含」。

## 八、部署值清单（`zephyr.json`）

三个字段：`dataDir`（数据根，唯一必须的——Finder 启动没有命令行与环境变量）、`mode`（`dev` / `prod`，
决定要不要起 HMR 旁路）、`port`（可覆盖项）。插件清单不进它：装配已经在 `src/server.ts` 的清单里。

`src/client` 在 build 之后**删除**：前端源码已在 `client_modules/` 的产物里，留着等于分发源码。
排查时代价是产物里看不到原始 `.tsx`，接受。
