状态：T1（两条空契约）、T2（建 `zephyr-dev`、把构建件搬出 `zephyr-app`）与 T3（产物改到 `outputDir`、静态前端、
删 `entry.mjs`）已落地；剩 `shiki` 的清单枚举（见「七、不做与已知债」）。

## 一、决定

| #   | 议题            | 决定                                                                                                                                                             | 一句话理由                                                                        |
| --- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | 新包            | 新建 `zephyr-dev`，拥有**开发运行时与最终构建**的浏览器侧全部：vite HMR 旁路、联邦预编译、前端产物落盘                                                           | dev 与 build 共用同一份解析规则与同一条产物算法，合成一个模块才不会长出第二条链   |
| 2   | `zephyr-app`    | 剥离开发构建，只剩**运行时**（宿主与浏览器双态）；不再依赖 `vite` / `chokidar` / `lightningcss`                                                                  | 运行时不需要构建器；同一包里混着两套依赖，浏览器面就得靠 external 表硬挡 rolldown |
| 3   | 产物根          | `server.outputDir`（相对配置文件或绝对），缺省 `target/<应用名>/`；`runBuild` 每次整目录重建                                                                     | 产物是「可分发的一份应用」；落哪归应用配置，与 vite 的 `build.outDir` 同一习惯    |
| 4   | 产物形状        | `client_modules/`（前端联邦产物 + 页面骨架）、`node_modules/`（`pnpm deploy --prod` 闭包）、`src/server.ts`（源码面入口）、`package.json`                        | 一个目录就是一份可运行的应用，拷到别处不改任何路径也能起                          |
| 5   | 前端产物        | **静态前端**：`client_modules/` 就是一份纯静态目录（`index.html` + 按包的 `<pkg>@<ver>/*.js` + `.files.json`），生产态只做文件投递，不跑任何构建                 | 产物是文件，不是服务；静态目录能直接丢给任何 http server，也能被桌面壳读          |
| 6   | dev 的 HMR 旁路 | 可选：点名 `@morlay/*` 走 vite 逐文件（改它要热更），其余一律联邦                                                                                                | 热更是开发期的局部收益，不该成为整条链的第二形态                                  |
| 7   | 缓存            | 联邦缓存与产物目录**同一语义、只换目录**：dev 写 `<dataDir>/cache/client-modules`，build 直接写 `<outputDir>/client_modules`                                     | 一份算法两处落点，读代码的人不必先分辨「这是哪种缓存」                            |
| 8   | node 侧入口     | **源码面** `src/server.ts`，由 `@morlay/dsh-oxc-node` 直接跑；不再打 `entry.mjs` 单文件                                                                          | 闭包里本来就有 loader；少一次 rolldown，也少一份「只有打包时才炸」的错位          |
| 9   | 页面骨架        | `index.html` 进 `client_modules/`，`src/` 只留 server 侧源码                                                                                                     | 前端产物自包含在一个目录里                                                        |
| 10  | 环境事实        | `AppEnv` 是唯一来源：`profileDir`（装配根）/ `dataDir`（数据根）/ **`defaultWorkingDirectory`**（新会话起始目录）；`process.cwd()` 只在它的构造里出现一次        | 装配面逐层传路径参数，等于把同一事实抄 N 份，抄漏一处就是路径分叉                 |
| 11  | 部署值          | **写进 `bootstrap.mjs`**（构建期确定的：`profileDir` / 产物根 / 形态）与它的启动参数（可变的：`--data-dir` / `--port`）；不另立配置文件                          | `bootstrap.mjs` 本身就是部署值 + 装配的代码，再存一份 JSON 就是同一事实两个 home  |
| 12  | dev 的启动机制  | dev 也生成 `<工作区>/node_modules/.zephyr/<port>/bootstrap.mjs`：dev 与 prod 走**同一个**启动机制，差别只在它 import 的是源码面 `src/server.ts` 还是产物里的那份 | 两条启动路径 = 两套排查方式；按端口分目录便于多开对照                             |

## 二、现状事实

- 构建三步在 `zephyr-cli/src/build/builder.ts`（**已按本设计改形**）：`buildClient`（`compile()` → `<outputDir>/client_modules`）、
  `buildRuntime`（`pnpm deploy --prod` 到临时目录、只把 `node_modules` 搬进 `<outputDir>/node_modules`）、
  `assembleEntry`（复制 `src/` 源码面入口、写 `package.json` 与 `bootstrap.mjs`、删 `src/client`）。`bundleEntry` 已删。
- 这些构建件**已经不在了**（T2）：`zephyr-app` 的 `dependencies` 里没有 `vite` / `chokidar` / `lightningcss`、
  `peerDependencies` 里没有 `rolldown`（判据 `zephyr-app/src/__tests__/dev-deps-absent.spec.ts`）；
  它们连同"按请求产出联邦产物"的实现一起住进 [`zephyr-dev`](../../zephyr-dev/README.md)。
- 实测规模：`pnpm deploy --prod` 闭包 **928M / 923 个包**；现行 `dist/` **14M**。
- 实测可行性（本机探针）：`bundlePackage({ input: { client: apps/zephyr-custom/src/client/app-boot.ts } })` 产出 **6.8KB** 的 `client.js`，
  外部依赖 9 条 `/_zephyr/@modules/…`，无相对 import、无 assets/chunks 引用——应用入口可以是一个普通联邦目标。
- 实测可行形态：`target/<app>/{package.json, node_modules → 闭包, src/, client_modules/}` 里用
  `node --import <loader> --input-type=module -e 'await import("./src/server.ts")'` **能加载**（导出 `default` 是函数）。
- loader 在闭包里：`runtime/node_modules/@morlay/dsh-oxc-node` 存在，所以产物自带启动器。
- vite 8 下「循环 re-export 报错」这条理由**不成立**（vite / rolldown / esbuild 里都没有该措辞，构造的循环包两种形态都不报），
  见 `.scratch/dev-build-research/notes.md`；`dev.include` 因此只剩「哪些包要 HMR」这一条产品含义。

## 三、模块边界与接口

结论：`zephyr-dev` 是**一个能独立启动的服务**（开发运行时），也是**构建器**；`zephyr-app` 只留运行时与两条空契约；
`zephyr-cli` 只做命令编排。`zephyr-dev → zephyr-app` 是允许的方向（它要 `WebServer` / `AppEnv` 才能起服务）。

| 模块         | 拥有（职责与不变量）                                                                                                                                         | 不拥有（明确排除）                                                                                                                   | 依赖方向                 | 接缝 / 适配器                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------ |
| `zephyr-dev` | **开发运行时**：自己起 http 服务与 vite、按请求产出联邦产物；**构建器**：解析规则、`compile()` 写前端产物、build 时生成生产态装配文件                        | 域行、命令树、node 侧闭包（`pnpm deploy` 归 CLI）                                                                                    | → `zephyr`、`zephyr-app` | `startDev(options)` / `compile(options)` / `devProviders(mode)` / 生成的 `bootstrap.mjs`               |
| `zephyr-app` | 运行时（宿主与浏览器双态）：web server 与路由表 / connection / remote / api-gateway / 渲染骨架 / `AppEnv` 部署参数；两条**空契约**：`ClientAssets`、`DevHmr` | 任何开发态实现：页面兜底（`ServeDefault`）、联邦路由、vite/rolldown/chokidar 依赖、预编译、node 运行时补强（`@oxc-project/runtime`） | ← `zephyr` 的 DSL        | `ClientAssets.serve(req,res)`（dev 由 `zephyr-dev` 实现，prod 读 `client_modules/`）；`DevHmr.install` |
| `zephyr-cli` | 命令与编排、工作区配置解析、布局与数据根、运行模式（部署值）、`pnpm deploy` 闭包                                                                             | 构建算法细节、服务运行时                                                                                                             | → `zephyr-dev`           | `layoutOf` / `resolveDataDir`                                                                          |

**依赖方向**：`zephyr-cli → zephyr-dev → zephyr-app → zephyr`。不为「运行时产物里不能有构建器」在此设限——
隔离靠**产物**：`client_modules/` 与 `node_modules/` 闭包都检查不到 `zephyr-dev`（判据见五）。

这条方向是**单向且必须单向**：`zephyr-app` 不能声明对 `zephyr-dev` 的依赖（哪怕只为再导出）。
`pnpm -r` 的任务图一旦成环就整体拒跑（`ERR_PNPM_TASK_CYCLE`），`just audit` / `just build` 表现为
「没有任何包报告」——判据假红，最容易被误读成工具坏了。所以搬完之后 `zephyr-app` 的旧出口
（`./build`、`./node`、`./federation/prebundle(-plan)`）**直接删掉**，装配面改指向 `@morlay/zephyr-dev`。

**布局**（`ZephyrLayout` 的目标形状；根由 `server.outputDir` 给，缺省 `target/<应用名>/`）：

```
<outputDir>/
  client_modules/      静态前端：index.html + 按包的联邦产物（<pkg>@<ver>/*.js + .files.json）
  node_modules/        宿主闭包（pnpm deploy --prod，含 @morlay/dsh-oxc-node）
  src/server.ts        应用清单（源码面：导出 (mode) => ProviderList）
  bootstrap.mjs        生产态装配（build 生成；见「四、行为与边界」）
  package.json         应用清单（type: module、files）
```

**`node_modules/` 闭包的形态**（判据要照它写，别按直觉猜）：

`pnpm deploy --prod` 装出来的是一份**实体闭包**，不是指回仓库的软链：

```
<outputDir>/node_modules/
  @morlay/zephyr -> ../.pnpm/@morlay+zephyr@file+…/node_modules/@morlay/zephyr
  .pnpm/…            真正的实体副本（按依赖图装齐）
```

两层含义，都影响判据：

1. **在 `<outputDir>` 原地跑就是它自己的解析面**：loader 与所有依赖都在闭包里，不需要复制到仓库外去证「自包含」，
   也不需要断言「解析路径必须以 `<outputDir>/node_modules` 为前缀」——`.pnpm/` 那一段是 deploy 的正常形态，不是缺陷。
2. **闭包里的包 ≠ 预编译清单里的包**：`deploy` 沿依赖图带齐（`shiki` 在闭包里），而 `planPrebundle` 从应用的
   `src/client/app-boot.ts` 出发、只跟静态 import，到 `@morlay/*` 包边界就停——它看不到 `dsh-client-ui-primitives/src/markdown/highlight.ts`
   里的 `import 'shiki/core'`。所以「`createRequire(应用清单).resolve('shiki/package.json')` 返回 `undefined`」是**预期**的：
   应用清单没声明它，不是它不在盘上。判定「清单缺包」要按枚举范围查，不能按解析成败查。

**dev 不落这种目录**：`zephyr dev` 在**进程内**把 `devProviders()` 叠在应用清单之前装配（见 §四），
不生成 `bootstrap.mjs`、也不建按端口分的目录。dev 与 prod 共用的是**同一条清单函数签名**
（`(mode) => ProviderList`）与同一个启动结果（一棵行树），不是同一个文件。

可重建的中间物只有 vite 缓存：`<dataDir>/cache/vite`（与 `AppEnv.cacheDirOf("vite")` 同一处），整目录可删。

**三条空契约**（都只声明、不含实现，`zephyr-app` 侧零构建依赖）：

| 契约           | 签名                                                                        | 谁实现                                                                                                    | 谁消费                     |
| -------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------- |
| `ClientAssets` | `serve(req, res): Promise<boolean>`；`transformHtml(html): Promise<string>` | dev：`zephyr-dev`（vite + 按请求联邦）；prod：`zephyr-app` 的静态目录投递（读 `client_modules/`，无构建） | `ServeDefault`（页面兜底） |
| `DevHmr`       | `install(hooks)`：`hooks.restart(files)` 是唯一的入参；返回撤销函数         | dev：`zephyr-dev`；prod：不装                                                                             | `dev` 命令（换树）         |
| `IdleGuard`    | `isIdle()`（**多值**令牌，`inject.all`）                                    | 各域自己装：`dsh-agent`（开着的 turn）、`dsh-job`（跑着的后台任务）                                        | `DevHmr` 的实现汇总        |

**形态由启动器注入，应用源码零形态痕迹**：`server.ts` 只写域行，不写 `mode.dev ? … : …`；
`zephyr dev` 把 `devProviders()` 叠在应用清单**之前**，`build` 把生产态装配写进 `bootstrap.mjs`。

**契约变更**：

| 契约                                | 现在                                              | 谁必须跟着改                                                                                                                                                       |
| ----------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ZephyrServerConfig`                | `{ entry }`                                       | 加 `outputDir`（缺省 `target/<应用名>`）：产物根从它算，不再写死在 `layoutOf`                                                                                      |
| `ZephyrLayout`                      | `{root, dist, runtime, cache, entry}`             | 换成 `{root, clientModules, nodeModules, serverEntry, bootstrap, manifest, deploy}`                                                                                |
| 静态资源投递                        | `ServeDefault` 直接持 `ViteHandoff`               | **已落地**：`ClientAssets` 空契约留在 `zephyr-app`，`ServeDefault` + `WebServe` 契约 + `provideHttp()` 全部搬到 `zephyr-dev`（页面要认 `/@fs` 与 `/@vite/client`） |
| dev 换树                            | `ServerHmr` + `CustomDevLifecycle` 两处适配       | **已落地**：`DevLifecycle` 整个删除（`dev` 命令直接 `tryGet(DevHmr)` 并 `install({ restart })`）；业务空闲判据由各域装的 `IdleGuard` 汇总，装配面不写任何域知识 |
| `AppEnv.appBootDir` / `packageRoot` | `AppEnv` 上的两个成员                             | **已删**：页面骨架与 vite root 是开发态事实，改由 `zephyr-dev` 的 `appBootDirOf(profileDir)` 推；包根由 `devPackageRoot()` 推。`AppEnv` 只留两种形态都成立的值     |
| `provideClientModules()`            | 在 `zephyr-app` 里，含 `ViteHandoff`/`Federation` | 拆：`zephyr-app` 只出 `provideHttp`/`provideWeb`；开发与联邦的行由 `zephyr-dev` 的 `devProviders()` 给                                                             |

## 四、行为与边界

**dev**：`zephyr dev` 装配**一棵**树（不再有「CLI 树 + 应用树」两棵）。清单 = `devProviders(mode)` + 应用 `server.ts` 的清单，
后者是 `(mode) => ProviderList`，`zephyr-dev` 起自己的 http 服务与 vite，把端口写回 `CliMode`。请求先到 `ClientAssets`：
命中 HMR 名单的包走 vite 逐文件，其余按包返回联邦产物（未命中则现算并落 `<dataDir>/cache/client-modules`）。
改源码 = 该包产物失效重编译；服务端源码变更 → `DevHmr.restart` → dispose 整树、带新 `?v=` 重新 import 清单；
换树只在该域都说空闲时发生（`IdleGuard`：开着的 turn、跑着的后台任务都把换树按住）。

**build**：`rm -rf <outputDir>` → `pnpm deploy --prod --config.inject-workspace-packages=true` 到 `node_modules/` →
`compile()` 把应用 client 图与入口打到 `client_modules/` → 复制 `src/server.ts`、写 `package.json` →
生成 `bootstrap.mjs` → 冒烟：复制到仓外、用闭包里的 loader 起 `bootstrap.mjs`。

**静态前端**：`client_modules/` 里只有文件，没有任何「服务」。`compile()` 结束后它就定型了：

```
client_modules/
  index.html                     页面骨架（入口 script 指向应用入口的联邦地址）
  zephyr-custom@0.2.2/client.js  应用入口（6.8KB，9 条外部地址，零资产）
  @morlay+zephyr@0.0.1/index.js  按包的联邦产物（URL 与磁盘路径一一对应）
  …/.files.json                  每个包的产物清单（资产与 chunk 的文件名在它里面）
```

生产态的服务只做两件事：把 `/_zephyr/@modules/<pkg>@<ver>/<file>` 映射到磁盘上的同名相对路径；
其余按静态文件投递（`.js` → `text/javascript`，`.css` / 字体 / 图片按扩展名）。**没有编译、没有缓存失效、没有 vite**。
`?v=` 是 URL 的一部分但只用于浏览器缓存区分，服务端忽略它。

**`bootstrap.mjs`（生产态装配，build 生成）**：内容见[八、部署值](#八部署值)（那里是唯一一份，避免同一段代码两处维护）。

为什么生成而不是写进 `src/server.ts`：生产态的行（静态目录投递、部署值绑进 `AppEnv`）由 `zephyr-app` 提供，
**不引 `zephyr-dev`**；而应用源码不该知道自己在生产态。生成这个文件 = 把形态判断从应用源码挪到构建产物。
`preview` 只认它；`dev` 不生成也不读它。

**preview**：只吃 `<outputDir>`，启动前校验 `client_modules/` 与 `bootstrap.mjs` 齐全（缺则 `CliError`，不回退到现场编译）。

**错误**：清单为空 / 缺已知包 / 产物缺失都是构建失败，不静默降级。

**回收**：`<outputDir>` 整目录可删；`<dataDir>/cache/client-modules` 整目录可删（下次按需重建）。

| 7   | 缺产物时 preview 报错退出，不静默重建                                      | `preview` 的装配级用例      | 删一个产物目录再看退出码                                                       |

## 六、取舍

- **不用 `pnpm deploy` 之外的办法解决 node 侧**：已经完全打通过一次，闭包 928M 是体积代价但换来「零自研模块装载」；
  全打包成单文件实测 16.2MB 仍留 `koffi` / `node:sqlite` / `@vitejs/devtools/*` 逃逸，反而多一份名单要维护。
- **不打 `entry.mjs`**：闭包里本来就有 loader，源码面入口少一层 rolldown，也让 stack trace 指向真实文件。
- **prod 的静态前端就是联邦产物**（而不是 vite build 出一个打包后的 bundle）：接受首屏请求数多，换 dev/prod 只有一种形态，
  且产物是可逐个文件核对、可按包替换的目录。
- **保留 HMR 旁路**：不追求「纯粹一种形态」到丢掉热更；旁路是开发期的局部，不参与产物。
- **vite 的 optimizeDeps 不作为主链**：它的 key 是裸说明符字符串，同名多版本会塌成一份（`zod@4.4.3` 静默变成 4.6.6），
  而我们要把版本写进 URL；CJS 具名导出也依赖「请求方由 vite 转译」这一条。详见调研笔记。

## 七、不做与已知债

- 不做「node 侧零 node_modules」的打包（见取舍）。
- 已知债：`target/` 里 `node_modules` 928M，分发体积大；销账条件是出现按包增量装载的方案。
- 已知债：dev 的联邦缓存与 build 的产物目录是两份字节（同算法不同落点），磁盘占用翻倍；
  销账条件是 build 能直接复用 dev 的缓存目录而不破坏「target 自包含」。

## 八、部署值

两个来源，按「变不变」分：

| 部署值                                         | 谁给                                          | 为什么                                                           |
| ---------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------- |
| `profileDir` / 产物根 / 形态                   | `bootstrap.mjs`（构建期写死）                 | 由构建决定，运行期不该有机会猜错                                 |
| `dataDir` / `port` / `defaultWorkingDirectory` | 启动参数（`--data-dir` / `--port` / `--cwd`） | 用户会改：同一份产物要能在不同机器、不同数据根、不同项目目录上跑 |

不另立配置文件（`zephyr.json` 已从这个方案里删掉）：`bootstrap.mjs` 本身就是「部署值 + 装配」的代码，
再存一份 JSON 等于同一事实两个 home，且两者不同步时以谁为准没有答案。

`bootstrap.mjs` 因此长这样（值在 build 时内联，可变项从参数来）：

```js
// 由 zephyr build 生成，不是源码。
import providers from "./src/server.ts";
const PROFILE_DIR = new URL("./", import.meta.url).pathname; // 构建期确定的产物根
// 启动参数 `--cwd` 覆盖；缺省是进程 cwd（从哪个项目目录启动，就在哪儿干活）
const DEFAULT_WORKING_DIRECTORY = process.cwd();
process.chdir(DEFAULT_WORKING_DIRECTORY); // 上游那些读 cwd 的行在这里收口
export default async function (mode) {
  const { bootstrapApplication } = await import("@morlay/zephyr");
  const { productionProviders } = await import("@morlay/zephyr-app");
  return bootstrapApplication({
    providers: [
      ...productionProviders({
        ...mode,
        profileDir: PROFILE_DIR,
        defaultWorkingDirectory: DEFAULT_WORKING_DIRECTORY,
      }),
      ...providers(mode),
    ],
  });
}
```

`src/client` 在 build 之后**删除**：前端源码已在 `client_modules/` 的产物里，留着等于分发源码。
排查时代价是产物里看不到原始 `.tsx`，接受。

## 九、环境事实的唯一来源（`AppEnv` 兜住 cwd、默认工作目录与环境变量）

结论：`AppEnv` 是**唯一**回答「我在哪个目录、数据在哪、新会话从哪开始」的地方；其余代码（含上游行）只读它给的派生值，
装配面不再逐层传路径参数。

**`AppEnv` 的字段**（新增两项，`profileDir` / `dataDir` 不变）：

| 字段                      | 语义                                            | 缺省                      | 谁读                                                                      |
| ------------------------- | ----------------------------------------------- | ------------------------- | ------------------------------------------------------------------------- |
| `profileDir`              | 装配根（`package.json`、依赖解析、产物根）      | `process.cwd()`           | 页面骨架、`node-stub`、闭包里的 loader                                    |
| `dataDir`                 | 数据根（DSH_HOME）：会话 / 设置 / 凭证 / 缓存   | `<profileDir>/.dsh-store` | 各域、`cacheDirOf`                                                        |
| `defaultWorkingDirectory` | **新会话 / agent 的起始目录**（「从哪儿开始」） | `process.cwd()`           | `WorkingDirectory.defaultDirectory`、`SandboxPolicy.workspaceRoot` 的缺省 |

**为什么 `defaultWorkingDirectory` 不复用 `profileDir`**：打包形态的 `profileDir` 是 `Resources/runtime`（只读、在包内），
agent 绝不该在那儿干活；而起始目录是「用户从哪个项目启动的」。两者在 dev 下恰好同一个值，在打包下不是。

**`process.cwd()` 只在 `AppEnvDefault` 的构造里出现一次**（连同 `dataDir` 的缺省）。其余任何地方读 cwd 都是错的。

**现状里违反这条的地方**（本层自己能改的）：

| 位置                                                 | 现在                                     | 改成                                                                |
| ---------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| `dsh-sandbox/src/sandbox.provide.ts` 的 `DEFAULTS`   | `workspaceRoot: process.cwd()`           | `inject(AppEnv).defaultWorkingDirectory`（仍可经 `configure` 覆盖） |
| `dsh-agent/src/server/working-directory.provide.ts`  | `defaultDirectory: process.cwd()`        | `inject(AppEnv).defaultWorkingDirectory`（仍可经 `configure` 覆盖） |
| `dsh-workspace/src/default-workspace.service.ts`     | `process.cwd()` 兜底                     | `AppEnv.defaultWorkingDirectory`                                    |
| `dsh-workspace/src/server/session-workspace.host.ts` | `request.cwd ?? process.cwd()`           | `request.cwd ?? AppEnv.defaultWorkingDirectory`                     |
| `configurable-sandbox/src/sandbox-rules.service.ts`  | `cwd: process.cwd()`                     | 同上                                                                |
| `apps/zephyr-custom/src/zephyr.provide.ts`           | 模块级 `appRoot` + 逐层传 `dataDir` 参数 | 删掉两者：`AppEnv` 由启动器给，下游从 `inject(AppEnv)` 派生         |

**两个下游配置仍各自可覆盖**：`SandboxPolicy.workspaceRoot` 是「能写哪儿」、`WorkingDirectory.defaultDirectory` 是「从哪儿开始」，
语义不同；只是**缺省**来自同一个 `AppEnv.defaultWorkingDirectory`。装配面要收紧沙箱（只读）时不必改起始目录。

**上游侧的 cwd / env：只收口，不改**。`vendor/**` 是只读副本，上游生产代码里的 `process.cwd()` 兜底与 `process.env` 读取
（`claude-code-mods`、`hooks-*`、`app-boot`、`pwsh-local`、`relay-fetch`、`llm-pi-ai`）保持原样。
我们的责任边界是**自己体系内一致**：`AppEnv` 一处定事实，`bootstrap.mjs` 起手 `process.chdir` 让上游读到的 cwd 是我们要的那个；
上游行要的值由装配面显式传进它们的配置。不为对齐上游去改 vendor，也不为它加第二套路径来源。

**`DSH_HOME` 的归属**：上游 `@deepseek-ai/dsh-home-paths` 把 `DSH_HOME` 当数据根覆盖。
我们的 `AppEnv.values.dataDir` 是同一件事的本地事实——两者不并存：装配面算好 `dataDir` 后，上游那些行读到的是我们显式给的值。
