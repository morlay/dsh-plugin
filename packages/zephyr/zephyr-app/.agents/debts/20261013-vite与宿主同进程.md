# vite dev server 与宿主同进程

状态：未销账（接受中，只在 dev 形态）——vite 起在宿主进程里，它的崩溃就是宿主的崩溃。
位置：`packages/zephyr/zephyr-app/src/internal/serve-vite.ts`（`startViteDev`）、`packages/zephyr/zephyr-app/src/vite-handoff/vite-handoff.service.ts`。

**现象**

dev 形态（`just custom dev` → `zephyr dev`）把 vite 的 dev server 起在**宿主进程内**：`server.middlewareMode: true`，`WebServe` 把请求直接交给它，HMR 的 upgrade 也挂在同一个 http server 上。

同进程的两条已知代价：

- vite 的原生绑定（rolldown / lightningcss）崩一次是 segfault，宿主跟着没了——用户看到的是「整个服务被打挂」，而不是「页面热更新失效」。
- 为了让 vite 别自己重启（`restart()` 会连带拆掉宿主），配置只能全内联：`configFile: false`、不监听 `vite.config.*`。

**影响**

- 只有 dev 形态：build 形态吃的是联邦产物，没有 vite。
- 撞上时是**偶发**的（原生绑定 + 特定输入），表现是进程消失、端口不再监听；重启一次即恢复，没有残留状态。
- 因为 `configFile: false`，应用想改 vite 配置只能经 `zephyr.config.ts` 的 `client.vite` 内联对象——那是设计，不是这条债的代价。

**触发条件**

- 要动 dev 形态的进程模型（把 vite 挪出宿主进程）之前，先解这条。
- 要让 vite 读 `vite.config.ts`（那会打开它自己的 `restart()` 路径）之前，先解这条。

**销账条件**

Done when：vite 跑在自己的进程或 worker 里、宿主经代理转发请求与 upgrade，且 `just custom dev` 的页面渲染与 HMR 仍按[how-to-e2e](../../../../../.agents/standards/how-to-e2e.md) 的判据通过（vite 崩了宿主还在，重启子进程即可恢复）。

**不修的理由**

- 隔离要引入一层代理与子进程生命周期管理（含 HMR 的 ws 归属），复杂度不小，收益只在 dev 形态的偶发崩溃上。
- 崩溃可恢复、只影响开发者本机，不影响装出来的产物。
