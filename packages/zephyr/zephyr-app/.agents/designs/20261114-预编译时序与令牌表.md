# 预编译时序与令牌表：为什么 ZEPHYR_DESKTOP_PACKAGED=1 缺 config-forms（分析，未实施）

状态：分析完成——结论是「不是清单顺序问题，是模块实例/令牌表问题」，验证手法留在 §四。
范围：装配内核的 apply 顺序 vs client-modules 预编译的模块图；只回答 config-forms 这一条。
非目标：CSS 子路径、CJS 互操作（各自另有记录）。

## 一、三个问题与回答

| 问题                                              | 回答                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `provide` 的注册发生在模块求值还是 kernel apply   | **kernel apply**：`provide([...])` 只是返回清单（纯数据）；真正的服务注册在 `bootstrapApplication` 里对每行 `ctx.reflect.provide(名字, 实例)`，位置在**该行的 apply loop 内**                                                                            |
| `LocaleDefault` 的 `inject(ConfigForms)` 何时解析 | 该行被 apply 之前：内核先按 `inject` 声明做拓扑排序，再逐行 `fillInjections`（把占位换成实例）→ 最后 `ctx.plugin` 跑 `onInit`。所以"解析时刻"= **本行 turn**，不是模块加载时                                                                             |
| 普通模式为什么能跑                                | 同一份清单 + 同一份 `@morlay/zephyr` 模块实例：令牌表（`token.ts` 的模块级 `Map`）只有一张，拓扑排序按声明生效，`SettingsHost` 排在链之前                                                                                                                |
| 预编译模式为什么缺                                | **令牌表不止一张**：`clientModules.include` 清空后整块 client 半被 prebundle 成独立产物，prebundle 内的 `@morlay/zephyr` 与页面图里那份是**两个模块实例** → `tokenMetaOf(ConfigForms)` 在两张表里给出**不同的令牌对象** → `inject(ConfigForms)` 解析不到 |

## 二、代码级证据

- `packages/zephyr/zephyr/src/bootstrap.ts`：`orderByDependencies(rows)` 按 `inject` 声明排序；每个行 `fillInjections(...)` → `ctx.plugin({ apply: onInit })`。注册与回填都在这一层，**没有任何一处在模块求值时注册服务**。
- `packages/zephyr/zephyr/src/provider.ts`：`provide(list, defaults)` = `(...features) => features.reduce(...)` —— 纯数据，无副作用。
- `packages/zephyr/zephyr/src/token.ts`：`registered` / `byName` 是**模块级 `Map`**；设计记录里已写明「同一进程里存在两份 zephyr 就是两张表——`tokenMetaOf` 对未登记的类只按类名派生，`multi` / `alias` 丢失」（`20261104-zephyr-是-cordis-plugin-的语法糖.md` 二·令牌表在模块里）。
- `federation.service.ts`：预编译把每个包（含 `@morlay/zephyr-app` 的 client 半）打成独立产物，产物之间按联邦地址引用；`@morlay/zephyr` 若被**内联**进某份产物，它就不再是页面图里那一个实例。

## 三、结论

- **不是「清单顺序 + 模块图顺序不同构」**：内核的 apply 顺序只由清单里每行的 `inject` 声明决定，与模块怎么加载无关；两种形态用的是同一份清单。
- **是「同一份 zephyr 被装了两遍」**：令牌身份按对象/模块实例判定，两张表 → `inject(ConfigForms)` 拿不到。
- 因此不需要在 client-modules 的入口图上加"注册顺序"约束；需要的是**让 `@morlay/zephyr`（以及任何持有模块级状态的包）在页面图里只有一个实例**：预编译把它当 external 指回页面侧同一 URL，而不是内联。

## 四、验证手法（下一步一条命令）

起 `ZEPHYR_DESKTOP_PACKAGED=1 just custom dev`，在浏览器控制台取两处拿到的令牌对象比较身份：
`import("/_zephyr/@modules/@morlay+zephyr@0.0.1/index.js").then(m => m.Injectable)` 与页面图里的同名导出——不相同即坐实"两份实例"。
或者更直接：在 `fillInjections` 里临时打印 `tokenMetaOf(placeholder.token).name` 与表大小（打点写完即删）。

## 五、与清单顺序无关（澄清）

- **清单顺序不是根因**：内核按每行的 `inject` 声明排序后逐行回填，两种形态共用同一份清单；`provideSettingHost` 的拆分保留是**契约清晰化**（谁提供 `configForms` 写在一处），**不是**本 bug 的修复。
- **本 bug 的修复是单实例**：`@morlay/zephyr`（令牌表）与 `@morlay/zephyr-app`（`InjectionToken` 身份）在页面图里只能有一份——预编译把它们预先放进外置名单（`bundle.ts` 的 `resolvable` + `esmExternalRequirePlugin`），改成联邦地址而不是内联。
- **判据**：预编译跑过一次后 `grep -rl "morlay.zephyr.inject" apps/zephyr-custom/.dsh-store/cache/client-modules` 只剩 `@morlay+zephyr@*/index.js`（`compat.js` 若同被单实例化则只 1 份），`@morlay+zephyr-app@*/client.js` 不再命中。
