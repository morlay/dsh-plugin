## 一、决定（提案）

| #   | 议题           | 提案                                                                                                                                          | 一句话理由                                                                                              |
| --- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1   | CJS→ESM 互操作 | **删掉自研 `cjsShimOf`**，交给 rolldown 的 CJS 转换 + `output.exports: "named"` / `output.interop`                                            | 手写"求值 CJS 入口补具名导出"在子路径、版本、副作用上连出错，而这是打包器的本职                         |
| 2   | 入口解析       | 用 `createRequire(import.meta.url).resolve(specifier)`（或 `import.meta.resolve`）代替 `exportTargetOf` + `fileInPackage` 的猜扩展名          | 原生解析**尊重 `exports` 条件**（`import`/`default`/`require` 与子路径），不用我们维护三种 exports 形状 |
| 3   | 包根/版本      | `rootOf` 以"引用方解析到的实际那份"为唯一事实（`findPackageJSON(name, from)` / `createRequire(from).resolve`），版本取它自己的 `package.json` | 同一名字多份副本时，缓存键与产物都该按"实际被引用的那份"                                                |
| 4   | 若原生仍不够   | 退回 **Vite 的 deps optimizer**（`optimizeDeps` / rolldown 的 CJS 插件）作为预构建器，而不是继续加 shim                                       | `needsInterop` / `commonjsOptions` 是这条路上被验证过的实现                                             |
| 5   | `cssShimOf`    | **保留**                                                                                                                                      | 那是 CSS 入口特例（vite 库模式不允许 `.css` 作 input），与 CJS 无关                                     |
| 6   | 判据           | 加一条"具名导出"用例：`use-sync-external-store/shim/with-selector` 的产物必须含 `useSyncExternalStoreWithSelector`                            | 这条用例就是当前 bug 的最小复现                                                                         |

## 二、现状事实

- 我们的预编译**直接用 rolldown 库 API**（`bundle.ts:20` `import { rolldown }`），没有走 vite 的 build / optimizeDeps。
- `cjsShimOf`（`bundle.ts:507-552`）的注释自陈动机："rolldown 对 CJS 入口产物的具名导出只能靠静态分析；`module.exports = require(…)` 与 UMD 包装它都分析不到"——于是改成**求值一次 module.exports 拿键**，再 `export const <键> = __cjs[键]`。
- 入口解析（`internal/resolve.ts`）：`exportTargetOf` 手写三种 `exports` 形状 + `module`/`main` 回退；`fileInPackage` 按 `.js/.cjs/.mjs + /index.*` 猜扩展名。
- 包根解析（`federation.service.ts::rootOf`）：先直拼 `<profileDir>/node_modules/<name>/package.json`，再走 `findPackageJSON`；同一名字多份副本（`use-sync-external-store` 同时装 1.6.0 与 1.7.0）时会命中陈旧那份，缓存键随之写成旧版本。
- 已出现的症状：子路径 `shim/with-selector` 的产物导出的是主入口符号；缓存键 `@1.6.0` 与实际 `1.7.0` 不符。

## 三、三条路线对比

| 维度                 | A. rolldown 原生（`output.exports: "named"` + `interop`）             | B. Vite deps optimizer（`optimizeDeps`）                            | C. 自研 `cjsShimOf`（现状）                   |
| -------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------- |
| CJS 具名导出         | 由打包器静态分析 + 运行时命名空间生成；嵌套 `require` 由 CJS 插件处理 | esbuild/rolldown 的 CJS 转换，`needsInterop` 决定是否包一层默认导出 | 我们求值一次 module.exports 拿键              |
| 子路径               | 走 `createRequire().resolve` 后按文件打包，不依赖"出口名"约定         | 以 `optimizeDeps.include` 的说明符为单位                            | 需要我们自己把子路径解析对（当前出错点）      |
| 副作用 / 单例        | rolldown 保持模块单例与 side-effect 语义                              | 同样是模块图，且与 vite dev 一致                                    | 求值 CJS 会产生一次真实副作用（可能重复执行） |
| dev 与 packaged 一致 | 需要两条链都切到同一套                                                | **天然一致**（vite dev 与 build 都走它）                            | 只有我们自己在跑，vite 侧另有一套             |
| 维护成本             | 低（配置 + 解析）                                                     | 中（引入 vite 的预构建器与缓存约定）                                | 高（每遇一个包就加一条规则）                  |

## 四、`use-sync-external-store/shim/with-selector` 在原生机制下的预期

- 入口：`createRequire(profileManifest).resolve("use-sync-external-store/shim/with-selector")` → `…/shim/with-selector.js`（CJS，`module.exports = require('./cjs/…')`）。
- rolldown 以该文件为 entry 打包 → 产物 **`export default` + 具名 `useSyncExternalStoreWithSelector`**（命名导出由 CJS 转换生成），不再需要我们的 shim。
- 版本：入口解析所在包根的 `package.json` 决定缓存键（`@1.7.0`），旧 `@1.6.0` 目录自然不再命中。

## 六、取舍与开放问题

- **为什么不直接给 `cjsShimOf` 打补丁**：它解决的是"打包器本该做的事"，每补一条就多一个只在某些包上正确的规则；子路径与版本两次出错已经说明这条路不可持续。
- **A 与 B 的取舍**：优先 A（留在 rolldown，改动面小、与现有插件链同源）；只有当 rolldown 的 CJS 静态分析在某类包上确实不够（UMD / 动态 `module.exports`）时，再引入 B。
- **开放问题**：`output.exports: "named"` 与 `interop` 的具体取值要在真实产物上验（`auto` 在纯 CJS 包上可能只给 `default`）；`external`/`platform: "browser"` 与现有 alias 的交互要一并验。
- **实测（A 路线否决）**：删掉 `cjsShimOf` 后跑最小复现 `use-sync-external-store/shim/with-selector`——`version=1.7.0`、`cacheKey=use-sync-external-store@1.7.0`、`files=shim/with-selector`、`namedExport=false`；`interop: "auto"` 与 `"esModule"` 同样是 false（`bundle.spec` 的 CJS/UMD 用例同时红）。结论：rolldown 1.2.16 对 `module.exports = require('./cjs/…')` 给不出具名导出，**A 不可行**——`cjsShimOf` 保留，B（Vite deps optimizer）作为后续选项。

## 七、已知噪音：`CONFIGURATION_FIELD_CONFLICT`（接受）

- **现象**：预编译跑 rolldown 时逐文件打印 `compilerOptions.experimentalDecorators from tsconfig.json is overridden by legacy from transform.decorator`。
- **为什么接受**：`decorator: { legacy: true }` 是必需的——实测去掉它后，住在 `node_modules` 里、祖先链没有 tsconfig 的包不再降级装饰器（`bundle.spec` 的「没有 tsconfig 祖先」用例直接红：产物里还留着 `@Remote`）。两处都写同一件事，rolldown 就会告警；去掉任何一处都要付上面那个代价。
- **影响**：纯噪音，转译结果正确（`legacy` 胜出，与项目 `experimentalDecorators: true` 语义一致）。
- **销账条件**（任一即可）：① rolldown 提供关闭该诊断的开关；②「最小 tsconfig」方案验证过 `paths` / `include` 不丢（构建期生成一份不含 `experimentalDecorators` 的 tsconfig 给 `resolve.tsconfigFilename`，装饰器仍靠 `legacy` 选项降级）。在此之前不为它生成 tsconfig、不改 `resolveTsconfigPath()`。
