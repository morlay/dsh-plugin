| 现象                      | 事实                                                                                                                                                                                                                                                                 | 影响                                                                        |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 命名两套                  | 只有 `settings` / `webServer` 显式对齐上游；`remote` / `slots` / `locale` / `typert` / `typertGateway` / `remoteAccess` / `connection` 都用派生名（`remote` / `slots` / `locale` 与上游**同名纯属巧合**，`typert-gateway` / `remote-access` 与上游驼峰名**不一致**） | 宿主已发布同名服务时，装配器认不出「已提供」，于是重复 mount 或永远 pending |

| 能力无 owner              | `DevHmr` / `IdleGuard` / `ContextMenus` / `Layout` / `Shortcuts` / `Theme` / `ClientAgentScopes` 只有契约没有实现                                                                                                                                                    | 「没有提供者」类报错会出现在装配期，而不是由组合选择规避                    |
| endpoint 散在四处         | wire 协议在 `remote/**`（6 文件）、`api-gateway/**`（9 文件）、`api-remotes/**`（2 文件）、`client/remote/**` 各有一部分                                                                                                                                             | 同一件事被拆成四份，消费方不知道从哪引                                      |

## 边界：框架只出通用挂载机制，不装任何业务组

`remote` 那一面（`Remote.$mount` / `remoteDescriptorsOf` / `@RemoteGroup` / `@RemoteMethod`）是**机制**；
具体的组（`session` / `workspace` / `workspaceFiles` / `job` / …）是**业务的 wire 契约**，归各自的域：

| 东西 | home |
| --- | --- |
| `@RemoteGroup` / `@RemoteMethod` 装饰器、`Remote.$mount`、`remoteDescriptorsOf`、`RemoteDefault` | 框架（`zephyr-app`） |
| 组的契约类（`@RemoteGroup({ name })` + `@RemoteMethod()`）、宿主实现（`registerRemoteGroup`）、客户端挂载行 | 组所属的域（`dsh-session` / `dsh-workspace` / `dsh-job` …） |

两条由此派生的硬判据：

1. **wire 描述符只有一个来源：我们自己的 `@RemoteGroup` 契约。** 客户端挂载写
   `remote.$mount(remoteDescriptorsOf(<组契约>))`，与宿主侧 `registerRemoteGroup(实现)` 同一份声明；
   **不 `$mount` 上游的 `TYPERT_REMOTE`**——那是「上游控制器」的声明，不是我们的 wire 契约。
2. **框架里不出现业务组的契约与挂载行。** 框架侧若出现某个业务组，说明那一行该回到它所属的域；
   同理，业务域的 UI 行要跨域 UI 上下文（`uiSession` / `uiConversation` / `uiWorkspace`）时，契约与装配归
   会话界面的组装域（`dsh-conversation`），只靠本域数据面 + 框架通用令牌就能跑的独立组件留在本域。

方法名差异（客户端 API 名 ≠ wire 方法名，如 `readPage` ↔ `page`）由**契约的客户端形态**负责，
不在调用点叠别名表。
