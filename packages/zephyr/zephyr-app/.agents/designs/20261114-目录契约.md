# 目录契约（zephyr-app 的路径面：profile / data / cache / 产物 / 日志）

状态：草稿——契约成形，代码只部分满足（缺口见七），分批见五。
范围：**本包**（`@morlay/zephyr-app`）的路径面：`AppEnv` 契约与它的默认实现，以及这些值从哪些部署参数**递进来**（`CliMode`）。桌面用户数据不在这里，只留一句指针（见下）。
非目标：各域在数据根下**放什么内容**（sessions / settings / credentials 的格式归各域）；`zephyr-cli` 的 `resolveDataDir` / `layoutOf` 实现细节（本文只写它们**递进来什么**）；**桌面用户数据（桌面侧部署值）**；发布与安装布局。

## 一、决定

| #   | 议题         | 决定                                                                                                                                                             | 一句话理由                                      |
| --- | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 1   | 唯一来源     | 本包的行内只认 `AppEnv`（`values` 由装配面从 `CliMode` 转手）；实现里不读 `process.env`、不拿 `process.cwd()` 兜底、不向上找                                     | 两处各自猜一次 cwd，打包形态就对不上            |
| 2   | 装配根       | `profileDir` = 装配根（`package.json` 所在）。源码形态 = 工作区；打包形态 = 闭包根（真目录，不是 asar）                                                          | 依赖解析、`src/client`、闭包入口都按它定位      |
| 3   | 数据根       | `dataDir`（DSH_HOME）只放**宿主侧、我们自己的格式**：sessions / settings / credentials / storages / 运行期缓存                                                   | 与运行环境的 profile 目录混放后就没法只清一边   |
| 4   | 两套 cache   | 保留两套但**改名分家**：`AppEnv.cacheDir` → `runtimeCacheDir`（跟数据根走、跨进程共用）；`layout.cache`（跟产物根走、只有构建用）                                | 现在同名不同命，读代码的人以为是一处            |
| 4b  | 缓存命名空间 | 缓存根按**用途**分一层：`<cacheDir>/<namespace>`，唯一入口是 `AppEnv.cacheDirOf(namespace)`；白名单是联合类型 `CacheNamespace`（首批 `client-modules` / `vite`） | 根下散落 `<pkg>@<ver>` 目录，没人说得清哪个能删 |
| 5   | 日志         | 行日志走 stdout/stderr（`LoggerExporterDefault`），不落盘、不进数据根；要落盘另开`logsDir` 派生                                                                  | 一个出口一处名字：日志出口已经有一处            |
| 6   | 可打印       | 目录表要能一条命令打出来（`zephyr doctor`），每行带**来源**（default / config / flag）                                                                           | 调试第一句话是「它到底用了哪个目录」            |
| 7   | 桌面用户数据 | `userDataDir` 是**桌面侧部署值**，**不进 `AppEnv`**；形态默认值与接法见 `zephyr-desktop-bundle` 的包级记录                                                       | 子插件的目录不属于通用框架，底层不描述上层      |

**缓存的命名空间**（`<cacheDir>/<namespace>`；新增用途要改 `CacheNamespace` 联合类型并在这里登记）：

| namespace        | 放什么                                                 | 谁读写                                                                        |
| ---------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `client-modules` | 联邦预编译产物与 `.files.json` 清单（`<pkg>@<ver>/…`） | `FederationDefault`（`cacheRoot`）                                            |
| `vite`           | vite 的依赖预构建缓存                                  | `serve-vite`（`cacheDir` 由 `ViteHandoffDefault` 从 `cacheDirOf("vite")` 给） |

**旧缓存不迁移**：命名空间化之前直接落在缓存**根**上的那些 `<pkg>@<ver>` 目录不再被读，也不会自动删；`<cacheDir>` 的语义就是「删了只慢一次」，所以整目录删是安全的。

**两套 cache 的区别**（要改名分家的理由）：

|            | `AppEnv.cacheDir`（建议 `runtimeCacheDir`）     | `layout.cache`                              |
| ---------- | ----------------------------------------------- | ------------------------------------------- |
| 语义       | 运行期缓存：联邦预编译产物 + `.files.json` 清单 | 构建缓存：vite / rolldown 的 transform 结果 |
| 跟谁走     | 数据根（`<dataDir>/cache`）                     | 产物根（`node_modules/.zephyr/cache`）      |
| 谁写谁读   | `FederationDefault`（跨进程共用同一份）         | `buildClient`（只有构建进程）               |
| 出现的形态 | dev（宿主跑起来就写）                           | 只有 build                                  |
| 删掉的代价 | 下次启动重建（首屏慢一次）                      | 下次构建重建（构建慢一次）                  |
| 含用户数据 | 否                                              | 否                                          |

**形态矩阵**（本包相关的三种）：

| 目录         | dev                                             | build    | preview               |
| ------------ | ----------------------------------------------- | -------- | --------------------- |
| `profileDir` | 工作区                                          | 工作区   | 闭包目录              |
| `dataDir`    | `<工作区>/.dsh-store`（`dataDir: "workspace"`） | 同左     | 同左                  |
| `layout.*`   | 只用 `cache`（预构建）                          | 全量产出 | 只读 `dist` + `entry` |

**桌面用户数据不在这里**：`userDataDir` 是桌面侧部署值，**不进 `AppEnv`**（决定 7）；它在哪种形态落到哪个目录、端口偏好放哪，都由 `zephyr-desktop-bundle` 的包级记录定义。

**test 形态没有隐式默认**：用例自己给临时目录（`tmpdir()` / `tempDataDir`），不给就说明这条用例没想清落点。

**接口**（调用方要知道的）：

- 行内只认 `AppEnv`：要新目录就加一条派生（例如 `logsDir`），**不要**在行里拼字符串。
- 装配面只认 `CliMode` 与自己写进 `configure(AppEnvDefault, …)` 的值；两者冲突时以 `configure` 为准（`AppEnv.values` 是最终事实）。
- 删除语义分三种：**用户数据**（`dataDir`：删 = 重置，只能人工）、**可重建缓存**（`runtimeCacheDir` / `layout.cache`：删 = 慢一次）、**产物**（`layout.{dist,runtime,entry}`：删 = 下次构建重出）。

## 四、行为与边界

- 正常路径：`dev` 起于工作区，`dataDir` = `<工作区>/.dsh-store`，运行期缓存落 `<dataDir>/cache`；`build` 把三件产物写进 `node_modules/.zephyr`，下次构建先整目录删；`preview` 只读产物。
- 错误：`dataDir` 落进只读位置（装到只读介质上）→ 首个写盘的行失败；症状是「设置读得到、存不进去」。判据：启动日志打印 `dataDir` 与可写性。
- 清理：`layout.root` 每次构建整删（`runBuild` 的第一句），所以**任何持久数据都不能住在它下面**。
- 顺序：先解析 `CliMode`（含 `dataDir`）→ 再构造 `AppEnv`（`configure` 覆盖）→ 再装行；行不得在构造期读目录。

## 六、取舍

- **否掉「把桌面用户数据并进本包契约」**：那是子插件的部署值，底层描述上层就会互相引用成环；本包只声明「不进 `AppEnv`」，形态默认值归桌面侧记录。
- **否掉「合并两套 cache」**：一个跟数据根走、跨进程共用（联邦预编译），一个跟产物根走、只有构建用；合并后要么构建污染用户数据目录，要么运行期缓存被每次构建删掉。
- **否掉「`dataDir` 默认值写在 `AppEnvDefault`」**：默认值属于部署（平台、应用名、`--data-dir` 写法），只有 CLI 知道；写在行里就变成「两份默认值互相覆盖」。
- **否掉「给 `AppEnv` 加一堆字段（`logsDir` / `userDataDir` …）」**：先按需加（T5 才需要 `logsDir`），YAGNI。

## 七、不做与已知债

- **`AppEnvDefault` 仍用 `process.cwd()` 兜底**（`app-env.service.ts`）：违反决定 1；销账条件 = T4 落地且判据 2 的 grep 为 0。
- **行日志不落盘**：打包形态里行日志随 stderr 消失。销账条件 = T5，或明确「只走 stdout」。
- **`AppEnv.cacheDir` 与 `layout.cache` 同名**：读代码时容易以为是同一处。销账条件 = T3。
- **`dataDir` 下的子目录格式归各域**（sessions / storages / settings），本契约只管「它们住在 dataDir 下」这一条。

## 八、开放问题

- `runtimeCacheDir` 要不要按形态分（dev 一份、打包一份）？现在共用 `<dataDir>/cache`；打包形态的 `dataDir` 已是应用独占目录，暂时不需要。
- `zephyr doctor` 的输出格式：人读表 + `--json`（给报障收集）两个面，还是一份 JSON 让调用方渲染？倾向：**先只做人读表**，`--json` 等有消费方再加。
