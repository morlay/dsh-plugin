# 闭包里的包是源码面：preview 与闭包不是同一份 zephyr

状态：未销账（触发中）——`zephyr preview` 在 CLI 进程里装配闭包清单，而闭包自带一份 `@morlay/zephyr`。
位置：`packages/zephyr/zephyr-cli/src/commands/preview.ts`（`installSourceLoader` + `loadServerProviders`）、`packages/zephyr/zephyr-cli/src/server-entry.ts`、`packages/zephyr/zephyr/src/token.ts`（模块级令牌表）。

**现象**

`zephyr build` 的三步产物都齐（`dist/`、`runtime/`、`runtime/entry.mjs`），`preview` 也能装上 `@morlay/dsh-oxc-node` 把闭包里的 `.ts` 转译过去；卡住的是**下一层**：

- 闭包（`pnpm deploy --prod`）以源码面发布我们的包，闭包里因此有一份自己的 `node_modules/@morlay/zephyr`；
- `preview` 在 CLI 进程内 `import` 闭包的 `entry.mjs`，清单里的类是在**那份副本**上跑过 `@Injectable()` 的；
- 而 `bootstrapApplication` 用的是 CLI 自己那份副本——令牌元数据存在**模块级 `Map`**（`packages/zephyr/zephyr/src/token.ts` 的 `registered` / `byName`），跨副本看不到；
- 于是 `tokenMetaOf` 对每个类退化到「按类名派生」：契约身份、`multi` 标记与 `alias` 全部丢失，注入解析与多值聚合对不上（装配期报缺提供者，或同一个服务被登记两次）。

**影响**

- 撞上的是**跑闭包的形态**：`preview`，以及壳里 `import Resources/runtime/entry.mjs` 的那条（壳从 `runtime/node_modules` 解析 `@morlay/zephyr` 就是为了避开这一条）。
- dev 形态不受影响：工作区里只有一份 `@morlay/zephyr`。
- 表现是启动期报错（不是运行期静默），排查方向明确；但 ｢产物都齐了却起不来` 会让问题看起来在构建。

**触发条件**

- 要跑 `zephyr preview` 验证产物时（当前判据 `curl http://127.0.0.1:<port>/` 返回 200 且页面 `#root` 有内容）。
- 任何「在 CLI 进程内装配闭包清单」的新命令出现时。

**销账条件**

Done when：`preview` 的清单与装配器是同一个 `@morlay/zephyr` 实例（子进程里用 `createRequire(<entry>)` 解析闭包那份，或让闭包复用宿主的实例），且 `curl /` 200、页面 `#root` 有内容。

**不修的理由**

- 现有规避已经覆盖主要场景：桌面壳在子进程里从 `runtime/node_modules` 解析，不受影响；`preview` 的使用频率低于 dev。
- 改成子进程要新增进程编排、信号转发与输出归并，收益要等 ｢preview 成为常规验证手段` 才成立。
