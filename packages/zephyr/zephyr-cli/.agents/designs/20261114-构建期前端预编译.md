# 构建期前端预编译

状态：**已实施**——`zephyr build` 的第一步就是把应用的 client 图打成 `<outputDir>/client_modules/`（静态前端），
`preview` 与桌面壳都只吃这份产物。
范围：`zephyr build` 的「前端预编译」这一步、`zephyr preview` 复用同一份产物、产物落点。
非目标：dev 服务期的即时预编译（保留现状）、联邦产物格式、CJS 互操作。
关联：[目录契约](../../zephyr-app/.agents/designs/20261114-目录契约.md) · [客户端资源的联邦式预编译](../../zephyr-app/.agents/designs/20261013-客户端资源的联邦式预编译.md)

## 一、决定（提案）

| #   | 议题              | 提案                                                                                                                                          | 一句话理由                                                                            |
| --- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1   | 构建的一步        | `build` 的第一步「静态前端」：按清单把整棵 client 图的模块预先打成联邦产物                                                                  | 产物固定，可直接 grep 检查，不必等 dev 服务期生成                                     |
| 2   | 入口来源          | 与 dev 同源：`clientModules.include`（packaged 形态为空 = 全量）+ 应用的 client 入口图；由 `Federation` 契约给，不在 CLI 里另写一份清单       | 两种形态必须同构，否则又是两条链                                                      |
| 3   | 复用逻辑          | 抽 `zephyr-app` 的公共函数（如 `prebundleAll(options)`），内部复用 `bundlePackage` 与 `entryOf` 的解析；CLI 只传布局与清单                    | 不在 CLI 重写一遍预编译                                                               |
| 4   | 产物落点          | **直接写 `<outputDir>/client_modules`**（不进任何缓存目录）；preview 与桌面壳读同一处                                                        | 产物就是「一份可分发的应用」的一部分；多一层缓存会让「盘上的这份」有两种说法            |
| 5   | build 时的 AppEnv | 由 `build` 的部署参数给：`--data-dir` / `zephyr.config.ts` 的 `dataDir`（与 dev/preview 同一套 `resolveDataDir`），缺省 `<工作区>/.dsh-store` | 路径只有一个来源，不在 CLI 里另算                                                     |
| 6   | preview 校验      | 启动时按清单校验 `client-modules`：缺任何一个产物 / 指纹不符即**报错退出**，不静默回退到服务期预编译                                          | 回退会让「build 有问题」变成「preview 偶发慢/偶发错」                                 |
| 7   | 与 dev 的差异     | dev 仍按需预编译（首屏快）；build/preview 用构建期产物（确定性）。两者共用 `bundlePackage` 与缓存目录                                         | 差异只在「何时构建」，不在「怎么构建」                                                |

## 二、现状事实

- `build` 三步在 `packages/zephyr/zephyr-cli/src/build/builder.ts`：`buildClient`（`compile()` 写 `<outputDir>/client_modules`）、`buildRuntime`（`pnpm deploy --prod`）、`assembleEntry`（复制源码面入口 + 写 `bootstrap.mjs`）。`runBuild` 每次先 `rm(layout.root)`。
- 预编译的实现在开发运行时那个包：`zephyr-dev/src/build/compile.ts`（`compile()` → 按 `planPrebundle` 的清单调 `bundlePackage`）。枚举规则见 `federation/prebundle-plan.ts`。
- 服务期的按需预编译仍在 `zephyr-dev/src/federation/federation.service.ts::serve`（dev 形态）：`entryOf` + `bundlePackage` + `cjsShimOf`/`cssShimOf`，落 `<dataDir>/cache/client-modules`。
- 生产形态不跑服务期预编译：`client_modules/` 在 build 时就定型了，`StaticClientAssets` 只做文件投递。

## 三、模块边界与接口

| 模块                           | 拥有                                           | 不拥有                      | 依赖方向                  | 接缝              |
| ------------------------------ | ---------------------------------------------- | --------------------------- | ------------------------- | ----------------- |
| `zephyr-cli` 的第一步          | 何时跑、传什么清单、失败即构建失败             | 预编译算法本身              | ← `zephyr-dev` 的 `compile()` | 命令行与布局      |
| `zephyr-dev` 的 `compile()`    | 遍历清单、调用 `bundlePackage`、汇总产物与错误 | 何时被调用                  | ← `planPrebundle` 的清单  | 纯函数 + 产物目录 |
| `preview` 的校验               | 清单齐全性、指纹一致、失败即退出               | 重建产物（那是 build 的事） | ← 同一份清单              | 启动自检          |

## 四、判据

| #   | 判据                                       | 证据                                                                                                                                                                    |
| --- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | build 后 `<outputDir>/client_modules` 有全部产物 | 遍历目录按联邦地址规则反查，全部命中（判据见 [开发构建与产物布局](../../../.agents/designs/20261113-开发构建与产物布局.md) §五） |
| 2   | preview 页面 200、无 404                   | 起 preview 后 `curl -o /dev/null -w %{http_code} /`、浏览器 console 无 404                                                                                              |
| 3   | 无 config-forms / use-sync / CSS 报错      | 同一次 preview 的日志与页面                                                                                                                                             |
| 4   | 产物可 grep 比对                           | 例：`grep -l useSyncExternalStoreWithSelector <cache>/client-modules/use-sync-external-store@*/shim/with-selector.js`；`grep -rl morlay.zephyr.inject` 只剩 zephyr 自己 |
| 5   | 缺产物即失败                               | 删掉一个产物再 preview → 启动报错退出（不静默预编译）                                                                                                                   |

## 五、取舍与风险

- **产物直接落 `<outputDir>/client_modules`，不另设缓存根**：产物就是可分发的应用的一部分，多一层缓存会让「盘上这份是不是最终那份」有两种说法；`runBuild` 每次整目录重建，缓存换不来什么。dev 的按需预编译仍落 `<dataDir>/cache/client-modules`（那是运行期缓存，与产物无关）。
- **build 变慢**：预编译整棵 client 图（几十个包）会显著拉长 build；可用 `clientModules.include` 收窄范围（dev 同款开关）。
- **不在 preview 里回退**：宁可红，也不要「有时能跑」。
- **风险**：build 时没有运行期 ctx（`FederationDefault` 是 Provider），所以公共函数必须做成「参数进、结果出」的纯函数（清单 + 布局 + 版本表），不能靠 `inject`。
