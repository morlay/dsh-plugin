# 命令内核与四阶段

状态：已实现——命令是 zephyr 的装配行，树由 CLI 摆；`dev` / `build` / `preview` 永远在清单里。
范围：`packages/zephyr/zephyr-cli/src/`（`run.ts` 的两段解析、`tree.ts`、`params.ts`、`config/`、`layout.ts`、`data-dir.ts`、`build/builder.ts`、`dev-lifecycle.ts`、`commands/`）。
非目标：HMR 的实现（归应用与 vite）、安装包（归 `zephyr-desktop-bundle`）、发布式 profile 的辅助命令。
关联：[设计 宿主装配面与 client-modules](../../../zephyr-app/.agents/designs/20261022-client-modules-重写.md)、[债务 闭包里的包仍是源码面](./../debts/20261110-闭包里的包仍是源码面.md)。

## 一、决定

| #   | 议题       | 决定                                                                                                                             | 一句话理由                                                                      |
| --- | ---------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1   | 命令是什么 | `Command` 是 `@Injectable({ multi: true })` 的行：`path` 说明位置、`params` 手写声明、`run(input)` 返回退出码                    | 插件能追加命令，核心不必认识桌面那套依赖                                        |
| 2   | 命令树     | 由 CLI 根按 `app.getAll(Command)` 与各自的 `path` 摆出来                                                                         | 命令不知道树长什么样、也不知道自己被谁调起                                      |
| 3   | 参数       | 声明即注册：`params` 同时供 argv 解析、`--help` 与类型用，没有第二份 schema                                                      | 多写一份 schema 就多一处漂移                                                    |
| 4   | 配置面     | 唯一配置是工作区根的 `zephyr.config.ts`（`server.entry` / `client.entry` / `desktop` / `dataDir` / `build` / `plugins`）         | 一份配置只有一个 home；核心命令不在配置里，｢为什么没有 zephyr build｣ 不必读配置 |
| 5   | 部署值     | `CliMode` 值行（`command` / `workspace` / `profileDir` / `dataDir` / `dataDirSpec` / `configFile` / `port` / `host`）由 CLI 提供 | 部署参数只有装配面知道值，应用不该读环境变量                                    |
| 6   | 四阶段     | `dev`（装配 + 把重载口交给应用）、`build`（三步）、`preview`（只吃产物）、`desktop bundle`（插件追加）                           | 每阶段的职责边界固定，插件不改变核心命令                                        |
| 7   | 构建       | 三步：静态面（vite build）、运行时闭包（`pnpm deploy --prod`）、入口 bundle（rolldown）；**不装配任何清单**                      | 构建的输入是布局与解析规则，不是运行期行树                                      |
| 8   | 产物根     | `node_modules/.zephyr/{dist,runtime,cache}`（可被 `build.outDir` 覆盖）                                                          | 与 vite 的 `.vite` 同域：装出来、可重建、不进版本库                             |

## 二、现状事实

- **入口**：`src/cli.ts`（bin）→ `src/run.ts` 的 `runCli`。两段解析：第一段只认全局 flag（`--config` / `--data-dir` / `--port` / `--host` / `--log-level` 与位置参数），装配后第二段在命令树上完整解析。
- **清单**：`src/provide.ts` 的 `provideCli({ mode, resolved, streams, logLevel })` 返回值行（`CliMode` / `Workspace` / `Logger` / `BuildSteps`）+ 三条命令。
- **装配根**：`build` / `preview` 的 `profileDir` 是闭包目录（`layout.runtime`），其余是工作区（`run.ts` 里按命令名判）。
- **命令树**：`src/tree.ts`。同一 path 注册两次、父路径没有对应命令，都在装配期抛（｢装配错误｣，不是运行期错误）。
- **参数**：`src/params.ts`（`string` / `number` / `boolean` / `enum`（可 `allowPath`）/ `position`，`--no-name` 是布尔的反向）。
- **布局**：`src/layout.ts` 的 `layoutOf(workspace, outDir?)` 给出 `root` / `dist` / `runtime` / `cache` / `entry`。
- **数据目录**：`src/data-dir.ts` 的 `resolveDataDir` 三态（`workspace` → `<profileDir>/.dsh-store`、`xdg` → 平台应用数据目录、绝对路径原样）。
- **服务端入口**：`src/server-entry.ts` 的 `loadServerProviders(entry, mode, version)`：入口默认导出（或具名 `providers`）可以是清单，也可以是 `(mode) => 清单`；`version` 是重载时的缓存失效参数。
- **dev**：`commands/dev.ts` 装配 → `tryGet(DevLifecycle).install({ restart })` → 等信号；护栏两条：拆旧树 20s、装配 60s（`withDeadline`）。
- **build**：`commands/build.ts` 调 `runBuild({ resolved, layout }, steps)`，把每步耗时与产出位置打成一张表；三步的实现可在测试里换成替身（`BuildSteps` 是值令牌）。
- **preview**：`commands/preview.ts` 先 `access(entry)`，缺产物直接报错（不顺手 build）；再装 `@morlay/dsh-oxc-node` 以便加载闭包里的 `.ts`。

## 三、模块边界与接口

| 模块                        | 拥有（职责与不变量）                                       | 不拥有（明确排除）                                            | 依赖方向                                              | 接缝 / 适配器                      |
| --------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| `run.ts`（内核）            | 两段解析、装配根的选择、`CliMode` 的组装、退出码与错误输出 | 命令的实现；配置的语义；框架的 bootstrap                      | ← `@morlay/zephyr`、`config/`、`tree.ts`、`params.ts` | 可在测试里换输出流（`CliStreams`） |
| `command.ts` + `tree.ts`    | 命令契约、按 `path` 摆树、重复注册与缺父路径的判据         | 命令做什么；help 的排版（在 `params.ts`）                     | ← zephyr 的 `@Injectable`                             | 契约类；插件实现它                 |
| `params.ts`                 | 声明 → argv 解析 / `--help` / 类型                         | 业务语义（参数怎么用）                                        | 无                                                    | 纯函数                             |
| `config/`                   | ｢这个工作区是什么｣、`ResolvedConfig` 与 `Workspace` 值令牌 | 命令清单（核心命令永远在）；平台差异                          | ← 文件系统                                            | `loadConfig` 可注入配置路径        |
| `layout.ts` / `data-dir.ts` | 产物布局、数据目录三态                                     | 产物内容；数据本身的读写                                      | 无                                                    | 纯函数（平台与 home 可注入）       |
| `build/builder.ts`          | 三步编排、`BuildSteps` 值令牌、汇总                        | 解析规则（框架层给，应用在 `client.vite` 里展开）；不装配清单 | ← vite / pnpm / rolldown                              | `BuildSteps` 可换替身              |
| `dev-lifecycle.ts`          | 重载口的契约（`install({ restart })`）                     | HMR 的实现与空闲判据（应用给）                                | ← zephyr                                              | 契约；无实现则 dev 不重载          |
| `commands/`                 | 三条核心命令的编排与护栏                                   | 桌面命令（插件追加）                                          | ← 上面各面                                            | 每阶段一个类                       |

**接口**：`runCli(argv, { cwd, stdout?, stderr? }): Promise<number>`；`Command.run(input): Promise<number | void>`（`undefined` 视为 0）；`BuildSteps = { client, runtime, entry }`；`resolveDataDir({ spec, profileDir, appName, platform?, homeDir? })`。
不变量：核心三命令永远在清单里；命令树在装配期就完整；构建三步按顺序跑且先清产物根。

**深度**：删掉这层，每个应用都要自己写一遍 argv 解析、命令树、布局与数据目录规则，桌面插件也没有地方追加命令。

## 四、行为与边界

- 正常：`runCli` → 读配置 → 装配 → 摆树 → 解析 → 执行 → 退出码；无命令时打印根帮助并返回 0。
- 错误：未知命令 → stderr 一行 + 根帮助，退出码 2；`CliError` → 一行 `zephyr: <message>` 与它自带的退出码；其它异常 → 栈 + 退出码 1。
- 取消：信号处理只在命令里（`dev` / `preview` 等 SIGINT / SIGTERM），内核不接管。
- 生命周期：`execute` 的 `finally` 里 `app.dispose()`；`dev` 的重载是「拆旧树 → 起新树」，换 `version` 让 import 拿新模块。
- 并发：无并发编排；三步串行。

## 六、取舍

- 否掉「commander 单文件注册所有命令」：新增命令要改核心、插件无法追加，桌面那套（electron / electron-builder）会进核心依赖。
- 否掉「把核心命令也写进配置」：｢为什么这台机器没有 `zephyr build｣ 就变成必须读配置才能回答的问题。
- 否掉「build 也装配清单」：为了拿一个构建器去 bootstrap 一棵树，等于把「装一次服务」的成本摊到每次构建。
- 否掉「`client.entry` 是 JS 入口 + 并列 html 字段」：页面入口就是 `index.html`，vite 的 root 是它的目录，少一个字段就少一处「谁说了算」。
- 否掉「再包一层 `package.json` 的 dsh 段」：一份配置只有一个 home。

## 七、不做与已知债

- 不迁发布式 profile 的辅助命令（`publish` / `login` / `manifest` / `check-*` / 种子准备）：本仓库不维护那套体系。
- 不产安装包、不签名（`zephyr desktop bundle` 只出目录，`--install` 才拷进系统的应用目录）。
- 已知债：[闭包里的包仍是源码面](./../debts/20261110-闭包里的包仍是源码面.md)。

## 八、开放问题

- 工作区位置参数的判据是「命令段之后的最后一个位置参数，且它确实是个目录」（`run.ts` 的 `workspaceOf`）：命令名段数要到装配后才知道，这里先用「存在目录」猜。判错了会给一句明确的报错，但要不要换成显式 `--workspace`，未定。
- `build` 每次都 `rm -rf` 产物根（`runBuild` 开头）：联邦产物的缓存目录与它同根（`cache`），构建期间正在跑的 dev 会短暂丢产物。是否把 `cache` 挪出这次清理，未定。
