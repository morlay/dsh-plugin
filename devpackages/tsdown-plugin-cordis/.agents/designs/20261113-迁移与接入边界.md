# 迁移与接入边界（接入前置条件与试点结论）

状态：已对齐——包内实现与用例齐备；接入本身未落地，前置条件见第九节
范围：本包作为**被接入方**对每个接入包提出的要求——先满足什么、配置怎么写、清单该长什么样、怎么判绿；附 `packages/zephyr/zephyr` 的单包试点结论
非目标：接入本身（本步不推进实现）；声明生成与它的问题修复（归 `devpackages/dts-prepare`）；client 半的运行期服务（归 `packages/zephyr/zephyr-app`）
关联：[包 README](../../README.md) · 本包验证判据 [`how-to-verify.md`](../standards/how-to-verify.md) · 层设计 [`20261113-工具链层.md`](../../../.agents/designs/20261113-工具链层.md) · 债 [`20261113-声明树生成阻塞清单写回.md`](../debts/20261113-声明树生成阻塞清单写回.md) · 上游只读红线见 [`AGENTS.md`](../../../../AGENTS.md)

## 一、决定

| #   | 议题                 | 决定                                                                | 一句话理由                                                                                                 |
| --- | -------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | 接入形态             | `entry` 写**对象形**、值带 `./`；`plugins: [cordisPlugin()]`        | 数组形会被 `declaredEntries` 命名成 `src_index_ts`；不带 `./` 的顶层 `exports` 是非法值                    |
| 2   | 接入顺序             | 先还声明树生成（B1）→ 再声明依赖（B2）→ 最后改配置                  | 干净环境里 B1 让 `build:done` 抛错，配置改了也拿不到写回                                                   |
| 3   | 「构建能跑」不是判据 | 判据是接入包的 `pnpm exec oxlint <包>` 绿                           | tsdown 的 config 加载能解析 `@local/*`（实测），oxlint 的类型解析不能                                      |
| 4   | 试点范围             | 只 `packages/zephyr/zephyr`；两个前置都不在接入包里，所以试点不落地 | 前置不修，单包试点也只能靠本地伪造完成标记才拿得到写回                                                     |
| 5   | 产物路径             | 出口键是承诺、路径不是；布局变 flat 要有意识地接受                  | 变 flat 后与 `zephyr-cli` / `zephyr-desktop-bundle` 口径一致，不再是数组形遗留的 `dist/<入口名>/index.mjs` |

## 二、现状事实

清单的三类字段全部由构建推导并写回，没有一处手写；写回口径只在 `src/package-exports.ts`。

- **顶层 `exports` 指源码**：值取 entry 的源码路径**原样**（不补 `./`、不改写），键由入口名决定（`index` → `.`）。
- **`publishConfig.exports` 指产物**：从 `build:done` 的产物块按入口名取 `.mjs` / `*.d.mts`，路径带 `./<outDir>/`。
- **声明不在 tsdown 里出**：`build:done` 先 `ensureWorkspaceDts`，再 `emitDts` 从 `target/dts` 合并（`src/cordis-host.ts`）。
- **声明树生成**：`devpackages/dts-prepare/src/dts.ts` 的 `generateWorkspaceDts`（`noCheck: true`），`run()` 把 `tsc` 的任何非零退出当失败。
- **全仓清单仍手写**：除本试点外没有任何 `packages/**` 的构建引用本包（`grep -rn tsdown-plugin-cordis packages apps --include=tsdown.config.ts`）。

## 三、模块边界与接口

| 模块                 | 拥有（职责与不变量）                                                                   | 不拥有（明确排除）                      | 依赖方向                          | 接缝 / 适配器                                  |
| -------------------- | -------------------------------------------------------------------------------------- | --------------------------------------- | --------------------------------- | ---------------------------------------------- |
| `cordis-host`        | 把 tsdown 的 `entry` 与包约定合成一份 `UserConfig`；host/client 两半的 format 与内外联 | 入口该有哪些、声明内容                  | tsdown → 本模块 → `cordis-client` | `cordisPlugin(options)` 的 `tsdownConfig` 钩子 |
| `package-exports`    | 出口清单的口径：`exports` / `publishConfig.exports` / `engines.dsh` 从产物推导         | 谁该有哪个入口（调用方的 `entries` 给） | 只读产物块 + 写 `package.json`    | `packageExportsHook` / `writePackageManifest`  |
| 声明树（本包不拥有） | 生成、锁、完成标记（`devpackages/dts-prepare`）                                        | 合并成单文件、写回清单                  | 本包 → `dts-prepare`              | `ensureWorkspaceDts` / `emitDts`               |
| 接入包（本包不拥有） | `entry` 的入口名与源码路径、`devDependencies` 声明                                     | 出口键、产物路径、`engines.dsh` 的值    | 接入包 → 本包（构建期单向）       | `tsdown.config.ts`                             |

接口：`cordisPlugin(options)` 的选项表见 `src/cordis-host.ts` 的 `CordisPluginOptions`；`entries` 不在选项里，只来自 tsdown 的 `entry`。

## 四、行为与边界

- **正常路径**：一轮构建进一次 `build:done`，每个要导出的入口都拿到产物后写一次清单，同一个 cwd 只写一次。
- **错误**：产物没齐**不写也不报**——构建照常成功，所以验收判据是「清单里出现了该有的键」，不是「构建没报错」。
- **环境**：`DEEPSEEK_HARNESS_VERSION` 缺失或认不出时不写 `engines.dsh`，清单原值保留，不失败。
- **并发与顺序**：多包并行时声明树由 `@local/dts-prepare` 的目录锁串行化，谁先到谁生成、其余等锁。

## 五、验收判据

接入一个包的 Done when 是下面六条同时成立；第 1 条的前置见第九节。

| #   | 判据（Done when）                                                | 测试面（接缝） | 证据（命令）                                                                                    |
| --- | ---------------------------------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------- |
| 1   | 干净环境（无 `target/dts/.complete`）构建退出 0 且清单被写回     | 构建链         | `rm -f target/dts/.complete && mise exec -- pnpm --filter <接入包> run build`                   |
| 2   | 接入包 lint 绿                                                   | 类型解析       | `pnpm exec oxlint <接入包>`（未声明依赖必红 TS2307）                                            |
| 3   | 顶层 `exports` 每个值以 `./` 开头且指向存在的源码                | 清单           | `node --input-type=module -e "await import('<接入包>/<面>')"` 不报 `ERR_INVALID_PACKAGE_TARGET` |
| 4   | 发布态出口覆盖顶层出口的每个键，且每个值指到真实产物             | 清单 / 产物    | `ls <接入包>/dist` 与 `publishConfig.exports` 对账                                              |
| 5   | `engines.dsh` 等于 `>= <DEEPSEEK_HARNESS_VERSION> < 下一 patch>` | 清单           | `node -p "require('<接入包>/package.json').engines.dsh"` 与 `mise.toml` 对账                    |
| 6   | 接入包的测试与格式口径不变                                       | 包测试 / 格式  | `pnpm exec vitest run <接入包>`、`pnpm exec oxfmt --check <接入包>`                             |

## 六、取舍

| 选项                                       | 否掉的理由                                                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| entry 值不带 `./`（`"src/index.ts"`）      | 写回把 entry 值原样放进顶层 `exports`，实测被 Node 判 `ERR_INVALID_PACKAGE_TARGET`（目标必须以 `./` 开头）                |
| 数组形 entry                               | `declaredEntries` 按 `\W+ → _` 取名（`src_index_ts`），与 tsdown 自己的归一（`compat/index`）不一致，出口键与产物路径都歪 |
| 接入后保留（不回滚）                       | 干净环境构建红 + 接入包 lint 红：把「清单不再手写」换成两条常红，得不偿失                                                 |
| 手工写 `target/dts/.complete` 让构建走下去 | 那是伪造「生成成功」，CI 里没有这个标记，只是把红灯推迟到发布链                                                           |

## 七、不做与已知债

- **本步不落地接入**：`packages/**` 的 `tsdown.config.ts` 与 `package.json` 无一改动（试点改动已复原）。
- **接入前置的跨包债**：[`20261113-声明树生成阻塞清单写回.md`](../debts/20261113-声明树生成阻塞清单写回.md)——干净环境下声明树生成失败，清单写回跑不到。
- **既有债（本包不新增声明）**：构建期样式与资产两份、装饰器降级散在四个转译点，见仓库根 `.agents/debts/`。

## 八、开放问题

- **B1 的修法**：让不可命名的类型可命名（导出 `AdaptedClass` 一类），还是让声明生成对 `TS2883` 这类「产物质量」诊断分级而不是一律失败——两条都会改到 `dts-prepare` 与框架层的口径。
- **推广批次**：31 个包的 `engines.dsh` 与全部 `exports` 会在同一次接入里改完，是否与上游同步一批评审。

## 九、接入前置条件与试点结论

接入被两处前置挡住，两处都不在接入包的文件里：B1 是跨包既有阻塞，B2 需要改接入包的依赖声明与 lockfile。以下结论来自 `packages/zephyr/zephyr` 的单包试点（试点改动已复原，当前清单仍是手写）。

### 9.1 B1：干净环境下声明树生成失败，清单写回跑不到

`build:done` 的第一件事是 `ensureWorkspaceDts`，它调 `generateWorkspaceDts` → `tsc`；后者在当前树上**退出 1**，于是 `build:done` 抛错、**清单不写回**、`just build` 在接入包这一行红。

证据（两条都验过，任一条都能在干净环境复现）：

```sh
pnpm exec node devpackages/dts-prepare/src/cli.ts   # 干净环境等价：exit 1，抛「命令失败: pnpm exec tsc -p .tmp/dts-host.json」
pnpm exec tsc -p .tmp/dts-host.json                 # 上面那一步写出的 host face 配置：exit 1
# 130 × error TS2883（129 × AdaptedClass，1 × SessionFormatCatalog）
```

- `AdaptedClass` 来自 `packages/zephyr/zephyr/src/compat/from-cordis.ts`（未导出 → 装饰器返回类型写不进声明）。
- 分布跨 15+ 包：`dsh-conversation` 35、`dsh-agent` 14、`dsh-agent-loop` 12、`dsh-workspace` 8、`dsh-sandbox` 8、`dsh-session` 6、`zephyr-app` 5 …
- **与接入无关**：把试点配置复原后再跑同一命令，仍是 130 个、129 个 `AdaptedClass`。
- 债与销账条件：[包级债](../debts/20261113-声明树生成阻塞清单写回.md)。

### 9.2 B2：接入包必须声明 `@local/tsdown-plugin-cordis`

接入包要在 `devDependencies` 写 `"@local/tsdown-plugin-cordis": "workspace:^"` 并更新 `pnpm-lock.yaml` 的 importer；否则接入包的 type-aware lint 直接红。

- 未声明时：`pnpm exec oxlint packages/zephyr/zephyr` → `Found 0 warnings and 1 error`：`typescript(TS2307): Cannot find module '@local/tsdown-plugin-cordis'`（`packages/zephyr/zephyr/tsdown.config.ts`）。
- 同一状态下 `run build` **是能跑的**（tsdown 的 config 加载靠工作区提升解析到了它）——所以「构建绿」不能当作「依赖声明够了」的判据，判据只看第 2 条验收。
- 复原后同一命令：`Found 0 warnings and 0 errors`。

### 9.3 两个口径坑

| 坑                | 现象                                                                                                                                        | 正确写法                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| entry 值不带 `./` | 顶层 `exports` 变成 `"src/index.ts"`，消费方 `import '@morlay/zephyr/compat'` 报 `ERR_INVALID_PACKAGE_TARGET: targets must start with "./"` | `{ index: "./src/index.ts", … }`——写回值与手写值逐字相同（无 diff） |
| 数组形 entry      | `declaredEntries` 按 `\W+ → _` 取名得 `src_index_ts`，出口键与产物路径全歪（清单还会静默不写）                                              | 对象形，entry 名就是产物名与出口键                                  |

### 9.4 试点实测 diff（`packages/zephyr/zephyr/package.json`）

| 字段                                 | 接入前（手写）                                                      | 接入后（构建写回）                                                      |
| ------------------------------------ | ------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 顶层 `exports`                       | `./src/index.ts`、`./src/compat/index.ts`、`./src/testing/index.ts` | **不变**（前提：entry 值带 `./`）                                       |
| `publishConfig.exports["./compat"]`  | `./dist/compat/index.{d.mts,mjs}`                                   | `./dist/compat.{d.mts,mjs}`                                             |
| `publishConfig.exports["./testing"]` | `./dist/testing/index.{d.mts,mjs}`                                  | `./dist/testing.{d.mts,mjs}`                                            |
| `engines.dsh`                        | `>= 0.2.1-rc.1 < 0.2.2`                                             | `>= 0.2.2-rc.1 < 0.2.3`（跟 `mise.toml` 的 `DEEPSEEK_HARNESS_VERSION`） |

- 构建产物：`dist/index.mjs`、`dist/compat.mjs`、`dist/testing.mjs` + 共享 chunk，`5 files, total: 35.08 kB`；声明由 `emitDts` 合并出 `*.d.mts`。
- 产物布局变化**不影响任何消费方**：全仓按出口键 `@morlay/zephyr/compat` / `/testing` 引用（100+ 处），没有一处直连 `dist/compat/index.mjs` 之类的产物路径（`grep -rn "dist/compat\|zephyr/dist" packages apps devpackages` 只命中各自 `package.json`）。
- 试点期间的测试与格式无回归：`vitest run packages/zephyr/zephyr` → `Test Files 70 passed | 1 skipped`、`Tests 509 passed | 2 skipped`（该路径过滤是前缀匹配，连带跑了 `zephyr-*` 兄弟包）。

### 9.5 接入三步 ticket

1. **还 B1**：让干净的声明树生成退出 0（修法见第八节），判据：`pnpm exec node devpackages/dts-prepare/src/cli.ts` 退出 0（今天 exit 1，130 × TS2883）。
2. **声明依赖**：接入包加 `@local/tsdown-plugin-cordis` 到 `devDependencies` 并 `pnpm install`（会改 `pnpm-lock.yaml`），判据：`pnpm exec oxlint <接入包>` 绿。
3. **改配置并验收**：`tsdown.config.ts` 换成对象形 entry（值带 `./`）+ `plugins: [cordisPlugin()]`，按第五节的六条判据逐条取证据；**只做单包**，清单 diff 与产物布局变化随票评审。
