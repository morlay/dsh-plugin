# 数据与工作目录的 layout

状态：已实现。范围：`dshdev` 起的两种形态（dev / bundle）各自在哪些目录上落什么，以及 profile 从哪来。

## 三个不同的东西（别混）

| 名字           | 是什么                                                       | 谁读它                                            |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------- |
| **profileDir** | **profile 清单所在的目录**（`package.json` 的 `dsh` 段在这里） | 装配时按它解析 bundle 与插件面                    |
| **dataDir**    | **数据面根**（`$DSH_HOME`）：`logs/`、会话库、各种 store      | 宿主与上游各行按 `DSH_HOME` 读；壳的日志也落这里   |
| **buildCache** | **构建/打包的缓存目录**（不是运行时数据，随时可重建）         | `dshdev` 自己：装配壳、备 runtime、备 seed、放产物 |

三者互不嵌套是常态：dev 下 profileDir 与 buildCache 都在工作区里，dataDir 默认也在工作区里；bundle 运行期
profileDir 与 dataDir 同属 `$DSH_HOME`，buildCache 只属于构建机。

## dev（`dshdev web` / `dshdev desktop`）

| 目录          | 值                                              | 说明                                                                |
| ------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| workspace     | `apps/dsh-custom-next`（首个位置参数，缺省 cwd） | app 目录：`package.json` 的 `dsh` 段是装配输入                       |
| **profileDir** | `<workspace>`                                   | **dev 的 app 目录就是 profile 目录**（有 `dsh` 段的那份清单）         |
| **dataDir**   | `<workspace>/.dsh-store`（`--data-dir` 可换）    | `--data-dir=xdg` / `=env` / `=<绝对路径>`，与打包形态同一份解析规则   |
| **buildCache** | `<workspace>/node_modules/.dshdev`              | 见下                                                                |
| ↳ `shell/`    | 装配出的 **Electron app 目录**                   | 引导 + 转译后的 `dist/` + 清单 + 本地化；壳从这里启动                 |
| ↳ `development/` | dev 的 Electron `--user-data-dir`            | Chromium 自己的状态，与 dataDir 无关                                 |
| ↳ `runtime/`  | 随包的 node + TS loader + pnpm                  | 宿主子进程用它起                                                     |
| ↳ `seed/`、`deploy/` | 官方包的源码种子 / 部署面                 | "官方闭包"的两种落法                                                 |

### 为什么不合成一份 profile

dev 的 profile root **就是 app 目录本身**（Electron 与 `web` 都一样）：装配清单与 patch 层本来就住在那里，
中间再合成一份只多一个会过期的事实。代价是插件页的安装 / 卸载会改 app 的 `package.json` 与工作区 lockfile
（那正是"这个目录就是 profile"的语义），这些运行时状态因此要 gitignore。

dev 的安装根就是工作区 pnpm store（`<workspaceRoot>/node_modules/.pnpm`，零复制、零镜像）：它的
`node_modules/` 是扁平 store，`import.meta.resolve('@deepseek-ai/dsh/package.json')`（cwd 在该目录下）解析到
`vendor/deepseek-harness/apps/cli/package.json`——即工作区源码面那份，正是 dev 要的。

### 两个形态的装配入口

| 形态            | profileDir | runtimeDir                     | boot 入口                                                          | overlay                                              |
| --------------- | ---------- | ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------- |
| dev（Electron） | app 目录   | `<workspaceRoot>/node_modules/.pnpm` | 宿主 [`src/index.ts`](../../../packages/desktop/dsh-desktop-host/src/index.ts)（官方 `loadProfileDirectory` + `runProfile`） | 桌面 patch + [dev-only bundle](../..//../bundles/web-custom-profile/package.json) |
| dev（web）      | app 目录   | 同上                            | 宿主的 web 入口 [`src/web.ts`](../../../packages/desktop/dsh-desktop-host/src/web.ts) | 同一个 dev-only bundle                                |

只有 web 形态需要一条 dev 专用入口：上游 `dsh web` 会按 profile 名去 `$DSH_HOME/profiles/<name>` 找 profile，
而 dev 的 profile 在工作区的 app 目录里。装配本身仍复用上游那两步（`loadProfileDirectory` + `runProfile`）——
自己实现一遍等于把上游的兼容性检查、跳过清单上报、fail-loud、关停语义全部抄一遍并跟着版本走。

### dev 在 profile root 里留下的文件

| 文件                              | 谁写                               | gitignore（app 目录形态） |
| --------------------------------- | ---------------------------------- | ------------------------- |
| `cordis.yml`                      | `runProfile`（每次启动重写空根）    | 是                        |
| `compatibility.json`              | 插件版本豁免操作（设置面板 / CLI）  | 是                        |
| `.plugin-manager/`                | 插件页的包操作（安装记录、日志）    | 是                        |
| `node_modules/`、`pnpm-lock.yaml` | 包操作（dev 下就是工作区的）        | `node_modules/` 已有      |

## bundle（`dshdev desktop bundle`，以及产物运行起来之后）

构建期（构建机上）：workspace 与 buildCache 同上，其中 `artifacts/` 是 electron-builder 的产物
（`mac-arm64/…`），`shell/` 是装配出的 app 目录（原样进产物）。

运行期（用户机器上）：

| 目录           | 值                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------- |
| **profileDir** | `<dataDir>/profiles/desktop`                                                                  |
| **dataDir**    | `appconfig.dshHome` 解析：`xdg` → 平台数据目录 + app 名，`env` → 环境里的 `DSH_HOME`，或绝对路径 |
| app 目录       | `<Resources>/app`（`asar: false`，与 dev 的 `shell/` 结构一致）                                 |
| runtime、seed  | `<Resources>/runtime`、`<Resources>/seed`                                                      |

打包形态走的是"运行时与 profile 分离、由随包 pnpm 安装"那套官方语义：种子在 `seed/profiles/<name>`，manifest 由
工具生成（官方 bundles 在前，app 自己声明的 bundle 按包名去重后排在后面），`cordis.patch.yml` 是用户数据
（重种豁免），随包 pnpm 离线装、runtime `overrides` 指回随包 runtime。app 的 `dsh.profile.bundles` 因此是
**声明**：dev 直接读它，打包由工具按官方形态落成清单。

## 日志

两处日志同放 **`<dataDir>/logs/`**，对着看就能定位"页面 → 壳 → 宿主"断在哪一段：

- `shell.log`：壳写（启动形态、宿主就绪、失败原因）——[`index.ts`](../../../packages/desktop/dsh-desktop-shell/src/index.ts)；
- `dev-host.log`：宿主写（`@morlay/dsh-client-modules` 的 dev 面）。

## 遗留

- 上游 `loadProfileDirectory` 会对清单里出现**已退役 bundle** 的 profile 回写 `package.json`（`RETIRED_BUNDLES`）。
  dev 形态下即回写源码目录里的 app 清单：只有在 app 真的列了那个包时才会发生。
- dev 的 profile root 是源目录，因此 `pnpm` 的包操作会写工作区清单与 lockfile。
